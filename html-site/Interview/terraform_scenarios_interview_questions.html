Terraform: 30 Real-World Scenario Questions

A practical interview pack for engineers with around 5 years of experience. Questions focus on production incidents, state, modules, AWS infrastructure, CI/CD, security, and operational judgement.

How to conduct the mock interview

Allow 2–3 minutes per scenario. Ask the candidate to explain the investigation, commands or configuration they would use, risks, rollback plan, and how they would prevent recurrence. Strong candidates explain trade-offs rather than jumping straight to a command.

01

State management

Scenario 01
A developer accidentally deletes the Terraform state file for a production VPC. The AWS resources still exist. What would you do?
Model answer / what a strong candidate should cover

First, stop all pipelines and prevent anyone from running apply against that workspace. Check whether the state can be restored from the remote backend's versioning or backup. For an S3 backend, inspect object versions and restore the correct state version; keep the DynamoDB lock table intact if it is used. Validate the restored state with terraform state list and terraform plan. If no usable backup exists, rebuild state carefully by importing each existing resource using its exact Terraform address and ID. Do not recreate the VPC or run a blind apply. After recovery, enable state versioning, access controls, encryption, locking, and tested backups.

Listen for: State recovery, blast-radius control, backend versioning, and safe import strategy.
02

Remote backend and locking

Scenario 02
Two engineers start Terraform applies against the same environment at nearly the same time. How do you prevent state corruption?
Model answer / what a strong candidate should cover

Use a shared remote backend with state locking supported by that backend. For an S3 backend, configure bucket versioning and encryption, and use the supported S3 lockfile mechanism (or DynamoDB locking in setups that still use it). Ensure all engineers and CI jobs use the same backend key and workspace. A lock prevents concurrent state-writing operations; it does not replace CI/CD approvals or environment isolation. Never use -lock=false as a routine workaround. If a lock is stale, verify no operation is active before carefully removing it.

Listen for: Backend design, locking semantics, shared state, and safe stale-lock handling.
03

Terraform drift

Scenario 03
A console administrator changes an EC2 instance's instance type directly. The next Terraform plan shows a change. How do you handle it?
Model answer / what a strong candidate should cover

Treat the plan as drift detection. Confirm whether the console change was authorized and whether it should become the desired configuration. If it is intentional, update the Terraform code and review the resulting plan. If it is unauthorized, plan a controlled remediation back to the declared configuration. Do not blindly apply: inspect replacement indicators, dependencies, downtime, and data impact. For ongoing detection, run scheduled plans and route drift alerts to the owning team.

Listen for: Difference between configuration, state, and real infrastructure; deliberate reconciliation.
04

Import existing infrastructure

Scenario 04
Your team must bring an existing production S3 bucket under Terraform management without recreating it. Explain the process.
Model answer / what a strong candidate should cover

Write a resource block that accurately represents the bucket, then import the existing bucket into the intended state. With modern Terraform, use an import block or terraform import with the correct resource address and provider-specific ID. Run terraform plan, then adjust configuration until the plan is non-destructive and reflects the real settings. Import only records the object in state; it does not generate a complete configuration or guarantee that every setting is represented. Review versioning, encryption, policies, lifecycle rules, ownership, and dependencies before applying.

Listen for: Import is state adoption, not resource creation or full configuration discovery.
05

Module design

Scenario 05
A team has copied the same VPC Terraform code into development, staging, and production repositories. How would you improve it?
Model answer / what a strong candidate should cover

Create a reusable, versioned VPC module with clear input variables, validated types, useful outputs, and documented defaults. Keep environment-specific values in separate root configurations or environment variable files, and pin the module to a released version or immutable source reference. Avoid building a module with dozens of unrelated toggles. Add examples and automated validation/tests. Promote module releases through environments after review rather than changing every environment independently.

Listen for: Reusable module boundaries, version pinning, input/output contracts, and promotion.
06

count versus for_each

Scenario 06
You create three IAM users with <code>count</code>. Later, you remove the second item from the list and Terraform proposes unexpected user replacements. Why, and what would you use instead?
Model answer / what a strong candidate should cover

count addresses instances by numeric index, so removing or reordering list elements can shift identities and cause Terraform to associate an index with a different logical user. For independently named objects, use for_each with a map or set of stable keys. Resource addresses then use those keys, such as aws_iam_user.user["deploy"]. When migrating existing resources, use carefully reviewed moved blocks or state moves so Terraform does not destroy and recreate them.

Listen for: Stable resource identity and migration of state addresses.
07

Secrets in Terraform

Scenario 07
A Terraform plan or state file contains a database password. The team marks the variable as sensitive. Is that enough?
Model answer / what a strong candidate should cover

No. sensitive = true redacts values in many CLI outputs, but it does not encrypt or remove the value from state. Use a secured remote backend with encryption, strict IAM access, audit logging, and state version access controls. Prefer retrieving secrets from a secrets manager at runtime and avoid passing them through outputs or committed tfvars files. Restrict CI logs and artifacts, rotate any exposed credential, and remember that plans can also contain sensitive values.

Listen for: Sensitive display flags versus actual secret protection; state and plan security.
08

Environment isolation

Scenario 08
How would you structure Terraform for dev, test, and production so a developer cannot accidentally apply development changes to production?
Model answer / what a strong candidate should cover

Use separate root configurations and separate state locations/keys for each environment, with distinct cloud roles and least-privilege permissions. CI should select the environment explicitly, validate the target account and workspace/backend key, and require stronger approval for production. Use separate credentials or role assumptions per environment. Workspaces can help with similar deployments, but they are not a security boundary by themselves. Keep production approvals and deployment controls outside a developer's local default workflow.

Listen for: State isolation, identity boundaries, CI guardrails, and workspace limitations.
09

Dependency ordering

Scenario 09
A subnet must be created inside a VPC. Terraform sometimes tries to create the subnet before the VPC. How do you troubleshoot this?
Model answer / what a strong candidate should cover

Terraform builds a dependency graph from references. If the subnet's vpc_id references the VPC resource's ID, Terraform infers the dependency automatically. If the dependency is not represented by an expression—for example, an external prerequisite—use depends_on sparingly to express the hidden dependency. Inspect the plan and graph with terraform graph. Avoid adding broad dependencies everywhere because they reduce parallelism and can obscure the real relationship.

Listen for: Implicit dependencies first, explicit dependencies only for hidden ordering.
10

Lifecycle prevent_destroy

Scenario 10
A production database must never be removed by an ordinary Terraform apply. How would you protect it, and what are the limitations?
Model answer / what a strong candidate should cover

Use a lifecycle rule such as prevent_destroy = true on the database resource, and consider provider-level deletion protection where supported. Review backups, retention, and recovery procedures as well. prevent_destroy blocks plans that would destroy the resource while the rule remains in configuration, but removing the resource block also removes that protection from the configuration. It is not a substitute for IAM controls, approvals, backups, or cloud-side deletion protection.

Listen for: Terraform lifecycle behavior and defense in depth.
11

create_before_destroy

Scenario 11
An application load balancer replacement causes downtime. How can Terraform lifecycle settings help, and what must be checked?
Model answer / what a strong candidate should cover

Where the provider and resource semantics allow it, create_before_destroy = true can ask Terraform to create the replacement before destroying the old object. Check naming uniqueness, quotas, immutable attributes, dependencies, DNS cutover, health checks, and whether both resources can coexist. It does not guarantee zero downtime: some resources cannot coexist or have fixed names. Design an explicit traffic migration or blue/green strategy when availability requirements demand it.

Listen for: Lifecycle ordering, provider constraints, and real zero-downtime design.
12

Provider and Terraform versions

Scenario 12
A pipeline succeeds on one engineer's laptop but fails on another due to provider changes. How do you make runs reproducible?
Model answer / what a strong candidate should cover

Set a supported Terraform CLI version constraint and explicit provider version constraints in required_providers. Commit .terraform.lock.hcl so provider selections and checksums are consistent. In CI, use a controlled Terraform version and run terraform init without casually upgrading providers. Upgrade deliberately with review, tests, and a plan diff. The lock file locks provider selections; it does not pin the Terraform CLI binary itself.

Listen for: Version constraints, dependency lock file, and controlled upgrades.
13

Terraform init -upgrade

Scenario 13
A provider bug fix is required, but the lock file pins an older version. What is the safe upgrade workflow?
Model answer / what a strong candidate should cover

Review the provider's release notes and compatibility requirements. Update the allowed version constraint if needed, then run terraform init -upgrade in a controlled branch to select a permitted newer version. Review the lock-file diff, run formatting, validation, tests, and plans in a non-production environment, then promote the change. Do not delete the lock file as a shortcut; that can cause unrelated dependency selections to change.

Listen for: Intentional dependency upgrades and lock-file review.
14

Data sources

Scenario 14
Your Terraform code needs the ID of an existing VPC that is managed by another team. Would you create the VPC resource again?
Model answer / what a strong candidate should cover

No. Use a data source to look up the existing VPC using a stable identifier or carefully scoped filters, then reference its attributes. Make the lookup deterministic—avoid filters that could match multiple VPCs—and fail clearly if the expected object is absent. A data source reads existing infrastructure; it does not take ownership of it. Coordinate interface changes with the owning team and consider publishing stable outputs through a remote-state or service-discovery contract where appropriate.

Listen for: Resource versus data source, deterministic lookup, and ownership boundaries.
15

Remote state outputs

Scenario 15
A networking team owns the VPC state and an application team needs subnet IDs. How can they share this information safely?
Model answer / what a strong candidate should cover

Expose only the required values as outputs from the networking root module. The application configuration can consume them through a supported remote-state data source or, often better for cross-team boundaries, through a controlled service catalog or parameter store. Remote-state access can expose the entire state snapshot to readers, not just declared outputs, so grant access carefully. Keep backend keys and environment mapping explicit, and avoid coupling application deployments to unstable internal resource addresses.

Listen for: Output contracts and the security implications of remote-state access.
16

Partial apply failure

Scenario 16
Terraform creates a VPC and two subnets, then fails while creating a route table. What do you do next?
Model answer / what a strong candidate should cover

Do not delete the state or immediately rerun with manual edits. Read the error and identify which operations succeeded. Terraform normally records successfully completed resource operations in state, even if a later operation fails. Fix the underlying issue, refresh/inspect state as appropriate, and run a new plan to understand the remaining work. Check for resources created outside Terraform or provider timeouts that may have left ambiguous outcomes. Never assume the whole apply rolled back atomically.

Listen for: Terraform apply is not a transactional rollback across cloud resources.
17

Manual state editing

Scenario 17
A teammate suggests editing the Terraform state JSON directly to fix a resource address. Is that acceptable?
Model answer / what a strong candidate should cover

Avoid editing state JSON manually. Use supported commands such as terraform state mv, terraform state rm, terraform import, or declarative moved blocks, depending on the intended change. Back up state first, coordinate with the team, and ensure no apply is running. State surgery is high risk; inspect the resulting plan carefully before any apply. Direct JSON editing should be an exceptional last resort with expert review and a recoverable backup.

Listen for: Supported state operations, backups, locking, and plan verification.
18

Resource replacement

Scenario 18
A small change to an EC2 resource causes Terraform to show <code>- / +</code>. What does that mean and how do you respond?
Model answer / what a strong candidate should cover

It indicates replacement: Terraform plans to destroy and recreate the object rather than update it in place. Inspect the attribute marked as requiring replacement and consult provider documentation. Determine whether the instance contains stateful data, whether a replacement can coexist, and what downtime or IP/DNS changes will occur. If replacement is unsafe, redesign the resource or migration path. Do not approve a replacement solely because the configuration diff looks small.

Listen for: Plan symbols, immutable attributes, and impact assessment.
19

for_each key change

Scenario 19
You rename a key in a <code>for_each</code> map from <code>api</code> to <code>backend</code>. Terraform proposes destroy and create. How do you avoid unnecessary replacement?
Model answer / what a strong candidate should cover

Terraform treats the key as part of the resource address. If the real object should remain the same, add a moved block from the old keyed address to the new one, or use terraform state mv with a coordinated migration. Run a plan and confirm Terraform recognizes an address move rather than a physical replacement. Keep the key stable over time and choose keys based on logical identity, not display labels that frequently change.

Listen for: Address migration and stable keys.
20

Provisioners

Scenario 20
A team uses <code>local-exec</code> to install software on every EC2 instance after creation. What concerns would you raise?
Model answer / what a strong candidate should cover

Provisioners are a last resort because they are not modeled as declarative infrastructure and can be difficult to retry, observe, and make idempotent. Prefer immutable images, cloud-init/user data, configuration management, or a deployment pipeline. If a provisioner is unavoidable, make it idempotent, handle failures, secure credentials, and understand its creation/destruction triggers. Do not use provisioners to compensate for missing provider resources or to orchestrate an entire deployment.

Listen for: Declarative design and alternatives to provisioners.
21

Sensitive outputs

Scenario 21
A module outputs a database connection string that includes credentials. How should the output be handled?
Model answer / what a strong candidate should cover

Avoid including credentials in outputs if consumers can retrieve them from a secrets manager. If an output must contain sensitive data, mark it sensitive = true, restrict state access, and avoid printing it in CI logs. Remember that sensitive outputs are still stored in state. Prefer separating non-secret connection metadata from the secret value and grant applications direct access to the secret store.

Listen for: Output minimization and state confidentiality.
22

Dynamic blocks

Scenario 22
You need to configure a variable number of ingress rules in a security group. How would you avoid copy-pasting repeated nested blocks?
Model answer / what a strong candidate should cover

Use a typed variable such as a list or map of rule objects and a dynamic block to generate the nested provider blocks. Validate required fields, protocols, and port ranges, and give each rule a clear logical key where possible. Keep the abstraction readable; if the dynamic block becomes difficult to understand, use a dedicated module or a provider resource model that represents each rule separately.

Listen for: Typed input design, dynamic nested blocks, and maintainability.
23

Workspaces

Scenario 23
A candidate says Terraform workspaces are the best way to isolate production from development. Do you agree?
Model answer / what a strong candidate should cover

Not automatically. Workspaces create separate state instances for one configuration, which can be useful for multiple similar deployments. They do not provide separate cloud credentials, access controls, backend policies, or a strong security boundary. For production isolation, use separate root configurations or controlled deployment roots, separate state locations, and distinct IAM roles. Workspaces can still be part of a design when the isolation and operational model are appropriate.

Listen for: Workspace purpose and limits as an isolation mechanism.
24

CI/CD pipeline

Scenario 24
Design a Terraform pipeline for a pull request that changes an AWS VPC module. What stages would you include?
Model answer / what a strong candidate should cover

A typical pipeline checks out code, installs a pinned Terraform CLI, configures short-lived cloud credentials through role assumption/OIDC, runs terraform fmt -check, terraform init, terraform validate, security/lint checks, and a plan. Publish the plan securely for review, with sensitive output protected. On merge, require environment approval as appropriate, generate or revalidate a plan against the current state, and apply the reviewed plan. Keep state locking enabled and separate plan/apply permissions. Never expose long-lived cloud keys in repository secrets if federation is available.

Listen for: Pipeline stages, identity federation, plan review, approvals, and state locking.
25

Plan file safety

Scenario 25
A team saves a Terraform plan file as a public CI artifact so a manager can review it. What is the risk?
Model answer / what a strong candidate should cover

A saved plan can contain sensitive values and infrastructure details, even when terminal output redacts them. Store it only in access-controlled, short-lived artifacts, encrypt where appropriate, and apply the exact reviewed plan only if it is still valid. Plans can become stale if state or configuration changes; regenerate and review rather than forcing an old plan. Treat plan files as sensitive operational artifacts.

Listen for: Plan artifact confidentiality, staleness, and controlled promotion.
26

Authentication and IAM

Scenario 26
How should a GitHub Actions workflow authenticate to AWS for Terraform without storing permanent access keys?
Model answer / what a strong candidate should cover

Prefer GitHub Actions OIDC federation to an AWS IAM role. Configure the role trust policy to restrict the expected repository, branch, or deployment environment, and grant only the permissions required for that stack. Use separate roles for plan and apply where practical, with production apply protected by environment approval. Audit role sessions and avoid wildcard permissions. Ensure the Terraform backend access permissions are included but scoped to the correct state objects and lock mechanism.

Listen for: OIDC trust conditions, least privilege, and separation of duties.
27

Multi-account AWS

Scenario 27
Your company has separate AWS accounts for networking, security, and applications. How would Terraform manage resources across them?
Model answer / what a strong candidate should cover

Use provider configurations with explicit aliases and assume roles into each target account. Keep account IDs, regions, and role ARNs explicit and validated. Use separate state boundaries aligned to ownership and blast radius—for example, networking state and application state—rather than one giant state spanning the organization. Grant each pipeline identity only the account roles it needs. Avoid embedding credentials in provider blocks; use the CI identity chain or role assumption.

Listen for: Provider aliases, role assumption, account boundaries, and state decomposition.
28

VPC module design

Scenario 28
You are asked to build a reusable VPC module supporting public/private subnets across two Availability Zones. What would you include?
Model answer / what a strong candidate should cover

Define inputs for CIDR, AZ selection, subnet sizing, DNS settings, and optional NAT strategy. Create public and private subnets with route tables and associations, internet gateway, and NAT gateways according to the chosen availability/cost trade-off. Expose VPC and subnet IDs and useful metadata as outputs. Validate CIDR relationships and AZ counts. Document whether NAT is one-per-AZ or shared, because that is a cost-versus-resilience decision. Add examples and tests, and avoid hardcoding account-specific IDs.

Listen for: Network architecture, availability/cost trade-offs, validation, and module outputs.
29

Drift and refresh

Scenario 29
What is the difference between <code>terraform refresh</code>, <code>terraform plan</code>, and <code>terraform apply</code>? How would you investigate drift today?
Model answer / what a strong candidate should cover

A plan refreshes the state view from provider APIs as part of planning by default, then compares configuration and refreshed state to propose actions. Apply executes the approved changes and updates state. The legacy standalone terraform refresh command is deprecated; avoid using it as a casual drift fix because it can update state without changing configuration. Use terraform plan (or a refresh-only plan when appropriate) to inspect drift, decide whether code or infrastructure is authoritative, and apply only after review.

Listen for: Modern refresh behavior and safe drift investigation.
30

Destroy protection and incident response

Scenario 30
A production apply unexpectedly proposes destroying a shared subnet used by several applications. What is your immediate response?
Model answer / what a strong candidate should cover

Stop the deployment and do not approve the plan. Identify why Terraform believes the subnet must be destroyed: changed CIDR, address/key change, module refactor, provider behavior, or state mismatch. Check dependencies and which workloads use the subnet. If it is a refactor, use a moved block or state migration where appropriate. If the desired change is real, design a staged network migration with replacement subnets, route updates, workload migration, and rollback. Add approvals and policy checks for destructive changes to shared infrastructure.

Listen for: Operational judgment, dependency analysis, migration planning, and safeguards.

Suggested scoring rubric

4 – Strong: Structured investigation, safe commands, trade-offs, security, rollback, and prevention.

3 – Good: Correct solution and understands most operational risks.

2 – Developing: Knows Terraform concepts but misses production safeguards or edge cases.

1 – Weak: Jumps to commands without understanding state, blast radius, or recovery.

Hiring signal: For a 5-year engineer, look for ownership of production changes, clear state-management practices, modular design, secure pipelines, and the ability to explain why a proposed action is safe.
