Scraping & Service Discovery
A mission-critical payment exporter shows `UP == 0` in Prometheus with error `context deadline exceeded`. The service is healthy. How do you troubleshoot?
⌄

Strong answer

context deadline exceeded means the scrape request took longer than the configured scrape_timeout (default: 10s or equal to scrape_interval).

  • Root Cause 1 (Payload Size / Serialization Delay): The application metrics endpoint (/metrics) is dumping tens of thousands of lines (megabytes of text) due to runaway cardinality or uncompressed histograms.
    • Test via curl: time curl -s http://payment-service:8080/metrics | wc -l. If it takes 12 seconds and returns 400,000 lines, the endpoint is generating too much metric data to scrape in 10s.
  • Root Cause 2 (Slow DB Queries inside Metric Endpoint): The application runs expensive SQL queries (e.g. SELECT count(*)) synchronously inside the Prometheus scrape handler rather than computing metrics asynchronously in background worker threads.
  • Immediate Fix:
    • Temporarily increase scrape_timeout: 30s and scrape_interval: 30s in the ServiceMonitor or Prometheus config.
    • Refactor application code to update metric gauges in the background so /metrics serves static in-memory counters in <10ms.

Scraping & Service Discovery
How do you monitor external public endpoints, TCP ports, and SSL certificate expiration across 50 domains using the Prometheus Blackbox Exporter?
⌄

Strong answer

The Blackbox Exporter performs external synthetic probing (HTTP/S, DNS, TCP, ICMP) and exposes probe latency, status codes, and certificate expiry timestamps.

  • Blackbox Module Config (blackbox.yml): 
    modules:
  http_2xx:
    prober: http
    timeout: 5s
    http:
      valid_http_versions: ["HTTP/1.1", "HTTP/2.0"]
      valid_status_codes: [200, 301, 302]
      fail_if_ssl: false
      tls_config:
        insecure_skip_verify: false
  • Prometheus Scrape Configuration: Relabel the target URL into the __param_target query parameter: 
    - job_name: 'blackbox-external-http'
  metrics_path: /probe
  params:
    module: [http_2xx]
  static_configs:
    - targets: ['https://api.company.com', 'https://auth.company.com']
  relabel_configs:
    - source_labels: [__address__]
      target_label: __param_target
    - source_labels: [__param_target]
      target_label: instance
    - target_label: __address__
      replacement: blackbox-exporter:9115
  • SSL Expiration Alert: 
    expr: (probe_ssl_earliest_cert_expiry - time()) / 86400 < 14
annotations:
  summary: "SSL certificate for {{ $labels.instance }} expires in less than 14 days!"

Scraping & Service Discovery
Explain the exact difference between `relabel_configs` and `metric_relabel_configs` in a Prometheus scrape job. Give a concrete production use case for each.
⌄

Strong answer

Both modify labels using regular expressions, but execute at completely different stages of the scrape lifecycle:

  • relabel_configs (Pre-Scrape):
    • Runs before Prometheus makes the HTTP scrape request.
    • Operates on target metadata labels discovered via Service Discovery (e.g. __meta_kubernetes_pod_name, __address__).
    • Use Case: Deciding which targets to scrape or drop (e.g. only scrape pods with annotation prometheus.io/scrape: true), or re-writing the target scrape URL / port.
  • metric_relabel_configs (Post-Scrape):
    • Runs after the HTTP scrape request completes, but before samples are committed into TSDB storage memory.
    • Operates on individual metric names and labels exposed by the exporter.
    • Use Case: Dropping high-cardinality label keys (e.g. dropping user_id or session_id labels) or dropping noisy metric series entirely (e.g. action: drop; regex: "jvm_gc_memory_allocated_bytes_total") to protect TSDB memory.

Scraping & Service Discovery
An engineer asks why Node Exporter and kube-state-metrics report different memory usage for the same Kubernetes node. What does each measure?
⌄

Strong answer

Each exporter measures completely different layers of the infrastructure stack:

  • Node Exporter:
    • Measures raw OS / host kernel hardware metrics directly from /proc and /sys.
    • Reports true physical RAM usage: node_memory_MemTotal_bytes - node_memory_MemAvailable_bytes (accounts for Linux page cache, slab, and active memory).
    • Has zero awareness of Kubernetes pods, namespaces, or container limits.
  • kube-state-metrics (KSM):
    • Listens to the Kubernetes API server and converts object specs into metrics.
    • Reports what is requested or allocated according to Kubernetes manifests (e.g. kube_pod_container_resource_requests{resource="memory"}).
    • Does NOT measure physical hardware utilization. A node might have 100% memory requested by pods according to KSM, while actual physical RAM usage measured by Node Exporter is only 15%.
  • cAdvisor: Embedded in kubelet; measures actual physical cgroup usage consumed by individual containers (container_memory_working_set_bytes).

Scraping & Service Discovery
A developer creates a `ServiceMonitor` CRD in Kubernetes, but Prometheus does not scrape their service. How do you troubleshoot the Prometheus Operator?
⌄

Strong answer

The Prometheus Operator matches ServiceMonitors via label selectors. Systematic troubleshooting sequence:

  • Check 1 (ServiceMonitorSelector match): Check the Prometheus custom resource: 
    kubectl get prometheus -n monitoring -o yaml | grep -A 5 serviceMonitorSelector
    If Prometheus has serviceMonitorSelector: matchLabels: release: prometheus-stack, your ServiceMonitor MUST have the exact label release: prometheus-stack in its metadata, or the Operator will silently ignore it.
  • Check 2 (Namespace Selector): Check serviceMonitorNamespaceSelector. If null or restricted, the Operator will not discover ServiceMonitors created in application namespaces (e.g. payments).
  • Check 3 (Service Port Name Match): The endpoints[].port field in the ServiceMonitor must match the name of the port in the Kubernetes Service (e.g. port: http-metrics), NOT the numeric port number (e.g. 8080).
  • Check 4 (Endpoints Active): Verify the underlying Kubernetes Service actually has healthy endpoints: kubectl get endpoints my-service -n payments. If 0 endpoints exist (pods unready), Prometheus will not scrape.

PromQL & Query Optimization
A developer deployed a metric `http_requests_total{user_id="12345"}` with 10 million distinct user IDs. Prometheus crashed with OOMKilled. How do you remediate and prevent this?
⌄

Strong answer

This is a catastrophic High-Cardinality Explosion. In Prometheus, every unique combination of key-value label pairs creates an independent time series in RAM.

  • Step 1 (Immediate Triage): Drop the offending metric or label at scrape time using metric_relabel_configs in the scrape configuration: 
    metric_relabel_configs:
  - source_labels: [__name__]
    regex: "http_requests_total"
    action: labeldrop
    regex: "user_id"
    This strips the user_id label before it enters the TSDB head block, dropping time-series count from 10,000,000 to ~20.
  • Step 2 (Limit Scraping via sample_limit): Set sample_limit: 10000 on the scrape job so any exporter emitting >10,000 series is rejected automatically.
  • Step 3 (Post-incident Analysis): Query top cardinality contributors: 
    # In Prometheus UI -> Status -> TSDB Status -> Head Stats:
"Top 10 label names with highest series count"
  • Best Practice: High-cardinality identifiers (UUIDs, IP addresses, emails, user IDs) belong in distributed tracing (Jaeger/Tempo) or logs (Loki/Elasticsearch), NEVER in Prometheus metric labels.

PromQL & Query Optimization
Explain the mathematical and practical differences between `rate()` and `irate()` in PromQL. When is using `irate()` in alerting rules dangerous?
⌄

Strong answer

Both calculate the per-second rate of increase on counter metrics, but over different sample windows:

  • rate(http_requests_total[5m]):
    • Calculates the average per-second rate across the entire 5-minute time window (compares the first and last samples, handles counter resets).
    • Result: Smooth curve. Filters out short-lived noise and temporary dips.
    • Standard for: Alerting rules and SLO monitoring.
  • irate(http_requests_total[5m]):
    • Calculates the "instant rate" using strictly the last two data points within the window.
    • Result: Highly volatile, high-frequency spiky graph. Captures instantaneous bursts.
    • Standard for: High-resolution exploratory troubleshooting on Grafana dashboards.
  • Why irate() is dangerous in Alerting: A single 1-second traffic burst or momentary counter glitch will cause irate() to spike massively, triggering false-positive alerts. rate() averages out transient anomalies.

PromQL & Query Optimization
An executive Grafana dashboard with 20 panels querying 90 days of HTTP latency times out with `504 Gateway Timeout`. How do you precompute these with Recording Rules?
⌄

Strong answer

Computing quantiles (like histogram_quantile(0.99, sum(rate(...)))) over millions of raw samples in real time over 90 days exhausts CPU and memory. Use Recording Rules to precompute and store results as lightweight time series.

  • Create Recording Rule (rules.yml): 
    groups:
  - name: api_performance_rules
    interval: 30s
    rules:
      - record: job:http_requests:rate5m
        expr: sum(rate(http_requests_total[5m])) by (job, status)

      - record: job:http_latency:p99_5m
        expr: histogram_quantile(0.99, sum(rate(http_request_duration_seconds_bucket[5m])) by (le, job))
  • Update Grafana Panels: In Grafana, replace the complex 4-line histogram quantile query with the precomputed metric: 
    job:http_latency:p99_5m{job="billing-api"}
  • Result: Grafana now queries pre-calculated single-point values. Dashboard load time drops from 60 seconds (or timeout) to <200 milliseconds.

PromQL & Query Optimization
You need to calculate the percentage of memory used per Pod, joining `container_memory_working_set_bytes` with `kube_pod_container_resource_limits`. Write the PromQL query using `group_left`.
⌄

Strong answer

Joining two metric vectors with different label sets requires explicit vector matching with on() and group_left (many-to-one) or group_right (one-to-many).

  •   sum(container_memory_working_set_bytes{container!=""}) by (namespace, pod, container)
/
  sum(kube_pod_container_resource_limits{resource="memory"}) by (namespace, pod, container)
* 100
  • If matching against node labels or extra metadata from kube_pod_info: 
      container_memory_working_set_bytes{container!=""}
* on(namespace, pod) group_left(node)
  kube_pod_info
  • Explanation: group_left(node) signifies that the left side has higher cardinality (multiple containers per pod), and copies the node label from the single kube_pod_info series onto each container series on the left.

PromQL & Query Optimization
How does `histogram_quantile(0.95, ...)` estimate percentiles under the hood, and why is setting the right `le` bucket boundaries critical?
⌄

Strong answer

Prometheus does NOT store raw individual request durations (which would require infinite storage); it increments counters inside cumulative buckets bounded by le (Less than or equal to).

  • Under the hood (Linear Interpolation): histogram_quantile() identifies which bucket contains the 95th percentile rank, and assumes samples inside that bucket are uniformly distributed, performing linear interpolation between the bucket's lower and upper bounds.
  • The Danger of Bad Bucket Sizing:
    • If your buckets are [0.1, 1.0, 10.0] and all requests take between 1.1s and 9.8s, Prometheus assumes an even spread; the p95 calculation will be wildly inaccurate.
    • If the highest bucket before +Inf is 2 seconds, and a server outage causes requests to take 30 seconds, histogram_quantile caps the estimate at 2.0s, completely hiding the severity of the incident!
  • Rule: Tailor bucket boundaries exponentially around your expected SLA/SLO (e.g. [0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10]).

TSDB Storage & Compaction
Following a power outage on a storage node, Prometheus enters a CrashLoopBackOff with `panic: corrupt WAL segment`. How do you recover the database?
⌄

Strong answer

The Write-Ahead Log (WAL) records incoming in-memory samples before they are committed to 2-hour TSDB blocks. An abrupt node power cut can corrupt the active WAL segment file.

  • Step 1 (Backup current data): 
    cp -r /data/wal /data/wal_corrupt_backup
  • Step 2 (Remove the corrupted WAL segment): Identify the corrupted segment from the crash logs (e.g. /data/wal/00000142). Delete or move that specific segment file: 
    rm /data/wal/00000142
  • Step 3 (Alternative - Clear entire active WAL): If all WAL segments are unreadable, wipe the WAL directory: 
    rm -rf /data/wal/*
    Trade-off: You lose the last 1–2 hours of uncompacted in-flight data, but all historical 2-hour TSDB blocks remain 100% intact.
  • Step 4 (Restart): Prometheus initializes a fresh WAL and starts cleanly.
  • Step 5 (Preventative Flag): Pass flag --storage.tsdb.wal-compression to reduce WAL disk footprint and enable automatic snapshot backups.

TSDB Storage & Compaction
You configured `--storage.tsdb.retention.time=30d`. A sudden traffic surge causes the EBS persistent volume to hit 99% disk space in 10 days. How do you prevent disk exhaustion?
⌄

Strong answer

Relying exclusively on retention.time is an operational anti-pattern because metric ingestion rate is dynamic. Configure both retention time AND retention size.

  • Configure Dual Retention Flags: 
    --storage.tsdb.retention.time=30d
--storage.tsdb.retention.size=180GiB # On a 200GiB Persistent Volume
  • How it works: Prometheus triggers block deletion as soon as either limit is reached:
    • Under normal traffic: Keeps data for 30 days.
    • Under unexpected traffic surge: Deletes the oldest 2-hour historical blocks as soon as disk usage reaches 180GB, guaranteeing that the persistent volume never hits 100% full.
  • A 100% full disk causes TSDB compaction locks to fail, corrupting WAL segments and taking down the monitoring system.

TSDB Storage & Compaction
Explain how Prometheus TSDB compaction works (Head Block → 2h Blocks → Overlapping Blocks) and how tombstones handle metric deletion.
⌄

Strong answer

Prometheus TSDB organizes time-series data into hierarchical chunks:

  • Head Block (In-Memory + WAL): Ingests live data. Every 2 hours, the Head Block cuts and writes a non-overlapping, immutable 2-hour block to disk containing chunks, index, and meta.json.
  • Compaction: In the background, Prometheus merges multiple smaller 2-hour blocks into larger blocks (e.g. 6-hour, 12-hour, 24-hour) to reduce index overhead and improve query performance.
  • Tombstones (Deletions): When you call the delete API (/api/v1/admin/tsdb/delete_series), Prometheus does NOT physically rewrite gigabytes of immutable chunk files on disk immediately. Instead, it writes a lightweight tombstone file marking time ranges as deleted.
    • Queries filter out tombstones at runtime.
    • The physical disk space is only freed when the compaction engine eventually merges the block and drops the marked samples.

TSDB Storage & Compaction
Every 2 hours on the dot, Prometheus query latency spikes from 50ms to 8 seconds and scrape drops occur. What is happening and how do you resolve it?
⌄

Strong answer

Every 2 hours, Prometheus TSDB flushes the in-memory Head Block to disk and initiates background block compaction, causing a massive sequential read/write disk I/O burst.

  • Root Cause: Disk IOPS saturation. On cloud disks (like AWS EBS gp2 or gp3 with default 3000 IOPS), the compaction flush exhausts IOPS and disk queue depth rises, causing incoming HTTP scrapes and user queries to queue and time out.
  • Remediation:
    • Upgrade EBS storage to gp3 with provisioned 8,000+ IOPS and 350+ MB/s throughput, or use local NVMe SSDs.
    • Enable WAL compression: --storage.tsdb.wal-compression.
    • Offload long-term storage and heavy compaction entirely to an external engine: deploy Thanos or Grafana Mimir, disabling multi-day local compaction in Prometheus with --storage.tsdb.min-block-duration=2h --storage.tsdb.max-block-duration=2h.

TSDB Storage & Compaction
How do you take a consistent, live backup of a running Prometheus database without stopping the server or taking downtime?
⌄

Strong answer

Use the Prometheus Admin API Snapshot endpoint.

  • Step 1 (Enable Admin API flag): Ensure Prometheus is started with the flag: 
    --web.enable-admin-api
  • Step 2 (Trigger Snapshot via HTTP POST): 
    curl -XPOST http://localhost:9090/api/v1/admin/tsdb/snapshot
  • Response: 
    {"status":"success","data":{"name":"20261118T120000Z-7a3b4c1d"}}
  • How it works: Prometheus creates hardlinks to all committed 2-hour TSDB blocks and flushes active head memory into a dedicated snapshot directory located at /data/snapshots/<name>. Because it uses hardlinks, the operation completes in <1 second without duplicating disk space or locking queries.
  • Step 3 (Copy to S3): An automated cron job syncs /data/snapshots/<name> to Amazon S3 or GCP Cloud Storage.

Alertmanager & Incident Routing
A top-of-rack network switch fails. Alertmanager immediately sends 400 separate PagerDuty alerts for every single VM, container, and database behind that switch. How do you suppress this using Inhibition Rules?
⌄

Strong answer

Use Alertmanager Inhibition Rules (inhibit_rules) to mute a set of downstream alerts when a root-cause alert is already firing.

  • Inhibition Configuration (alertmanager.yml): 
    inhibit_rules:
  - source_matchers:
      - alertname = "NetworkSwitchDown"
      - severity = "critical"
    target_matchers:
      - alertname =~ "InstanceDown|KubeNodeNotReady|DatabaseUnreachable"
    equal: ['rack_id', 'datacenter']
  • How it works:
    • source_matchers: Detects that the root cause alert NetworkSwitchDown is active for rack_id: rack-04.
    • target_matchers: Automatically suppresses all downstream InstanceDown and DatabaseUnreachable alerts that share the identical rack_id label.
  • Result: On-call engineers receive exactly 1 critical page for the network switch rather than 400 noisy notifications.

Alertmanager & Incident Routing
CPU utilization hovers right around 85%, triggering an alert every 2 minutes and resolving 1 minute later, causing alert fatigue. How do you eliminate flapping?
⌄

Strong answer

Alert flapping occurs when metric values oscillate around a rigid threshold. Resolve it using the for: duration directive and hysteresis / smoothing.

  • Fix 1 (Enforce `for:` duration): 
    alert: HighCPUUsage
expr: 100 - (avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100) > 85
for: 15m # Must stay continuously above 85% for 15 full minutes before firing
labels:
  severity: warning
    During the 15-minute pending state, momentary dips below 85% reset the evaluation timer, preventing transient spikes from waking up on-call engineers.
  • Fix 2 (Smoothed average): Use a longer rate window: rate(...[15m]) instead of rate(...[1m]) to smooth high-frequency oscillations.
  • Fix 3 (Alertmanager repeat_interval): Set repeat_interval: 4h so an unresolved alert doesn't re-notify repeatedly.

Alertmanager & Incident Routing
Design an Alertmanager routing tree: Critical billing alerts page PagerDuty immediately, warning alerts post to Slack, and all alerts also copy to an audit webhook.
⌄

Strong answer

Use a hierarchical route tree with matchers and the continue: true directive.

  • route:
  receiver: 'default-slack'
  group_by: ['alertname', 'cluster', 'service']
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
  routes:
    # Route 1: Audit webhook receives everything
    - receiver: 'audit-webhook'
      continue: true # Evaluates subsequent sibling routes!

    # Route 2: Critical Billing Alerts -> PagerDuty
    - receiver: 'pagerduty-billing'
      matchers:
        - team = "billing"
        - severity = "critical"

    # Route 3: Team Slack Channels
    - receiver: 'slack-billing'
      matchers:
        - team = "billing"
  • continue: true: Critical for multi-casting. By default, Alertmanager stops evaluating routes on the first match. continue: true ensures the audit logging service receives a copy of the alert before Alertmanager routes it to PagerDuty or Slack.

Your database team is performing a 3-hour planned maintenance window on `prod-db-cluster`. How do you programmatically create a Silence using `amtool`?

Alertmanager & Incident Routing
Explain the exact relationship between `group_by`, `group_wait`, and `group_interval` in Alertmanager. How do they prevent message flood?
⌄

Strong answer

These three settings control Alertmanager's batching and aggregation engine:

  • group_by: ['alertname', 'cluster']: Bundles all alerts sharing the same alertname and cluster into a single consolidated notification.
  • group_wait: 30s: When the first alert in a new group fires, Alertmanager pauses for 30 seconds before sending the initial notification. If 15 related microservice alerts fire within those 30 seconds, they are batched together into one single Slack message listing all 15 items.
  • group_interval: 5m: If new additional alerts join an already-firing group while an incident is ongoing, Alertmanager waits 5 minutes before sending an updated batch notification.
  • repeat_interval: 4h: If no new alerts arrive and the incident remains unresolved, Alertmanager re-sends the notification every 4 hours as a reminder.

Grafana Visualization & GitOps
A mission-critical Grafana dashboard takes 45 seconds to load and crashes browser tabs. What are the top 4 performance anti-patterns to audit and fix?
⌄

Strong answer

Slow Grafana dashboards almost always stem from unoptimized query design and frontend overload:

  • Anti-Pattern 1 (Overlapping Regex Variables): Top-level dropdown variables using unconstrained regex (label_values(node) across 5,000 nodes). Change query to filter by namespace/cluster first: label_values(node_uname_info{cluster="$cluster"}, node).
  • Anti-Pattern 2 (Unconstrained Range / $__rate_interval): Queries using hardcoded small windows like rate(metric[1m]) over a 30-day time range force Prometheus to return millions of data points. Replace hardcoded intervals with $__rate_interval: 
    rate(http_requests_total[$__rate_interval])
    Grafana automatically scales the window to match the panel pixel width.
  • Anti-Pattern 3 (Too Many Panels on One Dashboard): 50 panels making 50 simultaneous PromQL queries. Consolidate into collapsed Dashboard Rows (Grafana only queries panels when the row is expanded).
  • Anti-Pattern 4 (Missing Max Data Points): Enforce Max Data Points = 1000 in panel options so Prometheus downsamples server-side.

Grafana Visualization & GitOps
When should an organization use Grafana Unified Alerting instead of Prometheus Alertmanager? What are the architectural trade-offs?
⌄

Strong answer

Both alert engines overlap, but have fundamental architectural differences:

  • Prometheus Alertmanager:
    • How: Prometheus server evaluates PromQL rules natively against local TSDB and pushes firing alerts to Alertmanager.
    • Pros: Extremely reliable; continues alerting even if Grafana is down; version-controlled via YAML.
    • Cons: Limited strictly to Prometheus data sources.
  • Grafana Unified Alerting:
    • How: Grafana backend executes alert queries across any configured data source.
    • Pros: Multi-datasource alerting (can join Prometheus metrics + Elasticsearch/Loki logs + CloudWatch metrics + SQL database queries in a single alert expression). Rich visual UI builder for non-SRE teams.
    • Cons: If Grafana crashes or runs out of memory, all alerting ceases. Harder to manage at massive scale via pure GitOps without specialized APIs.
  • Standard Practice: Use Prometheus Alertmanager for core infrastructure and Kubernetes availability; use Grafana Alerting for multi-source business KPIs and dashboard-bound alerts.

Multi-Cluster, Thanos & High Availability
Explain the architecture of Thanos for scaling Prometheus across 20 Kubernetes clusters with multi-year S3 long-term storage and deduplication.
⌄

Strong answer

Thanos transforms standalone Prometheus instances into a globally scalable, multi-cluster monitoring system with unlimited retention:

  • Component Breakdown:
    • Thanos Sidecar: Runs alongside each Prometheus pod. Backs up completed 2-hour TSDB blocks to object storage (S3/GCS) and provides a gRPC query interface for Prometheus's local live data.
    • Thanos Query (Querier): The central entrypoint for Grafana. Evaluates PromQL across all clusters simultaneously by querying Sidecars (live data) and Store Gateways (historical data). Automatically deduplicates HA replicas based on cluster/replica labels.
    • Thanos Store Gateway: Acts as an efficient proxy over object storage, caching indexes to allow querying petabytes of multi-year historical metrics without downloading raw chunks.
    • Thanos Compactor: A single-instance background worker that merges multi-cluster blocks in S3 and performs long-term downsampling (to 5m and 1h resolutions) to speed up multi-year queries.

How do you achieve High Availability for Prometheus? If two identical Prometheus replicas scrape the same target, how does Thanos or Grafana deduplicate them?
⌄

Strong answer

Run dual independent Prometheus replicas (Replica A & Replica B) scraping the exact same targets simultaneously.

  • Configuration (External Labels): Give each replica a unique replica label and a shared cluster label: 
    # Prometheus Replica A:
external_labels:
  cluster: "us-east-prod"
  replica: "A"

# Prometheus Replica B:
external_labels:
  cluster: "us-east-prod"
  replica: "B"
  • Deduplication via Thanos Query: Run Thanos Query with flag: 
    --query.replica-label="replica"
    When Grafana executes a PromQL query, Thanos Query strips the replica label, compares time-series timestamps from both replicas, and drops duplicate samples.
  • If Replica A crashes or restarts, Replica B transparently serves metrics with zero graph gaps and zero user impact.

Why must Thanos Compactor strictly run as a singleton (replica: 1), and what catastrophic issue occurs if two compactors run on the same S3 bucket?
⌄

Strong answer

Thanos Compactor is fundamentally not concurrency-safe across multiple instances.

  • The Danger: The Compactor performs heavy block index merging, overlapping block deduplication, and downsampling directly in object storage. If two Compactor replicas run simultaneously against the same bucket, both will read the same blocks, create duplicate compacted output blocks, and produce overlapping TSDB blocks.
  • Catastrophic Consequence: The Thanos Store Gateway and Query engines will crash with: halt: found overlapping blocks during compaction, permanently breaking queries for that time range until manual bucket reconciliation is performed using thanos tools bucket inspect.
  • Rule: Always deploy Thanos Compactor as a Kubernetes Deployment with replicas: 1 and a Recreate strategy (never RollingUpdate) to guarantee dual pods never run concurrently.

Compare Thanos vs Grafana Mimir (Cortex). When would an enterprise choose Mimir's Remote-Write Push architecture over Thanos's Sidecar Pull model?
⌄

Strong answer

Both provide long-term scalable Prometheus storage, but use opposing ingest architectures:

  • Thanos (Pull + Sidecar):
    • Prometheus scrapes and stores data locally; Thanos Sidecar uploads blocks every 2h and Thanos Query pulls via gRPC.
    • Pros: Works naturally with existing Prometheus setups; zero ingress load balancer required for metric ingestion; local Prometheus retains full functionality if central Thanos fails.
  • Grafana Mimir / Cortex (Push via Remote-Write):
    • Edge Prometheus instances scrape metrics and immediately forward them via HTTP remote_write to a centralized Mimir cluster.
    • When to Choose Mimir:
      • Network restrictions: Edge environments (IoT, retail stores, private client VPCs) where central query engines cannot establish inbound network connections to pull data.
      • Multi-tenancy: Native hard multi-tenancy with strict tenant limits (X-Scope-OrgID header) built into the core engine.

If Prometheus or Alertmanager crashes completely, no alerts can fire. How do you architect a 'Dead Man's Switch' (Watchdog) to monitor the monitoring system?
⌄

Strong answer

Solve the "Who monitors the monitor?" problem using an inverted heartbeat signal called a Dead Man's Switch (Watchdog alert).

  • Step 1 (Prometheus Always-Firing Alert): Create an alert rule in Prometheus that evaluates to true 100% of the time: 
    alert: Watchdog
expr: vector(1)
for: 0m
labels:
  severity: none
annotations:
  summary: "Continuous heartbeat signal to external monitoring"
  • Step 2 (Alertmanager Heartbeat Webhook): Alertmanager continuously forwards this firing alert every 60 seconds to an external independent SaaS health-checker (such as Healthchecks.io, Dead Man's Snitch, or Opsgenie Heartbeats).
  • Step 3 (Fail-Safe Alerting):
    • As long as the external service receives the ping every 60 seconds, all is quiet.
    • If Prometheus crashes, Alertmanager dies, the network severed, or Kubernetes nodes fail, the pings stop.
    • The external service detects the missing heartbeat after 3 minutes and directly pages the SRE team via SMS/PagerDuty: "ALERT: Prometheus Monitoring System is DOWN!"
