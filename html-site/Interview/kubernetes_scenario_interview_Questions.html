Kubernetes Real-Time Scenario-Based Interview Questions & Answers

Practical production troubleshooting and DevOps interview preparation for engineers with 4–5 years of experience.

How to use this guide

For each scenario, explain the symptom, commands used, likely root cause, corrective action and prevention. In an interview, describe what you would verify before making a production change. Commands and examples are starting points; adapt namespaces, resource names and permissions to your environment.

1. Pod Troubleshooting

Q1. Your pod is stuck in Pending state. How will you troubleshoot?

Answer: Run kubectl get pods -n production, kubectl describe pod <pod> -n production and inspect events. Common causes include insufficient CPU or memory, node selectors, taints/tolerations, unbound PVCs, quotas and scheduling constraints. Check node capacity with kubectl describe nodes and kubectl top nodes, then fix the specific scheduling constraint.

Q2. Your pod is in CrashLoopBackOff. What will you do?

Answer: Inspect kubectl describe pod <pod>, kubectl logs <pod> and especially kubectl logs <pod> --previous. Look for application startup errors, bad commands, missing configuration, dependency failures, permission problems, OOM kills or failed probes. Correct the root cause rather than repeatedly deleting the pod.

Q3. Your pod is in ImagePullBackOff. How will you resolve it?

Answer: Use kubectl describe pod <pod> to see the pull error. Verify the image repository, tag, registry reachability and credentials. For private registries, configure an imagePullSecret in the same namespace and reference it under spec.imagePullSecrets. Confirm the image exists and the node can reach the registry.

Q4. Your pod is Running, but the application is not accessible. What will you check?

Answer: Check application logs, listening port, pod readiness, Service selector, targetPort, endpoints and NetworkPolicies. Run kubectl get pods -o wide, kubectl get svc, kubectl describe svc <service> and kubectl get endpointslice. Verify the process listens on the expected interface and port.

Q5. Your pod keeps getting terminated and recreated. Why?

Answer: Inspect kubectl describe pod, container termination reason, events and previous logs. Possible causes include OOMKilled, liveness probe failures, node pressure, node failure or a controller rollout. Check resource usage with kubectl top pod and investigate the specific termination reason.

Q6. Your pod shows Running, but the application is not responding. Why?

Answer: Running only means the container process is running; it does not guarantee the application is ready. Check logs, readiness probe results, application port, dependencies and health endpoint. Verify that the Service only routes traffic to ready endpoints.

2. Deployments and ReplicaSets

Q7. A new application deployment is stuck. How will you troubleshoot?

Answer: Run kubectl rollout status deployment/<name>, kubectl describe deployment <name>, kubectl get rs and inspect pod events. Check image pulls, scheduling, readiness probes, resource requests and startup logs. Roll back if the new release is impacting production.

Q8. You updated the image, but Kubernetes still runs the old version. Why?

Answer: Inspect the live Deployment image with kubectl get deployment <name> -o yaml and check rollout status. Verify namespace, container name, image tag and whether the manifest was applied. Reusing a mutable tag such as latest with IfNotPresent can retain cached images. Prefer unique immutable tags or digests.

Q9. You need five replicas, but only three pods are running. What will you check?

Answer: Check kubectl get deployment, kubectl describe deployment and pending pod events. Look for insufficient node capacity, quota limits, affinity rules, taints, image pull failures and readiness failures. Resolve the scheduling or startup issue and confirm desired, updated and available replica counts.

Q10. How will you perform a low-downtime deployment?

Answer: Use a RollingUpdate strategy with suitable maxSurge and maxUnavailable, readiness probes and graceful shutdown handling. Ensure enough cluster capacity and backward-compatible application/database changes. For example, maxUnavailable: 0 and maxSurge: 1 can maintain available replicas during a rollout, provided the cluster can schedule the extra pod.

Q11. A new release causes production issues. How will you roll back?

Answer: Check kubectl rollout history deployment/<name>, then run kubectl rollout undo deployment/<name>. To return to a specific revision use --to-revision=<number>. Verify with kubectl rollout status, application health checks and monitoring. Investigate the failed release before redeploying.

Q12. What happens if you manually delete a pod?

Answer: If it is managed by a Deployment/ReplicaSet or StatefulSet, its controller normally creates a replacement to maintain desired state. A standalone pod has no controller to recreate it. Check ownership using kubectl get pod <pod> -o yaml or kubectl describe pod.

3. Services and Networking

Q13. Frontend pods cannot communicate with backend pods. How will you troubleshoot?

Answer: Check pod status, Service selectors, EndpointSlices, ports, DNS and NetworkPolicies. Use kubectl get svc, kubectl get endpointslice, kubectl describe svc and test DNS/connectivity from a diagnostic pod. Confirm the backend Service name and namespace are correct.

Q14. Explain ClusterIP, NodePort and LoadBalancer.

Answer: ClusterIP exposes a Service internally within the cluster. NodePort exposes it on a port on each node. LoadBalancer requests an external load balancer from a supported cloud/provider integration. Choose based on exposure requirements; in EKS, a LoadBalancer Service commonly integrates with AWS load-balancing infrastructure.

Q15. A Service has no endpoints. What could be wrong?

Answer: Check whether the Service selector matches pod labels, whether pods are in the same namespace and whether pods are Ready. Run kubectl describe svc, kubectl get pods --show-labels and kubectl get endpointslice. Correct selector/labels or fix pod readiness.

Q16. The application works inside the cluster but not externally. What will you check?

Answer: Check Service type, Ingress rules, Ingress controller, load balancer target health, DNS, TLS, security groups and firewall rules. Use kubectl get svc,ingress -A and describe the relevant resources. In EKS, inspect AWS Load Balancer Controller events and AWS target group health.

Q17. Pods cannot resolve Kubernetes Service DNS names. How will you troubleshoot?

Answer: Check CoreDNS pods and logs in kube-system, then test kubernetes.default from a diagnostic pod. Inspect DNS configuration, NetworkPolicies, CNI health and CoreDNS resource limits. Commands include kubectl get pods -n kube-system and kubectl logs -n kube-system deployment/coredns.

4. ConfigMaps, Secrets and Storage

Q18. You changed a ConfigMap, but the application still uses old configuration. Why?

Answer: Environment variables sourced from ConfigMaps do not update inside existing containers. Mounted ConfigMap volumes update eventually, but the application may need to reload files. Check the ConfigMap and pod specification; use a controlled rollout restart if the application cannot reload configuration.

Q19. How will you manage database passwords securely?

Answer: Use Kubernetes Secrets or an external secrets manager, restrict access with RBAC, enable encryption at rest for Kubernetes data and rotate credentials. Secrets are base64-encoded by default, not automatically encrypted. Avoid committing secret values to source control or embedding them in images.

Q20. A PersistentVolumeClaim is Pending. How will you resolve it?

Answer: Run kubectl describe pvc, kubectl get pv and kubectl get storageclass. Check StorageClass, provisioner/CSI driver, access modes, requested capacity, quotas, topology and cloud permissions. In EKS, check the EBS CSI driver when using EBS volumes.

Q21. A database pod is deleted. Will data be lost?

Answer: Not necessarily. If data is stored on a persistent volume, it can survive pod recreation. Check the PVC/PV and StatefulSet configuration. Confirm the volume can be reattached and that backups exist. A persistent volume is not a substitute for database backups.

Q22. Multiple pods need shared storage. What would you use?

Answer: Choose storage based on access mode and performance needs. On AWS, EFS is commonly used for shared ReadWriteMany filesystem access; EBS is block storage commonly used with single-node attachment patterns. Object storage is better for object data, not as a POSIX filesystem. Validate CSI driver support and application consistency requirements.

5. Node and Cluster Troubleshooting

Q23. A worker node becomes NotReady. How will you troubleshoot?

Answer: Run kubectl describe node <node> and inspect node conditions/events. On the node, check kubelet and container runtime with systemctl status kubelet, systemctl status containerd and journalctl -u kubelet. Investigate network, disk, memory, certificates and runtime health.

Q24. A node shows DiskPressure. What will you do?

Answer: Check df -h, df -i, container logs, image usage and ephemeral storage. Identify safe cleanup targets and expand disk if necessary. Do not manually delete active container-runtime data. Configure log rotation and ephemeral-storage requests/limits where appropriate.

Q25. A node shows MemoryPressure. How will you resolve it?

Answer: Use kubectl top nodes, kubectl top pods -A and node descriptions to identify memory consumers. Investigate leaks and requests/limits, adjust workloads, or add node capacity. Check system reservations and eviction events.

Q26. You need to prevent new pods from scheduling on a node during maintenance. How?

Answer: Run kubectl cordon <node> to mark it unschedulable. Drain eligible workloads with kubectl drain <node> --ignore-daemonsets, after checking PodDisruptionBudgets, local storage and workload availability. After maintenance, run kubectl uncordon <node>.

Q27. The cluster has insufficient resources for new pods. What will you do?

Answer: Inspect pending pod events, node capacity, requests/limits, quotas and scheduling constraints. Use kubectl describe pod, kubectl top nodes and kubectl describe nodes. Right-size requests, remove unnecessary workloads or add node capacity through the configured node autoscaler.

Q28. What happens when a worker node suddenly crashes?

Answer: The control plane detects missed node heartbeats and marks the node NotReady/Unknown. After configured monitoring and eviction periods, controller-managed pods may be recreated on healthy nodes, subject to storage and scheduling constraints. Check node events, pod placement, volume attachment and application availability.

6. Autoscaling

Q29. Traffic increases and pod CPU rises. How will you handle it?

Answer: Configure HPA using CPU, memory or custom metrics. Ensure resource requests and metrics are configured, set sensible minimum/maximum replicas and monitor scaling behavior. HPA adjusts pod replica counts; it does not itself add worker nodes.

Q30. HPA is configured, but pods do not scale. What will you check?

Answer: Run kubectl describe hpa and kubectl top pods. Check Metrics Server, resource requests, target metrics, HPA conditions and maximum replicas. For CPU utilization targets, CPU requests are needed to calculate utilization.

Q31. Pods scale up, but worker nodes do not. Why?

Answer: HPA scales pods; Cluster Autoscaler or Karpenter scales nodes when pods cannot be scheduled due to capacity. Check pending pod events, node group limits, autoscaler logs, instance constraints, subnet capacity and scheduling rules.

Q32. There are too many replicas when traffic is low. How will you optimize?

Answer: Review HPA minimum replicas, metrics, target utilization and scale-down stabilization behavior. Check whether metrics are accurate and whether requests are appropriately sized. Tune policies carefully to avoid oscillation or compromising availability.

7. Probes and Application Health

Q33. Explain Liveness, Readiness and Startup probes.

Answer: Liveness determines whether a container should be restarted. Readiness determines whether a pod should receive Service traffic. Startup gives slow-starting applications time to initialize before liveness/readiness checks take effect. Use endpoints and thresholds that reflect actual application behavior.

Q34. A liveness probe repeatedly restarts your application. What will you do?

Answer: Inspect pod events and logs. Verify endpoint, port, timeout, initial delay and application startup time. A startupProbe can protect slow-starting applications. Do not simply disable liveness; ensure it detects a genuinely unrecoverable process state.

Q35. Pods are Ready, but users still see errors. Why?

Answer: The readiness check may be too shallow or may not validate critical dependencies. Check application error rates, database/external service connectivity, logs and health endpoint design. Make readiness represent the application's ability to serve requests, without making transient dependencies cause unnecessary flapping.

8. Security and RBAC

Q36. A developer can list pods but cannot delete them. How will you troubleshoot?

Answer: Use kubectl auth can-i delete pods -n production and inspect Roles/RoleBindings. Grant only the required verbs and resources in the intended namespace. Avoid broad cluster-admin permissions.

Q37. How will you restrict backend access to only frontend pods?

Answer: Use a NetworkPolicy selecting backend pods and allowing ingress from pods with the frontend label. Confirm the cluster CNI enforces NetworkPolicies. Policies are additive and namespace scope matters; explicitly consider DNS and other required traffic.

Q38. Containers are running as root. How will you improve security?

Answer: Run as a non-root UID, drop unnecessary Linux capabilities, disable privilege escalation, use read-only root filesystems where possible and apply Pod Security Standards. Scan images and keep base images patched.

Q39. A Kubernetes Secret is accidentally deleted. What will you do?

Answer: Restore it from the approved source of truth, such as an external secrets manager or protected backup. Assess affected workloads, access logs and whether credentials require rotation. Improve RBAC and recovery procedures.

9. Monitoring and Logging

Q40. The application is failing, but kubectl logs are insufficient. What will you do?

Answer: Check current and previous container logs, pod events and node conditions. Use centralized logging such as Fluent Bit with Elasticsearch/OpenSearch or Loki. Correlate timestamps, namespace, pod, container and request IDs.

Q41. How will you monitor Kubernetes cluster health?

Answer: Use Prometheus and Grafana or a managed monitoring platform. Track node and pod CPU/memory, restarts, readiness, API server, scheduling, storage, network and application SLOs. Configure actionable alerts and dashboards.

Q42. A pod consumes high CPU despite low traffic. How will you investigate?

Answer: Identify top consumers with kubectl top pods -A --sort-by=cpu. Inspect application profiling, background jobs, loops, excessive logging, garbage collection and thread behavior. Correlate metrics and logs before changing limits.

10. Jenkins and CI/CD

Q43. Explain a Jenkins-to-Kubernetes deployment pipeline.

Answer: Typical stages are source checkout, build, unit tests, Docker image build, image scan, registry push, manifest/Helm update, deployment and rollout verification. Use immutable image tags/digests, securely managed credentials, least-privilege Kubernetes access and an explicit rollback strategy.

Q44. Jenkins pushes an image successfully, but Kubernetes deployment fails. What will you check?

Answer: Inspect Deployment status, pod events, image name/tag, registry credentials, RBAC, manifest validity, scheduling capacity and application startup. Use kubectl describe deployment, kubectl describe pod and kubectl get events to locate the failing stage.

Q45. How will you automatically roll back a failed deployment?

Answer: Have the pipeline wait for kubectl rollout status deployment/<name> --timeout=120s. If verification fails, execute kubectl rollout undo deployment/<name>, then verify rollout and application health. Account for database migrations and changes that are not backward-compatible.

11. Advanced Production Scenarios

Q46. The Kubernetes API server is not responding. What will you do?

Answer: Check cluster endpoint reachability, kubeconfig context, authentication, certificates and control-plane health. For managed EKS, inspect cluster status, endpoint access settings, AWS service health and relevant control-plane diagnostics. Distinguish client connectivity from an actual control-plane outage.

Q47. A pod is evicted although it has not reached its memory limit. Why?

Answer: Eviction can result from node-level memory or disk pressure, inode pressure, ephemeral-storage pressure or kubelet eviction thresholds. Inspect pod events and node conditions; a container's own memory limit is not the only factor.

Q48. What happens when you delete a Deployment?

Answer: By default, Kubernetes garbage collection removes dependent ReplicaSets and pods. With kubectl delete deployment <name> --cascade=orphan, dependent objects can be orphaned. Use this deliberately because orphaned pods are no longer managed by that Deployment.

Q49. A StatefulSet pod is stuck Terminating. How will you troubleshoot?

Answer: Inspect pod events, finalizers, termination grace period, application shutdown, node reachability and volume detach/unmount events. Check PVC/PV and CSI driver status. Force deletion is a last resort because it can risk duplicate processes or data consistency.

Q50. How will you isolate multiple applications in one cluster?

Answer: Use namespaces plus RBAC, ResourceQuotas, LimitRanges, NetworkPolicies and separate ConfigMaps/Secrets. Namespaces provide logical isolation, not a complete security boundary by themselves.

Q51. How will you design a highly available application?

Answer: Run multiple replicas across nodes and availability zones, use topology spread or anti-affinity, readiness probes, PodDisruptionBudgets, autoscaling and a load balancer. Ensure databases, storage and external dependencies also have their own HA and recovery design.

Q52. How do you ensure replicas do not run on the same worker node?

Answer: Use pod anti-affinity with a label selector matching the application and topologyKey kubernetes.io/hostname. Required anti-affinity enforces separation but can leave pods Pending if there are not enough eligible nodes.

Q53. An application must run only on high-memory nodes. How?

Answer: Label suitable nodes using kubectl label nodes <node> node-type=high-memory and configure nodeSelector or node affinity in the pod template. Use taints/tolerations as an additional control when needed.

Q54. Only two of ten replicas should be unavailable during maintenance. How?

Answer: Create a PodDisruptionBudget with maxUnavailable: 2 and a selector matching the application pods. PDBs limit voluntary disruptions, such as drain operations; they do not prevent involuntary failures.

Q55. How will you manage different Dev, QA and Production configurations?

Answer: Use environment-specific overlays with Helm or Kustomize, keep common templates reusable and inject configuration through ConfigMaps and secrets through a secure secret manager. Promote the same immutable application image across environments.

12. Amazon EKS Scenarios

Q56. EKS worker nodes are not joining the cluster. How will you troubleshoot?

Answer: Check node group health, EC2 instance status, subnet routes, security groups, cluster endpoint access, node IAM role, bootstrap/user data, authentication/access configuration and kubelet logs. Review EKS managed node group health issues in the AWS Console.

Q57. An EKS pod cannot access an S3 bucket. What will you do?

Answer: Check pod identity using EKS Pod Identity or IRSA, IAM role trust and permissions, S3 bucket policy, region and network egress. Avoid embedding long-lived AWS access keys in images or environment variables.

Q58. An EKS LoadBalancer Service remains Pending. How will you troubleshoot?

Answer: Describe the Service and inspect events. Verify AWS Load Balancer Controller or cloud integration, IAM permissions, subnet discovery/tags, annotations, security groups and subnet IP capacity. Check controller logs and AWS resources.

Q59. An EKS application returns HTTP 503 through an ALB. What will you check?

Answer: Inspect Ingress, AWS Load Balancer Controller logs, target group health, pod readiness, Service selectors/endpoints, health-check path/port and security groups. Compare ALB target health with Kubernetes endpoint state.

Q60. New EKS pods remain Pending even though autoscaling is configured. Why?

Answer: Check scheduling events, node group maximum size, Karpenter/Cluster Autoscaler logs, instance constraints, pod requests, taints, affinity and subnet IP availability. Autoscaling cannot help if no eligible instance type or subnet capacity exists.

Q61. EKS pods fail with an IP address allocation error. What will you do?

Answer: Investigate Amazon VPC CNI logs and configuration, subnet free IPs, ENI limits, pod density and prefix delegation if enabled. Expand or redesign subnet capacity where appropriate and validate CNI permissions and health.

Q62. How will you upgrade EKS without application downtime?

Answer: Review version compatibility and deprecated APIs, upgrade the control plane, then compatible add-ons and worker nodes according to AWS guidance. Use surge/rolling node replacement, sufficient capacity, PDBs, readiness checks and post-upgrade validation. Back up important data and test the process in a non-production cluster first.
