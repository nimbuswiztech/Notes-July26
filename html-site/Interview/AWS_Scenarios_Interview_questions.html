Compute & scaling

EC2 · Auto Scaling · Load Balancing
01
Compute & scaling
An EC2-hosted application experiences 95% CPU utilization every day at peak hours. How would you investigate and prevent recurring incidents?
⌄

Strong answer

I would first establish whether CPU is the bottleneck or a symptom. I would correlate CloudWatch CPU, network, disk and status-check metrics with application latency, request rate and logs. On the instance, I would inspect processes and thread pools, then review recent deployments and traffic patterns.

  • Scale horizontally with an Auto Scaling group behind an ALB; use target tracking on a suitable metric such as average CPU or ALB requests per target.
  • Set minimum, maximum and desired capacity, health checks, cooldown/warm-up and scaling policies carefully.
  • Load-test changes and check database connection limits and downstream bottlenecks before simply adding instances.
  • Use scheduled scaling only for predictable peaks; retain dynamic scaling for unexpected demand.
Probe: What if CPU is low but response time is high? Look at database latency, thread/connection pools, network, locks and external dependencies.
02
Compute & scaling
Users receive intermittent 503 responses from an Application Load Balancer. The EC2 instances appear to be running. What do you check?
⌄

Strong answer

Running instances do not guarantee healthy targets. I would inspect the target group's healthy/unhealthy target counts, health-check path, port, protocol, matcher, thresholds and reason codes.

  • Confirm the application listens on the registered port and the health endpoint returns the expected status quickly.
  • Check instance security groups allow traffic from the ALB security group, plus NACLs and host firewall rules.
  • Review ALB access logs, CloudWatch metrics and application logs around the failure window.
  • Check whether deployments, connection exhaustion or capacity changes temporarily remove all targets.

Fix the root cause; do not blindly loosen health checks or return success from an endpoint that does not verify readiness.

Probe: How do you distinguish ALB-generated 503 from an application-generated 503? Correlate ALB access-log fields, target status and application request logs.
03
Compute & scaling
An EC2 instance is running, but SSH is failing. Explain your troubleshooting sequence.
⌄

Strong answer

  • Check instance and system status checks, state, subnet route table, public/private addressing and whether a bastion, VPN or SSM path is expected.
  • Verify security-group inbound rules, NACL inbound and outbound rules, route to the internet/NAT/VPN, and the client source IP.
  • Confirm the correct username, key pair, SSH daemon, disk space and OS firewall.
  • Use Systems Manager Session Manager if the instance is managed and has the required IAM role, agent and network connectivity.
  • For OS-level failure, use EC2 Serial Console where supported, or a controlled root-volume recovery procedure.

I would avoid opening SSH to 0.0.0.0/0 as a quick fix.

Probe: Can an instance in a private subnet be managed without a bastion? Yes—Systems Manager endpoints/connectivity and suitable IAM permissions can provide access.
04
Compute & scaling
During an Auto Scaling scale-in event, users lose in-flight requests. How would you make scale-in graceful?
⌄

Strong answer

Use ALB connection draining/deregistration delay and an application shutdown process that stops accepting new work while completing in-flight requests. Configure an Auto Scaling lifecycle hook to allow a controlled drain period and signal completion.

  • Make the application handle SIGTERM and stop new work gracefully.
  • Set deregistration delay and lifecycle-hook timeout based on actual request/job duration.
  • Persist important work in a durable queue rather than relying on instance memory.
  • Test scale-in during active traffic and ensure the hook cannot leave instances stuck indefinitely.

Networking & delivery

VPC · Route 53 · CloudFront · API Gateway
05
Networking & delivery
EC2 instances in a private subnet cannot download operating-system updates. Public instances work. What is your diagnosis?
⌄

Strong answer

Private instances need an outbound path. I would check the private subnet route table for 0.0.0.0/0 to a NAT Gateway (or NAT instance), and the public subnet route table for a route to an Internet Gateway. The NAT Gateway must be in a public subnet and have an Elastic IP.

  • Check NAT Gateway state, subnet association, routes, NACLs and DNS resolution.
  • Confirm security groups permit required egress and the destination is reachable.
  • For AWS services, consider VPC endpoints to avoid routing service traffic through NAT.

A NAT Gateway enables outbound connections; it does not allow unsolicited inbound internet connections to private instances.

06
Networking & delivery
Two VPCs need private communication. VPC peering is configured, but instances cannot connect. What could be wrong?
⌄

Strong answer

I would validate non-overlapping CIDR ranges, accepted peering status, routes on both sides, security groups, NACLs, host firewalls and DNS requirements. Peering is not transitive: a VPC cannot use one peering connection to route through another VPC.

  • Add explicit routes to the peer CIDR in each relevant subnet route table.
  • Allow the required protocol and port in security groups and NACLs.
  • Check return-path routing and whether private DNS names resolve as expected.
  • For many VPCs or centralized connectivity, evaluate Transit Gateway rather than a large peering mesh.
07
Networking & delivery
A production website must fail over to a secondary region if the primary region becomes unhealthy. How would you design DNS failover?
⌄

Strong answer

Use Route 53 health checks and failover routing (or an appropriate latency/weighted design) with primary and secondary endpoints. The secondary region must already be deployable and capable of serving traffic.

  • Health checks should represent meaningful application health, not merely whether a host responds.
  • Choose TTL and health-check thresholds with failover detection and DNS caching in mind.
  • Replicate data and secrets, validate certificates, warm capacity and test dependencies in the secondary region.
  • Run regular failover and failback exercises; DNS failover alone does not replicate application state.
Probe: Why might some clients continue reaching the primary? Recursive resolvers and clients can cache DNS responses.
08
Networking & delivery
A static website hosted in S3 works through the S3 URL but returns 403 through CloudFront. How do you troubleshoot?
⌄

Strong answer

  • Identify whether the origin is an S3 REST endpoint or S3 website endpoint; they have different access and feature behavior.
  • For a private S3 REST origin, configure CloudFront Origin Access Control (OAC), sign requests and grant the CloudFront distribution access in the bucket policy.
  • Check object key/case, default root object, origin path, encryption/KMS permissions and distribution behavior.
  • Review CloudFront and S3 logs, then invalidate cached errors after correcting the origin configuration.

Keep Block Public Access enabled where possible; do not make the bucket public just to bypass the issue.

Storage & databases

S3 · EBS · RDS · DynamoDB
09
Storage & databases
A developer accidentally deletes important production files from S3. How would you recover them and prevent recurrence?
⌄

Strong answer

First check whether versioning was enabled before deletion. With versioning, a delete marker may hide previous object versions; restore by removing the delete marker or copying the required version. If versioning was not enabled, recovery depends on any independent backup or replica that existed.

  • Enable versioning, appropriate lifecycle rules and, for stronger protection, S3 Object Lock where requirements justify it.
  • Use least-privilege IAM and bucket policies; separate delete permissions and consider MFA Delete where operationally suitable.
  • Enable CloudTrail data events for object-level audit where needed, and test restore procedures.
10
Storage & databases
A Linux EC2 server reports “No space left on device.” The EBS volume has been increased, but the application still fails. Why?
⌄

Strong answer

Increasing EBS capacity does not automatically expand the partition and filesystem. I would inspect lsblk, df -h and df -i to distinguish block exhaustion from inode exhaustion.

  • Verify the EBS modification completed and the OS sees the larger device.
  • Extend the partition if required (for example with growpart), then grow the filesystem using the correct tool: resize2fs for ext filesystems or xfs_growfs for XFS.
  • Find large logs, temporary files or deleted-but-open files; clean safely and configure log rotation.
  • Monitor disk and inode usage and alert before the filesystem reaches capacity.
11
Storage & databases
An RDS database is causing application latency. CPU and connections are high. What is your troubleshooting and remediation plan?
⌄

Strong answer

Correlate CloudWatch metrics (CPU, freeable memory, storage, IOPS, latency and connections) with Performance Insights/Database Insights and database slow-query information. Identify whether the issue is query load, connection storms, missing indexes, lock contention or undersized resources.

  • Optimize expensive queries and indexes; inspect execution plans.
  • Use connection pooling and consider RDS Proxy for supported engines/workloads to manage connection churn.
  • Scale instance/storage performance only after understanding the bottleneck.
  • Consider read replicas for read-heavy workloads, while understanding replication lag and that they do not solve write bottlenecks.
  • Set alarms and load-test the fix.
12
Storage & databases
A business asks for high availability and read scaling for an RDS database. Explain Multi-AZ versus read replicas.
⌄

Strong answer

Multi-AZ is primarily for availability and failover; it maintains a standby in another Availability Zone for supported configurations. A read replica is primarily for scaling read traffic and can have replication lag. Exact capabilities vary by database engine and deployment type.

  • Use Multi-AZ to improve database availability and reduce the impact of an AZ failure.
  • Use read replicas for eligible read-only workloads and direct suitable reads to them.
  • For regional disaster recovery, plan cross-region replication/backup and a tested promotion and application cutover process.
  • Define RPO/RTO and test failover; neither feature removes the need for backups.
13
Storage & databases
A DynamoDB table starts throttling during a traffic spike. What do you investigate?
⌄

Strong answer

Inspect throttled requests, consumed capacity, read/write patterns, throttling reasons and key distribution. A hot partition or uneven partition-key access can throttle even when overall table capacity looks sufficient.

  • Review partition-key design and distribute high-volume access; avoid a single heavily used key.
  • Evaluate on-demand capacity or adjust provisioned capacity and autoscaling where appropriate.
  • Use exponential backoff with jitter for retryable throttling and avoid aggressive retry storms.
  • Consider caching (for example DAX where suitable), batching and access-pattern redesign.

Security & identity

IAM · KMS · Secrets Manager · Organizations
14
Security & identity
An application on EC2 gets “AccessDenied” when reading an S3 bucket. How do you isolate the permission issue?
⌄

Strong answer

Confirm the identity actually used by the process, preferably the EC2 instance profile role via the instance metadata service. Then evaluate identity policies, bucket policy, permissions boundary, session policy, SCPs, VPC endpoint policy and explicit denies.

  • Check the exact action and resource ARN, including object ARN (bucket/*) versus bucket ARN.
  • Check KMS key policy and kms:Decrypt if objects use SSE-KMS.
  • Use IAM policy simulator and CloudTrail event details as diagnostic aids.
  • Grant only required actions/resources; avoid long-lived access keys on instances.
15
Security & identity
An AWS access key is accidentally committed to a public Git repository. What actions do you take immediately?
⌄

Strong answer

  • Disable/deactivate the exposed key immediately; do not wait for a code cleanup or assume deleting the commit removes exposure.
  • Identify the owning IAM principal, review CloudTrail for suspicious use, assess affected resources and follow incident-response escalation.
  • Rotate any dependent secrets, remove the key from repository history and prevent recurrence with secret scanning and CI checks.
  • Replace static keys with IAM roles, federation or short-lived credentials wherever possible.
  • Document the incident and verify no unauthorized persistence or resource changes occurred.
Probe: Would you delete the IAM user immediately? Not before understanding dependencies and evidence; contain the credential first and follow the incident plan.
16
Security & identity
Your application stores a database password in an environment file on EC2. How would you improve secret management?
⌄

Strong answer

Move the credential to AWS Secrets Manager (or Parameter Store for appropriate configuration/secret use cases), encrypt it with KMS, and grant the workload role permission to retrieve only that secret.

  • Retrieve secrets at runtime or through a controlled refresh mechanism; do not bake them into AMIs, source code or logs.
  • Enable rotation where supported and design the application to handle credential changes safely.
  • Restrict who can read/update the secret and audit access.
  • Plan caching, retry behavior and secret-service network access so an outage does not create uncontrolled failures.
17
Security & identity
A developer has an IAM policy allowing an action, but the action is still denied in a member account. What could override the allow?
⌄

Strong answer

IAM authorization is evaluated across multiple policy layers. An explicit deny wins. I would inspect the Organizations SCP, permissions boundary, session policy, resource-based policy, VPC endpoint policy and any applicable key policy, in addition to the identity policy.

I would use the denied CloudTrail event and policy simulator where applicable, identify the exact principal/action/resource/context, and change the narrowest relevant policy. SCPs set maximum available permissions; they do not grant permissions by themselves.

Monitoring & reliability

CloudWatch · CloudTrail · Backup · DR
18
Monitoring & reliability
A CloudWatch alarm shows no data for an EC2 disk-usage metric. CPU metrics are visible. Why?
⌄

Strong answer

EC2 basic monitoring exposes standard hypervisor metrics such as CPU, but guest OS memory and filesystem utilization generally require the CloudWatch Agent or another telemetry agent. I would check agent installation, configuration, service status, IAM permissions, log/metric namespace, dimensions and network access.

  • Verify the agent is publishing the expected metric and dimensions.
  • Check the alarm's period, statistic, threshold and missing-data treatment.
  • Ensure the alarm is not silently treating missing telemetry as healthy when that is unsafe.
19
Monitoring & reliability
A production security group rule was deleted, causing an outage. Management asks who changed it and when. How do you investigate?
⌄

Strong answer

Search CloudTrail management events around the incident for the relevant API action, such as authorizing or revoking security-group ingress/egress. Identify the event time, principal/session issuer, source IP, user agent, request parameters and response.

  • Check whether an IAM user, assumed role, automation pipeline or AWS service performed the change.
  • Correlate with deployment and change-management records.
  • Restore the approved rule through infrastructure as code, then investigate drift and prevent console-only changes.
  • Ensure organization-wide trails, retention, integrity controls and alerting meet audit requirements.
20
Monitoring & reliability
Design a disaster-recovery strategy for a business-critical application with an RTO of 30 minutes and RPO of 5 minutes.
⌄

Strong answer

I would translate the RTO/RPO into measurable recovery requirements for compute, database, object storage, networking, secrets and DNS. A pilot-light or warm-standby architecture may fit, but the actual choice depends on workload and cost.

  • Use cross-region data replication or frequent backups with a recovery point that meets five minutes; verify actual replication lag.
  • Pre-provision critical networking, IAM, certificates, images and deployment automation.
  • Automate health detection and recovery runbooks while retaining controlled approval for risky cutovers.
  • Run timed DR exercises and measure achieved RTO/RPO, including DNS/client caching and data validation.

Backups alone do not guarantee a 30-minute recovery.

Containers & serverless

ECS · EKS · Lambda · SQS
21
Containers & serverless
An application deployed on EKS has pods stuck in Pending. What is your troubleshooting workflow?
⌄

Strong answer

Start with kubectl describe pod and events to identify scheduler or provisioning reasons. Check requested CPU/memory, node allocatable capacity, taints/tolerations, node selectors, affinity, PVC binding and topology constraints.

  • Check node-group/cluster-autoscaler or Karpenter capacity and EC2 quota/subnet IP availability.
  • For networking-related failures, inspect VPC CNI, available pod IPs and subnet address capacity.
  • For image pull or startup issues, distinguish Pending from ContainerCreating/ImagePullBackOff and inspect events.
  • Fix requests/constraints or add suitable capacity; do not remove scheduling controls without understanding why they exist.
22
Containers & serverless
An EKS service is reachable inside the cluster but returns 502 through an AWS Load Balancer. What do you check?
⌄

Strong answer

  • Check ingress/service configuration, AWS Load Balancer Controller events and target-group target type (instance or IP).
  • Verify service selectors, endpoints, container port, service targetPort and application bind address.
  • Check ALB/NLB health-check path, port, protocol, success codes and target health reason.
  • Validate security-group rules, subnet tags/discovery, IAM permissions for the controller and network ACLs.
  • Inspect application logs and load-balancer access logs to determine whether the target returned an error or was unreachable.
23
Containers & serverless
A Lambda function intermittently times out after being placed inside a VPC to access RDS. What might have changed?
⌄

Strong answer

VPC attachment changes the networking path. I would check Lambda subnet selection, security groups, routes, NACLs, DNS and whether the function can reach the database port. A private subnet may need NAT or VPC endpoints for other outbound dependencies.

  • Check CloudWatch logs, duration, init duration, errors and concurrent executions.
  • Verify RDS inbound rules allow the Lambda security group.
  • Review connection creation and database connection limits; use RDS Proxy where suitable.
  • Set realistic timeout/memory, reduce cold-start work and avoid opening a new DB connection for every invocation unnecessarily.
24
Containers & serverless
An SQS consumer processes some messages more than once. The business says duplicate processing must not create duplicate payments. What do you design?
⌄

Strong answer

SQS standard queues provide at-least-once delivery, so consumers must be idempotent. Use a stable business transaction/idempotency key and persist processing state atomically with the business operation.

  • Set visibility timeout longer than normal processing time and extend it for long-running work when needed.
  • Configure a redrive policy and DLQ with a suitable max receive count; monitor age of oldest message and DLQ depth.
  • Delete messages only after successful durable processing.
  • For FIFO queues, understand deduplication and ordering guarantees, but still design safe processing and external payment idempotency.

Infrastructure as code

CloudFormation · Terraform · deployment safety
25
Infrastructure as code
A Terraform plan proposes replacing a production database instance unexpectedly. What do you do?
⌄

Strong answer

I would stop the apply and inspect the plan in detail. Identify which attribute forces replacement, compare configuration with actual state, review provider/version changes, recent manual modifications and resource lifecycle settings.

  • Confirm backups/snapshots and recovery options before any database change.
  • Refresh/reconcile state carefully; do not blindly edit state or use -target as a routine fix.
  • Correct configuration or import/reconcile drift, then produce and peer-review a new plan.
  • Use protected production workspaces/accounts, remote state with locking, version pinning and CI approval gates.

prevent_destroy can be a useful guardrail, but it is not a replacement for review and backups.

26
Infrastructure as code
A CloudFormation stack update fails and enters UPDATE_ROLLBACK_FAILED. How would you recover safely?
⌄

Strong answer

Inspect stack events to find the first failing resource and the rollback failure reason. Determine whether a resource was manually changed, deleted or blocked by a dependency or service quota.

  • Correct the underlying issue and use the supported continue-update-rollback workflow, skipping resources only when necessary and with a clear reconciliation plan.
  • After recovery, reconcile skipped resources and template/state so future updates are safe.
  • Use change sets, stack policies for critical resources, drift detection and controlled deployment pipelines.

Cost & governance

Budgets · tagging · Organizations · FinOps
27
Cost & governance
The AWS bill increases by 40% month over month. How do you identify the cause and control spend?
⌄

Strong answer

Use Cost Explorer grouped by service, linked account, region and usage type; compare the dates against deployments and traffic changes. Review CUR for detailed attribution if needed.

  • Investigate common drivers: NAT Gateway processing, data transfer, idle EC2/EBS, unattached volumes, snapshots, oversized databases, log ingestion/retention and unexpected autoscaling.
  • Use tags and account-level cost allocation to identify owners; enable budgets and anomaly detection alerts.
  • Right-size, schedule non-production shutdowns, apply lifecycle policies and evaluate Savings Plans/Reserved Instances for stable usage.
  • Validate performance and resilience before making cost reductions.
28
Cost & governance
A company has 20 AWS accounts and wants consistent security and governance. What architecture would you recommend?
⌄

Strong answer

Use AWS Organizations with a multi-account strategy and an established landing zone approach, commonly AWS Control Tower where appropriate. Separate workloads by environment, business unit or security boundary, with dedicated log archive and security/audit functions.

  • Apply SCP guardrails, centralized identity/federation, delegated administration and least-privilege roles.
  • Centralize CloudTrail, AWS Config and security findings; use Security Hub and GuardDuty as appropriate.
  • Standardize networking, account vending, tagging, budgets and baseline policies.
  • Keep SCPs as guardrails rather than treating them as permission grants; test policy changes before broad rollout.
29
Cost & governance
A workload has unexpectedly high data-transfer charges. How do you find and reduce them without harming availability?
⌄

Strong answer

Break down cost by usage type, region, service and account using Cost Explorer/CUR. Map traffic flows: internet egress, cross-AZ traffic, cross-region replication, NAT Gateway processing and inter-service transfers.

  • Use CloudFront for cacheable public content and keep chatty services close together where architecture allows.
  • Review NAT placement and VPC endpoints for AWS service traffic.
  • Optimize payload size, compression, caching and replication frequency while respecting RPO and latency.
  • Do not consolidate everything into one AZ merely to reduce transfer costs; preserve fault tolerance.
30
Cost & governance
A compliance scan finds an S3 bucket and an RDS database exposed publicly. How do you respond and prevent recurrence?
⌄

Strong answer

Treat this as a security incident until exposure is understood. Confirm actual reachability and data sensitivity, restrict public access immediately using an approved containment process, preserve audit evidence and notify the security owner.

  • For S3, review Block Public Access, bucket/access-point policies, ACLs and CloudTrail data events where enabled.
  • For RDS, disable public accessibility where possible, restrict security groups to trusted sources and validate private subnet routing.
  • Use AWS Config managed rules, Security Hub controls, GuardDuty and organization-level guardrails to detect and prevent recurrence.
  • Use IaC policy checks and CI/CD controls; assign owners and track remediation to closure.
Interviewer scoring guidance: Score each answer from 1–5. A strong 5-year candidate should clarify impact, state a logical investigation sequence, name relevant AWS metrics/logs/configuration, explain a safe remediation, and mention prevention or validation. Give partial credit for a sound method even if the candidate does not recall an exact console menu.
