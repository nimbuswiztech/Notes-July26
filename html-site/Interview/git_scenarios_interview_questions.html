01
Branching & Merge Conflicts
A release branch diverges significantly from main, causing recurring conflicts across 20+ feature branches. How do you resolve and prevent this?
⌄

Strong answer

Recurring conflicts across multiple downstream branches usually stem from delayed integration or long-lived feature branches. Immediate remediation involves rebasing feature branches against main regularly or creating a stabilization integration branch.

  • Enable git config --global rerere.enabled true (Reuse Recorded Resolution) across the team so previously resolved conflicts are automatically re-applied without manual intervention.
  • For the active release, coordinate a structured merge window where release stabilization fixes are back-merged into main immediately (or cherry-picked) rather than waiting until post-release.
  • Adopt Trunk-Based Development or Short-Lived Feature Branches (max 24–48 hours) guarded by feature toggles to prevent drift.
Interviewer Probe: What are the risks of using rerere? If an engineer records an incorrect resolution, Git will silently reproduce the broken code unless git rerere forget <file> is executed.
02
Branching & Merge Conflicts
During a rebase of 15 commits, a junior engineer hits a severe conflict, runs `git rebase --skip`, and finds several critical changes missing. How do you recover?
⌄

Strong answer

git rebase --skip discards the entire commit that triggered the conflict instead of resolving it. Never panic; Git records every reference change in the reflog.

  • Inspect the reflog: run git reflog to find the commit hash right before the rebase started (e.g. HEAD@{1} or branch@{upstream}).
  • Abort the rebase immediately if it is still in progress: git rebase --abort.
  • If the rebase already completed and updated the branch, hard-reset to the pre-rebase SHA: git reset --hard HEAD@{5} (using the exact hash identified in reflog).
  • Guide the developer through interactive rebase with git checkout --theirs or git checkout --ours, followed by git add and git rebase --continue.
Interviewer Probe: Notice that during a rebase, what does --ours vs --theirs mean? During rebase, --ours is the upstream branch you are rebasing onto, and --theirs is the incoming commit being replayed!
03
Branching & Merge Conflicts
When should an enterprise DevOps team mandate Squash Merge vs Rebase vs 3-Way Merge for pull requests?
⌄

Strong answer

There is no one-size-fits-all; the choice depends on traceability, rollback ease, and branch isolation requirements:

  • Squash and Merge: Best for feature/bugfix PRs in high-velocity teams. Collapses messy "WIP" and "fix lint" commits into one atomic commit per PR with the PR number referenced. Makes git revert <sha> trivial during production incidents.
  • Rebase and Merge: Best for repositories requiring a strictly linear Git history without extra merge commits, but where individual commits within the PR represent logical, independent architectural steps.
  • Merge Commit (3-way): Best for long-running release branches or integrating stable release candidates where preserving true branching topology and multiple author timestamps is legally or compliantly required.
Interviewer Probe: What breaks with squash merging? git cherry-pick tracking and continuous sub-branch sync can produce duplicate conflict resolutions because the original commit SHAs cease to exist on the main line.
04
Branching & Merge Conflicts
A developer complains that Git rejected a push with `[rejected - non-fast-forward]`. What caused this and how should they proceed safely without losing team work?
⌄

Strong answer

A non-fast-forward rejection means remote branch tip has commits that do not exist in the developer's local branch. Someone else pushed to the branch, or history was rewritten.

  • Never run git push --force blindly, as this overwrites teammate commits.
  • Fetch remote refs: git fetch origin.
  • Inspect differences: git log HEAD..origin/branch --oneline.
  • If changes are complementary, run git pull --rebase origin <branch> to replay local commits on top of the remote tip.
  • If a force push is genuinely needed (e.g. after deliberate feature branch rebase), use the safe flag: git push --force-with-lease, which fails if someone else has pushed new commits in the interim.
Interviewer Probe: Why is --force-with-lease safer than --force? It verifies that the remote ref still matches your local remote tracking branch before overwriting.
05
Branching & Merge Conflicts
What is an Octopus merge in Git, when would you use it, and what happens if a conflict arises during execution?
⌄

Strong answer

An Octopus merge combines more than two branches into a single merge commit simultaneously (e.g. git merge feature-a feature-b feature-c).

  • Use case: Bundling multiple independent, ready-to-test feature branches into a staging or QA testing branch in one step.
  • Conflict behavior: Git's Octopus merge strategy strictly requires that all branches can be merged cleanly without any manual conflict resolution. If even one file conflicts between any pair of branches, Git refuses the Octopus merge and aborts.
  • Recovery: If an Octopus merge aborts due to conflicts, resolve them by merging branches sequentially one by one using standard 2-way recursive/ort merges.

History Rewriting & Recovery
A developer ran `git reset --hard HEAD~5` and realized 2 hours later that 5 critical unpushed commits are gone. How do you recover them?
⌄

Strong answer

Commits in Git are almost never immediately deleted because Git uses content-addressable storage with garbage collection grace periods (typically 30–90 days).

  • Run git reflog show <branch-name> or simply git reflog to view the chronological record of where HEAD has pointed.
  • Identify the commit SHA right before the reset was triggered (e.g., HEAD@{1}: commit: implemented payment webhook).
  • Create a recovery branch at that commit: git branch recovery-branch <SHA>.
  • Inspect the recovered commits with git log recovery-branch -p.
  • Merge or fast-forward the original branch back to the recovered state: git reset --hard recovery-branch.
Interviewer Probe: What if uncommitted changes (dirty working tree) were blown away by git reset --hard? Unstaged files that were never added via git add cannot be recovered from Git; check local IDE file history (e.g. VS Code Timeline).
07
History Rewriting & Recovery
An engineer accidentally worked for a full day in a 'Detached HEAD' state and switched to `main`. Their commits disappeared. How do you rescue their work?
⌄

Strong answer

Working in a detached HEAD means commits were made without being attached to any named branch reference. When switching to another branch, Git warns that commits will be orphaned.

  • Immediately run git reflog to find the detached commit hashes. The top entries will clearly indicate commit: ... made on HEAD.
  • Attach a new branch to the latest detached commit: git branch rescued-work <orphaned-commit-sha>.
  • Switch to the rescued branch: git checkout rescued-work.
  • Verify with git log -n 5 --graph --oneline to confirm all day's commits are intact.
  • Rebase or merge rescued-work into their intended feature branch.
08
History Rewriting & Recovery
You need to backport 4 non-sequential bugfix commits from `main` to an active production release branch `release-2.4`. How do you execute this cleanly?
⌄

Strong answer

Cherry-picking specific commits across release branches requires careful order execution and recording provenance.

  • Checkout the release branch: git checkout release-2.4 and ensure working directory is clean.
  • Use git cherry-pick -x <SHA1> <SHA2> <SHA3>. The -x flag appends a line (cherry picked from commit ...) to the new commit message, providing auditability for CVEs and hotfixes.
  • If a conflict occurs: pause, resolve the conflict files, run git add <resolved-files>, and proceed with git cherry-pick --continue.
  • If a commit is irrelevant or already present: use git cherry-pick --skip. If things get tangled, safely revert with git cherry-pick --abort.
Interviewer Probe: Can you cherry-pick a merge commit? Yes, but you must pass -m 1 or -m 2 to specify which parent mainline number Git should calculate diffs against.
09
History Rewriting & Recovery
A developer submitted a PR containing 10 commits, 4 of which are 'fix typo' and 'test build'. How do you guide them to clean up history before merging?
⌄

Strong answer

Use interactive rebase to squash, reorder, and reword commits into logical, self-contained atomic changes.

  • Run interactive rebase against upstream: git rebase -i origin/main (or git rebase -i HEAD~10).
  • In the editor prompt, leave the main feature commit as pick.
  • Change subsequent minor/fixup commits from pick to fixup (or f) to combine them into previous commit while discarding redundant commit messages. Use squash (or s) if you wish to combine messages.
  • Save and exit. Git replays the history.
  • Push the clean history to their remote fork/branch using git push --force-with-lease origin feature-branch.

History Rewriting & Recovery
An engineer accidentally ran `git stash drop` on work they spent all day writing. How do you recover a dropped Git stash?
⌄

Strong answer

A Git stash is actually a set of commit objects (commit of staged index and commit of unstaged work) referenced by refs/stash. Dropping the reference leaves the commit as an unreachable dangling object.

  • If the terminal output is still visible, look for the dropped message: Dropped refs/stash@{0} (d7a8f1e...). You can immediately run git cherry-pick -m 1 d7a8f1e or git merge d7a8f1e.
  • If the SHA was not recorded, find dangling commits with: git fsck --unreachable | grep commit | cut -d' ' -f3 | xargs git log --merges --oneline.
  • Search for the stash message: look for commits with message WIP on branch: ....
  • Apply the recovered stash commit: git stash apply <commit-hash>.

Secrets & Repository Cleanup
A developer accidentally commits and pushes an active AWS production IAM Secret Key into a shared repository. What are your immediate and follow-up actions?
⌄

Strong answer

Treat this as an active security breach first, and a Git problem second.

  • Step 1 (Immediate Containment): Revoke or deactivate the compromised IAM key immediately in AWS IAM console or CLI. Assume automated GitHub scraping bots compromised it within seconds of push. Check CloudTrail for unauthorized API calls.
  • Step 2 (Local & Remote Purge): Merely creating a new commit deleting the file leaves the secret in history. Use modern git-filter-repo (recommended over legacy git filter-branch or BFG): 
    git-filter-repo --path config/credentials.json --invert-paths
  • Step 3 (Force Push & Notify): Force-push to all remotes with git push origin --force --all and git push origin --force --tags. Notify all contributors to re-clone the repository to prevent accidentally pushing old history back.
  • Step 4 (Prevention): Install client-side pre-commit hooks (gitleaks, git-secrets, or trufflehog) and enable GitHub Secret Scanning & Push Protection.

Secrets & Repository Cleanup
A 2GB `.tar.gz` artifact was accidentally committed across multiple branches. Cloning now takes 20 minutes. How do you find and remove it permanently?
⌄

Strong answer

Git stores every version of every file permanently in the .git/objects/pack database. Removing the file from latest commit does not reduce clone size.

  • Identify the top bloated objects in pack files: 
    git verify-pack -v .git/objects/pack/*.idx | sort -k 3 -n | tail -5
  • Find the filenames corresponding to the heavy blob SHAs: 
    git rev-list --objects --all | grep <blob-sha>
  • Strip the file from every branch and tag using git-filter-repo: 
    git-filter-repo --strip-blobs-bigger-than 50M
  • Expire reflogs and force aggressive garbage collection: 
    git reflog expire --expire=now --all
git gc --prune=now --aggressive
  • Force-push updated refs and mandate Git LFS (Large File Storage) for binary assets going forward.

Secrets & Repository Cleanup
Explain how Git LFS works under the hood (clean and smudge filters) and how you diagnose an LFS pointer mismatch error in CI/CD.
⌄

Strong answer

Git LFS replaces large files in the Git tree with a lightweight text pointer file containing the SHA-256 hash and size of the file. The actual binary is stored in external LFS storage.

  • Under the hood:
    • clean filter: On git add, converts the raw binary into an LFS pointer and pushes the binary to the local LFS cache.
    • smudge filter: On git checkout, replaces the text pointer in the working tree with the actual downloaded binary.
  • CI/CD Issue: CI runners that do not have git-lfs installed or forget to run git lfs pull checkout the literal 130-byte pointer text file instead of the binary (e.g., Docker builds fail with corrupt zip headers).
  • Fix: Ensure CI steps include git lfs install && git lfs pull (or in GitHub Actions: actions/checkout@v4 with lfs: true).

Secrets & Repository Cleanup
A developer adds `.env` and `*.log` to `.gitignore`, but Git continues to track changes in those files. What is the root cause and resolution?
⌄

Strong answer

.gitignore only prevents untracked files from being added to Git. If a file was already tracked in the Git index prior to updating .gitignore, Git will continue to track its modifications.

  • Root cause: The file is already committed in the Git tree or staged in the index cache.
  • Resolution: Untrack the file without deleting it from local disk: 
    git rm --cached .env
git rm --cached -r logs/
  • Commit the index removal: 
    git commit -m "chore: stop tracking .env and logs in git index"
  • Push the commit. Now .gitignore rules will properly ignore local changes to `.env`.

Secrets & Repository Cleanup
What is the critical difference between `git update-index --assume-unchanged` and `git update-index --skip-worktree` in a local developer workflow?
⌄

Strong answer

Both commands tell Git to ignore changes to a tracked file in the working copy, but they have completely different purposes and lifecycle behaviors:

  • --assume-unchanged: Intended for performance optimization. It tells Git that a large directory or file rarely changes, allowing Git to skip running stat() calls on it. If an upstream pull modifies that file, Git resets the flag and prompts conflict resolution.
  • --skip-worktree: Designed for developer configuration overrides (e.g. local database configs, debug settings). It instructs Git to never touch or overwrite local modifications even if an upstream git pull or checkout occurs. Git retains your local edits silently.
  • To resume tracking: use git update-index --no-skip-worktree <file>.

Submodules & Monorepos
A CI build fails because a submodule pointer points to an unreachable commit SHA that someone created locally but never pushed to remote. How do you resolve and prevent this?
⌄

Strong answer

A Git submodule pointer is simply a commit SHA in the parent repository. If a developer commits submodule changes locally, updates the parent repo pointer, and pushes the parent repo without pushing the submodule, remote CI clones will fail with fatal: reference is not a tree.

  • Triage: Contact the developer to push the submodule commits from their local machine to the submodule's remote upstream.
  • Alternative hotfix: If the author is unavailable, rollback the parent repository's submodule pointer to the last known stable remote commit: 
    cd path/to/submodule
git checkout origin/main
cd ..
git add path/to/submodule
git commit -m "fix: revert submodule pointer to valid remote commit"
  • Prevention: Configure Git push check: git config push.recurseSubmodules check (or on-demand), which automatically refuses to push the parent repository if submodule commits have not been pushed first.
17
Submodules & Monorepos
In an enterprise with shared libraries, compare Git Submodules vs Git Subtrees. When would you migrate from submodules to subtrees?
⌄

Strong answer

Both allow nesting external repositories, but with major operational trade-offs:

  • Git Submodule: Stores only an external remote URL and commit hash.
    • Pros: Keeps parent repository lightweight; strict version pinning.
    • Cons: Requires explicit git submodule update --init --recursive; confusing detached HEAD issues for junior devs; CI clone overhead.
  • Git Subtree: Inlines the external project's actual source code into a subfolder of the parent repo.
    • Pros: Seamless clones for developers (regular git clone works out of the box); CI works without extra credentials; changes can be committed in the parent repo and pushed back with git subtree push.
    • Cons: Increases parent repo size and history complexity.
  • Migration signal: Migrate to Subtrees (or private package managers) when developer friction with submodule checkout flags and CI token propagation across multiple private submodule repos creates persistent build failures.

Submodules & Monorepos
Your company monorepo is 80GB, containing 150 services. Developers only work on 1 or 2 services at a time. How do you configure Git for fast onboarding?
⌄

Strong answer

Leverage modern Git sparse-checkout combined with blobless / treeless partial clones:

  • Step 1 (Blobless clone): Clone only commit history and trees without file contents: 
    git clone --filter=blob:none --no-checkout <repo-url> <folder>
  • Step 2 (Initialize sparse checkout): 
    cd <folder>
git sparse-checkout init --cone
  • Step 3 (Set target directories): Only populate the desired service directory: 
    git sparse-checkout set services/billing-service common/libs
  • Step 4 (Checkout): 
    git checkout main
  • This reduces local workspace size from 80GB to under 200MB and speeds up checkout and status commands from minutes to milliseconds.
Interviewer Probe: What does --cone mode do? It restricts patterns to directory prefixes, allowing Git to use an O(1) hash check rather than regex matching every path in the repository.
19
Submodules & Monorepos
In a CI pipeline using `git clone --depth=1`, a semantic release tool fails because it cannot calculate tags or changes between releases. How do you fix it efficiently?
⌄

Strong answer

A shallow clone (--depth=1) fetches only the single latest commit. Tools like git describe --tags, changelog generators, or git diff <old-tag> HEAD fail because the ancestor commit history and tag graph do not exist.

  • Solution 1 (Unshallow on demand): Keep the shallow clone fast, but fetch missing history only when release steps run: 
    git fetch --unshallow || true
  • Solution 2 (Depth by commit window): Instead of full history, fetch with sufficient depth: git fetch --deepen=50 --tags.
  • Solution 3 (Filter blobless instead of shallow): If tag graphs are always required, replace --depth=1 with git clone --filter=blob:none. This downloads the complete commit and tag graph instantly (tiny data transfer) while downloading file blobs only for the current checkout.

Submodules & Monorepos
You are in the middle of a 2-hour long compilation on a feature branch when an urgent production P1 bug requires immediate hotfix. How do you work on both simultaneously without stashing or re-cloning?
⌄

Strong answer

Use git worktree to attach multiple working trees to the same single local repository database.

  • Do not stash or touch your active branch compiling in terminal 1.
  • In terminal 2, create a new linked working tree in an adjacent folder: 
    git worktree add ../hotfix-p1 -b hotfix/payment-gateway
  • Navigate to the new folder: cd ../hotfix-p1.
  • Write the hotfix, run tests, commit, and push directly to remote.
  • Return to original work: cd ../feature-repo.
  • Clean up the temporary worktree once done: git worktree remove ../hotfix-p1.
  • Why this is superior: Saves disk space (shares same .git object store) and avoids invalidating build caches in the primary directory.

Bisect & Code Forensics
A production regression bug appeared somewhere across 800 commits between `v2.0` and `v2.4`. How do you locate the exact commit automatically in under 5 minutes?
⌄

Strong answer

Use binary search with git bisect run driven by an automated test script (O(log N) efficiency = ~10 checks for 800 commits).

  • Create a small shell script test.sh that returns exit code 0 on success and non-zero (e.g. 1) when the bug is present (e.g., npm test -- -t "auth test").
  • Start bisect: 
    git bisect start
git bisect bad v2.4
git bisect good v2.0
  • Automate execution: 
    git bisect run ./test.sh
  • Git tests midpoints automatically, narrows the range, and prints: <SHA> is the first bad commit.
  • Finish and return to original branch: git bisect reset.
Interviewer Probe: What exit code should your script return if a commit cannot be tested due to an unrelated compile error? Exit code 125 signals Git bisect to skip that commit.

Bisect & Code Forensics
A team ran Prettier/Black formatting across the entire codebase. Now `git blame` attributes every single line to that formatting commit. How do you restore meaningful blame history?
⌄

Strong answer

Git provides native ignore-revs capability to bypass bulk reformatting commits during blame analysis.

  • Find the SHA of the large formatting commit (e.g. a1b2c3d4).
  • Create a file .git-blame-ignore-revs in repository root and add the commit hash and explanation: 
    # Format entire codebase with Prettier
a1b2c3d4e5f67890abcdef1234567890abcdef12
  • Configure Git locally and in team onboarding: 
    git config blame.ignoreRevsFile .git-blame-ignore-revs
  • Run blame: git blame -w -C -C file.js. Git now looks past whitespace and formatting commits to show the actual author of the logic.
  • GitHub, GitLab, and Azure DevOps natively recognize .git-blame-ignore-revs in their web UI blame views.

Bisect & Code Forensics
A configuration constant `MAX_RETRY_COUNT` was deleted months ago by an unknown developer. How do you find which commit removed it and why?
⌄

Strong answer

Use Git's "pickaxe" search (-S or -G) to search across historical commit diffs rather than file text.

  • Pickaxe (-S): Finds commits where the occurrence count of the string changed (added or removed): 
    git log -S "MAX_RETRY_COUNT" --source --all -p
  • Regex Pickaxe (-G): If searching with pattern matching: 
    git log -G "MAX_RETRY_.*" --oneline
  • Once the deletion commit SHA is found, inspect author, date, and commit message to understand why it was removed.
  • To see the commit details with surrounding context: git show <SHA>.

Bisect & Code Forensics
A bad release consisting of 6 consecutive commits (including 1 merge commit) caused an immediate production outage. How do you revert all 6 commits safely in one PR?
⌄

Strong answer

In production outages on shared branches, never use git reset --hard and force push. Create a clean inverse revert commit.

  • Reverting a range of commits in reverse chronological order: 
    git revert --no-commit HEAD~5..HEAD
  • For the merge commit inside that range, specify the mainline parent: 
    git revert -m 1 <merge-commit-sha> --no-commit
  • The --no-commit flag stages all the undo modifications in the working tree without generating 6 separate noisy revert commits.
  • Verify test suite passes locally.
  • Commit the clean single rollback: git commit -m "revert: rollback release v2.4 (commits SHA1..SHA6) due to outage incident #402".
  • Push and deploy immediately.

Bisect & Code Forensics
Explain the exact difference between `git diff`, `git diff --staged`, and `git diff HEAD`. When would each be used during pre-commit code verification?
⌄

Strong answer

These commands inspect differences across the three core areas of Git architecture (Working Directory, Staging Area / Index, and Repository Commit Graph):

  • git diff: Compares Working Directory vs Staging Area. Shows modifications you made that have NOT yet been staged with git add.
  • git diff --staged (or --cached): Compares Staging Area vs latest commit (HEAD). Shows exactly what will be included if you run git commit right now. Essential for final code review before committing.
  • git diff HEAD: Compares Working Directory directly against HEAD. Shows all changes regardless of whether they have been staged or not.

Release, Hooks & Governance
A developer bypasses linting and secret checks by running `git commit --no-verify`. How do you enforce compliance in an enterprise environment?
⌄

Strong answer

Client-side hooks (such as .git/hooks/pre-commit or Husky) live in local clones and can always be bypassed by developers using --no-verify. They are developer convenience tools, NOT security boundaries.

  • Solution 1 (Server-side pre-receive hooks): In self-hosted GitHub Enterprise / GitLab, install an immutable server-side pre-receive hook that scans every incoming commit for secrets (Gitleaks) and rejects the push if violations exist.
  • Solution 2 (CI/CD Quality Gates): In cloud repositories (GitHub.com), configure branch protection rules requiring mandatory status checks (lint, SAST, secret scanner) before any PR can be merged into main.
  • Solution 3 (Push Protection): Enable GitHub native Secret Scanning with Push Protection at the organization level.

Release, Hooks & Governance
Why can anyone forge a commit in Git using `git commit --author="ceo@company.com"`, and how do you protect production releases using commit signature verification?
⌄

Strong answer

Git's author and committer headers are plain text metadata; anyone can set arbitrary names and emails in git config user.email without authentication.

  • Attack vector: An attacker could commit malicious code under a lead architect's email address to bypass informal peer reviews.
  • Remediation (GPG / SSH / S/MIME signing):
    • Generate a GPG or SSH signing key: ssh-keygen -t ed25519 -C "dev@company.com".
    • Configure Git auto-signing: git config --global commit.gpgsign true.
    • Upload the public key to GitHub/GitLab account (yields "Verified" badge).
    • In repository settings, enable "Require signed commits" branch protection on main and release branches. Unsigned commits are strictly blocked from merging.

Release, Hooks & Governance
What is the technical difference between a Lightweight Tag and an Annotated Tag in Git, and which one must be used in CI/CD release pipelines?
⌄

Strong answer

Understanding tag objects is crucial for CI/CD versioning and semantic releases:

  • Lightweight Tag (git tag v1.0.0): Simply a pointer (ref) to a commit SHA, identical to a branch that never moves. Stores no metadata, no tagger name, no date, and cannot be cryptographically signed.
  • Annotated Tag (git tag -a v1.0.0 -m "Release v1.0.0"): Stored as a full, independent object in the Git object database. Contains tagger identity, timestamp, tag message, points to the commit SHA, and can be signed with GPG (git tag -s).
  • CI/CD Rule: Always use Annotated Tags for production releases. Tools like git describe look for annotated tags by default to calculate semantic version distances, and audit compliance requires knowing who tagged the release and when.

Release, Hooks & Governance
A build runner is failing because left-over build artifacts, `.o` files, and untracked folders from a previous crashed run pollute the directory. How do you reset to pristine state safely?
⌄

Strong answer

Running git reset --hard only resets tracked files; it leaves untracked build artifacts and directories in place. You must combine it with git clean.

  • Step 1 (Dry-run safety): Always verify what will be deleted before executing: 
    git clean -ndx
    (where -n is dry-run, -d includes directories, and -x includes ignored files like node_modules or compiled binaries).
  • Step 2 (Force wipe): 
    git reset --hard HEAD
git clean -fdx
  • This completely resets the working tree and index to a bit-for-bit pristine clone state without having to re-clone the entire repository over the network.

Release, Hooks & Governance
An engineer accidentally runs `git branch -D feature-payments` instead of deleting a test branch. The branch had 3 weeks of unmerged work. How do you recover it in 60 seconds?
⌄

Strong answer

Deleting a branch with -D simply removes the named reference file inside .git/refs/heads/feature-payments. The underlying commits remain in the object database until garbage collection runs.

  • When git branch -D executed, Git printed: Deleted branch feature-payments (was c4e5f6a)..
  • If you have the SHA: immediately recreate the branch: 
    git branch feature-payments c4e5f6a
  • If the terminal output was closed or cleared, inspect reflog for the branch: 
    git reflog
    Look for the last checkout or commit on that branch (e.g. checkout: moving from feature-payments to main).
  • Recreate the branch pointing to that SHA: 
    git checkout -b feature-payments <SHA>
  • Verify commits: git log -n 5 --oneline. 100% of the work is instantly restored.
Interviewer Scoring Guide: A strong 5-year DevOps engineer should demonstrate deep comfort with the Git internal object database (blobs, trees, commits, tags), know how to inspect and leverage the reflog to undo catastrophic mistakes, understand the security implications of secrets and commit forging, and evaluate branching strategies from a CI/CD automation perspective.
