Google Kubernetes Engine (GKE)
Your security team forbids storing GCP Service Account JSON keys in Kubernetes Secrets. How do you implement GKE Workload Identity for a payment pod accessing Cloud Storage?
⌄

Strong answer

GKE Workload Identity binds a Kubernetes Service Account (KSA) directly to a Google Cloud IAM Service Account (GSA), eliminating permanent keys entirely.

  • Step 1 (Enable on Cluster): Ensure GKE cluster has Workload Identity enabled (--workload-pool=PROJECT_ID.svc.id.goog).
  • Step 2 (Create GSA & Grant Permissions): 
    gcloud iam service-accounts create payment-gsa
gcloud projects add-iam-policy-binding PROJECT_ID \
  --member="serviceAccount:payment-gsa@PROJECT_ID.iam.gserviceaccount.com" \
  --role="roles/storage.objectViewer"
  • Step 3 (Bind KSA to GSA via IAM): 
    gcloud iam service-accounts add-iam-policy-binding payment-gsa@PROJECT_ID.iam.gserviceaccount.com \
  --role="roles/iam.workloadIdentityUser" \
  --member="serviceAccount:PROJECT_ID.svc.id.goog[payments/payment-ksa]"
  • Step 4 (Annotate KSA in Kubernetes): 
    apiVersion: v1
kind: ServiceAccount
metadata:
  name: payment-ksa
  namespace: payments
  annotations:
    iam.gke.io/gcp-service-account: payment-gsa@PROJECT_ID.iam.gserviceaccount.com
  • Pods running with serviceAccountName: payment-ksa automatically receive short-lived OAuth2 tokens from GKE metadata server.
Interviewer Probe: What happens if GKE Node metadata concealment is disabled? Workload Identity relies on the GKE metadata server interception; without it, pods could potentially query the underlying VM's node service account.

Google Kubernetes Engine (GKE)
After migrating to a Private GKE Cluster, pods cannot pull external public Docker images or connect to third-party APIs. How do you fix this while keeping nodes private?
⌄

Strong answer

In a Private GKE Cluster, worker node VMs do not have external public IP addresses. Outbound internet connectivity must be provided via Cloud NAT.

  • Root Cause: Nodes have only private RFC 1918 IPs. Egress traffic to external registries (Docker Hub, Quay) drops because there is no route to an internet gateway without NAT.
  • Remediation:
    • Create a Cloud Router in the cluster's VPC region: 
      gcloud compute routers create gke-nat-router --network=my-vpc --region=us-central1
    • Attach a Cloud NAT gateway: 
      gcloud compute routers nats create gke-nat-gw \
  --router=gke-nat-router \
  --region=us-central1 \
  --auto-allocate-nat-external-ips \
  --nat-all-subnet-ip-ranges
  • Internal Google APIs: For Google services (GCR, Artifact Registry, Cloud Storage), enable Private Google Access on the subnet so traffic reaches Google APIs via internal Google backbone routing without consuming NAT gateway bandwidth.

Google Kubernetes Engine (GKE)
Compare GKE Autopilot vs GKE Standard for a financial enterprise with strict compliance and custom daemonsets. When would you reject Autopilot?
⌄

Strong answer

GKE Autopilot manages node provisioning, security hardening, and OS upgrades automatically, billing strictly per pod CPU/RAM request rather than per VM. However, it imposes strict guardrails:

  • Reject Autopilot when:
    • Privileged Containers & Host Access: Security or monitoring agents (Falco, Sysdig, custom eBPF daemons) requiring privileged: true or hostPath volumes are blocked by Autopilot's admission controller.
    • Custom OS or Kernel tuning: You cannot modify sysctl kernel parameters or install custom host OS packages.
    • Specialized Hardware & Spot GPU clusters: Standard offers finer-grained control over GPU drivers, local NVMe SSD RAID arrays, and TPU configurations.
  • Choose Autopilot when: General microservices and standard web workloads where offloading node security patching, OS hardening, and pod bin-packing saves substantial DevOps engineering overhead.

Google Kubernetes Engine (GKE)
A GKE node pool upgrade is scheduled. How do you guarantee zero downtime for production workloads and prevent PodDisruptionBudget (PDB) deadlocks?
⌄

Strong answer

GKE node upgrades drain and recreate nodes. Zero downtime requires tuning surge upgrade settings and Pod Disruption Budgets.

  • Configure Surge Upgrades: Set max-surge-nodes=20% and max-unavailable-nodes=0 in the node pool settings: 
    gcloud container node-pools update production-pool \
  --cluster=prod-gke \
  --max-surge-upgrade=2 \
  --max-unavailable-upgrade=0
    This ensures GKE provisions new healthy replacement nodes first before draining old nodes.
  • Prevent PDB Deadlocks: If a deployment has replicas: 1 and a PDB with minAvailable: 1, GKE drain commands will hang indefinitely waiting for available pods. Ensure deployments have at least 2 replicas across distinct AZs with anti-affinity, or configure PDB with maxUnavailable: 1.
  • Graceful Termination: Configure preStop hooks and adequate terminationGracePeriodSeconds (e.g. 60s) so inflight HTTP connections finish processing before SIGKILL.

Networking & Hybrid Connectivity
Explain the architecture of a GCP Shared VPC. How do you delegate subnet access to a Service Project (dev team) without giving them network admin rights?
⌄

Strong answer

A Shared VPC centralizes network management in a dedicated Host Project while allowing workloads in multiple Service Projects to attach to shared subnets.

  • Architecture:
    • Host Project: Owned by Network/Infra team. Contains the VPC, subnets, Cloud Routers, Cloud NAT, and firewall rules.
    • Service Projects: Owned by application teams (e.g. payments-proj, analytics-proj). Contains GKE clusters and Compute Engine VMs attached to Host Project subnets.
  • Subnet Delegation via IAM:
    • At the Host Project level, do NOT grant Compute Network Admin.
    • Grant Compute Network User (roles/compute.networkUser) strictly on the specific subnet (e.g. payments-subnet-us-east1) to the Service Project's Compute Engine default service account and Cloud Services SA: 
      gcloud compute networks subnets add-iam-policy-binding payments-subnet \
  --project=host-net-prod --region=us-east1 \
  --member="serviceAccount:123456@cloudservices.gserviceaccount.com" \
  --role="roles/compute.networkUser"

Networking & Hybrid Connectivity
During a high-traffic flash sale, microservices report connection timeouts to external third-party payment gateways. Cloud NAT logs show dropped packets. How do you troubleshoot and fix NAT port exhaustion?
⌄

Strong answer

This is classic Cloud NAT source port exhaustion. Each Cloud NAT IP has ~64,000 ephemeral TCP ports available.

  • Diagnosis: Query Cloud Monitoring for compute.googleapis.com/nat/dropped_sent_packets_count with metric label reason: OUT_OF_RESOURCES.
  • Immediate Fix:
    • Allocate additional static external IP addresses to the Cloud NAT gateway: 
      gcloud compute routers nats update gke-nat-gw \
  --router=my-router --region=us-central1 \
  --nat-external-ip-pool=nat-ip-1,nat-ip-2,nat-ip-3,nat-ip-4
      Each IP adds 64,000 translation tuples.
    • Enable Dynamic Port Allocation (--enable-dynamic-port-allocation), allowing Cloud NAT to scale port allocations dynamically per VM based on actual traffic demand rather than reserving fixed static blocks.
  • Application Layer Fix: Ensure application HTTP clients reuse connections via HTTP Keep-Alive and connection pooling rather than establishing a fresh TCP handshake per API call.

Networking & Hybrid Connectivity
Design an Enterprise Hybrid Connectivity architecture between an on-premise datacenter and GCP with a 99.99% availability SLA. What are the requirements?
⌄

Strong answer

Achieving Google's 99.99% SLA requires dual Cloud Interconnect connections across two separate colocation facilities (metres) and two Cloud Routers in a single region:

  • Topology for 99.99%:
    • Two Dedicated Interconnect connections in Colocation Facility A terminating on Edge Availability Domain 1 & 2.
    • Two Dedicated Interconnect connections in Colocation Facility B terminating on Edge Availability Domain 1 & 2.
    • Four redundant VLAN attachments connected to two Cloud Routers in the target VPC region.
  • Routing & BGP: Run dynamic BGP routing. Configure BGP Multi-Exit Discriminator (MED) and AS-Path prepending so traffic uses the primary link under normal operations and automatically fails over sub-second upon BGP session loss.
  • Cost-effective Alternative (99.9% SLA): Dual Cloud Interconnect + HA VPN over the internet as backup failover path.

Networking & Hybrid Connectivity
VPC A is peered with VPC B. VPC B is peered with VPC C. Why can VMs in VPC A not communicate with VPC C, and what architectures resolve this?
⌄

Strong answer

GCP VPC Network Peering is strictly non-transitive. Peering directly connects only the two participating VPCs; it never routes traffic across intermediary networks.

  • Root Cause: GCP does not forward traffic through a peered network to a third network.
  • Architecture Solutions:
    • Solution 1 (Full Mesh Peering): If scale is small, establish a direct VPC peering connection between VPC A and VPC C.
    • Solution 2 (Network Connectivity Center - NCC): Use GCP's Network Connectivity Center with Cloud Routers to establish a hub-and-spoke transit topology.
    • Solution 3 (Private Service Connect - PSC): If VPC A only needs access to a specific service or database hosted in VPC C, publish an internal load balancer in VPC C as a PSC Service Attachment and consume it via a private endpoint IP in VPC A.

Compute Engine & Serverless
How do you execute an automated rolling update of a 50-node regional Managed Instance Group (MIG) with new application code with zero downtime?
⌄

Strong answer

Use Compute Engine Managed Instance Group Rolling Replacement paired with an updated Instance Template and health checks.

  • Step 1 (Create New Instance Template): Bake a new Golden Image via Packer or specify new startup script/container metadata: 
    gcloud compute instance-templates create app-template-v2 --source-instance-template=app-template-v1 ...
  • Step 2 (Trigger Rolling Action with Safety Gates): 
    gcloud compute instance-groups managed rolling-action start-update prod-mig \
  --region=us-central1 \
  --version=template=app-template-v2 \
  --max-surge=5 \
  --max-unavailable=0 \
  --min-ready=60s \
  --replacement-method=substitute
  • Parameters Explained:
    • --max-unavailable=0: Never terminates an existing VM until a replacement is verified healthy.
    • --max-surge=5: Creates 5 new VMs in advance to maintain capacity.
    • --min-ready=60s: Requires newly provisioned instances to pass application health checks for at least 60 seconds before draining and deleting old instances.

A containerized microservice on Cloud Run needs to query an internal Cloud SQL PostgreSQL database with a private IP. How do you establish connectivity?

Strong answer

Compute Engine & Serverless
A Java Spring Boot service deployed on Cloud Run suffers from 8-second cold starts, causing p99 latency spikes. How do you optimize this without moving to GKE?
⌄

Strong answer

Cold starts in Cloud Run can be mitigated through configuration tuning, concurrency management, and runtime optimization:

  • Step 1 (Set Minimum Instances): Keep a warm pool running 24/7 to absorb baseline traffic: 
    gcloud run services update my-service --min-instances=3
    Billed at a heavily discounted idle rate when instances are idle.
  • Step 2 (Tune Concurrency): Unlike AWS Lambda (1 request per container), Cloud Run containers handle up to 1,000 concurrent requests (default: 80). Set --concurrency=80 so a single warm container handles bursts without triggering new instance cold starts.
  • Step 3 (Startup CPU Boost): Enable CPU allocation during container initialization: 
    gcloud run services update my-service --cpu-boost
    Temporarily allocates extra vCPU cores during JVM boot, cutting cold start time in half.
  • Step 4 (GraalVM Native Image): Compile Java Spring Boot into a standalone native Linux binary via GraalVM, reducing startup time from 8 seconds to <80 milliseconds.

How do you architect a massive batch video encoding pipeline on Compute Engine using Spot VMs with automated preemption handling?
⌄

Strong answer

Spot VMs offer 60–91% discounts over On-Demand VMs, but can be preempted by Google at any time with a 30-second warning.

  • Step 1 (Graceful Preemption Hook): Compute Engine exposes a 30-second ACPI shutdown signal. Run a daemon polling local metadata: 
    curl http://metadata.google.internal/computeMetadata/v1/instance/preempted -H "Metadata-Flavor: Google"
    Upon receiving TRUE, immediately save active video chunk state to a Cloud Storage checkpoint and notify the job queue (Cloud Pub/Sub).
  • Step 2 (MIG Auto-healing & Multi-Zone): Configure the Managed Instance Group to span all zones in a region. Enable instance redistribution so if one zone faces Spot capacity shortages, the MIG automatically provisions Spot VMs in adjacent zones.
  • Step 3 (Idempotent Workflows): Ensure tasks are chunked into small, idempotent jobs (<5 minutes per segment) so lost instances only replay minimal progress.

Compute Engine & Serverless
A poison-pill message in a Cloud Pub/Sub subscription causes downstream Cloud Run subscribers to crash in an infinite crash-loop. How do you isolate it?
⌄

Strong answer

Without redrive protection, unacknowledged messages are retried infinitely by Pub/Sub, overwhelming consumers.

  • Configure Dead-Letter Queue (DLQ):
    • Create a dead-letter topic: gcloud pubsub topics create orders-dlq.
    • Attach a redrive policy to the main subscription with --max-delivery-attempts=5: 
      gcloud pubsub subscriptions update orders-sub \
  --dead-letter-topic=orders-dlq \
  --max-delivery-attempts=5
  • How it works: If a subscriber fails or times out 5 times, Pub/Sub automatically forwards the malformed message to orders-dlq and acknowledges it in the primary queue, restoring normal pipeline processing.
  • Alerting: Set up a Cloud Monitoring alert on pubsub.googleapis.com/subscription/dead_letter_message_count > 0 to notify engineers for manual payload inspection.

Cloud Storage & Databases
Explain how Cloud SQL High Availability (HA) failover works. What happens to the IP address and active connections during an unexpected primary zone failure?
⌄

Strong answer

Cloud SQL HA uses a Regional Multi-Zone configuration consisting of a Primary instance in Zone A and a Standby instance in Zone B with synchronous disk replication.

  • Failover Mechanics:
    • Google's control plane monitors primary heartbeat. If Zone A fails or hardware crashes, failover triggers in ~60–90 seconds.
    • The persistent regional disk attaches to the standby instance in Zone B.
    • IP Address Persistence: The static private/public IP address of the instance remains identical. It is automatically reassigned to the standby instance; applications DO NOT need DNS changes or configuration updates.
  • Application Impact: All active TCP connections are severed. Applications must implement connection retry logic with exponential backoff to reconnect seamlessly once the standby completes database recovery.

Cloud Storage & Databases
An engineer accidentally deleted all objects in a production Cloud Storage bucket. How do Object Versioning and the new GCS Soft Delete protect you?
⌄

Strong answer

Google Cloud Storage provides two complementary recovery mechanisms:

  • Object Versioning: When enabled, deleting an object does not erase data; it places a delete marker as the live version while retaining the old version as a noncurrent generation.
    • To restore: list noncurrent objects and copy them back: 
      gcloud storage cp gs://my-bucket/file#1712345678 gs://my-bucket/file
  • Soft Delete (Default in GCS): Even if versioning is disabled or an object is permanently deleted, GCS retains deleted objects in a soft-deleted state for a retention duration (default: 7 days) before permanent erasure.
    • To restore soft-deleted files: 
      gcloud storage restore gs://my-bucket/** --restore-all-soft-deleted
  • Bucket Lock (Retention Policy): In compliance environments, configure Object Retention Lock with WORM (Write Once, Read Many) compliance to mathematically forbid deletions until retention expires.

Cloud Storage & Databases
The monthly BigQuery bill unexpectedly jumps from $2,000 to $18,000 due to unoptimized queries scanning terabytes of data. How do you enforce cost guardrails?
⌄

Strong answer

BigQuery on-demand pricing charges \$6.25 per TB scanned. Unpartitioned tables and `SELECT *` quickly burn budgets.

  • Step 1 (Table Partitioning & Clustering): Mandate partitioning by date/timestamp and clustering by frequently filtered keys (e.g. `customer_id`). Queries with `WHERE created_at >= '2026-01-01'` scan only relevant partitions, reducing scanned bytes by 95%+.

  • Step 3 (BigQuery Reservations / Capacity Pricing): Switch from On-Demand to Editions (Standard / Enterprise) with a fixed baseline of Slots (e.g. 100 slots) with Autoscaling slot limits, capping maximum financial liability regardless of query volume.

Cloud Storage & Databases
When should an enterprise migrate from Cloud SQL or Firestore to Cloud Spanner? What trade-offs must be evaluated?
⌄

Strong answer

Cloud Spanner is Google's globally distributed, horizontally scalable relational database that provides ANSI SQL and ACID transactions with 99.999% availability via TrueTime atomic clocks.

  • Migrate to Spanner when:
    • Data scale exceeds single-instance limits of Cloud SQL (>64TB or >100,000 writes/sec).
    • True Multi-Region Active-Active read/write consistency without asynchronous replication lag is required.
    • Zero maintenance downtime requirements (Spanner scales nodes and schema updates online with zero locks).
  • Trade-offs:
    • Cost: Base entry cost is significantly higher (~$0.90/node-hr or modern Spanner processing units).
    • Schema Design: Anti-patterns like monotonically increasing auto-incrementing primary keys create severe write hotspots; keys must be UUIDv4 or bit-reversed hashes.

IAM, Governance & Security
What is VPC Service Controls (VPC SC), and how does it prevent a rogue developer with valid IAM credentials from exfiltrating data to their personal Cloud Storage bucket?
⌄

Strong answer

Standard IAM controls who has access, but cannot control from where or to where data moves. VPC Service Controls defines a security perimeter around Google Cloud resources.

  • How it works:
    • Sensitive projects (containing Cloud Storage, BigQuery) are placed inside a Service Perimeter.
    • API requests to Google services are only permitted from within authorized VPC networks inside the perimeter or through explicit Ingress/Egress perimeter bridge rules.
  • Preventing Exfiltration: Even if a rogue employee generates a valid IAM token with Storage Admin, if they attempt to copy data from the corporate bucket inside the perimeter to a personal bucket outside the perimeter (gsutil cp gs://corp-bucket/* gs://personal-bucket/), Google's API gateway blocks the transfer with a VPC Service Controls perimeter violation.

IAM, Governance & Security
How does Cloud KMS Customer-Managed Encryption Keys (CMEK) work with Envelope Encryption in Cloud Storage and Compute Engine?
⌄

Strong answer

By default, Google encrypts all data at rest using Google-managed keys. CMEK gives the customer full custody over key rotation, revocation, and cryptographic destruction.

  • Envelope Encryption Architecture:
    • DEK (Data Encryption Key): A fast symmetric key generated locally by the storage service to encrypt the raw data blocks.
    • KEK (Key Encryption Key): A master key managed inside Cloud KMS (or Cloud HSM) used exclusively to encrypt and protect the DEK.
  • Operation: When writing data, Cloud Storage requests Cloud KMS to encrypt the DEK. The encrypted DEK is stored alongside the ciphertext. When reading, Cloud Storage sends the wrapped DEK to Cloud KMS for decryption.
  • Kill-Switch Capability: If a regulatory or security breach occurs, disabling or destroying the master KEK in Cloud KMS instantly renders all encrypted disks and buckets permanently unreadable without needing to zero-fill petabytes of disk storage.

A high-throughput GKE cluster ingests 50TB of debug logs per month into Cloud Logging, resulting in a $25,000 monthly bill. How do you slash this cost immediately?

Strong answer

Observability & Cost Optimization
Explain the difference between Resource-Based Committed Use Discounts (CUDs) and Flexible/Spend-Based CUDs in GCP. How do you calculate optimal commitment?
⌄

Strong answer

CUDs provide up to 57–70% discounts in exchange for a 1-year or 3-year commitment:

  • Resource-Based CUDs:
    • You commit to a specific quantity of vCPUs and RAM within a single machine family (e.g. N2 or C2) in a specific region.
    • Discount: Highest (up to 55–70%).
    • Risk: Inflexible. If you switch architecture from N2 to ARM (Tau T2A) or change regions, the commitment does not apply.
  • Flexible / Spend-Based CUDs:
    • You commit to spending a minimum dollar amount per hour on compute across any region, machine family, Cloud Run, or GKE Autopilot.
    • Discount: Slightly lower (~28–46%), but highly resilient to architectural changes.
  • Best Practice: Commit to 60–70% of historical minimum baseline compute using Resource-Based CUDs, and cover floating/elastic workloads with Flexible CUDs or Spot VMs.

How do you implement an SRE Error Budget Burn Rate alert in Cloud Monitoring for an API with a 99.9% availability SLO over a 30-day rolling window?
⌄

Strong answer

Modern SRE practices alert on burn rates rather than instantaneous error thresholds to detect outages without alert fatigue.

  • SLI (Service Level Indicator): Ratio of good requests (HTTP status < 500) over total valid requests.
  • Error Budget: 100% - 99.9% = 0.1% tolerated failure over 30 days.
  • Multi-Window Multi-Burn-Rate Alert:
    • High Burn Rate (14.4x burn): Consumes 2% of budget in 1 hour → Immediate PagerDuty page to on-call engineer.
    • Slow Burn Rate (6x burn): Consumes 5% of budget in 6 hours → Ticket/email notification during business hours.
  • Configure the policy using Cloud Monitoring Service Monitoring or MQL (Monitoring Query Language) measuring the loadbalancing.googleapis.com/https/request_count metric.

Can a GCP Billing Budget automatically shut down your resources if spending exceeds $10,000, and how do you implement automated cost-capping safely?
⌄

Strong answer

By default, GCP Billing Budgets DO NOT automatically stop resources; they only send notification emails. Automatic shutdown requires programmatic action.

  • Implementation:
    • Configure Billing Budget to publish threshold alerts (50%, 90%, 100%) to a Cloud Pub/Sub topic.
    • Subscribe a Cloud Function / Cloud Run service to the topic.
    • When cost > \$10,000, the Cloud Function disables billing on the project via Cloud Billing API: 
      gcloud billing projects unlink PROJECT_ID
  • Production Warning & Safer Alternative: Disabling billing immediately shuts down all VMs, databases, and GKE clusters, potentially destroying state and causing data loss!
    • Safer Automation: Instead of unlinking billing, have the Cloud Function scale non-production GKE node pools or MIGs to 0 replicas, or disable external IP addresses.
