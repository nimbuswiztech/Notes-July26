DevOps Hands-On Study Guide

Mastering Docker Volumes & Storage

By default, Docker containers are completely ephemeral—meaning any files created inside them disappear forever when the container is removed. In this masterclass, you will learn how to connect containers to persistent storage, run production databases safely, hot-reload code in development, and perform automated backups.

🖼️ Architectural Blueprint

The 3 Docker Storage Strategies

Study how each mount type connects your container to the host computer.

Figure 1: Architectural relationship between Container Writable Layer, Docker-Managed Named Volumes, Host Bind Mounts, and Tmpfs RAM.
Mount Type Where Data Lives on Host When You Should Use It Survival on `docker rm`
Named Volume Docker-managed folder: /var/lib/docker/volumes/ Production databases (Postgres, Mongo), stateful microservices ✅ 100% Preserved until explicitly deleted
Bind Mount Any host path: e.g. /Users/you/project/src Local development hot-reloading & host configuration files ✅ Preserved on your laptop's filesystem
Tmpfs Mount Host RAM memory (never touches physical hard drive) Sensitive encryption keys, session credentials, temporary caches ❌ Destroyed immediately upon container stop
🛠️ Interactive Tool

Volume Command Generator

Configure your storage requirements below to generate both the shorthand -v and modern --mount command flags.

GENERATED COMMANDS:
Shorthand Syntax (-v): 
$ docker run -d -v my_database_data:/var/lib/postgresql/data postgres
Modern Explicit Syntax (--mount): 
$ docker run -d --mount type=volume,source=my_database_data,target=/var/lib/postgresql/data postgres
🧪 Guided Exercise 1

Zero Data Loss with PostgreSQL & Named Volumes

Follow these steps to experience how Docker volumes preserve data across container lifecycles.

🎯 Lab Objective:
Write data to a database container, force-delete the container, start a completely new container with the same volume, and prove that no data was lost.

Step 1: Create a Dedicated Named Volume

docker volume create student_records_data

Step 2: Start Container 1 mounting this Volume

docker run -d \
  --name database-server-v1 \
  -v student_records_data:/var/lib/postgresql/data \
  -e POSTGRES_PASSWORD=mysecretpassword \
  postgres:16-alpine

Step 3: Create a Table and Insert Records

docker exec -i database-server-v1 psql -U postgres -c "
  CREATE TABLE lab_results (id SERIAL, name VARCHAR(50), score INT);
  INSERT INTO lab_results (name, score) VALUES ('Alex', 98), ('Sarah', 100);
  SELECT * FROM lab_results;
"

Step 4: The Chaos Test - Destroy Container 1!

# Force remove the container immediately!
docker rm -f database-server-v1

Step 5: Start Container 2 and Verify Zero Data Loss

# Launch a brand-new container (v2) pointing to the same volume
docker run -d \
  --name database-server-v2 \
  -v student_records_data:/var/lib/postgresql/data \
  -e POSTGRES_PASSWORD=mysecretpassword \
  postgres:16-alpine

# Query the new container!
docker exec -i database-server-v2 psql -U postgres -c "SELECT * FROM lab_results;"

🎉 Congratulations! Notice how Alex and Sarah's records are completely intact.

🧪 Guided Exercise 2

Developer Hot-Reloading with Bind Mounts

How full-stack developers edit code on their host machine without rebuilding images.

💡 The "node_modules Shield" Pattern:
When mounting your local project directory into a Linux container, your laptop's local dependencies might conflict with the container's OS. Adding an anonymous volume at -v /app/node_modules protects the container's internal libraries from being overwritten! 
# Mount host directory for live code editing
docker run -d \
  --name local-dev-api \
  -p 3000:3000 \
  -v "$(pwd)":/usr/src/app \
  -v /usr/src/app/node_modules \
  node:20-alpine \
  npm run dev
🧪 Guided Exercise 3

Backup & Restore Using Ephemeral Helper Containers

The industry-standard Swiss-Army container pattern for extracting volume data into `.tar.gz`.

Figure 2: The standard ephemeral helper container pattern for backing up and restoring named Docker volumes.

The 1-Line Backup Command

# Spin up a temporary Alpine container that reads the volume and writes a tarball to your laptop
docker run --rm \
  -v student_records_data:/data \
  -v "$(pwd)":/backup \
  alpine \
  tar czf /backup/database_backup.tar.gz -C /data .

The 1-Line Restore Command

# 1. Create a fresh target volume
docker volume create student_records_restored

# 2. Extract the archive into the new volume
docker run --rm \
  -v student_records_restored:/data \
  -v "$(pwd)":/backup \
  alpine \
  tar xzf /backup/database_backup.tar.gz -C /data
📄 Dockerfile Deep Dive

The `VOLUME` Instruction in Dockerfiles

How to declare persistence boundaries in your image recipes. 

FROM alpine:3.19

# Step 1: Create directories and set permissions BEFORE VOLUME
RUN mkdir -p /var/log/my-app && chown -R 1001:1001 /var/log/my-app

# Step 2: Declare the volume mountpoint
VOLUME ["/var/log/my-app"]

# ⚠️ CRITICAL RULE: Never place RUN instructions after VOLUME that write to that path!
# RUN touch /var/log/my-app/seed.log  <-- THIS WILL BE DISCARDED DURING BUILD!

USER 1001
CMD ["tail", "-f", "/dev/null"]
⚠️ What happens if you run an image with `VOLUME` without `-v`?
Docker will automatically create an Anonymous Volume (a 64-character hash name). If you start and stop 20 containers without `-v`, you will leave 20 anonymous volumes cluttering your hard drive! Run docker volume prune regularly.
🩺 Debugging Clinic

Common Student Storage Bugs

How to resolve the most frequent volume issues in development.

Bug 1: "Permission Denied" on Mounted Folders

Occurs when a container running as a non-root user (e.g. UID 1000) tries to write to a host folder owned by root. 

# Fix: Tell Docker to match your current host laptop user's UID and GID
docker run -d --user "$(id -u):$(id -g)" -v "$(pwd)":/app my-image

Bug 2: "volume is in use" when deleting

Docker will not let you delete a volume if even a stopped container is still attached to it. 

# Fix: Find and remove the stopped container first, then remove the volume
docker ps -a --filter volume=my_vol
docker rm <container_id>
docker volume rm my_vol
