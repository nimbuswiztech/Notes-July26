The 3 Golden Rules of Docker Layers

1. Which Instructions Actually Create Layers?

Only RUN, COPY, and ADD create physical, byte-storing filesystem layers. Instructions like ENV, EXPOSE, WORKDIR, USER, and CMD only modify image metadata JSON (0 MB added).

2. The "Cache Busting" Domino Effect

Docker checks layer hashes from top to bottom. If any line changes (or files copied in that line are modified), Docker invalidates the cache for that layer AND every single layer that follows it!

3. The Copy-on-Write (CoW) Runtime Magic

When 100 containers run from the same 500 MB image, they all share the exact same read-only layers in RAM/Disk. Only modifications made while the container is running are written to its private thin top writable layer.

FROM Image Foundation Creates Layer
Order: First non-ARG instruction
FROM [--platform=<platform>] <image>[:<tag>] [AS <name>] Syntax

In Plain English for Students: Think of FROM as choosing the foundation of a house. Are you building on Ubuntu, Debian, Alpine Linux, or a pre-configured Python/Node runtime? Everything you build sits on top of this base image. You can also start from pure scratch using FROM scratch for compiled Go/Rust binaries. 

# Production Best Practice: Explicit pinned version & lightweight Alpine distribution
FROM python:3.11-slim-bookworm AS base

# Multi-stage build: Building in one stage, deploying in scratch
FROM golang:1.22-alpine AS builder
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 go build -o /bin/app

FROM scratch
COPY --from=builder /bin/app /bin/app
ENTRYPOINT ["/bin/app"]
⚠️ Common Student Trap
Never write FROM node or FROM python:latest. Using latest means your build is non-deterministic. If Python 3.12 drops tomorrow, your CI/CD pipeline might fail without any code changes!
✅ Teacher's Best Practice
Use minimal distribution tags like -slim or -alpine to keep images under 100 MB, eliminating thousands of unneeded packages and CVE security vulnerabilities.
RUN Build Execution Creates Layer
Forms: Shell Form & Exec Form
RUN <command> (shell form)  |  RUN ["executable", "param1", "param2"] (exec form) Syntax

In Plain English for Students: RUN executes commands during the build process to install software, create users, compile code, or configure directories. The resulting filesystem changes are committed into a new read-only image layer. 

# BAD PRACTICE: Creates 3 separate heavy layers and leaves 40MB of apt-cache on disk
# RUN apt-get update
# RUN apt-get install -y curl git
# RUN rm -rf /var/lib/apt/lists/*

# GOOD PRACTICE: Chain commands with && and clean up in the SAME layer
RUN apt-get update && apt-get install -y --no-install-recommends \
    curl \
    ca-certificates \
    git \
 && rm -rf /var/lib/apt/lists/*
⚠️ The Cache Poisoning Trap
If you write RUN apt-get update on its own line, Docker caches it. When you later add a package to RUN apt-get install nginx, Docker reuses the outdated cached update, leading to 404 package errors!
✅ Teacher's Best Practice
Always pair apt-get update && apt-get install -y ... together on one line, and always delete temporary package lists with rm -rf /var/lib/apt/lists/*.
CMD Default Execution Metadata Only
Override: Easily replaced by docker run
CMD ["executable","param1","param2"] (Exec)  |  CMD ["param1","param2"] (with ENTRYPOINT) Syntax

In Plain English for Students: CMD sets the default program or default arguments to execute when a container starts up. If the user passes any arguments to docker run my-image [args...], the entire CMD is overridden and discarded! 

# Preferred: Exec Form (JSON array)
CMD ["python", "app.py", "--host", "0.0.0.0"]

# If paired with an ENTRYPOINT, CMD only provides default arguments:
ENTRYPOINT ["nginx"]
CMD ["-g", "daemon off;"]

# If the student runs:
# $ docker run my-nginx -g "daemon on;"
# CMD is completely replaced by the user's argument!
⚠️ Shell Form vs Exec Form Bug
If you write CMD python app.py (shell form), Docker secretly runs /bin/sh -c "python app.py". The shell becomes PID 1, and Linux signals like SIGTERM (used by docker stop) will not reach your Python app, causing graceful shutdowns to hang!
✅ Teacher's Best Practice
Always use the Exec form (JSON array with double quotes): CMD ["python", "app.py"].
ENTRYPOINT Fixed Executable Metadata Only
Override: Requires --entrypoint flag
ENTRYPOINT ["executable", "param1", "param2"] Syntax

In Plain English for Students: ENTRYPOINT turns your container into an executable command-line tool. It configures the command that will always run. Any arguments passed to docker run (or defined in CMD) will be appended directly to the ENTRYPOINT! 

# Creating a container that behaves like a CLI tool (e.g. curl)
FROM alpine:3.19
RUN apk add --no-cache curl
ENTRYPOINT ["curl", "-s"]
CMD ["https://api.github.com"]

# Running without args: runs 'curl -s https://api.github.com'
# $ docker run my-curl

# Running with custom args: replaces CMD but keeps ENTRYPOINT!
# $ docker run my-curl https://httpbin.org/ip
# Runs: curl -s https://httpbin.org/ip
⚠️ Accidentally Locking Out Shells
If you set ENTRYPOINT ["node", "app.js"], a student trying to debug with docker run -it my-img /bin/sh will find that Docker tries to run node app.js /bin/sh! They must use docker run --entrypoint /bin/sh -it my-img.
✅ Teacher's Best Practice
Use an entrypoint.sh script that performs migrations, checks database connectivity, and ends with exec "$@" to smoothly hand over PID 1 to the passed command.
WORKDIR Execution Context Metadata Only
Replacement for 'cd'
WORKDIR /path/to/workdir Syntax

In Plain English for Students: WORKDIR sets the working directory for all subsequent RUN, CMD, ENTRYPOINT, COPY, and ADD instructions. If the directory does not exist, Docker will automatically create it for you! 

# BAD PRACTICE: 'cd' does NOT persist across RUN instructions!
# RUN mkdir /app
# RUN cd /app
# RUN touch file.txt  <-- Created in root /, NOT in /app!

# GOOD PRACTICE: WORKDIR creates the folder and persists for all lines
WORKDIR /usr/src/app
COPY package.json .
RUN npm install
COPY . .
⚠️ The "cd doesn't work" Myth
Students often write RUN cd /opt/myapp and wonder why the next command runs in /. Each RUN statement starts in a fresh subshell! Always use WORKDIR instead of RUN cd.
✅ Absolute vs Relative Paths
Always use absolute paths: WORKDIR /app. If you write relative paths: WORKDIR a then WORKDIR b, your path becomes /a/b, which can lead to confusion.
COPY File Transfer Creates Layer
Recommended over ADD for files
COPY [--chown=<user>:<group>] [--from=<stage>] <src>... <dest> Syntax

In Plain English for Students: COPY takes files or directories from your host build context machine and duplicates them into the container filesystem. It is transparent, predictable, and standard. 

# 1. Copy dependencies first for caching
COPY requirements.txt ./

# 2. Copy with permissions applied directly (avoids an extra RUN chown layer!)
COPY --chown=appuser:appgroup config/ /etc/myapp/

# 3. Multi-stage copying: grabbing the compiled artifact from the 'builder' stage
COPY --from=builder /go/bin/api-server /usr/local/bin/api-server
⚠️ The Duplicate Chown Bloat
Writing COPY app /app followed by RUN chown -R myuser:myuser /app doubles your image size because Docker copies every file into a brand new layer! Always use COPY --chown=myuser:myuser instead.
✅ Teacher's Best Practice
Always combine COPY with a solid .dockerignore file so you don't accidentally copy .git, node_modules, or .env files containing secret keys into the image.
ADD Advanced Transfer Creates Layer
Features: Tar extraction & Remote URLs
ADD [--chown=<user>:<group>] <src>... <dest> Syntax

In Plain English for Students: ADD is like COPY's older brother with two magic tricks: (1) It can download files from a remote URL, and (2) It automatically unpacks local tar archives (like .tar.gz) directly into the destination folder. 

# THE PRIMARY VALID USE CASE FOR ADD:
# Automatically uncompresses rootfs.tar.gz into the container root
ADD rootfs.tar.xz /

# Unpacking application bundle
ADD dist-bundle.tar.gz /var/www/html/

# WARNING: Remote URL downloading is discouraged!
# ADD https://example.com/bigfile.zip /tmp/  <-- Cannot clean up zip in same layer!
# Prefer: RUN curl -fsSL https://... | tar -xz -C /destination
⚠️ The URL Trap
Using ADD <url> downloads the file into an image layer. You cannot delete the downloaded archive in a subsequent step to save disk space. Use RUN curl ... && tar ... && rm ... instead.
✅ The Golden Docker Rule
The official Docker documentation states: If you are not unpacking a local tar file, always use COPY instead of ADD for clarity and security.
ENV Persistent Environment Metadata Only
Persists into running containers
ENV <key>=<value> <key2>=<value2> Syntax

In Plain English for Students: ENV defines environment variables that are available during the build AND persistently inside the running container. Applications access them using standard OS environment lookups (e.g. process.env.PORT in Node or os.environ.get() in Python). 

# Defining multiple environment variables in one instruction
ENV NODE_ENV=production \
    PORT=8080 \
    APP_HOME=/usr/src/app \
    PATH="/usr/src/app/bin:${PATH}"

WORKDIR $APP_HOME
EXPOSE $PORT

# Can be overridden dynamically at runtime:
# $ docker run -e PORT=4000 -e DEBUG=true my-app
⚠️ Hardcoding Secrets Security Flaw
NEVER put database passwords, AWS credentials, or API keys in ENV! Anyone who runs docker inspect <image> can see all ENV values in plain text JSON! Pass secrets via environment files or Docker secrets at runtime.
✅ Variable Expansion Feature
ENV supports bash-style expansion: ${VAR:-default} sets a fallback if not provided, and ${VAR:+alternate} sets a value if VAR is set.
ARG Build-Time Argument Metadata Only
Build-only: Not present in container
ARG <name>[=<default_value>] Syntax

In Plain English for Students: ARG defines variables that users can pass to Docker at build-time only using docker build --build-arg <varname>=<value>. Once the image is finished building, ARG variables disappear completely and cannot be read inside the running container! 

# 1. ARG before FROM can define the base image version
ARG NODE_VERSION=20
FROM node:${NODE_VERSION}-alpine

# 2. Must redeclare inside the build stage if needed after FROM!
ARG APP_VERSION=1.0.0
LABEL version=${APP_VERSION}

# 3. Passing from build arg into persistent ENV if needed at runtime:
ARG BUILD_ENV=production
ENV RUNTIME_ENV=${BUILD_ENV}

# CLI Build Command:
# $ docker build --build-arg NODE_VERSION=18 --build-arg APP_VERSION=2.1.0 -t my-app .
⚠️ The ARG Before/After FROM Trap
An ARG declared before FROM is outside the build stage. If you need it in a RUN or ENV instruction after FROM, you must redeclare ARG <name> with no value inside the stage!
✅ Predefined Build Arguments
Docker provides built-in ARGs automatically without declaring them: HTTP_PROXY, HTTPS_PROXY, TARGETPLATFORM, and TARGETARCH.
EXPOSE Network Intent Metadata Only
Documentation & Port Contract
EXPOSE <port> [/<tcp|udp>] [...] Syntax

In Plain English for Students: EXPOSE is an architectural contract and documentation statement. It informs Docker and human operators that the container listens on specified network ports. Crucial Lesson: EXPOSE does not actually publish the port to your host computer! You must still pass -p 8080:8080 when running the container. 

# Expose TCP web traffic
EXPOSE 80 443

# Expose UDP traffic (e.g. DNS or gaming server)
EXPOSE 53/udp 53/tcp

# Running with -P (Publish All): Automatically maps exposed ports to random high host ports
# $ docker run -d -P my-web-app

# Running with -p (Explicit Binding): Still strictly required!
# $ docker run -d -p 8080:80 my-web-app
⚠️ The #1 Student Confusion
Students write EXPOSE 3000 and wonder why http://localhost:3000 doesn't work in their browser. Tell them: "EXPOSE is like putting a door on a house; -p unlocks the gate from the street."
✅ Container Orchestrator Usage
Kubernetes and Amazon ECS read the EXPOSE metadata to auto-configure Service discovery and target port forwarding!
VOLUME Storage Mount Metadata Only
Data Persistence Boundary
VOLUME ["/var/log/", "/var/db/"]  |  VOLUME /data Syntax

In Plain English for Students: Containers are ephemeral (they can be deleted at any moment). VOLUME creates a designated mount point for holding persistent or shared database/log data. Any data written to a declared volume bypasses the Union File System and is stored directly on the host machine. 

# Declaring persistent directories for PostgreSQL or MongoDB
VOLUME ["/var/lib/postgresql/data", "/var/log/postgresql"]

# When run without flags, Docker generates an anonymous volume on the host:
# $ docker run -d postgres

# Production mapping with named volumes:
# $ docker run -d -v pgdata:/var/lib/postgresql/data postgres
⚠️ The Build Step Invalidation
Once a volume is declared in a Dockerfile (e.g. VOLUME /data), any subsequent RUN statement that modifies files inside /data will be discarded during the build! Always populate data before calling VOLUME.
✅ When to Declare in Dockerfile
Only declare VOLUME for directories that strictly require persistence (like databases or uploads). Avoid doing it for general codebases.
USER Security Best Practice Metadata Only
Root Mitigation Defense
USER <user>[:<group>]  |  USER <UID>[:<GID>] Syntax

In Plain English for Students: By default, Docker containers run as root (UID 0). If a hacker breaches your web application running as root inside a container, they might be able to escape to the host kernel! USER drops permissions to a non-privileged user. 

# 1. Create a dedicated non-root group and user with explicit UID
RUN addgroup -g 10001 appgroup && \
    adduser -u 10001 -G appgroup -s /bin/sh -D appuser

# 2. Assign folder permissions while still root
WORKDIR /app
COPY --chown=appuser:appgroup . .

# 3. Switch to the non-root user!
USER appuser

# Now RUN, CMD, and ENTRYPOINT execute safely as appuser
CMD ["./start.sh"]
⚠️ The Port 80 Privilege Trap
Linux restricts ports below 1024 to root only! If a student switches to USER appuser and tries to bind to port 80, the application will crash with EACCES: permission denied. Use port 3000, 8080, or 8443 instead.
✅ Use Numeric UID/GID
Always prefer numeric UIDs (e.g. USER 10001:10001) for compatibility with Kubernetes runAsNonRoot and PodSecurityPolicies.
HEALTHCHECK Self-Healing Metadata Only
Used by Docker Swarm & Compose
HEALTHCHECK [OPTIONS] CMD <command>  |  HEALTHCHECK NONE Syntax

In Plain English for Students: Just because a container is running doesn't mean your app is healthy (it might be stuck in an infinite loop or locked out of its database). HEALTHCHECK periodically runs a test command inside the container. If it returns exit code 0, it is healthy; if 1, Docker marks it unhealthy. 

# Production Web Application Healthcheck
HEALTHCHECK --interval=30s \
            --timeout=5s \
            --start-period=15s \
            --retries=3 \
  CMD curl -f http://localhost:8080/health || exit 1

# Options Explained:
# --interval=30s     : Run test every 30 seconds
# --timeout=5s      : Fail if probe takes longer than 5 seconds
# --start-period=15s: Grace period during bootup (failures don't count)
# --retries=3       : Must fail 3 consecutive times to mark unhealthy
⚠️ Forgetting Start Period
Heavy apps (Java Spring Boot, Rails) take 20+ seconds to boot. If you don't provide --start-period, Docker might kill or restart your container before it has even finished starting up!
✅ Disabling Inherited Healthchecks
If an upstream base image includes a healthcheck that fails in your environment, you can silence it using: HEALTHCHECK NONE.
LABEL Image Metadata Metadata Only
Replaces deprecated MAINTAINER
LABEL <key>=<value> <key2>=<value2> Syntax

In Plain English for Students: LABEL adds key-value metadata tags to your image. This is essential in corporate teams for tracking maintainers, source code Git commit hashes, licenses, documentation URLs, and CI build IDs. 

# Following Open Container Initiative (OCI) image specification
LABEL org.opencontainers.image.title="Customer Payment API" \
      org.opencontainers.image.description="Processes Stripe & PayPal webhooks" \
      org.opencontainers.image.version="2.4.1" \
      org.opencontainers.image.authors="devops@university.edu" \
      org.opencontainers.image.source="https://github.com/my-org/payments" \
      org.opencontainers.image.licenses="MIT"

# Note on MAINTAINER:
# MAINTAINER john@doe.com is DEPRECATED. Always use LABEL instead!
⚠️ The MAINTAINER Mistake
Many old Docker tutorials still teach MAINTAINER. Docker deprecated it years ago. Use LABEL maintainer="name <email>".
✅ Inspecting Labels
Students can view labels anytime without starting the container: docker inspect --format='{{json .Config.Labels}}' my-image.
SHELL Shell Configuration Metadata Only
Overriding default /bin/sh
SHELL ["executable", "parameters"] Syntax

In Plain English for Students: On Linux, Docker defaults to executing shell-form commands with ["/bin/sh", "-c"], and on Windows with ["cmd", "/S", "/C"]. SHELL lets you override this to use Bash (with strict error safety flags) or PowerShell. 

# Enable strict Bash execution with pipefail (so piped errors cause build failure!)
SHELL ["/bin/bash", "-o", "pipefail", "-c"]

# Now this build fails properly if curl errors, even when piped to grep!
RUN curl -fsSL https://example.com/bad-url | grep "OK"

# Windows Containers Example: Switching from cmd.exe to PowerShell
SHELL ["powershell", "-Command", "$ErrorActionPreference = 'Stop';"]
⚠️ The Silent Pipe Fail Trap
In default /bin/sh, if you run curl https://fail | tar -xz, the curl might return a 404 HTML error, but tar exits with code 0. Your build falsely passes with broken code! Using Bash with -o pipefail prevents this.
✅ Reverting Shells
You can change the shell multiple times in a single Dockerfile, e.g., using PowerShell for Windows setup, then switching back to CMD for runtime.
STOPSIGNAL Termination Signal Metadata Only
Default: SIGTERM
STOPSIGNAL <signal_name_or_number> Syntax

In Plain English for Students: When you tell Docker to stop a container via docker stop, it sends a Linux signal giving the process 10 seconds to finish in-flight requests and close DB connections before forcibly killing it with SIGKILL. While SIGTERM is standard, some web servers (like NGINX) require SIGQUIT to stop gracefully. 

# Official NGINX Dockerfile uses SIGQUIT for immediate graceful connection drain:
STOPSIGNAL SIGQUIT

# Systemd init-based containers require RTMIN+3 to shutdown cleanly:
STOPSIGNAL SIGRTMIN+3
⚠️ The 10-Second Wait of Shame
Ever run docker stop and had to wait an annoying 10 seconds before it finished? That's because the container ignored SIGTERM and Docker had to forcefully send SIGKILL!
✅ Matching App Handlers
Make sure your Node, Python, or Go code listens for the exact signal configured in STOPSIGNAL (e.g. process.on('SIGTERM', ...)).
ONBUILD Deferred Trigger Metadata Trigger
Triggered by DOWNSTREAM images
ONBUILD <INSTRUCTION> Syntax

In Plain English for Students: ONBUILD registers a "trigger" instruction that does nothing during the current image build. Instead, it gets baked into the image metadata. When another student uses your image as their FROM my-base-image, the ONBUILD triggers execute automatically! 

# --- In the Organization's Base Dockerfile (company-python-base) ---
FROM python:3.11-slim
WORKDIR /app

# When a developer builds FROM company-python-base, these lines run automatically:
ONBUILD COPY requirements.txt .
ONBUILD RUN pip install --no-cache-dir -r requirements.txt
ONBUILD COPY . .

# --- In the Developer's Downstream Project Dockerfile ---
FROM company-python-base
CMD ["python", "main.py"]
# ^ The developer doesn't need to write COPY or pip install! ONBUILD handles it!
⚠️ The "Magic Hidden Action" Warning
Many DevOps teams avoid ONBUILD because it creates hidden actions that make downstream builds confusing to debug when files are missing.
✅ Instructions Not Allowed
You cannot chain ONBUILD ONBUILD, and you cannot trigger ONBUILD FROM or ONBUILD MAINTAINER.
⚔️ Conceptual Battlegrounds

The 3 Great Confusions Solved

These are the three topics where students lose points on certification exams and make critical production errors. Let's make them crystal clear.

Showdown 1: ENTRYPOINT vs CMD (The Command Combinator)

The Golden Mental Model: ENTRYPOINT defines what program executes. CMD defines the default parameters passed to it.

🧪 Interactive Command-Line Simulator: Test What Actually Runs!
DOCKER ENGINE KERNEL SIMULATION PID 1 EXECUTABLE
$ docker run my-image
Result: python app.py --port 8080
Because no CLI arguments were passed, Docker used ENTRYPOINT as the base executable and appended CMD as the default flags.

Showdown 2: COPY vs ADD (Which Should You Teach?)

Almost every newcomer asks why both instructions exist. Here is the exact side-by-side comparison for students:

Capability COPY ADD
Copying local files & folders ✅ Yes (Clean, explicit, recommended) ✅ Yes
Multi-Stage Copying (--from=stage) ✅ Yes (COPY --from=builder ...) ❌ No (COPY is mandatory here)
Auto-Extract Local Archives (.tar, .tar.gz, etc.) ❌ No (Copies archive as raw .tar file) ✅ Yes (Automatically unpacks files into folder)
Remote URLs (https://example.com/file) ❌ No ⚠️ Yes (discouraged; leaves uncleaned cache)
Security & Predictability 🛡️ Highest (Zero side effects) ⚠️ Moderate (Risk of tarbombs or URL spoofing)
👨‍🏫 Teacher's One-Sentence Exam Rule:
"Use COPY for 99% of your files. The only time you should ever reach for ADD is when you need to auto-extract a local .tar.gz archive into the image."

Showdown 3: ARG vs ENV (Lifecycle & Variable Scope)

The distinction between ARG and ENV is entirely about Time and Scope.

Lifecycle Phase ARG (Build-Time Only) ENV (Build + Runtime)
During docker build ✅ Available in RUN commands ✅ Available in RUN commands
During docker run (In Container) ❌ NOT AVAILABLE (Purged) ✅ ACTIVE (Accessible to app)
How to pass from CLI docker build --build-arg VAR=val docker run -e VAR=val
Visible in docker inspect ❌ No (Unless stored in build history) ⚠️ Yes (Always visible in image metadata)
Ideal Use Case Software versions, git commit SHAs, build flags Database hostnames, ports, environment mode

Optimization: Bad vs Good Dockerfile

Show your students the dramatic difference between a poorly constructed Dockerfile (slow, 1.4 GB image) and a production-grade multi-stage Dockerfile (blazing fast, 42 MB image).

❌ The Amateur Dockerfile (1.4 GB)

Slow & Insecure 
# Flaw 1: Heavy bloated base image
FROM node:latest

# Flaw 2: Copying ALL code before installing deps!
# (Busts cache every time you edit a line of JS!)
COPY . /app
WORKDIR /app

# Flaw 3: Installs devDependencies in production
RUN npm install

# Flaw 4: Multiple separate RUN statements leaving junk
RUN apt-get update
RUN apt-get install -y curl

# Flaw 5: Running as default ROOT user
# Flaw 6: Shell form kills signal propagation
CMD npm start
  • 💔 Every code change requires re-downloading all NPM packages.
  • 💔 Image contains build compilers and test libraries.
  • 💔 Container runs with root capabilities on the host.

✅ The Pro Multi-Stage Dockerfile (42 MB)

Fast & Secure 
# Stage 1: Build & Dependencies
FROM node:20.11-alpine AS builder
WORKDIR /build
# Win: Copy package files first to cache layer!
COPY package*.json ./
RUN npm ci --only=production

# Stage 2: Clean, Tiny Production Container
FROM node:20.11-alpine
WORKDIR /app
ENV NODE_ENV=production PORT=8080

# Win: Copy ONLY artifacts from builder
COPY --from=builder /build/node_modules ./node_modules
COPY --chown=node:node . .

# Win: Security non-root user
USER node
EXPOSE 8080
CMD ["node", "server.js"]
  • 🚀 Code changes build in 0.5 seconds using cached dependencies.
  • 🚀 Image size reduced by 97%.
  • 🚀 Secure non-root execution with proper PID 1 signal handling.
