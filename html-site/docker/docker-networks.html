DevOps Hands-On Study Guide

Mastering Docker Networks & DNS

Learn how containers communicate across isolated subnets, why user-defined bridge networks provide automatic service discovery (DNS) while the default bridge doesn't, how to segment frontend and database microservices, and how packets flow from the outside world into your applications.

🖼️ Architectural Blueprint

The 4 Primary Network Drivers

Study how each driver type attaches containers to the host operating system.

Figure 1: Architectural comparison of Bridge (NAT), Host (Direct), Overlay (Multi-Host VXLAN), and None (Airgap) network drivers.
Driver Network Isolation Port Mapping (-p) Automatic DNS When You Should Use It
Bridge (User-Defined) High (Isolated Subnet) Required for host access ✅ Yes (by container name) Standard microservices, web apps, databases
Host None (Shared host stack) Not allowed (binds direct) Host DNS Ultra high-speed streaming, gaming, low-latency apps
Overlay High (Multi-host VXLAN) Ingress routing mesh ✅ Yes (Swarm VIP DNS) Multi-host clusters (Docker Swarm / Kubernetes)
None Total (Airgap isolation) Impossible (No eth0) ❌ None Offline batch processing, sensitive key generation
🖼️ Packet Routing Blueprint

Default Bridge vs User-Defined Custom Bridge & DNS

Understand why custom bridges allow containers to address each other by name.

Figure 2: Why Default Bridge fails name resolution, how Custom Bridge uses the 127.0.0.11 embedded DNS server, and port forwarding NAT flow.
💡 The #1 Golden Rule of Docker Networking:
Never run production containers on the default bridge! Always run docker network create my-net and attach containers with --network my-net so they can discover each other automatically by name.

🧪 Guided Exercise 1

The Default Bridge vs Custom Bridge DNS Test

Experience why DNS fails on the default bridge and how custom bridges solve it.

Step 1: Test Default Bridge (Watch it Fail!)

# Start a background container named 'my-db'
docker run -d --name my-db alpine sleep 3600

# Try to ping it by name from a new container
docker run -it --rm alpine ping my-db
# ERROR: ping: bad address 'my-db' (DNS resolution fails!)

Step 2: Create a Custom Bridge Network

# 1. Create a user-defined network
docker network create lab-network

# 2. Start container on the custom network
docker run -d --name custom-db --network lab-network alpine sleep 3600

# 3. Ping it by name on the same network
docker run -it --rm --network lab-network alpine ping -c 3 custom-db
# SUCCESS! 0% packet loss - Docker DNS resolved the hostname automatically!
🧪 Guided Exercise 2

Multi-Tier Microservice Network Segmentation

Build a secure enterprise 3-tier architecture: Frontend, API Gateway, and Database.

🎯 Security Objective:
The public-frontend should communicate with api-gateway, but must be completely blocked from reaching secure-db directly.

Step 1: Create Two Isolated Subnets

docker network create frontend-net
docker network create backend-net

Step 2: Deploy Database on Backend Network ONLY

docker run -d --name secure-db --network backend-net postgres:alpine

Step 3: Deploy API Gateway on BOTH Networks

# Start on frontend-net, then connect to backend-net
docker run -d --name api-gateway --network frontend-net alpine sleep 3600
docker network connect backend-net api-gateway

Step 4: Deploy Frontend NGINX on Frontend Network

docker run -d --name public-web --network frontend-net -p 8080:80 nginx:alpine

Step 5: Verify Isolation

# Test 1: Frontend CAN reach API Gateway
docker exec public-web ping -c 2 api-gateway  <-- SUCCESS!

# Test 2: Frontend CANNOT reach Database!
docker exec public-web ping -c 2 secure-db    <-- BLOCKED / FAILED!
🧪 Guided Exercise 3

Zero-Downtime Dynamic Network Attachment

How to attach and detach live networks without rebooting containers. 

# 1. Create a monitoring network
docker network create monitoring-net

# 2. Attach running container to the new network live
docker network connect monitoring-net secure-db

# 3. Inspect container to confirm it now possesses 2 distinct IP addresses
docker inspect secure-db --format='{{json .NetworkSettings.Networks}}'

# 4. Disconnect safely when done
docker network disconnect monitoring-net secure-db

🩺 Debugging Clinic

Common Student Networking Errors

The 3 most common networking mistakes and how to solve them.

Error 1: "Could not resolve host: db"

Cause: The containers are either on the default bridge or on different networks. 

# Fix: Verify both containers are on the same user-defined network
docker network inspect <network_name>

Error 2: How to reach Host Machine from inside Container?

Using localhost inside a container points to the container itself! 

# Fix on Mac & Windows: Use special DNS name 'host.docker.internal'
curl http://host.docker.internal:8000

# Fix on Linux: Add host flag when running
docker run --add-host=host.docker.internal:host-gateway my-app
