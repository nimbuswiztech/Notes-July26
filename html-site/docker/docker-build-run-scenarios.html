🏗️ Image Construction

Essential `docker build` Scenarios

From basic local directory compiles to BuildKit secrets and multi-architecture publishing.

Scenario B1

Dual Tagging: Semantic Versioning & Latest

Flags: -t, -t

The Challenge: You need to release version 1.4.2 of your service. If you only tag it as 1.4.2, users pulling without a tag won't receive it. If you only tag it as latest, you lose rollback history! 

# Apply both specific semver tag and mutable latest tag in a single build pass
docker build \
  -t mycompany/payment-service:1.4.2 \
  -t mycompany/payment-service:latest \
  .
⚙️ Engine Mechanics
Docker creates the physical image layers once. Both tags simply point their digest pointer to the exact same SHA-256 image ID (zero disk overhead).
⚠️ Student Gotcha
Never forget the dot (.) at the end! The dot specifies the build context directory sent to the daemon.
Scenario B2

Non-Standard Dockerfile in Subdirectory (-f)

Flags: -f

The Challenge: Real enterprise repositories maintain multiple Dockerfiles (e.g., Dockerfile.dev, Dockerfile.prod, or placed in a deploy/ directory) while needing access to root source files. 

# Point to Dockerfile inside deploy/ but keep root folder as build context
docker build \
  -f deploy/docker/Dockerfile.production \
  -t mycompany/web:prod \
  .
⚙️ Engine Mechanics
The -f flag tells Docker where the recipe lives, but the final argument (.) tells Docker what files can be referenced by COPY instructions.
⚠️ Student Gotcha
If you run cd deploy/docker && docker build ., your COPY package.json . will fail because parent source files are outside that context! Always run from project root.
Scenario B3

Building Directly from Remote Git Repo

Flags: Git Context

The Challenge: Build an image on a remote server or CI runner without cloning the Git repository locally beforehand. 

# Docker clones the repo in memory, checks out branch 'main', and builds the root Dockerfile
docker build \
  -t student-app:v1 \
  https://github.com/docker/getting-started.git#master
⚙️ Engine Mechanics
Docker Engine executes a shallow git clone into a temporary directory on the host, uses it as the context tarball, and cleans it up after the build.
⚠️ Student Gotcha
Private repos require configuring SSH forwarding via --ssh default or personal access tokens in the URL.
Scenario B4

Dynamic Build Arguments (--build-arg)

Flags: --build-arg

The Challenge: Build images with differing base versions or compile flags without modifying your committed Dockerfile. 

# Pass dynamic values matching ARG instructions in Dockerfile
docker build \
  --build-arg NODE_VERSION=20 \
  --build-arg COMMIT_SHA=$(git rev-parse --short HEAD) \
  -t mycompany/frontend:latest \
  .
⚙️ Engine Mechanics
Docker substitutes the ARG variables at compile time. If the build argument changes between builds, any layer using that ARG is cache-busted!
⚠️ Security Alert
Never pass passwords or API keys via --build-arg! Build arguments are permanently recorded in the image metadata history visible via docker history.
Scenario B5

Guaranteed Clean Rebuild (--no-cache)

Flags: --no-cache, --pull

The Challenge: You need to pull the newest Linux security patches in RUN apt-get update, but Docker keeps reusing yesterday's cached layer. 

# Force Docker to check upstream base images (--pull) and rebuild every layer from scratch
docker build \
  --pull \
  --no-cache \
  -t mycompany/secure-app:latest \
  .
⚙️ Engine Mechanics
Docker bypasses the local layer cache hash lookup and unconditionally executes every instruction anew, pulling fresh dependencies.
⚠️ Student Gotcha
Use sparingly in local development! A full no-cache rebuild takes minutes instead of seconds. Use it in nightly CI security builds.
Scenario B6

Targeting Multi-Stage Builds (--target)

Flags: --target

The Challenge: You want to run unit tests inside your Docker environment during a PR check without generating the final bloated production artifact. 

# Stops compilation at the 'test-runner' stage defined in Dockerfile
docker build \
  --target test-runner \
  -t myapp:test \
  .

# Run the unit tests immediately!
docker run --rm myapp:test npm test
⚙️ Engine Mechanics
BuildKit analyzes the dependency tree of stages and only compiles up to the targeted stage, completely skipping downstream stages.
⚠️ Teacher's CI Tip
This is the industry standard pattern for CI pipelines: target the test stage first; only if tests pass do you run the final build.
Scenario B7

Extracting Artifacts to Host (-o / --output)

Flags: -o type=local

The Challenge: You want to compile a Go binary or React frontend bundle using Docker's isolated toolchain, but output the compiled files directly onto your host laptop without leaving a container behind! 

# In Dockerfile: 'FROM scratch' copying compiled binary
# Export output directly to host folder './dist'
DOCKER_BUILDKIT=1 docker build \
  --output type=local,dest=./dist \
  .
⚙️ Engine Mechanics
BuildKit streams files from the final stage directly onto the host filesystem. No container image is saved into the Docker daemon store.
⚠️ Student Gotcha
Requires Docker BuildKit enabled. The final stage in the Dockerfile should typically be FROM scratch containing only the files to export.
Scenario B8

Secure Build-Time Secrets (--secret)

Flags: --secret

The Challenge: You need private GitHub tokens or an AWS secret during docker build to fetch internal packages, but the secret must NEVER be baked into any image layer. 

# 1. Mount the host secret securely during build
docker build \
  --secret id=npmtoken,src=$HOME/.npmrc \
  -t private-app:latest \
  .

# 2. In Dockerfile, consume it without persisting:
# RUN --mount=type=secret,id=npmtoken npm install
⚙️ Engine Mechanics
BuildKit mounts the secret into a temporary in-memory tmpfs mount during that single RUN instruction. It is impossible to extract the secret from the resulting image!
⚠️ Core Security Principle
Always teach this over --build-arg. --build-arg leaks credentials; --secret keeps them in memory only.
Scenario B9

Cross-Compilation for Multi-Arch (--platform)

Flags: --platform, buildx

The Challenge: Developers build on Apple Silicon Macbooks (ARM64), but production servers run on AWS EC2 x86 Intel/AMD (AMD64). 

# Create a multi-platform manifest and push to Docker Hub
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  -t mycompany/global-service:2.0.0 \
  --push \
  .
⚙️ Engine Mechanics
Docker uses QEMU virtualization to emulate target CPU architectures, building two separate layer trees and joining them under a single multi-arch manifest.
⚠️ Student Gotcha
Multi-arch images cannot be loaded directly into local Docker daemon images store without --load for a single platform; use --push to registry.
🚀 Container Execution

Essential `docker run` Scenarios

How to run containers like a seasoned DevOps engineer: background daemons, storage mounts, network topologies, resource throttling, and security controls.

Scenario R1

Background Web Service with Explicit Port Mapping

Flags: -d, -p, --name

The Scenario: Launch an NGINX web server in the background, named prod-web, accessible on host port 8080. 

docker run -d \
  --name prod-web \
  -p 8080:80 \
  nginx:1.25-alpine
⚙️ Engine Mechanics
Docker creates a bridge iptables rule: any traffic arriving at the host machine's port 8080 is forwarded through the Docker proxy to container IP port 80.
⚠️ Student Confusion
Format is always -p <HOST_PORT>:<CONTAINER_PORT> (Left is Host, Right is Container). If you flip them, your browser won't connect!
Scenario R2

Interactive Ephemeral Debugging Shell

Flags: -it, --rm

The Scenario: Jump into a fresh Ubuntu container to test network connectivity with ping or curl, ensuring no leftover garbage container remains after exit. 

docker run -it --rm \
  ubuntu:22.04 \
  /bin/bash
⚙️ Engine Mechanics
-i keeps STDIN open; -t allocates a pseudo-TTY terminal. --rm signals the daemon to completely delete the container and its writeable layer upon process termination.
⚠️ The Disk Exhaustion Trap
Students who omit --rm will accumulate hundreds of stopped containers in docker ps -a, quietly consuming gigabytes of disk space!
Scenario R3

Database with Persistent Named Volume & Env Variables

Flags: -v, -e, --restart

The Scenario: Run a PostgreSQL database where data survives container deletion, with environment passwords and automatic recovery if it crashes. 

docker run -d \
  --name pg-production \
  --restart unless-stopped \
  -v pgdata_volume:/var/lib/postgresql/data \
  -e POSTGRES_DB=school_db \
  -e POSTGRES_USER=admin \
  -e POSTGRES_PASSWORD=supersecret \
  -p 5432:5432 \
  postgres:16-alpine
⚙️ Engine Mechanics
Docker creates a managed named volume under /var/lib/docker/volumes/pgdata_volume. If the container is stopped, updated, or removed, the volume remains intact.
⚠️ Crucial Teaching Point
Containers are disposable; data is permanent. Always teach students to never store database tables inside the container's default filesystem!
Scenario R4

Developer Live Hot-Reloading with Host Bind Mount

Flags: -v host:container:ro

The Scenario: Mount your local source code folder into the container so that editing code in VS Code immediately reloads inside the running Node.js / Python container without rebuilding! 

docker run -d \
  --name dev-frontend \
  -p 3000:3000 \
  -v "$(pwd)":/app \
  -v /app/node_modules \
  -e NODE_ENV=development \
  node:20-alpine \
  npm run dev
⚙️ The node_modules Shield Trick
Notice -v /app/node_modules? This creates an anonymous volume that prevents your host laptop's node_modules from overriding the Linux-compiled modules inside the container!
⚠️ Performance Note on Mac/Windows
Bind mounts on macOS pass through osxfs/VirtioFS. Heavy file watchers (like Webpack) can experience CPU overhead unless configured carefully.
Scenario R5

Restricting Port to Localhost Only (127.0.0.1)

Flags: -p 127.0.0.1:port:port

The Scenario: You are running a Redis cache or administrative database on an AWS server. You need to access it via SSH tunnel, but it must NEVER be exposed to the public internet! 

# Bind exclusively to the loopback interface
docker run -d \
  --name internal-redis \
  -p 127.0.0.1:6379:6379 \
  redis:7-alpine
⚙️ Engine Mechanics
By default, -p 6379:6379 binds to 0.0.0.0 (all network interfaces, including public IP). Specifying 127.0.0.1 instructs iptables to only accept local traffic.
⚠️ Severe Security Flaw
Many developers accidentally expose private databases to the entire internet because they don't realize Docker bypasses standard UFW firewalls on Linux!
Scenario R6

Microservices with User-Defined Bridge Networks

Flags: --network, DNS

The Scenario: An API service needs to communicate with a PostgreSQL database using its container name as a hostname (e.g. db:5432), without hardcoding unstable IP addresses. 

# 1. Create a dedicated bridge network
docker network create my-app-net

# 2. Run database on the network (no host port publishing required!)
docker run -d --name db-service --network my-app-net -e POSTGRES_PASSWORD=pass postgres:alpine

# 3. Run API web service on the same network
docker run -d --name web-api --network my-app-net -p 8080:8080 -e DB_HOST=db-service my-api
⚙️ Engine Mechanics
User-defined bridge networks enable Docker's built-in DNS server (at 127.0.0.11). The container name db-service automatically resolves to its private container IP!
⚠️ Default Bridge Gotcha
Containers on the default bridge network CANNOT resolve each other by name! You must create a user-defined network with docker network create.
Scenario R7

Ultra-Fast & Secure In-Memory RAM Storage (--tmpfs)

Flags: --tmpfs

The Scenario: You are processing sensitive banking decrypts or high-frequency temporary cache files that must never touch the physical hard drive. 

docker run -d \
  --name secure-crypto-worker \
  --tmpfs /tmp:rw,noexec,nosuid,size=64m \
  mycompany/crypto-service
⚙️ Engine Mechanics
Mounts directly into host RAM. Data is never written to disk or container layers, and files vanish permanently the millisecond the container terminates.
⚠️ Student Gotcha
--tmpfs only works on Linux hosts. Always specify size=... to prevent a container from consuming all host RAM and crashing the server!
Scenario R8

Production Resource Throttling & Quality of Service

Flags: -m, --cpus, --memory-swap

The Scenario: Prevent a rogue container with a memory leak or infinite loop from starving other critical services on your server. 

docker run -d \
  --name constrained-worker \
  -m 512m \
  --memory-swap 1g \
  --cpus 1.5 \
  --pids-limit 100 \
  my-app:prod
⚙️ Engine Mechanics
Docker applies Linux cgroups (control groups). If the container consumes more than 512MB RAM plus swap, the kernel terminates it with an OOMKilled signal.
⚠️ The Fork Bomb Shield
Notice --pids-limit 100? This prevents recursive thread attacks or fork-bombs from crashing the host kernel.
Scenario R9

Automated Production Resilience (--restart)

Flags: --restart

The Scenario: Your server restarts automatically for system updates at 3:00 AM. Ensure your production containers reboot immediately with the host. 

docker run -d \
  --name resilient-api \
  --restart unless-stopped \
  -p 80:80 \
  my-web-api
⚙️ The 4 Restart Policies Compared
no: Never restart. on-failure:5: Restart only on non-zero exit codes. always: Reboot even if explicitly stopped. unless-stopped: Gold standard for production.
⚠️ The CrashLoop Trap
If your container has a syntax error, always will reboot it thousands of times per minute, filling log disks. Use on-failure:5 during testing.
Scenario R10

Maximum Security: Non-Root, Read-Only & Dropped Capabilities

Flags: --user, --read-only, --cap-drop

The Scenario: Run an untrusted third-party image in an impenetrable container sandbox where even a zero-day exploit cannot tamper with files. 

docker run -d \
  --name hardened-sandbox \
  --user 10001:10001 \
  --read-only \
  --cap-drop ALL \
  --cap-add NET_BIND_SERVICE \
  --security-opt no-new-privileges:true \
  --tmpfs /tmp \
  my-untrusted-app
⚙️ Engine Mechanics
Drops all Linux kernel capabilities (like raw socket creation or rebooting). The root filesystem is 100% read-only, preventing attackers from downloading malware.
⚠️ Teacher's Security Rule
Teach students: "Never run as root, never make filesystems writable unless needed, and drop all Linux capabilities."
Scenario R11

Enterprise Log Rotation to Prevent Disk Outages

Flags: --log-driver, --log-opt

The Scenario: A chatty application outputs millions of lines to STDOUT. Stop it from creating a 50GB log file that crashes the host hard drive. 

docker run -d \
  --name log-safe-app \
  --log-driver json-file \
  --log-opt max-size=10m \
  --log-opt max-file=3 \
  chatty-service:latest
⚙️ Engine Mechanics
Docker Engine rotates logs once they reach 10 Megabytes and retains a maximum of 3 historical rotated files (capping disk consumption at 30MB total).
⚠️ Silent Server Killer
By default, Docker's json-file driver has UNLIMITED log sizes! Unmonitored production servers frequently crash because of this single missing flag.
Scenario R12

Overriding ENTRYPOINT & CMD for Emergency Troubleshooting

Flags: --entrypoint

The Scenario: A container keeps crashing on startup. Its Dockerfile defines ENTRYPOINT ["node", "app.js"], but you need to inspect its internal files with a shell. 

# Forcefully override the baked ENTRYPOINT with a shell
docker run -it --rm \
  --entrypoint /bin/sh \
  broken-app:v1
⚙️ Engine Mechanics
Docker discards the immutable ENTRYPOINT instruction from the image metadata and executes /bin/sh as PID 1.
⚠️ Syntax Requirement
--entrypoint only takes a single executable (no flags)! Any flags or parameters must be appended after the image name as arguments.

Storage & Networking Deep Dive

Visual comparisons to help students master where data lives and how packets flow.

The 3 Docker Storage Strategies

Mount Type Syntax Example Where Data Lives Best For...
Named Volume -v dbdata:/data Docker-managed host directory (/var/lib/docker/volumes/) Databases, production data persistence, sharing data between containers
Bind Mount -v $(pwd)/src:/app/src Any arbitrary folder on host laptop/server Local development hot-reloading, mounting host configs (e.g. nginx.conf)
Tmpfs Mount --tmpfs /tmp Host RAM memory (never touches hard disk) Sensitive decryption keys, session tokens, ultra-fast temporary caches

The 4 Docker Network Drivers

Network Mode Syntax Flag Isolation Level DNS Resolution
Custom Bridge --network app-net High (Private virtual subnet with NAT) ✅ Automatic container-name DNS resolution
Default Bridge --network bridge High (Default 172.17.0.0/16 subnet) ❌ IP only (no name resolution without --link)
Host Network --network host None (Shares host network stack directly) Host DNS (Maximum packet throughput, no port mapping)
None (Airgap) --network none Total (Loopback interface only, zero network) ❌ None (Batch processing, sensitive cryptography)
🩺 Diagnostic Clinic

The Student Error Troubleshooting Lab

The 5 most common error messages students encounter when running Docker commands, and the exact steps to fix them.

ERROR 1 Error response from daemon: Bind for 0.0.0.0:80 failed: port is already allocated

Root Cause: Another container or a host process (like Apache, local NGINX, or Skype) is already listening on port 80. 

# Step 1: Identify which process or container owns the port
docker ps | grep 80
# OR on macOS/Linux:
sudo lsof -i :80

# Step 2: Solution A - Map to a different host port (e.g. 8080)
docker run -d -p 8080:80 nginx

# Step 2: Solution B - Stop the competing container
docker stop <old-container-id>
ERROR 2 Container starts and immediately stops with Exit Code 0

Root Cause: A container only stays alive as long as its PID 1 process is running in the foreground. If your program forks into the background (e.g. service nginx start) or is an interactive shell without -it, the container exits immediately! 

# Bad: Shell terminates immediately
docker run -d ubuntu bash  <-- Dies immediately!

# Fix for web servers: Run in FOREGROUND
CMD ["nginx", "-g", "daemon off;"]

# Fix for interactive containers: Keep STDIN open
docker run -it ubuntu bash
ERROR 3 touch: cannot touch '/app/log.txt': Permission denied

Root Cause: The container was configured with USER node (UID 1000), but the host bind mounted folder is owned by root (UID 0) or another user ID. 

# Fix: Match host user UID/GID when running the container
docker run -d \
  --user "$(id -u):$(id -g)" \
  -v "$(pwd)":/app \
  my-app
ERROR 4 Container died with Exit Code 137 (OOMKilled: true)

Root Cause: Exit code 137 = 128 + 9 (SIGKILL). The Linux kernel forcefully killed the container process because it exceeded its -m memory limit! 

# Step 1: Verify OOMKilled status
docker inspect <container_id> --format='{{.State.OOMKilled}}'  # Returns: true

# Step 2: Increase memory quota or profile memory leaks
docker run -d -m 1g --memory-swap 2g my-app
