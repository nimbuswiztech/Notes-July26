1. Jenkins Fundamentals

Jenkins is an open-source automation tool written in Java that allows continuous integration and supports continuous delivery by integrating with testing and deployment technologies.

Core idea: Jenkins automates the flow from source-code change → build → test → package → deploy.

Continuous Integration (CI)

Developers commit changes to a shared repository at regular intervals. Each commit can be built and verified continuously, helping teams detect problems earlier.

Why Jenkins?

  • Automates development, testing and deployment activities.
  • Integrates with source-control, build, code-quality, container and deployment tools through plugins.
  • Supports pipeline-as-code using a Jenkinsfile.

2. Jenkins Architecture: Controller and Agents

The notes describe the master/slave concept for distributing Jenkins workload. In current Jenkins terminology, these are generally referred to as controller and agents.

When multiple projects need different environments or machines, jobs can be executed on different agents instead of using one machine for everything.

Important agent concepts

  • Executors: determine how many jobs can run concurrently on an agent.
  • Remote directory: workspace location used by the agent.
  • Label: lets a job target a group of suitable agents rather than one specific machine.
  • Launch via SSH: one approach described in the original notes for connecting Linux agents.
Best practice from the notes: use labels when a job can run on multiple equivalent agents. This avoids a build waiting indefinitely for one specific offline node.

3. CI/CD Pipeline

A Jenkins pipeline is a collection of interlinked steps or jobs executed in a defined sequence. The notes also refer to pipelines as Deployment-as-Code.

Typical flow

  1. SCM Checkout — pull source code from Git.
  2. Build — compile/package the application.
  3. Push — publish the generated artifact to an artifact repository.
  4. Deploy — deploy the artifact to the target environment.

Continuous Delivery vs Continuous Deployment

Continuous DeliveryContinuous Deployment
Build, test and deliver improvements while keeping the application in a deployable state. The team decides what and when to deploy. Automatically releases changes that pass the required pipeline stages to production.

4. Jenkins Pipeline Structure

The main Declarative Pipeline structure consists of pipeline, agent, stages, stage and steps.

TermMeaning
PipelineSet of instructions for the overall build, test and delivery process.
Agent / NodeThe machine/environment where Jenkins executes work. A node block is mainly associated with scripted syntax in the supplied notes.
StageA logical section such as Build, Test or Deploy, mainly used to organize and visualize the pipeline.
StepA single task executed within a stage.

Basic Declarative Pipeline

pipeline {{
    agent any

    stages {{
        stage('Build') {{
            steps {{
                echo 'Build stage'
            }}
        }}

        stage('Test') {{
            steps {{
                echo 'Test stage'
            }}
        }}

        stage('Deploy') {{
            steps {{
                echo 'Deploy stage'
            }}
        }}
    }}
}}

5. Declarative vs Scripted Pipeline

DeclarativeScripted
More recent pipeline-as-code implementation described in the notes.Traditional pipeline implementation using Groovy/DSL.
Begins with pipeline.Begins with node in the supplied notes.
Uses structured stages and steps.Provides more general-purpose Groovy scripting.

Jenkinsfile

A Jenkins Pipeline can be stored in a text file called Jenkinsfile and committed to source control. This is the pipeline-as-code approach.

6. Pipeline Agents and Parallel Execution

Agents

  • any: run on any available agent.
  • none: no global agent; individual stages specify their own agents.
  • label: run on an agent matching the label.
  • docker: use a Docker container as the execution environment.

Parallel stages

If independent work needs to run at the same time, use a parallel block. The original notes describe this as the approach for running two or more stages concurrently.

stage('Parallel Work') {{
    parallel {{
        stage('Unit Tests') {{
            steps {{ echo 'Running unit tests' }}
        }}
        stage('Static Analysis') {{
            steps {{ echo 'Running static analysis' }}
        }}
    }}
}}

7. Build Triggers

Build Periodically

Runs the job according to a schedule, even when there are no source-code changes.

Poll SCM

Checks the source-control system for changes according to a cron-style schedule. If changes are detected, the pipeline is triggered.

GitHub / Generic Webhook

A webhook can trigger a Jenkins build in response to a repository event such as a push, rather than waiting for a polling interval.

TriggerUse
Build PeriodicallyRun on a schedule regardless of code changes.
Poll SCMCheck SCM periodically and run when changes are detected.
WebhookTrigger from a repository event such as a push.

Cron examples from the notes

0 * * * *       # minute 0 of every hour
0 0 * * *       # once a day at midnight
*/10 * * * *     # every 10 minutes
* 1-7 * * *      # every minute during hours 1 through 7

Webhook setup flow

  1. Open the GitHub repository.
  2. Go to Settings → Webhooks → Add webhook.
  3. Provide the Jenkins webhook endpoint.
  4. Select application/json.
  5. Configure the desired event, such as push.
  6. In Jenkins, enable the appropriate webhook trigger for the job.

8. Pipeline Options and Conditions

Options

OptionPurpose
buildDiscarderRemove older builds and artifacts based on configured retention.
disableConcurrentBuildsPrevent simultaneous execution of the same pipeline.
retryRetry the pipeline body when an exception occurs.
timeoutAbort execution after the configured timeout.
parallelRun nested stages concurrently.

when directive

The when block controls whether a stage should execute.

  • expression: execute when the expression evaluates to true.
  • not: execute when the nested condition is false.
  • allOf: all nested conditions must be true.
  • anyOf: at least one nested condition must be true.

9. Pipeline Post Actions

Post actions run according to the build or stage status.

ConditionWhen it runs
alwaysAlways.
changedCurrent status differs from the previous build.
fixedCurrent build succeeds after the previous build failed or was unstable.
regressionCurrent build fails/aborts/is unstable after a previous successful build.
unstableBuild is marked unstable.
abortedBuild is aborted.
failureBuild fails.
successBuild succeeds.
unsuccessfulBuild status is anything other than success.
cleanupRuns after other post conditions; useful for cleanup activities.
post {{
    always {{
        echo 'This always runs'
    }}
    success {{
        echo 'Build succeeded'
    }}
    failure {{
        echo 'Build failed'
    }}
    cleanup {{
        echo 'Cleanup'
    }}
}}

10. Jenkins Plugins

Plugins extend Jenkins capabilities and allow integration with many tools in a CI/CD toolchain.

  • Git plugin — Git operations such as checkout, fetch, branch and push.
  • SonarQube Scanner / plugin — integrate code-quality analysis.
  • Docker plugin — run builds using Docker environments.
  • Maven Integration plugin — Maven-related Jenkins integration.
  • Kubernetes plugin — integrate Jenkins with Kubernetes environments.
  • Blue Ocean — modern pipeline visualization/dashboard.
  • Periodic Backup / backup plugins — support Jenkins backup workflows.
  • Email plugin — notifications.
  • Pipeline plugin — pipeline functionality.
  • Matrix-based security — configure user permissions.
  • Amazon ECR integration — support image publishing to ECR.

11. Jenkins Security and Users

Matrix-based Security

The notes describe Matrix Authorization as a way to configure permissions for individual users based on their roles.

Project-based Matrix Authorization

This extends matrix authorization so permissions can be applied to specific projects.

Create a Jenkins user

  1. Open Jenkins Dashboard.
  2. Go to Manage Jenkins → Manage Users.
  3. Select Create User.
  4. Enter the user details and create the account.

12. Jenkins Backup

Jenkins stores important configuration and operational information under the Jenkins home directory. The notes identify job configurations, plugins, plugin configuration and build logs as examples of data that should be protected.

Backup approaches in the notes

  • ThinBackup plugin: install the plugin, configure the backup directory and run/schedule backups.
  • Backup plugin: install the plugin, configure the backup location and perform a backup.
  • Shell + cron: copy Jenkins home contents periodically to another location.

13. Jenkins Jobs: Freestyle Project

Create a Java/Maven freestyle job

  1. Create a new item in Jenkins.
  2. Choose Freestyle project.
  3. Configure Git under Source Code Management.
  4. Provide the repository URL and branch.
  5. Configure credentials if the repository is private.
  6. Add an Execute shell build step.
  7. Run the Maven build, for example mvn clean install.
  8. Save and run Build Now.
The original notes use the Jenkins workspace path under /var/lib/jenkins/workspace/ for the example.

14. Jenkins Agent Setup and Tomcat Deployment

Agent setup flow from the notes

  1. Open Manage Jenkins → Nodes and Clouds.
  2. Create a permanent agent/node.
  3. Configure executors, remote directory and label.
  4. Configure SSH launch and credentials.
  5. Use an SSH username/private key credential.
  6. Install Java and Maven on the agent.
  7. Configure the project to run on the required label.

WAR deployment flow

  1. Checkout Java source code.
  2. Run mvn clean install.
  3. Find the generated WAR in the target directory.
  4. Copy the WAR into the Tomcat webapps directory.
  5. Start/run Tomcat and verify the application.
Assignment: Set up a Jenkins controller/agent arrangement and execute a job on an agent that creates a WAR file and deploys it to Tomcat.

  • Reliability

  2. Create a project in SonarQube.

17. Groovy and Shared Libraries

Groovy

Groovy is an open-source scripting language implemented in Java and tightly integrated with Java. The notes describe it as adding features associated with languages such as Ruby and Python.

Jenkins Shared Library

A shared library is a collection of Groovy scripts that can be shared across multiple Jenkins jobs and pulled into Jenkinsfiles.

The notes state that shared libraries can retrieve source from local files, Git repositories and Jenkins SCM plugins.

Why use a shared library?

  • Avoid repeating the same pipeline code across projects.
  • Reduce coding effort.
  • Reduce duplicate code.

18. Multi-branch Pipeline

A multi-branch pipeline automatically creates Jenkins pipelines based on branches discovered in source control. The notes describe automatic branch discovery and pipeline creation for branches in GitHub.

19. Jenkins Agent Offline Scenario

If a job is tied to one specific agent and that agent is offline or all its executors are busy, the job waits for that agent to become available.

Approach described in the notes: associate jobs with a label representing a group of suitable nodes/agents. Any available node matching the label can then fulfill the build request.

20. Jenkins Remote Access API

The Jenkins Remote Access API provides programmatic access to Jenkins. The notes mention use cases such as creating/copying jobs, triggering builds and retrieving Jenkins information programmatically.

21. Jenkins Monitoring and Troubleshooting

System logs

The original notes mention accessing Jenkins system logs through Manage Jenkins → System Log and also reference the Jenkins log file under the Jenkins log directory.

Common checks from the training notes

  • Check the build console output.
  • Check Jenkins system logs.
  • Verify the target agent is online.
  • Verify Java/Maven/Git availability on the execution node.
  • Verify workspace and artifact paths.
  • Check plugin configuration and credentials.

22. Interview Questions & Answers

How many agents/slaves have you used?
The original training notes provide the example answer: “I have 7 slaves in my master machine.”
What plugins have you used in Jenkins?
Mention examples from the notes such as Git, Email, Pipeline, Docker, Kubernetes, Blue Ocean, backup, monitoring, Maven integration and SonarQube Scanner.
How do you manage Jenkins backups?
The notes describe using a backup plugin or a shell script scheduled with cron to copy Jenkins home data to another location.
How do you secure Jenkins?
The notes describe using matrix-based security to configure permissions for users according to their roles.
Build Periodically vs Poll SCM?
Build Periodically runs on a schedule regardless of source changes. Poll SCM checks SCM for changes and triggers the job when changes are detected.
What is a parallel pipeline?
It allows multiple stages or steps to run at the same time instead of sequentially.
What is an upstream/downstream job?
An upstream job triggers another job; the triggered job is the downstream job.
How do you check whether Tomcat is running?
The original notes give ps -ef | grep "Tomcat".
What are Jenkins environment variables?
The notes list examples including BUILD_ID, BUILD_NUMBER, BUILD_TAG, BUILD_URL, EXECUTOR_NUMBER, JAVA_HOME, JENKINS_URL, JOB_NAME, NODE_NAME and WORKSPACE.
What is a multi-branch pipeline?
It automatically creates pipelines based on branches discovered in source control.
What happens when a Jenkins agent is offline?
A job tied to that specific agent waits. The notes recommend using labels to allow execution on another suitable agent.
