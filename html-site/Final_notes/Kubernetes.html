01

Kubernetes Fundamentals

Kubernetes is described in the supplied notes as an open-source container orchestration platform for managing containerized or microservice applications across a distributed cluster. The notes emphasize deployment, scaling, rollback, high availability, self-healing and reducing the complexity of managing many containers.

Why orchestration? The source connects Kubernetes with the move from monoliths to microservices and the need to manage many containers with less manual work.
Core idea
Kubernetes
├── Control Plane
└── Worker Nodes
    └── Pods
        └── Containers

03

Control Plane Components

  • API Server: central management point and frontend through which requests are made.
  • etcd: distributed key-value store for cluster data and state.
  • Scheduler: selects nodes for unscheduled Pods based on resources and scheduling requirements.
  • Controller Manager: runs controllers that continuously work toward desired state.

The source also lists node, replication, endpoint and service controllers, plus cloud-controller responsibilities.

Typical interaction
kubectl
   ↓
API Server
   ↓
etcd / Controllers / Scheduler
   ↓
Worker Nodes
etcd backup example
etcdctl snapshot save <snapshot-file>

Worker Node Components

The supplied notes identify the Pod, container runtime, kubelet and kube-proxy as the major worker-node components.

  • Pod: smallest/basic execution unit and can contain one or more containers.
  • kubelet: node agent that keeps Pods and containers healthy and reports node status.
  • kube-proxy: maintains network rules and forwards traffic toward appropriate Pods.
  • Container runtime: underlying software used to run containers.
Node inspection
kubectl get nodes
kubectl get nodes -o wide
kubectl describe node <node-name>

Services & Service Discovery

The source explains Services as stable networking for Pods. Pods are ephemeral and their IP addresses can change, so clients should normally use a Service. Services use selectors/labels to identify backend Pods and provide a stable IP/DNS endpoint.

Service
apiVersion: v1
kind: Service
metadata:
  name: myapp-service
spec:
  selector:
    app: myapp
  ports:
  - name: http
    protocol: TCP
    port: 80
    targetPort: 8080
Inspect / test
kubectl get svc
kubectl describe svc <service-name>
curl <service-ip>:<port>

Ingress & Ingress Controller

Ingress is described as an API object for HTTP/HTTPS routing from outside the cluster to Services. Routing is controlled by Ingress rules, while an Ingress Controller acts as the inbound traffic handler. The source lists NGINX, AWS and GCE as examples.

Source distinction: the notes describe an Application Load Balancer as connecting to multiple servers, while an Ingress Controller routes external traffic to multiple microservices.

Volumes, PV, PVC & StorageClass

The source explains that container filesystem data is ephemeral. Kubernetes Volumes provide storage, while PersistentVolumes and PersistentVolumeClaims separate storage provisioning from application Pods. The notes describe both static and dynamic provisioning.

Storage flow
Static:
PV → PVC → Pod

Dynamic:
StorageClass → PVC → Pod
PV
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-vol
spec:
  storageClassName: staticpv
  capacity:
    storage: 1Gi
  accessModes:
  - ReadWriteOnce
  hostPath:
    path: /tmp/static
PVC
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pv-vol-claim
spec:
  storageClassName: staticpv
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi

ReplicaSet & ReplicationController

A ReplicaSet maintains a stable set of replica Pods. The source explains that it replaces failed Pods and maintains the desired count. ReplicationController is described as the older controller using equality-based selectors, while ReplicaSet supports equality-based and set-based selectors.

ReplicaSet
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: my-replicaset
spec:
  replicas: 2
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
      - name: my-container
        image: nginx
Scale
kubectl scale --replicas=5 replicaset <name>
kubectl get replicaset
kubectl get pods

Deployment Strategies, Rollout & Rollback

The source covers Recreate, Rolling Update, Rollback, Blue/Green, Canary and A/B testing. Rolling Update incrementally replaces old Pods. Blue/Green runs old and new versions together and switches the Service. Canary gradually exposes a new version to a subset of users.

kubectl rollout history deployment/<name>
kubectl rollout undo deployment/<name>

   ↓

Traffic → Blue

        ↓
Collect metrics
        ↓
Continue rollout OR rollback

Node Affinity & Pod Affinity

Affinity extends node selection with expressions and supports hard and soft scheduling rules. The source identifies requiredDuringSchedulingIgnoredDuringExecution as hard and preferredDuringSchedulingIgnoredDuringExecution as soft. Pod affinity/anti-affinity uses labels of other Pods and a topology key.

Node affinity
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: ec2
          operator: In
          values:
          - worker2
Pod affinity
affinity:
  podAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchExpressions:
        - key: app
          operator: In
          values:
          - nginx
      topologyKey: kubernetes.io/hostname

Taints & Tolerations

Taints are a node property that repel Pods. Tolerations are applied to Pods so they are allowed to schedule onto nodes with matching taints. The source gives dedicated-hardware examples such as GPU/high-resource nodes.

Taint
kubectl taint nodes <node-name> ec2=taint:NoSchedule
Remove taint
kubectl taint nodes <node-name> ec2=taint:NoSchedule-
Effects
NoSchedule
PreferNoSchedule
NoExecute
Toleration
tolerations:
- key: "ec2"
  operator: "Equal"
  value: "taint"
  effect: "NoSchedule"

Pod Probes — Liveness, Readiness & Startup

The notes describe three probe types. Liveness checks application health and a failed liveness probe causes the container to be restarted. Readiness controls whether the application receives traffic. Startup protects slow-starting applications by allowing initialization to complete before normal liveness/readiness behavior is applied.

Probe actions
HTTP request
Shell / exec command
TCP port check
Probe fields
initialDelaySeconds
periodSeconds
timeoutSeconds
successThreshold
failureThreshold
Difference
Liveness failure → restart container
Readiness failure → stop serving traffic
Startup probe → protect slow startup

RBAC — Role, ClusterRole & Access Model

RBAC is described as the Kubernetes mechanism for constraining access for users, groups and ServiceAccounts. The source organizes access around Subject → Resource → Verb. Role is namespace-scoped; ClusterRole can define cluster-wide permissions and rules for cluster-scoped resources.

Role
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: sa-role
  namespace: dev
rules:
- apiGroups: ["*"]
  resources: ["pods", "secrets"]
  verbs: ["get", "watch", "list"]
ClusterRole
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: sa-cluster-role
rules:
- apiGroups: ["*"]
  resources: ["pods", "secrets"]
  verbs: ["get", "watch", "list"]
Permission check
kubectl auth can-i list pods

RoleBinding & ClusterRoleBinding

A RoleBinding grants permissions within a namespace. A ClusterRoleBinding grants a ClusterRole cluster-wide. The source includes ServiceAccount-based bindings.

ClusterRoleBinding
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: sa-crb
subjects:
- kind: ServiceAccount
  name: devops
  namespace: default
roleRef:
  kind: ClusterRole
  name: sa-cluster-role
  apiGroup: rbac.authorization.k8s.io
CLI
kubectl create clusterrole sa-cluster-role \
  --resource=pods --resource=secrets \
  --verb=get --verb=list

kubectl create clusterrolebinding sa-crb \
  --serviceaccount=default:devops \
  --clusterrole=sa-cluster-role

Kubernetes High Availability

The notes describe HA using multiple control-plane/master nodes so another control-plane node can continue operating if one fails. They also note that worker workloads may continue running during control-plane failure, while creating new deployments or recovering from node failures depends on available control-plane components.

Cluster Failure & Recovery Concepts

The source discusses HA behavior when a control-plane/master node fails. In an HA setup, other control-plane nodes can continue operating. Worker nodes may continue running workloads, while management operations depend on available control-plane components.

Failure thinking
Control Plane failure
→ Existing worker workloads may continue
→ Management/reconciliation capabilities are affected
→ HA control plane reduces the impact of one control-plane failure
