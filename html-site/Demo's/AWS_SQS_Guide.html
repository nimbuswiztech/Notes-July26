📘 AWS Teaching Guide – Day Session

AWS SQS

Simple Queue Service — Fully managed message queuing for decoupling microservices, distributed systems, and serverless applications. Reliably delivers messages even if the consumer is offline.

🕐 60–75 Minutes 🎯 Beginner–Intermediate 📦 Message Queuing 🔗 Works with Lambda, SNS, ECS, EC2
📦

What is AWS SQS?

🏦 Analogy — Bank Queue (Token System)

Think of an SQS queue like a bank token system. Customers (producers) take a token and wait. Bank tellers (consumers) call tokens one by one. If there are no tellers (consumers down), tokens are still in the queue — no customer is lost. If there are many tellers, they process tokens faster. The queue absorbs spikes and decouples the arrival rate from the processing rate.

Why Do We Need Message Queues?

Without queuing — if Service A calls Service B directly (synchronous), and B is slow or down, A fails too. With SQS — A drops a message in the queue and returns immediately. B processes when it's ready. They're completely decoupled.

⚡

Decoupling

Producer and consumer are independent. Producer doesn't wait for consumer. Consumer processes at its own pace.

🛡️

Durability

Messages are replicated across 3 AZs. Even if consumer crashes, messages stay in the queue for up to 14 days.

📈

Buffer

Queue absorbs traffic spikes. 10K requests/sec hit the queue; consumer processes at 100/sec. No overload.

🔀

Queue Types: Standard vs FIFO

FeatureStandard QueueFIFO Queue
Message orderingBest-effort (NOT guaranteed). Messages may arrive out of order.Strict FIFO — first in, first out. Guaranteed.
DeliveryAt-least-once. May deliver duplicate messages — consumer must handle deduplication.Exactly-once processing — no duplicates.
ThroughputUnlimited (nearly). 300 msg/sec per API call, up to 3,000 with batching.300 msg/sec (or 3,000 with batching).
Use caseImage processing, notifications, email delivery, log ingestion. Order doesn't matter.Financial transactions, order placement, inventory. Order MATTERS.
NamingAny nameName must end with .fifo
Cost$0.40 per million requests$0.50 per million requests
⚠️
Teaching Point: Standard queues can deliver a message more than once. If your consumer isn't idempotent (safe to run twice), use FIFO or build deduplication logic.

Visibility Timeout — Most Important Concept

Timeline of a message in SQS: 00:00 Producer sends message to queue → Message is visible in queue 00:05 Consumer 1 calls ReceiveMessage → picks up the message → Visibility Timeout starts (default 30 seconds) → Message is HIDDEN from other consumers during this window Consumer 1 is processing... 00:20 Consumer 1 successfully processes the message → Calls DeleteMessage API → message is permanently removed ✅ --- OR FAILURE SCENARIO --- 00:20 Consumer 1 CRASHES before processing → Never calls DeleteMessage 00:35 Visibility Timeout EXPIRES (30 sec after 00:05) → Message becomes VISIBLE again in the queue 00:36 Consumer 2 picks up the same message → processes it ✅ → Calls DeleteMessage → message removed
💡
Key Insight: SQS doesn't auto-delete messages when a consumer reads them. The consumer MUST explicitly call DeleteMessage after successful processing. This is what guarantees no message loss.

Dead Letter Queue (DLQ)

If a message fails to be processed N times (configurable), SQS automatically moves it to a Dead Letter Queue instead of deleting it or looping forever.

Message arrives in queue
→
Consumer picks up → fails → message returns
→
Repeat 3 more times
→
After 4 failures → sent to DLQ
✅
Best Practice: Configure a CloudWatch alarm on the DLQ ApproximateNumberOfMessages metric. If DLQ has > 0 messages → alert the team. Set DLQ retention to 14 days to give the team time to investigate and replay.

Hands-On: Create SQS Queue (Step-by-Step)

Lab 1: Create a Standard Queue with DLQ

1
First — Create the Dead Letter Queue
  • SQS Console → Create Queue
  • Type: Standard, Name: orders-queue-dlq
  • Retention: 14 days, all other defaults → Create
2
Create the Main Queue
  • SQS Console → Create Queue
  • Type: Standard, Name: orders-queue
  • Visibility timeout: 30 seconds
  • Message retention: 4 days
  • Delivery delay: 0 seconds
  • Receive message wait time: 20 seconds (enables long polling)
3
Configure Dead Letter Queue
  • Scroll down to "Dead-letter queue" → Enable
  • Choose queue: orders-queue-dlq
  • Maximum receives: 3 (after 3 failed attempts → goes to DLQ)
4
Create Queue Note the Queue URL: https://sqs.ap-south-1.amazonaws.com/123456789012/orders-queue
🔬 Lab 2: Send and Receive Messages via CLI
Practice the full producer → queue → consumer cycle from the terminal
  1. Send a message (Producer): aws sqs send-message --queue-url https://sqs.ap-south-1.amazonaws.com/123456789012/orders-queue --message-body '{"orderId":"1001","item":"Laptop","amount":45000}'
  2. Send a batch (more efficient): aws sqs send-message-batch --queue-url URL --entries '[{"Id":"1","MessageBody":"Order 1"},{"Id":"2","MessageBody":"Order 2"}]'
  3. Receive the message (Consumer — long poll): aws sqs receive-message --queue-url URL --wait-time-seconds 20 --max-number-of-messages 10
  4. Note the ReceiptHandle in the output — save it!
  5. Delete the message after processing: aws sqs delete-message --queue-url URL --receipt-handle "RECEIPT_HANDLE_FROM_STEP_4"
  6. Check queue depth: aws sqs get-queue-attributes --queue-url URL --attribute-names ApproximateNumberOfMessages
🔬 Lab 3: Lambda Consumer — Process SQS Messages Automatically
Configure Lambda to automatically poll SQS and process messages — the most common production pattern
  1. Create a Lambda function (Python 3.12):
    • Function name: OrderProcessor
    • Execution role: needs sqs:ReceiveMessage, sqs:DeleteMessage, sqs:GetQueueAttributes
  2. Add SQS Trigger: Lambda → Configuration → Triggers → Add trigger → SQS → orders-queue
  3. Batch size: 10 (Lambda receives up to 10 messages per invocation)
  4. Lambda code:
Python Lambda Handler for SQS
import json def lambda_handler(event, context): for record in event['Records']: body = json.loads(record['body']) print(f"Processing order: {body['orderId']}") # Your processing logic here # If this function succeeds: Lambda auto-deletes the messages # If this function throws exception: Lambda returns messages to queue → retried return {'statusCode': 200, 'body': 'Processed successfully'}

When Lambda processes SQS, it handles the ReceiveMessage and DeleteMessage calls automatically. Your code just processes the messages.

⏱️

Short Polling vs Long Polling

FeatureShort Polling (default)Long Polling (recommended)
How it worksReceiveMessage returns immediately even if queue is emptyReceiveMessage waits up to 20 sec for a message before returning empty
Empty responsesMany — high costAlmost none — low cost
LatencyLow (responds immediately)Low for messages (up to 20 sec for empty)
CostHigh (many API calls)Low (fewer API calls)
EnableDefaultSet WaitTimeSeconds = 20 in ReceiveMessage, or set on queue
✅
Always use Long Polling (20 seconds) in production — it reduces empty ReceiveMessage API calls by up to 98%, cutting costs significantly.
🌐

SNS + SQS Fan-Out Pattern (Revisited from SNS)

Why combine SNS and SQS?

If you only use SNSIf you add SQS between SNS and consumers
If consumer (Lambda/HTTP) is down → message is lost (after retries)Messages buffer in SQS → consumer processes when it comes back up
Consumer must process at the same speed as messages arriveConsumer can process at its own pace — queue absorbs spikes
No replay — once processed, message is goneMessages stay in queue for up to 14 days — can reprocess
💡
Rule of Thumb: For critical workflows — SNS → SQS → Lambda/Worker. For simple notifications (email, SMS) — SNS direct subscription is fine.
🔒

SQS Security

IAM Policies (Identity-Based)

  • Grant sqs:SendMessage to producers
  • Grant sqs:ReceiveMessage + sqs:DeleteMessage to consumers
  • EC2 instances, Lambda, ECS use IAM roles — no hardcoded keys

SQS Resource Policy (Queue Policy)

  • Allow cross-account access (Account B can send to your queue)
  • Allow specific AWS services like SNS to send messages
  • Restrict access by source IP (aws:SourceIp condition)

Encryption at Rest

  • Enable SSE (Server-Side Encryption) — messages encrypted using KMS
  • Choose: AWS Managed Key (free) or Customer Managed Key (for compliance/audit trail)
  • Encryption happens at the SQS service level — transparent to producers/consumers

📚 Session Summary — SQS Key Takeaways

  • SQS = asynchronous message queue. Producer drops messages; consumer processes when ready
  • Standard Queue: best-effort order, at-least-once delivery, unlimited throughput
  • FIFO Queue: strict order, exactly-once delivery, 300 msg/sec (use when order matters)
  • Visibility Timeout: message hidden from other consumers while one is processing — prevents duplicate processing. Consumer must call DeleteMessage on success
  • Dead Letter Queue (DLQ): after N failed receive attempts → moves to DLQ. Always set up CloudWatch alarm on DLQ
  • Long Polling (20 sec): always use in production. Reduces empty API calls and cost significantly
  • Lambda + SQS: Lambda polls SQS automatically (event source mapping). Auto-deletes on success, returns on failure
  • SNS → SQS Fan-Out: SNS broadcasts; SQS queues buffer for each independent consumer microservice
