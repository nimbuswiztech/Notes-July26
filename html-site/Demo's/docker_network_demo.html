01

Why Do We Need Docker Networks?

Theory: 10 mins
🎙️ Instructor Talk Track

Start with a simple real-world analogy. "Imagine Docker containers are different computers in a data center. If two containers need to communicate, they need some form of networking."

Browser | v Frontend Container | v Backend Container | v Database Container

🔄 Container-to-Container

Allow your microservices, like a Node.js backend and a PostgreSQL database, to talk to each other securely without going out to the public internet.

🌐 Container-to-Host

Publish ports using -p so that external traffic from the user's browser hitting the Host machine gets routed to the correct container.

🛡️ Network Isolation

Ensure that the database container is completely isolated from the internet, and only the backend container can reach it.

02

Scenario 1 & 2: Default Bridge

Hands-on: 15 mins
SCENARIO 1

Explore the Default Bridge

Check existing networks on the host machine.

Terminal
$ docker network ls
NETWORK ID     NAME      DRIVER    SCOPE
xxxx           bridge    bridge    local
xxxx           host      host      local
xxxx           none      null      local
Network Purpose
bridge Default container networking
host Container shares host network namespace
none No external networking
SCENARIO 2

Container-to-Container Communication

Run two Ubuntu containers and show that they can ping each other using IP addresses.

Terminal
$ docker run -dit --name container1 ubuntu bash
$ docker run -dit --name container2 ubuntu bash
Terminal: Find IP Address
$ docker inspect -f '{{.NetworkSettings.IPAddress}}' container1
172.17.0.2

$ docker inspect -f '{{.NetworkSettings.IPAddress}}' container2
172.17.0.3
⚠️ Important Teaching Point

Ask students: "Can container1 directly use container2's name?"

Try to ping container2 from container1. It will FAIL! On the default bridge network, name-based discovery is not supported. This gives you a great reason to introduce Custom Networks!

03

Scenario 3 & 4: Custom Bridge & DNS

Hands-on: 20 mins
SCENARIO 3 & 4

Create Custom Network & Test DNS

Terminal
$ docker network create mynetwork

Now launch two containers explicitly attaching them to the custom network:

Terminal
$ docker run -dit --name app1 --network mynetwork ubuntu bash
$ docker run -dit --name app2 --network mynetwork ubuntu bash
app1 | | ping app2 | v Docker DNS | v app2 IP
💡 The "Aha!" Moment

When students ping app2 from app1, it works! Students don't need to remember IP addresses like 172.18.0.3. They can simply use container names, because user-defined bridge networks provide automatic DNS resolution.

04

Scenario 5: Real App (Web + DB)

Hands-on: 25 mins
SCENARIO 5

Build a Production-Style Architecture

User | | Host Port 8080 | v ┌───────────────┐ │ Web Container │ │ nginx │ └───────┬───────┘ | | Docker Network | v ┌───────────────┐ │ DB Container │ │ PostgreSQL │ └───────────────┘
Terminal
$ docker network create app-network

# Start PostgreSQL Database
$ docker run -d --name database --network app-network -e POSTGRES_PASSWORD=admin postgres

# Start Web Frontend
$ docker run -d --name web --network app-network -p 8080:80 nginx
🎙️ Very Important Rule to Teach
-p = external access
--network = internal communication

Explain that -p 8080:80 is for Host-to-Container traffic. --network app-network is for Container-to-Container traffic.
05

Scenario 7: Network Isolation

Hands-on: 15 mins
SCENARIO 7

Prove Containers Cannot Communicate Across Networks

Terminal
$ docker network create frontend
$ docker network create backend

$ docker run -dit --name front-app --network frontend ubuntu bash
$ docker run -dit --name back-app --network backend ubuntu bash
frontend network backend network frontend backend | X | backend

They are isolated! Containers connected to different Docker networks cannot normally communicate directly with each other. This is highly useful for segmenting security zones.

06

Scenario 8: Multi-Network Containers

Hands-on: 15 mins
SCENARIO 8

Bridging Two Networks Dynamically

frontend-net ┌─────────────────┐ │ │ frontend backend │ │ backend-net │ │ database

You can dynamically attach a running container to a second network without restarting it!

Terminal
# Connect the backend container to the backend-net network dynamically
$ docker network connect backend-net backend

# Verify the container is now connected to TWO networks
$ docker inspect backend
07

Scenario 12 & 13: Host & None Networks

Hands-on: 10 mins

Host Network

--network host

The container shares the host's network namespace. On Linux, this means the container can use the host's network interfaces directly. -p mappings are completely ignored because the container binds directly to host ports.

None Network

--network none

The container doesn't get normal external networking. If you inspect ip addr inside the container, you will only see the loopback interface (lo). Useful for highly isolated workloads.

SWARM DEMO

Deploying an Overlay Network across EC2s

This is where you make the concept very clear. Create an overlay network and attach two cross-host services to it.

Terminal: On Manager Node
# Create overlay network
$ docker network create --driver overlay my-overlay

# Create Redis database service
$ docker service create --name redis --network my-overlay redis

# Create Web App service
$ docker service create --name app --network my-overlay nginx

The application can communicate with redis:6379 seamlessly across physical EC2 hosts without needing Redis to be exposed publicly. That's a massive production concept!
