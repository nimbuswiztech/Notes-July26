📘 AWS Teaching Guide – Day Session

AWS SNS

Simple Notification Service — Fully managed pub/sub messaging for application-to-application (A2A) and application-to-person (A2P) communications at any scale.

🕐 45–60 Minutes 🎯 Beginner–Intermediate 📣 Pub/Sub Messaging 🔗 Integrates with CloudWatch, Lambda, SQS
📣

What is AWS SNS?

📺 Analogy — TV Broadcast Channel

Think of SNS like a TV broadcast channel. The TV station (Publisher) broadcasts a single program (message). Anyone who has tuned in to that channel (Subscribers) receives it simultaneously. One message → many receivers at once. You don't send individual messages to each subscriber — you broadcast once and SNS handles delivery to all of them.

SNS = Pub/Sub (Publish-Subscribe) Pattern

📤

Publisher (Producer)

Any entity that sends a message to an SNS Topic. Can be: your app, a CloudWatch Alarm, an S3 event, another AWS service.

📌

Topic

The messaging channel. A named resource in SNS. Publishers send to the topic; subscribers receive from it. Like a broadcast station ID.

📥

Subscriber (Consumer)

Receives messages from the topic. Can be: Email, SMS, HTTP endpoint, Lambda, SQS queue, mobile push.

┌─────────────────────────────────────────────┐ │ SNS TOPIC │ Publisher │ "OrderPlaced-Events" │ ┌──────────┐ publish │ │ │ Your App │ ────────►│ Message: {orderId: 1001, amount: $299} │ └──────────┘ │ │ └──────────────┬──────────────────────────────┘ │ Fan-Out (all at once) ┌──────────────┬─────────┴──────────┬──────────────┐ ▼ ▼ ▼ ▼ 📧 Email 📱 SMS λ Lambda 📦 SQS Queue (notify team) (alert manager) (process order) (update inventory)

SNS Topic Types

TypeDescriptionUse When
Standard TopicBest-effort ordering. May deliver duplicates. Very high throughput (100K+ msg/sec).Most use cases. Notifications, fan-out, decoupling.
FIFO TopicStrict ordering. Exactly-once delivery. Lower throughput (300 msg/sec).Financial transactions, inventory updates where order matters.

Supported Subscriber Protocols

  • 📧 Email / Email-JSON — direct emails (requires confirmation)
  • 📱 SMS — text message to phone number
  • λ AWS Lambda — trigger a function on every message
  • 📦 SQS — deliver to a queue for decoupled processing
  • 🌐 HTTP/HTTPS — POST to a web endpoint
  • 📲 Mobile Push — iOS (APNs), Android (FCM), Kindle (ADM)
  • 📬 Amazon SES — rich email via Simple Email Service
  • ⚡ Amazon EventBridge — event-driven workflows
⚙️

Hands-On: Create SNS Topic & Subscribe (Step-by-Step)

Lab 1: Create Topic and Email Subscription

1
Open SNS Console Go to AWS Console → Simple Notification Service → Topics → Create topic
2
Configure the Topic
  • Type: Standard
  • Name: DevOps-Alerts
  • Display name: DevOps Team Alerts (appears in SMS subject)
  • Encryption: Leave default (SSE disabled) for lab, enable SSE-KMS for production
  • Access Policy: Default (topic owner can publish and subscribe)
3
Create the Topic → Note the ARN ARN format: arn:aws:sns:ap-south-1:123456789012:DevOps-Alerts
4
Add Email Subscription
  • Topics → DevOps-Alerts → Create subscription
  • Protocol: Email
  • Endpoint: student@example.com
  • Create subscription → AWS sends a confirmation email
  • Open the email → Click "Confirm subscription" link
  • Status changes from PendingConfirmation to Confirmed
⚠️
Important: Email subscriptions must be confirmed by the recipient before they receive any messages. Unconfirmed subscriptions expire after 3 days.
5
Publish a Test Message
  • Topics → DevOps-Alerts → Publish message
  • Subject: Test Alert from DevOps
  • Message: This is a test notification from AWS SNS. Your monitoring is working!
  • Click Publish → Check your inbox within seconds!
🔬 Lab 2: Publish via AWS CLI
Practice publishing SNS messages from the command line — used in automation scripts
  1. Publish a message to your topic: aws sns publish --topic-arn arn:aws:sns:ap-south-1:123456789012:DevOps-Alerts --message "Server CPU is at 95%!" --subject "CRITICAL: High CPU Alert"
  2. Subscribe an SQS queue (from Lab later): aws sns subscribe --topic-arn arn:aws:sns:ap-south-1:123456789012:DevOps-Alerts --protocol sqs --notification-endpoint arn:aws:sqs:ap-south-1:123456789012:my-queue
  3. List all subscriptions for a topic: aws sns list-subscriptions-by-topic --topic-arn arn:aws:sns:ap-south-1:123456789012:DevOps-Alerts
🔔

Key Integration: SNS + CloudWatch Alarms

The Most Common SNS Pattern in Production

EC2 CPU > 80%
→
CloudWatch Alarm fires
→
SNS Topic: DevOps-Alerts
→
Email to team
+
SMS to on-call
+
Lambda: page PagerDuty

When you create a CloudWatch Alarm, the "Actions" section lets you select an SNS topic. SNS then fans out to all subscribers — email, SMS, Lambda — simultaneously.

✅
Best Practice: Create one SNS topic per severity level: Critical-Alerts, Warning-Alerts, Info-Alerts. Route different teams to different severity topics.
🔎

Message Filtering — Advanced Feature

What is Message Filtering?

Instead of every subscriber receiving every message, you can attach a filter policy to a subscription so subscribers only receive messages relevant to them.

💡
Example: An e-commerce app publishes all order events to one SNS topic. The payment service only needs "OrderPlaced" events. The shipping service only needs "PaymentConfirmed" events. Filter policies route only the right messages to each subscriber.
MESSAGE ATTRIBUTES (published with message)
{ "event_type": "OrderPlaced", "region": "india", "order_value": 299 }
FILTER POLICY ON PAYMENT SERVICE SUBSCRIPTION
{ "event_type": ["OrderPlaced"], "region": ["india", "us"] }
FILTER POLICY ON SHIPPING SERVICE SUBSCRIPTION
{ "event_type": ["PaymentConfirmed"] }

Result: Payment service only receives OrderPlaced events. Shipping service only receives PaymentConfirmed. Both subscribe to the same topic — no duplicate consumers needed.

🌐

SNS Fan-Out Pattern — The Most Important Architecture Pattern

SNS → Multiple SQS Queues (Fan-Out)

One message published to SNS is delivered to multiple SQS queues simultaneously. Each queue is processed independently by a different microservice. This achieves loose coupling and parallel processing.

ORDER PLACED EVENT │ ▼ [SNS Topic: orders] │ ──────┴─────────────────────────────────────── │ │ │ │ ▼ ▼ ▼ ▼ [SQS: payments] [SQS: inventory] [SQS: email] [SQS: analytics] │ │ │ │ ▼ ▼ ▼ ▼ Payment Reduce Send "Order Record to Lambda Stock Lambda Confirmed" Data Lake Lambda
✅
Why this pattern is powerful: If the inventory service is slow, it doesn't block payment or email. Each service processes at its own pace. If a service fails, messages stay in its SQS queue for retry — nothing is lost.
📬

Message Delivery, Retries & Dead Letter Queues

SNS Delivery Retries

When SNS can't deliver a message to an HTTP/Lambda subscriber, it retries automatically with exponential backoff.

ProtocolRetry Behaviour
HTTP/HTTPSUp to 100,000 retries over 23 days
LambdaUp to 3 retries
SQSNo retries needed — SQS stores the message indefinitely
EmailBest-effort, no guaranteed delivery. Not for critical flows.
SMSBest-effort based on carrier

Dead Letter Queue (DLQ) for SNS

After all retries are exhausted, failed messages can be sent to an SQS Dead Letter Queue for manual review.

⚠️
Always configure a DLQ for production SNS subscriptions. Without a DLQ, failed messages are silently dropped — you'll never know what was lost.

📚 Session Summary — SNS Key Takeaways

  • SNS = Pub/Sub: one publisher, many subscribers — "broadcast" model
  • Topic = the messaging channel. Publishers publish to a topic, subscribers receive from it
  • Standard Topics: high throughput, best-effort ordering. FIFO: strict order, exactly-once
  • Subscribers: Email, SMS, Lambda, SQS, HTTP, Mobile Push
  • Email subscriptions require manual confirmation (click link in email)
  • Fan-out pattern: SNS → multiple SQS queues → independent microservices (most common production pattern)
  • Message Filtering: subscribers only get messages that match their filter policy
  • DLQ: configure Dead Letter Queue for every HTTP/Lambda subscription in production
  • SNS + CloudWatch Alarms = standard monitoring → alerting pattern in AWS
