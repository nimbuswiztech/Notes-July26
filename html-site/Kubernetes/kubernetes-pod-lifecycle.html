Kubernetes Pod Lifecycle

Understand how Pods are created, scheduled, initialized, run, become ready, restart, terminate, and reach terminal states. Includes practical labs, probes, lifecycle hooks, troubleshooting and interview preparation.

1. Introduction

The Pod lifecycle describes the major stages a Kubernetes Pod passes through from creation until it finishes or is deleted. Kubernetes tracks a Pod's high-level phase, detailed conditions, and each container's state. The kubelet on the assigned node works with the container runtime to start and supervise containers and execute health probes.

Why it matters

Lifecycle knowledge helps engineers understand Pending Pods, image-pull failures, initialization delays, CrashLoopBackOff, readiness problems, graceful shutdown, and why a replacement Pod is not the same Pod instance.

Analogy

A Pod is like a temporary work assignment: it is requested, assigned to a workstation, prepared, starts work, becomes available, and eventually finishes or is retired. If the worker is replaced, it is a new assignment even if the label looks the same.

DevOps example

A web Deployment creates a Pod. The scheduler selects a node, the kubelet prepares networking and storage, the runtime starts the container, readiness determines whether it receives Service traffic, and termination hooks allow it to stop cleanly during a rollout.

Learning objectives

  • Differentiate Pod phase, Pod conditions, container states, and kubectl display status.
  • Explain Pending, Running, Succeeded, Failed, and Unknown.
  • Understand scheduling, init containers, probes, restart policies, lifecycle hooks, and graceful termination.
  • Use kubectl to inspect events, conditions, container restarts, and termination reasons.
  • Build and troubleshoot a small Pod and Deployment safely.
Important: A Pod phase is not a complete state machine. Values such as CrashLoopBackOff and Terminating often appear in the kubectl STATUS column, but they are not Pod phase values.

2. Core concepts and terminology

Pod phase

PhaseMeaningTypical investigation
PendingPod is accepted, but one or more containers are not set up to run. Includes waiting for scheduling and image downloads.kubectl describe pod; inspect Events, scheduling, volumes and image pulls.
RunningPod is bound to a node and all containers have been created; at least one container is running or starting/restarting.Check Ready condition, container state, probes and logs. Running does not guarantee traffic readiness.
SucceededAll containers terminated successfully and will not be restarted.Normal for completed Jobs or one-shot tasks.
FailedAll containers have terminated and at least one failed.Inspect exit code, termination reason and logs.
UnknownCluster cannot determine Pod state, often because communication with its node is unavailable.Inspect node health and control-plane/node connectivity.

Remember: Pod phase is a small, defined set. CrashLoopBackOff, ImagePullBackOff, and Terminating are commonly displayed status descriptions, not additional phases.

Container states

StateMeaningExample
WaitingContainer is not yet running; it may be pulling an image or waiting after failure.ImagePullBackOff, CrashLoopBackOff.
RunningContainer process is executing.Long-running NGINX process.
TerminatedContainer process has finished or was stopped; status includes exit code and reason.Exit code 0 for success, non-zero often indicates failure.

Pod conditions

Conditions are Boolean-like checkpoints whose status is True, False, or Unknown. Common conditions include:

  • PodScheduled: a node has been selected.
  • PodReadyToStartContainers: where supported, the Pod sandbox/network setup is ready. Availability depends on Kubernetes version; do not require this condition on every older cluster.
  • Initialized: init containers have completed successfully; Pods without init containers may satisfy this early.
  • ContainersReady: all containers are ready.
  • Ready: Pod can receive traffic from matching Services, subject to any readiness gates.

Pod lifecycle versus container lifecycle

Pod lifecycleContainer lifecycle
Tracks the Pod object and high-level phase/conditions.Tracks each container's Waiting, Running or Terminated state.
Pod is scheduled only once in its lifetime.A container in the same Pod may be restarted depending on restart policy.
A replacement Pod has a new UID and may run on another node.A container restart does not necessarily create a new Pod object.

Restart policy

spec.restartPolicy supports Always, OnFailure, and Never. For Pods managed by a Deployment, restart policy must be Always. Jobs commonly use OnFailure or Never. Restart policy controls container restart behavior within the Pod; it does not make a standalone Pod durable or recreate a deleted Pod.

Init containers and sidecars

Init containers run to completion before application containers start and are useful for setup tasks or waiting for a prerequisite. A failing init container is retried according to the Pod restart policy. Regular sidecar containers run alongside application containers; specialized native sidecar behavior is version-dependent, so this guide uses ordinary init containers for the beginner lab.

Probes

ProbeQuestion it answersFailure effect
StartupHas the application completed startup?After its failure threshold, container is killed and restarted according to policy; liveness/readiness checks are held until startup succeeds.
LivenessShould this container be restarted?Repeated failure causes kubelet to restart the container.
ReadinessShould this Pod receive traffic?Pod becomes not Ready and is removed from matching Service endpoint traffic.
Probe rule: Readiness failure does not itself restart a container. Liveness failure can. Use startup probes for applications that legitimately take a long time to initialize.

Graceful termination and lifecycle hooks

When a Pod is deleted, Kubernetes normally marks it for termination, runs applicable preStop hooks, sends the container's configured stop signal (commonly SIGTERM), waits for the grace period, then forcefully kills remaining processes if needed. The default termination grace period is 30 seconds. Hook execution consumes time from that grace period. Applications should stop accepting new work, finish or safely abandon in-flight requests, and exit promptly.

Controllers and Pod replacement

Pods are ephemeral. A Deployment manages ReplicaSets, and a ReplicaSet creates replacement Pods to maintain the desired count. Kubernetes does not move the same Pod UID to another node. A replacement may have a similar name/labels but a new UID.

3. Lifecycle architecture and workflow

Conceptual overview only. Actual status transitions are asynchronous, and not every Pod follows a single straight line. A Pod may never become Ready, may restart containers, or may terminate before readiness.

  1. Client submits a Pod manifest to the API server.
  2. The scheduler binds the Pod to a node; an unscheduled Pod may remain Pending.
  3. The kubelet prepares the Pod sandbox, networking, volumes and init containers as applicable.
  4. The container runtime pulls images as needed and starts containers.
  5. Probes and conditions determine whether the Pod is Ready to receive traffic.
  6. If a container exits, restart policy and probe behavior influence what happens next.
  7. On deletion, Kubernetes attempts graceful shutdown within the termination grace period.

4. Environment preparation

Use an authorized Kubernetes cluster, Minikube, or kind. This lab does not require EKS or a cloud load balancer. It does need a cluster that can pull the public nginx image. On cloud clusters, worker nodes and image/network traffic may incur cost.

kubectl version --client
kubectl cluster-info
kubectl get nodes
kubectl get namespaces
kubectl config current-context
  • kubectl version --client: checks the client installation.
  • kubectl cluster-info: checks API endpoint connectivity.
  • kubectl get nodes: confirms nodes are registered; check for Ready status.
  • kubectl get namespaces: shows available namespaces.

5. Step-by-step hands-on practice

Exercise 1: Observe a Pod's basic lifecycle

Objective: Create a long-running Pod and inspect its phase and conditions.

Manifest: save as pod-basic.yaml.

apiVersion: v1
kind: Pod
metadata:
  name: lifecycle-web
  namespace: nimbus-pod-lifecycle
  labels:
    app: lifecycle-web
spec:
  containers:
  - name: nginx
    image: nginx:1.27
    ports:
    - name: http
      containerPort: 80

Execute and verify:

kubectl apply -f pod-basic.yaml
kubectl get pod lifecycle-web -n nimbus-pod-lifecycle -w
kubectl get pod lifecycle-web -n nimbus-pod-lifecycle -o wide
kubectl describe pod lifecycle-web -n nimbus-pod-lifecycle
kubectl get pod lifecycle-web -n nimbus-pod-lifecycle -o yaml

Explanation: apiVersion: v1 is the core Pod API. Metadata identifies the Pod and labels it. The container uses an NGINX image. -w watches updates; -o yaml reveals phase, conditions and container status.

Expected result: A typical healthy Pod eventually shows Running and Ready=True. The exact transition timing and condition fields depend on cluster version.

Troubleshooting: If Pending, inspect Events. If image pull fails, verify the image reference and registry access. If Running but not Ready, inspect readiness configuration and container status.

Interview connection: Does Running mean Ready? No. A running process may still fail a readiness probe or readiness gate.

Exercise 2: Observe a Pod reach Succeeded

Objective: Understand a finite task that exits successfully.

Save as pod-success.yaml:

apiVersion: v1
kind: Pod
metadata:
  name: lifecycle-success
  namespace: nimbus-pod-lifecycle
spec:
  restartPolicy: Never
  containers:
  - name: task
    image: busybox:1.36
    command: ["sh", "-c", "echo Task started; sleep 2; echo Task completed; exit 0"]
kubectl apply -f pod-success.yaml
kubectl get pod lifecycle-success -n nimbus-pod-lifecycle -w
kubectl logs lifecycle-success -n nimbus-pod-lifecycle
kubectl get pod lifecycle-success -n nimbus-pod-lifecycle -o yaml

Expected result: After the command exits with code 0, the Pod typically reaches Succeeded. The Never restart policy means the container is not restarted by kubelet.

Troubleshooting: If image pull fails, inspect Pod events. If the Pod is Failed, inspect logs and status.containerStatuses[].state.terminated.

Interview connection: Succeeded is normal for one-shot tasks and Jobs; it is not the expected long-running state for a web server.

Exercise 3: Observe failure and restart behavior

Objective: Learn how a container that exits repeatedly behaves under restart policy Always.

Save as pod-restart.yaml:

apiVersion: v1
kind: Pod
metadata:
  name: lifecycle-restart
  namespace: nimbus-pod-lifecycle
spec:
  restartPolicy: Always
  containers:
  - name: loop
    image: busybox:1.36
    command: ["sh", "-c", "echo starting; exit 1"]
kubectl apply -f pod-restart.yaml
kubectl get pod lifecycle-restart -n nimbus-pod-lifecycle -w
kubectl describe pod lifecycle-restart -n nimbus-pod-lifecycle
kubectl logs lifecycle-restart -n nimbus-pod-lifecycle
kubectl logs lifecycle-restart -n nimbus-pod-lifecycle --previous

Expected result: The container exits non-zero and kubelet attempts to restart it. Repeated rapid failures commonly lead to a displayed CrashLoopBackOff while restart attempts are delayed with backoff. The Pod phase may still be Running because the container is being restarted.

Explanation: --previous reads logs from the previous terminated container instance. It is often more useful than current logs when a process exits immediately.

Troubleshooting: Inspect the command, exit code, previous logs, and Events. A restart loop is a symptom, not the root cause.

Exercise 4: Inspect init-container ordering

Objective: See that application containers wait for successful init-container completion.

Save as pod-init.yaml:

apiVersion: v1
kind: Pod
metadata:
  name: lifecycle-init
  namespace: nimbus-pod-lifecycle
spec:
  initContainers:
  - name: setup
    image: busybox:1.36
    command: ["sh", "-c", "echo setup-start; sleep 3; echo setup-complete"]
  containers:
  - name: app
    image: nginx:1.27
    ports:
    - containerPort: 80
kubectl apply -f pod-init.yaml
kubectl get pod lifecycle-init -n nimbus-pod-lifecycle -w
kubectl describe pod lifecycle-init -n nimbus-pod-lifecycle
kubectl logs lifecycle-init -n nimbus-pod-lifecycle -c setup
kubectl logs lifecycle-init -n nimbus-pod-lifecycle -c app

Expected result: The init container completes first; then the NGINX application container starts. Initialized becomes True after all init containers complete.

Troubleshooting: If the app never starts, check init-container logs and events. An init container that never exits successfully blocks app container startup.

Exercise 5: Observe readiness and liveness probes

Objective: Distinguish readiness from liveness in a running workload.

Save as deployment-probes.yaml:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: lifecycle-probes
  namespace: nimbus-pod-lifecycle
spec:
  replicas: 1
  selector:
    matchLabels:
      app: lifecycle-probes
  template:
    metadata:
      labels:
        app: lifecycle-probes
    spec:
      containers:
      - name: nginx
        image: nginx:1.27
        ports:
        - name: http
          containerPort: 80
        startupProbe:
          httpGet:
            path: /
            port: http
          periodSeconds: 2
          failureThreshold: 15
        readinessProbe:
          httpGet:
            path: /
            port: http
          periodSeconds: 5
          failureThreshold: 2
        livenessProbe:
          httpGet:
            path: /
            port: http
          periodSeconds: 10
          failureThreshold: 3
        resources:
          requests:
            cpu: 50m
            memory: 64Mi
          limits:
            cpu: 250m
            memory: 128Mi
kubectl apply -f deployment-probes.yaml
kubectl rollout status deployment/lifecycle-probes -n nimbus-pod-lifecycle
kubectl get pods -n nimbus-pod-lifecycle
kubectl describe pod -l app=lifecycle-probes -n nimbus-pod-lifecycle

Explanation: HTTP GET checks path / on the named port http. Startup probe allows time for initialization; readiness decides traffic eligibility; liveness decides whether to restart an unhealthy container. The example endpoint suits NGINX; do not copy this path blindly for another application.

Expected result: Pod eventually becomes Ready if NGINX starts normally. Do not intentionally break liveness on a shared or production cluster.

Troubleshooting: Probe failures appear in Events. Verify path, port, response code, startup delay and application startup time.

Exercise 6: Watch graceful termination

Objective: Understand termination grace period and a preStop hook.

Save as pod-termination.yaml:

apiVersion: v1
kind: Pod
metadata:
  name: lifecycle-termination
  namespace: nimbus-pod-lifecycle
spec:
  terminationGracePeriodSeconds: 20
  containers:
  - name: web
    image: nginx:1.27
    lifecycle:
      preStop:
        exec:
          command: ["/bin/sh", "-c", "echo preStop hook started; sleep 5"]
    ports:
    - containerPort: 80
kubectl apply -f pod-termination.yaml
kubectl wait --for=condition=Ready pod/lifecycle-termination -n nimbus-pod-lifecycle --timeout=120s
kubectl delete pod lifecycle-termination -n nimbus-pod-lifecycle
kubectl get pod lifecycle-termination -n nimbus-pod-lifecycle

Expected result: Deletion is requested; the Pod normally disappears after the hook and shutdown sequence. Once deleted, the Pod cannot be inspected with describe; use events or a separate observation terminal if desired.

Important: The preStop hook runs during termination and consumes part of the grace period. Do not rely on logs remaining available after the Pod object is removed.

Exercise 7: Compare a standalone Pod with a Deployment-managed Pod

Objective: Prove that controllers replace Pods but a standalone Pod is not automatically recreated when deleted.

kubectl delete pod lifecycle-web -n nimbus-pod-lifecycle
kubectl get pod lifecycle-web -n nimbus-pod-lifecycle

kubectl get pods -n nimbus-pod-lifecycle -l app=lifecycle-probes
kubectl delete pod -l app=lifecycle-probes -n nimbus-pod-lifecycle
kubectl get pods -n nimbus-pod-lifecycle -l app=lifecycle-probes

Expected result: The standalone Pod is not recreated by a controller. The Deployment's ReplicaSet should create a replacement Pod to maintain one replica.

Troubleshooting: If the replacement does not become Ready, inspect Deployment, ReplicaSet and Pod events; controller replacement does not guarantee successful startup.

6. Complete practical example: lifecycle-aware web workload

Requirement

Run one NGINX replica with a startup probe, readiness probe, liveness probe and resource settings. Observe rollout readiness, inspect conditions, and observe how a Deployment replaces a deleted Pod.

Save as pod-lifecycle-complete.yaml

apiVersion: v1
kind: Namespace
metadata:
  name: nimbus-pod-lifecycle
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: lifecycle-web
  namespace: nimbus-pod-lifecycle
spec:
  replicas: 1
  selector:
    matchLabels:
      app: lifecycle-web
  template:
    metadata:
      labels:
        app: lifecycle-web
    spec:
      terminationGracePeriodSeconds: 30
      containers:
      - name: nginx
        image: nginx:1.27
        ports:
        - name: http
          containerPort: 80
        startupProbe:
          httpGet:
            path: /
            port: http
          periodSeconds: 2
          failureThreshold: 15
        readinessProbe:
          httpGet:
            path: /
            port: http
          periodSeconds: 5
          failureThreshold: 2
        livenessProbe:
          httpGet:
            path: /
            port: http
          periodSeconds: 10
          failureThreshold: 3
        resources:
          requests:
            cpu: 50m
            memory: 64Mi
          limits:
            cpu: 250m
            memory: 128Mi
---
apiVersion: v1
kind: Service
metadata:
  name: lifecycle-web
  namespace: nimbus-pod-lifecycle
spec:
  type: ClusterIP
  selector:
    app: lifecycle-web
  ports:
  - name: http
    port: 80
    targetPort: http

Apply and validate

kubectl apply -f pod-lifecycle-complete.yaml
kubectl rollout status deployment/lifecycle-web -n nimbus-pod-lifecycle --timeout=180s
kubectl get deployment,replicaset,pods,service -n nimbus-pod-lifecycle
kubectl get pods -n nimbus-pod-lifecycle -l app=lifecycle-web -o yaml
kubectl get endpointslices -n nimbus-pod-lifecycle
kubectl describe deployment lifecycle-web -n nimbus-pod-lifecycle

Test traffic from a temporary in-cluster client if registry access is available:

kubectl run curl-check --image=curlimages/curl:8.10.1 --restart=Never -n nimbus-pod-lifecycle --command -- sh -c 'sleep 3600'
kubectl wait --for=condition=Ready pod/curl-check -n nimbus-pod-lifecycle --timeout=120s
kubectl exec curl-check -n nimbus-pod-lifecycle -- curl -I --max-time 5 http://lifecycle-web

Observe replacement and rollout

kubectl get pods -n nimbus-pod-lifecycle -l app=lifecycle-web -w
# In another terminal, list the Pod name:
kubectl get pods -n nimbus-pod-lifecycle -l app=lifecycle-web
# Replace POD_NAME with the actual Pod name shown above:
kubectl delete pod POD_NAME -n nimbus-pod-lifecycle
kubectl rollout status deployment/lifecycle-web -n nimbus-pod-lifecycle
kubectl get pods -n nimbus-pod-lifecycle -l app=lifecycle-web -o wide

Placeholder: Replace POD_NAME with the actual Pod name printed by the preceding command; do not type the placeholder literally.

How the components work together

  1. The Deployment declares one desired replica and creates a ReplicaSet.
  2. The ReplicaSet creates a Pod with the declared template.
  3. The kubelet starts the NGINX container; startup probe gates the other probes until startup succeeds.
  4. Readiness success makes the Pod eligible for Service traffic.
  5. If the Pod is deleted, the ReplicaSet creates a new Pod with a different UID.
  6. The Service keeps a stable in-cluster name while its endpoint set changes.

Common failures

  • Pending: inspect scheduling events, resource requests, node taints and volume setup.
  • ImagePullBackOff: inspect image reference and registry access.
  • Probe failures: confirm NGINX actually responds on / at port 80.
  • No endpoints: compare Service selector with Pod labels and check Pod Ready condition.
  • Restart loop: inspect current and previous logs plus termination reason.

Cleanup: after confirming the namespace contains only your lab resources, use the scoped cleanup in Section 12 or delete the dedicated lab namespace.

8. Best practices

  • Use a controller for durable workloads. Deployments replace deleted or failed Pods; a standalone Pod does not have a controller to recreate it.
  • Set realistic resource requests and limits. Scheduling and OOM behavior depend on them. Avoid arbitrary production values without measurements.
  • Choose probes for the actual application. Readiness controls traffic eligibility, liveness detects conditions that warrant restart, and startup protects slow initialization.
  • Avoid overly aggressive liveness checks. A transient slowdown can cause restart loops. Tune initial delay, period, timeout and failure threshold from observed startup/response behavior.
  • Implement graceful shutdown. Ensure the process handles its stop signal, stops taking new work, and drains in-flight requests within the grace period.
  • Keep init containers finite and observable. Log progress, use bounded retry/backoff in scripts, and avoid waiting forever without a clear failure signal.
  • Use namespaces and labels consistently. They improve resource discovery and safe operational targeting; namespaces alone are not complete security boundaries.
  • Inspect evidence before changing settings. Use events, current/previous logs, termination reasons, conditions and metrics to distinguish image, scheduling, app, probe and node failures.
  • Plan rollout capacity. Rolling updates may temporarily require extra capacity. Check availability and rollout status before declaring success.
  • Protect sensitive data. Do not put credentials in command history, logs, images or manifests committed to source control.
  • Test termination behavior. Validate preStop hooks, signal handling, and grace-period assumptions in a non-production environment before relying on them.

9. Interview preparation

Search the questions and expand each answer to self-test.

Level 1 — Basic questions

1. What is the Pod lifecycle?
The stages and state changes a Pod experiences from creation through running, completion, failure or deletion, tracked through phase, conditions and container states.
2. What are the official Pod phases?
Pending, Running, Succeeded, Failed and Unknown. Do not treat CrashLoopBackOff or Terminating as phases.
3. What does Pending mean?
The Pod has been accepted but one or more containers are not set up to run. It can include scheduling, image downloads, or preparation work. Inspect Pod Events to distinguish causes.
4. Does Running mean Ready?
No. Running describes container creation and execution state at a high level. Readiness probes and readiness gates determine whether the Pod is considered ready to serve traffic.
5. What is Succeeded?
All containers terminated successfully and will not be restarted. It is expected for finite tasks such as Jobs.
6. What is CrashLoopBackOff?
A displayed status indicating repeated container start/failure cycles with backoff between restart attempts. It is not a Pod phase. Inspect previous logs, exit reason and events.
7. What is the difference between Pod and container state?
Pod phase summarizes the Pod at a high level; each container separately has Waiting, Running or Terminated state and associated details.
8. What does a readiness probe do?
It determines whether a container/Pod should receive traffic. Failure makes the Pod not Ready; it does not directly restart the container.
9. What does a liveness probe do?
It detects when a container should be restarted. Repeated liveness probe failures cause kubelet to restart the container.
10. What is a startup probe?
It checks whether an application has completed startup and delays liveness/readiness checks until it succeeds, helping slow-starting applications.
11. What are init containers?
Containers that run to completion before application containers start. They are useful for setup and prerequisite checks.
12. What is the default termination grace period?
Normally 30 seconds unless configured otherwise. Kubernetes uses this time for graceful shutdown before forcefully killing remaining processes.

Level 2 — Intermediate questions

13. Why is Pod phase not a complete state machine?
It is a high-level summary only. Conditions, container states, restart counts, events and reasons provide more detail; do not infer all behavior from phase alone.
14. What is the difference between restartPolicy Always and a Deployment?
Restart policy controls restarting containers inside a Pod. A Deployment/ReplicaSet controls Pod replicas and replacement of Pod objects. Restart policy alone does not recreate a deleted standalone Pod.
15. What happens when a Deployment-managed Pod is deleted?
Its ReplicaSet normally creates a replacement to meet desired replicas. The replacement has a new UID and may be scheduled on a different node.
16. How do you investigate a restart loop?
Run describe for Events and termination reason, check current and previous logs, inspect exit code and lastState, and verify probes/configuration. Then fix the evidenced cause.
17. What is the difference between readiness and liveness failure?
Readiness failure removes the Pod from ready Service endpoints. Liveness failure can restart the container after the failure threshold is exceeded.
18. Why use a startup probe?
It prevents liveness checks from restarting a slow-starting application before it has had enough time to initialize. After startup succeeds, liveness and readiness checks proceed.
19. Does a preStop hook replace signal handling?
No. It is an action invoked before container termination, and its duration counts against the grace period. The application should still handle its stop signal and exit cleanly.
20. How can you inspect Pod conditions?
Use kubectl get pod POD -n NS -o yaml and inspect status.conditions, containerStatuses, restart count and last termination state.
21. What does Unknown usually suggest?
The control plane cannot determine the Pod state, commonly because it cannot communicate with the node. Inspect node readiness and node/kubelet connectivity.
22. What is the difference between a Pod replacement and a container restart?
A container restart occurs inside the same Pod object and UID. A replacement is a new Pod object with a new UID, commonly created by a controller.
23. Why can an init container block an application container?
Application containers do not start until all init containers complete successfully. A stuck command, unavailable dependency or image-pull failure can prevent initialization.
24. What happens if a readiness gate condition is absent?
The custom condition is treated as False, so the Pod does not become Ready until the required readiness gate conditions are True and all containers are ready.

Level 3 — Real-time scenario questions

25. Pod is Pending for five minutes. What is your investigation?
Commands: kubectl describe pod POD -n nimbus-pod-lifecycle, kubectl get nodes, and kubectl get events -n nimbus-pod-lifecycle --sort-by=.metadata.creationTimestamp. Read Events for insufficient resources, taints, node selectors, image pulls or volume setup. Pending does not identify one cause; use the event message to choose the next check. Verify after correcting the specific issue.
26. Pod is Running but Service traffic fails. Why?
Inspect Ready condition and readiness probe Events, then check Service endpoints. Use kubectl describe pod POD -n nimbus-pod-lifecycle and kubectl get endpointslices -n nimbus-pod-lifecycle. Possible causes include readiness failure, wrong Service selector, wrong target port, application listener failure or network policy. Verify with a request through the Service after fixing the evidenced cause.
27. Container enters CrashLoopBackOff immediately after deployment.
Run kubectl logs POD -n nimbus-pod-lifecycle --previous and kubectl describe pod POD -n nimbus-pod-lifecycle. Inspect exit code, command/arguments, missing configuration, permissions, OOMKilled and probe events. Correct the root cause, then watch restart count and readiness. Do not assume every loop is a liveness problem.
28. Init container keeps restarting and app container never starts.
Use kubectl describe pod POD -n nimbus-pod-lifecycle and kubectl logs POD -c INIT_CONTAINER -n nimbus-pod-lifecycle --previous. Check whether the command exits, dependencies resolve, credentials exist and image pulls succeed. Init containers must complete successfully before app containers start.
29. A liveness probe causes repeated restarts during startup.
Check probe failure Events and application startup duration. If the app legitimately starts slowly, add/tune a startup probe and ensure the liveness endpoint tests a condition that warrants restart. Avoid simply weakening readiness, since readiness protects traffic routing.
30. Pods remain Terminating beyond the grace period.
Inspect describe output, preStop hooks, finalizers, node connectivity and application shutdown behavior. Hooks consume grace-period time. If a node is unreachable or a finalizer blocks deletion, coordinate with the platform owner. Force deletion can leave processes running on an unreachable node and should not be a reflexive first step.
31. A Pod shows OOMKilled. What evidence is needed?
Inspect kubectl describe pod POD -n nimbus-pod-lifecycle, termination state, memory limit and available metrics. Consider memory leak, workload spike or undersized limit. Tune resources based on evidence and node capacity; raising limits blindly can affect other workloads.
32. A standalone Pod disappears after node failure. How do you prevent this?
For a long-running stateless application, use a Deployment with an appropriate replica count. The controller creates replacement Pods when needed. Validate scheduling capacity, topology and application readiness; no controller guarantees immediate recovery if the cluster lacks capacity.
33. A completed task Pod is Succeeded. Is it broken?
Not necessarily. If the process is designed to finish, Succeeded is the expected terminal phase. Use a Job for managed finite tasks and inspect logs/exit code to confirm expected completion.
34. Pod phase is Unknown and its node is NotReady.
Check kubectl get nodes, kubectl describe node NODE_NAME, and recent cluster events. The control plane may have lost contact with the node. Investigate kubelet/network/node health with the platform team; avoid assuming the container itself caused the problem.

10. Practice assignments

Beginner exercises

  1. Create a Pod running NGINX and record phase, Ready condition and node. Verify: kubectl get pod -o wide and kubectl get pod -o yaml. Hint: inspect status.conditions.
  2. Create a finite BusyBox Pod that exits 0. Expected: Succeeded. Hint: use restartPolicy: Never and an explicit command.
  3. Create a finite Pod that exits 1. Compare its phase and termination details with the successful Pod. Hint: inspect logs and exit code.
  4. Add an init container that sleeps briefly before the app starts. Verify: init logs and Initialized condition.
  5. Explain the difference between Waiting, Running and Terminated by examining containerStatuses.

Modification and troubleshooting exercises

  1. Deploy NGINX with readiness and liveness probes; verify readiness and inspect probe Events.
  2. Change the readiness path to a path that returns 404 in your isolated lab. Observe readiness change and Service endpoint impact; then restore /.
  3. Run a container that exits repeatedly and capture current and previous logs.
  4. Delete a Deployment-managed Pod and record the old/new Pod UIDs. Expected: replacement has a different UID.
  5. Set a longer termination grace period and observe how a preStop hook affects deletion duration.

Scenario challenges

  1. Startup failure: A new application Pod stays Pending. Identify the actual cause from Events and propose a fix.
  2. Readiness failure: The Pod is Running but absent from Service endpoints. Determine whether the cause is readiness, selector, or port configuration.
  3. Unclean shutdown: Requests are dropped during a rollout. Propose and test a graceful shutdown strategy using readiness, signal handling and termination grace period.

11. Quick revision and cheat sheet

Essential facts

  • Official Pod phases: Pending, Running, Succeeded, Failed, Unknown.
  • CrashLoopBackOff and ImagePullBackOff are displayed status descriptions, not phases.
  • Running does not guarantee Ready.
  • Readiness controls traffic eligibility; liveness can trigger a restart; startup gates the other probes during initialization.
  • Init containers complete before application containers start.
  • Pod restart policy controls container restart behavior; controllers replace Pod objects.
  • Replacement Pods have new UIDs; a Pod is not rescheduled to another node as the same Pod instance.
  • Graceful termination uses hooks/signals and a grace period; default is normally 30 seconds.

Common commands

kubectl get pods -n nimbus-pod-lifecycle -o wide
kubectl get pod POD_NAME -n nimbus-pod-lifecycle -o yaml
kubectl describe pod POD_NAME -n nimbus-pod-lifecycle
kubectl logs POD_NAME -n nimbus-pod-lifecycle
kubectl logs POD_NAME -n nimbus-pod-lifecycle --previous
kubectl logs POD_NAME -c CONTAINER_NAME -n nimbus-pod-lifecycle
kubectl get events -n nimbus-pod-lifecycle --sort-by=.metadata.creationTimestamp
kubectl get deployment,replicaset,pods -n nimbus-pod-lifecycle

Placeholders: Replace POD_NAME and CONTAINER_NAME with the actual names shown by kubectl get pods and kubectl describe pod.
