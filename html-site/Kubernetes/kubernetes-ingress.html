Kubernetes Ingress

Understand how HTTP/HTTPS traffic enters a Kubernetes cluster, follows host and path rules, and reaches the correct application Service. Includes a copy-ready lab, EKS notes, diagnostic flows, and interview practice.

02 · What is Kubernetes Ingress?

Ingress is a Kubernetes API resource that defines rules for routing HTTP and HTTPS requests from outside the cluster to Services inside the cluster. Typical rules match a hostname, URL path, or both.

Essential distinction: an Ingress object is configuration, not a proxy by itself. An Ingress Controller must be installed and watching the relevant Ingress resources to implement those rules. Kubernetes documentation now recommends considering Gateway API for new designs; the Ingress API remains supported but is frozen.

Analogy: an office reception desk

A visitor gives the receptionist a department or destination. The receptionist directs them to the right team. Ingress rules are the routing instructions; the controller/load balancer is the system that enforces them.

Real application example

One domain can route shop.example.com/ to a storefront Service and shop.example.com/api to an API Service, rather than exposing each application separately with its own public endpoint.

Common capabilities

  • Host-based virtual hosting.
  • Path-based routing.
  • TLS termination when configured with a suitable controller and certificate.
  • Controller-specific features such as redirects, authentication, or advanced traffic controls.

Ingress is primarily for HTTP/HTTPS. For arbitrary TCP/UDP services, consider an appropriate Service type or a controller-specific capability.

03 · Architecture and request flow

  1. Client resolves the hostname using DNS and connects to the published entry point.
  2. The configured load balancer or Ingress data-plane receives the HTTP/HTTPS request.
  3. Host and path rules select a backend Service (controller-specific behavior applies).
  4. The Service's endpoint information identifies eligible Pods.
  5. The application responds; the response returns through the established network path.

Interview shortcut: Ingress is a set of HTTP/HTTPS routing rules. A controller implements them. A Service provides stable access to Pods. These are complementary objects, not substitutes for one another.

05 · Prepare the environment

First verify that your current context points to the intended cluster. Commands below inspect state; they do not create cloud resources.

kubectl version --client
kubectl config current-context
kubectl cluster-info
kubectl get nodes
kubectl get namespaces

Local cluster note: kind and Minikube do not necessarily include an Ingress controller by default. Install and enable a controller appropriate to your local setup before expecting an Ingress rule to route traffic. A manifest can be accepted by the API even when no controller is fulfilling it.

06 · Hands-on lab: two web apps behind Ingress

Controller-neutral manifest This lab deploys two small web apps and creates one Ingress with path-based routing. It uses the common ingressClassName: nginx convention, so it assumes an NGINX Ingress Controller with class nginx is installed. If your controller uses another class, change the field to match your environment.

Run this in a test namespace. Do not apply these manifests to a production namespace without reviewing image policy, resource requests/limits, TLS, network exposure, and controller-specific settings.

Target architecture

Exercise 1 — create the namespace and applications

Create ingress-lab.yaml with the following complete manifests.

apiVersion: v1
kind: Namespace
metadata:
  name: ingress-lab
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: ingress-lab
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: web
        image: nginx:1.27
        ports:
        - name: http
          containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: web-svc
  namespace: ingress-lab
spec:
  type: ClusterIP
  selector:
    app: web
  ports:
  - name: http
    port: 80
    targetPort: http
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  namespace: ingress-lab
spec:
  replicas: 2
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api
    spec:
      containers:
      - name: api
        image: hashicorp/http-echo:1.0.0
        args: ["-text=Hello from the API demo"]
        ports:
        - name: http
          containerPort: 5678
---
apiVersion: v1
kind: Service
metadata:
  name: api-svc
  namespace: ingress-lab
spec:
  type: ClusterIP
  selector:
    app: api
  ports:
  - name: http
    port: 80
    targetPort: http

What to notice: each Service selector must match its Deployment's Pod labels. The API container listens on 5678, while its Service exposes port 80 and forwards to the named container port http. The web Service forwards to NGINX port 80.

Exercise 2 — apply and verify backend resources

kubectl apply -f ingress-lab.yaml
kubectl -n ingress-lab rollout status deployment/web
kubectl -n ingress-lab rollout status deployment/api
kubectl -n ingress-lab get deploy,pods,svc
kubectl -n ingress-lab get endpointslices

Expected state: two ready replicas for each Deployment and Services with endpoint addresses. Exact Pod names, IPs, and timing vary. If a rollout fails, inspect kubectl -n ingress-lab describe pod POD_NAME and kubectl -n ingress-lab logs deploy/api.

Exercise 3 — add the Ingress rule

Append this to the same file, or save as ingress.yaml.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: demo-ingress
  namespace: ingress-lab
spec:
  ingressClassName: nginx
  rules:
  - http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: api-svc
            port:
              number: 80
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web-svc
            port:
              number: 80
kubectl apply -f ingress.yaml
kubectl -n ingress-lab get ingress
kubectl -n ingress-lab describe ingress demo-ingress
kubectl get ingressclass

This example uses a hostless rule so it can be tested by IP/hostname with a suitable controller setup. In shared clusters, explicit hostnames are usually easier to manage. Path behavior can vary with controller features; this manifest does not configure a rewrite.

Exercise 4 — test the route

Find the controller's external address using the controller documentation and service status. For example, if its Service is a LoadBalancer:

kubectl get svc -A
# Set the address from your controller's published endpoint:
export INGRESS_HOST="YOUR_INGRESS_ADDRESS"
curl -i "http://${INGRESS_HOST}/"
curl -i "http://${INGRESS_HOST}/api"
Expected behavior: / should return the NGINX welcome page; /api should return text similar to Hello from the API demo. This is expected behavior based on the manifests, not output from an executed cluster.

Exercise 5 — verify Service endpoints directly

kubectl -n ingress-lab get svc
kubectl -n ingress-lab get endpointslices
kubectl -n ingress-lab port-forward svc/api-svc 8080:80
# In a second terminal:
curl -i http://127.0.0.1:8080/

Port-forwarding tests the Service-to-Pod path and helps separate backend issues from Ingress/controller issues.

07 · Amazon EKS: Ingress with an AWS Application Load Balancer

On EKS, a common pattern is to install the AWS Load Balancer Controller. It watches Kubernetes resources and provisions AWS load-balancing resources. With the controller configured for it, a Kubernetes Ingress typically provisions an Application Load Balancer (ALB), suitable for HTTP/HTTPS Layer 7 routing.

Typical prerequisites

  • A working EKS cluster and supported AWS Load Balancer Controller installation.
  • Correct IAM permissions for the controller and the required service account/role configuration.
  • Subnets in suitable Availability Zones, with the tags and routing required for public or internal load balancers.
  • Security groups and network routes that allow the intended traffic.
  • A controller-compatible IngressClass and annotations.
Cost and safety: creating an ALB can incur AWS charges. Use a training environment and remove the Ingress after the lab; wait for the controller to clean up its AWS resources. Do not install or upgrade the controller by copying a partial command. Follow the current official AWS setup guide for your EKS version and IAM model.

Illustrative ALB Ingress manifest

This example assumes the AWS Load Balancer Controller is already installed and configured, and that the backend Service exists in the same namespace. Validate your environment's subnet, security, target-type, and class requirements before applying.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-alb
  namespace: ingress-lab
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
spec:
  ingressClassName: alb
  rules:
  - http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web-svc
            port:
              number: 80
kubectl apply -f web-alb.yaml
kubectl -n ingress-lab describe ingress web-alb
kubectl -n ingress-lab get ingress -w

The ADDRESS may take time to populate while the controller reconciles AWS resources. A blank address is a diagnostic starting point, not proof of a single specific cause.

Flow B — backend returns errors

  1. Confirm the Ingress rule matches the request host and path.
  2. Confirm the backend Service exists in the same namespace and the named port is valid.
  3. Confirm EndpointSlices contain ready endpoints.
  4. Test the Service with port-forwarding or an in-cluster client.
  5. If Service testing succeeds but Ingress fails, inspect controller logs and controller-specific routing behavior.

09 · Best practices

Prefer

  • Explicit ingressClassName when multiple controllers exist.
  • Use TLS for sensitive traffic and manage certificate renewal.
  • Keep Service selectors and named ports consistent.
  • Restrict who can create or modify public routing rules.
  • Use health checks/readiness correctly and observe controller logs/events.
  • Review controller-specific annotations before using them.
  • Use DNS names and explicit hosts for predictable routing.

Avoid

  • Assuming an Ingress object automatically creates routing without a controller.
  • Assuming all controllers support identical annotations or rewrite behavior.
  • Publishing internal services accidentally with a public scheme.
  • Using broad wildcard hosts without ownership and security review.
  • Deleting shared Ingress resources or controller components casually.
  • Assuming a successful kubectl apply means requests work end-to-end.

Before vs after

Ingress has no class and multiple controllers exist.Set spec.ingressClassName to the intended class.

Only tests kubectl apply.Verify ingress address, backend endpoints, and actual HTTP response.
Public ALB created without checking cost/scope.Confirm public vs internal scheme, security controls, ownership, and cleanup.

10 · Interview preparation

Try answering each question before expanding the answer. Use the search box to filter questions by keyword.

Basic 1. What is Kubernetes Ingress?

An API resource defining HTTP/HTTPS routing rules from outside the cluster to backend Services, commonly using hostnames and paths.

Basic 2. Does an Ingress work by itself?

No. A compatible Ingress Controller must be running and configured to fulfill it.

Basic 3. What is an Ingress Controller?

A controller that watches Ingress-related resources and configures a proxy/load balancer or cloud load balancer to implement the desired routing.

Basic 4. What is IngressClass?

A resource that identifies the controller implementation intended to handle an Ingress. The Ingress refers to it with spec.ingressClassName.

Basic 5. What is host-based routing?

Routing based on the HTTP Host header, for example api.example.com to one Service and shop.example.com to another.

Basic 6. What is path-based routing?

Routing based on the request URI path, for example /api to an API Service and / to a web Service.

Basic 7. What does pathType Prefix mean?

It matches a path by URL path-element prefix according to Kubernetes Ingress path matching rules; it is not an arbitrary raw string-prefix rule.

Basic 8. Which API version should a new Ingress manifest use?

networking.k8s.io/v1.

Basic 9. Can Ingress expose raw TCP or UDP ports?

Standard Ingress is designed for HTTP/HTTPS. Use an appropriate Service type or controller-specific features for other protocols.

Basic 10. How do you inspect an Ingress?

Use kubectl get ingress, kubectl describe ingress NAME, and inspect controller status/logs as needed.

Intermediate 11. Why can an Ingress exist without a working endpoint?

Kubernetes can store the configuration even if no controller fulfills it, or if the controller cannot provision/configure its data plane.

Intermediate 12. How do Ingress and Service relate?

Ingress routes requests to a Service backend. The Service provides a stable endpoint and selects Pods through labels/selectors.

Intermediate 13. What causes an empty Service EndpointSlice?

Common causes include mismatched selectors, absent Pods, Pods not Ready, or a workload that failed to start. Inspect Pod labels, readiness, and events.

Intermediate 14. What is TLS termination?

The TLS connection is decrypted at a configured endpoint such as an ingress proxy or ALB, which then forwards traffic according to the controller's configuration.

Intermediate 15. How would you test a backend without Ingress?

Use kubectl port-forward svc/SERVICE LOCAL:REMOTE or a temporary in-cluster client. This separates backend issues from Ingress routing issues.

Intermediate 16. What is the difference between a 404 and a 503 here?

A 404 often indicates a route/host/path mismatch or default backend response. A 503 often points to unavailable backends, but verify the specific controller and logs.

Intermediate 17. Why specify ingressClassName?

It directs the Ingress to the intended controller, especially when multiple controllers exist or there is no default class.

Intermediate 18. How does AWS ALB differ from a generic NGINX Ingress setup?

The AWS Load Balancer Controller can provision and configure an AWS ALB from Ingress resources. NGINX-style setups use the chosen controller's own data-plane and exposure method. Annotations and operational requirements differ.

Intermediate 19. What is the difference between ALB and NLB on EKS?

ALB is Layer 7 and commonly used for HTTP/HTTPS Ingress. NLB is Layer 4 and commonly used for Service type LoadBalancer with TCP/UDP use cases. Verify current AWS/controller behavior for the chosen setup.

Intermediate 20. Is Ingress the preferred API for every new Kubernetes networking design?

No. The Ingress API is stable but frozen; Kubernetes recommends evaluating Gateway API for new designs that need its richer extensibility and role model.

Scenario 21. The Ingress has no ADDRESS. What do you do?

Inspect Ingress events and class, confirm the controller is healthy, then inspect controller logs and any provider prerequisites. On EKS, check IAM, subnet discovery/tags, security groups, and controller configuration before assuming a single cause.

Scenario 22. The browser shows 404, but the Pods are healthy. Why?

Check host header, path and pathType, IngressClass, and controller logs. Try a request matching the configured host/path. If host rules exist, an IP-only request may not match.

Scenario 23. The Ingress returns 503. What is your sequence?

Check the backend Service and port, inspect EndpointSlices, confirm Pod readiness, test the Service directly, then inspect controller-to-backend connectivity and logs.

Scenario 24. One path works and another fails.

Compare path definitions, ordering and controller-specific matching rules; verify both backend Services, port numbers, and EndpointSlices. Test the exact failing URL.

Scenario 25. The ALB is created but targets are unhealthy.

Inspect target group health reason, security groups/routes, target type, Pod/service ports, health-check path and success codes. Confirm the app returns the expected response on the health-check endpoint.

Scenario 26. You need two hostnames to route to separate apps.

Define two host rules under the Ingress (or separate Ingress objects if appropriate), map each host to its backend Service, configure DNS, and verify Host-header behavior.

Scenario 27. How do you add HTTPS?

Configure a certificate and TLS settings according to the selected controller. For generic Ingress this often uses spec.tls and a TLS Secret; on EKS ALB, certificate ARN annotations and listener configuration are common. Follow the controller's current docs.

Scenario 28. A deployment is successful, but requests still fail.

Deployment success only verifies workload rollout. Test Pod readiness, Service endpoints, Ingress rule matching, controller health, external DNS/network path, and actual HTTP response separately.

Scenario 29. How do you prevent accidentally exposing an internal app?

Review public/internal load-balancer scheme, host rules, security groups, authentication/network controls, RBAC, and who can modify Ingress resources. Test exposure from the intended network boundary.

Scenario 30. Would you choose Ingress or Gateway API for a new platform?

Compare required features, controller support, team familiarity, and migration constraints. Since Ingress is frozen and Kubernetes recommends Gateway API for new designs, evaluate Gateway API if its implementation and features meet requirements.

11 · Practice assignments

Beginner exercises

  1. Create the namespace and deploy the two backend applications from the lab.
  2. Change the web Deployment to three replicas and verify rollout status.
  3. Change the API demo response text and redeploy it.
  4. Inspect the IngressClass and identify which controller handles the lab.
  5. Use port-forwarding to test each Service independently.

Modification and troubleshooting exercises

  1. Break a Service selector intentionally in a disposable namespace; observe EndpointSlices and repair it.
  2. Change the backend Service port to an incorrect value; inspect the failure and fix it.
  3. Add an explicit host rule and test with a matching Host header using curl -H 'Host: demo.example.test' http://ADDRESS/.
  4. Make the Ingress class incorrect, observe the symptoms, and restore the correct class.
  5. Test a path not present in the rules and document the observed response.

Scenario challenges

  1. Design host-based routing for app.example.test and api.example.test.
  2. For EKS, document the prerequisites and verification steps for an internal ALB rather than an internet-facing ALB.
  3. Create a diagnostic runbook for an ALB with unhealthy targets, including the commands and AWS-side checks you would perform.
Hints and solution approach
  • For exercises 1–5, use the complete lab manifests and verify Deployments, Services, and EndpointSlices.
  • For selector/port failures, compare Deployment Pod labels, Service selectors, Service port, and targetPort.
  • For host-based routing, define host under an Ingress rule and test the exact Host header. DNS is not required to test a Host header locally.
  • For EKS challenges, consult the AWS Load Balancer Controller documentation for IAM, subnet discovery, scheme, target type, health checks, and security requirements.

13 · Cleanup and resource lifecycle

# Review what is in the lab namespace first
kubectl get all,ingress -n ingress-lab

# Delete lab namespace and all namespaced lab objects
kubectl delete namespace ingress-lab

# Verify the namespace is gone
kubectl get namespace ingress-lab
Shared cluster warning: do not delete the controller, shared IngressClass, or other teams' namespaces. If you created an EKS ALB Ingress, verify the associated AWS load balancer and target groups are removed after the controller reconciles. Manually created cloud resources may need separate cleanup.
