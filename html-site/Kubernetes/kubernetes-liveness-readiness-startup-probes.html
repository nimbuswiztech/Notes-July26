Kubernetes Liveness, Readiness & Startup Probes

Learn how Kubernetes checks whether a container has started, is able to serve requests, and should be restarted. This hands-on guide includes self-contained diagrams, practical YAML, failure demonstrations, debugging workflows, revision notes, and interview practice.

1. Introduction

A Kubernetes probe is a diagnostic performed by the node's kubelet to learn something about a container. A probe can run a command inside the container or make a network request to the container. Kubernetes uses the result to decide whether to restart a container or treat its Pod as ready for traffic.

Simple analogy

Think of a hospital: a startup check asks, “Has the patient finished waking up after surgery?”; a readiness check asks, “Can the patient safely receive visitors?”; a liveness check asks, “Is the patient in a state that requires a restart of treatment?”

Practical DevOps example

A Java API takes 45 seconds to warm caches, later temporarily rejects requests when overloaded, and may occasionally deadlock. Startup gives it time to initialize, readiness keeps it out of traffic while unavailable, and liveness restarts it if it becomes irrecoverably stuck.

Why probes matter

A process can exist without being ready. A container can also remain running while the application is deadlocked. Probes give Kubernetes signals beyond “the process has a PID.”

Learning objectives

  • Explain the separate jobs of startup, readiness, and liveness probes.
  • Configure HTTP, TCP, and exec probe mechanisms, and understand where gRPC applies.
  • Set sensible probe timing, thresholds, and timeouts.
  • Observe readiness changes, endpoint membership, and container restarts.
  • Diagnose false failures, slow starts, bad paths, and over-aggressive checks.
  • Apply probe design safely in Deployments and shared environments.
Remember this first: a failed readiness probe normally makes the Pod unready; it does not restart the container. A failed liveness or startup probe, after its failure threshold is reached, causes the kubelet to terminate and restart the affected container according to the Pod's restart policy.

2. Core concepts and terminology

The three probe types

ProbeQuestion it answersWhat happens on repeated failure?Typical use
StartupHas the application completed startup?Kubelet kills/restarts the container after failureThreshold failures. Liveness and readiness checks do not run until startup succeeds.Slow Java/.NET applications, migrations or cache warm-up.
LivenessIs the running application still making progress, or is it irrecoverably stuck?Kubelet kills/restarts the affected container.Deadlock or unrecoverable internal failure detection.
ReadinessCan this container accept traffic right now?Container continues running; Pod becomes not Ready and is excluded from normal Service endpoints.Warm-up, overload, temporary dependency unavailability, maintenance mode.

How readiness relates to a Service

A Service typically routes to ready endpoints. When a readiness probe fails, the Pod's Ready condition becomes false and the EndpointSlice controller updates matching Service endpoint readiness. The Pod does not necessarily stop running; it can become ready again when later checks succeed.

Probe mechanisms

MechanismHow it checks healthSuccess conditionImportant caveat
httpGetKubelet makes an HTTP GET request to a port/path.HTTP status code 200 through 399.Endpoint should be fast and deterministic. HTTPS probes do not validate the server certificate.
tcpSocketKubelet attempts to open a TCP connection to the specified port.Connection succeeds.Proves a socket accepts connections, not that application requests succeed.
execKubelet executes a command inside the container.Exit code 0.Frequent exec probes create processes and can add overhead. The command must exist in the image.
grpcKubelet uses the gRPC Health Checking Protocol.Health response is SERVING.Stable since Kubernetes v1.27. Requires application support; probe port is numeric, not a named port.

Important probe fields

FieldMeaning and practical guidance
initialDelaySecondsDelay before checks start after the container starts. Defaults to 0. A startup probe is usually more flexible for slow initialization than a very long delay.
periodSecondsApproximate interval between checks; default 10 seconds, minimum 1. Readiness checks may run more frequently while a container is not Ready.
timeoutSecondsHow long a check may take before failing; default 1 second. Raise it when a legitimate check needs more time, but avoid hiding hangs.
failureThresholdConsecutive failures needed to mark a check failed; default 3. Startup/liveness failures can trigger restart; readiness failure removes the Pod from normal traffic.
successThresholdConsecutive successes required after a failed check before success is accepted; default 1. Must be 1 for startup and liveness probes.
terminationGracePeriodSecondsOptional probe-specific grace period for startup/liveness failure; when set, it overrides the Pod-level grace period. It cannot be set for readiness probes.
httpGet.pathHTTP path called by the kubelet. Use a dedicated, low-cost endpoint such as /healthz or /readyz.
portContainer port number or name for HTTP/TCP. gRPC uses a numeric port.

When should the probes be different?

  • Startup vs liveness: startup can allow a long initialization window. Once startup succeeds, liveness can detect later deadlocks more quickly.
  • Readiness vs liveness: temporary inability to serve requests should often make a Pod unready, not restart it. Restart only for states where process restart is likely to help.
  • Separate endpoints: /healthz might check that the application process is alive; /readyz might additionally verify essential dependencies and that the app can serve its contract.
Avoid a cascading restart loop: never make liveness fail merely because a shared database or remote API is temporarily slow unless restarting the application is genuinely the correct recovery action. During a dependency outage, restarting every replica can amplify load and worsen the incident.

Common misunderstandings

  • “Running means ready.” Not necessarily; the process can still be warming up or rejecting requests.
  • “Readiness failure restarts the container.” Normally it does not; it affects the Pod Ready condition and Service endpoint eligibility.
  • “Startup runs continually.” Startup probing stops after the first successful result for that container lifecycle; liveness/readiness then take over.
  • “A TCP check proves the API works.” It only confirms that a TCP connection could be opened.
  • “A probe is a complete monitoring solution.” Probes are lifecycle/traffic signals, not a substitute for metrics, logs, tracing, synthetic tests, or service-level objectives.

3. Architecture and probe workflow

The following original SVG is a conceptual workflow, not a screenshot of a live Kubernetes cluster.

Walkthrough

  1. The container begins running and Kubernetes has not yet decided that the application has completed initialization.
  2. If a startup probe is defined, liveness and readiness checks wait for it to succeed.
  3. If startup never succeeds within its failure budget, kubelet terminates the container; the Pod's restart policy controls subsequent behavior.
  4. Once startup succeeds, liveness checks for unrecoverable failure and readiness checks whether the container should receive traffic.
  5. Readiness changes update the Pod's Ready condition and endpoint eligibility for Services. Liveness failure instead initiates container restart.

4. Environment preparation

Use a local Minikube/kind cluster or an authorized existing Kubernetes cluster. The labs use a dedicated namespace and public images; no cloud load balancer, EKS, or paid service is required. Container image pulls require registry/network access. A basic single-node local cluster is sufficient.

Verify access

kubectl version --client
kubectl cluster-info
kubectl get nodes
kubectl get namespaces
kubectl config current-context
  • kubectl version --client checks the installed command-line client.
  • kubectl cluster-info verifies access to the API server and cluster services.
  • kubectl get nodes lists available nodes and their readiness.
  • kubectl get namespaces shows where resources are logically grouped.
  • kubectl config current-context confirms which cluster commands will affect.

Optional Minikube start command, when Minikube is already installed: minikube start.

Prepare an isolated lab namespace

mkdir -p kubernetes-probes-lab
cd kubernetes-probes-lab
kubectl create namespace nimbus-probes-lab
kubectl config set-context --current --namespace=nimbus-probes-lab
Context note: the final command changes the default namespace for your current context, not the cluster itself. Commands in this guide still explicitly use -n nimbus-probes-lab so the target is obvious. If the namespace already exists, inspect it and ensure it belongs to your lab.

Check permissions if apply or patch is denied: kubectl auth can-i create deployments -n nimbus-probes-lab and kubectl auth can-i patch deployments -n nimbus-probes-lab.

5. Step-by-step hands-on labs

Run labs in order. Save manifests in the working folder named above. Outputs are representative; Pod names, timing, event wording, and image-pull duration can differ by cluster.

Exercise 1 — Deploy an HTTP app with all three probes

Objective: configure a healthy HTTP application with startup, liveness and readiness probes, then verify readiness and traffic through a Service.

Concept: separate paths make it clear what each probe checks. A successful startup probe gates the other probes; readiness controls whether the Pod is eligible for Service traffic; liveness restarts the container after repeated failures.

Step 1 — Save as probes-web.yaml:

apiVersion: v1
kind: ConfigMap
metadata:
  name: probes-web-pages
  namespace: nimbus-probes-lab
data:
  index.html: |
    <!doctype html>
    <html><body><h1>Nimbuswiztech Probe Lab</h1><p>Application is serving requests.</p></body></html>
  healthz: |
    OK - process health endpoint
  readyz: |
    OK - ready to accept traffic
  startupz: |
    OK - startup completed
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: probes-web
  namespace: nimbus-probes-lab
spec:
  replicas: 2
  selector:
    matchLabels:
      app: probes-web
  template:
    metadata:
      labels:
        app: probes-web
    spec:
      containers:
      - name: nginx
        image: nginx:1.27
        ports:
        - name: http
          containerPort: 80
        startupProbe:
          httpGet:
            path: /probes/startupz
            port: http
          periodSeconds: 2
          timeoutSeconds: 2
          failureThreshold: 30
        livenessProbe:
          httpGet:
            path: /probes/healthz
            port: http
          periodSeconds: 10
          timeoutSeconds: 2
          failureThreshold: 3
        readinessProbe:
          httpGet:
            path: /probes/readyz
            port: http
          periodSeconds: 5
          timeoutSeconds: 2
          failureThreshold: 3
          successThreshold: 1
        resources:
          requests:
            cpu: 50m
            memory: 64Mi
          limits:
            cpu: 250m
            memory: 128Mi
        volumeMounts:
        - name: pages
          mountPath: /usr/share/nginx/html/probes
          readOnly: true
      volumes:
      - name: pages
        configMap:
          name: probes-web-pages
---
apiVersion: v1
kind: Service
metadata:
  name: probes-web
  namespace: nimbus-probes-lab
spec:
  selector:
    app: probes-web
  ports:
  - name: http
    port: 80
    targetPort: http
  type: ClusterIP

Step 2 — Apply the manifest:

kubectl apply -f probes-web.yaml
kubectl rollout status deployment/probes-web -n nimbus-probes-lab --timeout=180s

Step 3 — Verify the containers, probe configuration and Service endpoints:

kubectl get deployment,pods,service -n nimbus-probes-lab
kubectl describe deployment probes-web -n nimbus-probes-lab
kubectl get endpointslices -n nimbus-probes-lab -l kubernetes.io/service-name=probes-web

When both replicas are ready, EndpointSlices should show ready endpoints for the Service. Exact addresses depend on the cluster.

Step 4 — Test the page:

kubectl port-forward service/probes-web 18090:80 -n nimbus-probes-lab

Leave that command running. In a second terminal execute curl -i http://127.0.0.1:18090/ and curl -i http://127.0.0.1:18090/probes/readyz. The server should return an HTTP 200 status and the page text.

Explain important fields: the named port http avoids repeating a numeric port; startupProbe.failureThreshold: 30 with a 2-second interval allows a generous startup budget; readiness succeeds only when /probes/readyz is reachable; liveness uses a separate low-cost /probes/healthz endpoint. Requests and limits reserve and cap example resources.

Troubleshooting: check image pull failures, probe HTTP paths, ConfigMap mount and Pod events. A misspelled path returns 404 and counts as a failed HTTP probe.

Interview connection: Why use different readiness and liveness endpoints? Because an app can be alive but temporarily unable to serve requests.

Exercise 2 — Demonstrate readiness failure without a restart

Objective: intentionally make a Pod unready and prove the container continues running while its endpoint is removed from normal Service traffic.

Concept: readiness failure is a traffic eligibility signal. It should not restart the container by itself.

Step 1 — Confirm the starting state:

kubectl get pods -n nimbus-probes-lab -l app=probes-web
kubectl get endpointslices -n nimbus-probes-lab -l kubernetes.io/service-name=probes-web

Step 2 — Change only the readiness path to a non-existent resource:

kubectl patch deployment probes-web -n nimbus-probes-lab --type=json -p='[{"op":"replace","path":"/spec/template/spec/containers/0/readinessProbe/httpGet/path","value":"/probes/not-ready"}]'

This updates the Pod template and causes a Deployment rollout. New Pods should fail readiness because NGINX returns 404 for the path. Liveness still succeeds at /probes/healthz, so the container should not restart because of readiness failure.

Step 3 — Observe the condition, endpoints and restart count:

kubectl get pods -n nimbus-probes-lab -l app=probes-web
kubectl describe deployment probes-web -n nimbus-probes-lab
kubectl get endpointslices -n nimbus-probes-lab -l kubernetes.io/service-name=probes-web
kubectl get events -n nimbus-probes-lab --sort-by=.metadata.creationTimestamp

Expected result: the new Pods are not Ready, the Service should not list them as ready backends, and their restart counts should remain unchanged for this readiness-only failure. On a rolling Deployment, availability may remain low or the rollout may stall until corrected.

Step 4 — Restore readiness:

kubectl patch deployment probes-web -n nimbus-probes-lab --type=json -p='[{"op":"replace","path":"/spec/template/spec/containers/0/readinessProbe/httpGet/path","value":"/probes/readyz"}]'
kubectl rollout status deployment/probes-web -n nimbus-probes-lab --timeout=180s

Interview takeaway: a readiness failure removes the Pod from normal Service traffic; it is not a restart command.

Exercise 3 — Demonstrate liveness failure and container restart

Objective: observe how a failed liveness check causes Kubernetes to restart the affected container.

Safety: only run this experiment in the dedicated lab namespace. The intentionally bad path will make the workload unhealthy until the path is restored.

Step 1 — Change the liveness path to a missing file:

kubectl patch deployment probes-web -n nimbus-probes-lab --type=json -p='[{"op":"replace","path":"/spec/template/spec/containers/0/livenessProbe/httpGet/path","value":"/probes/not-live"}]'

Wait for Pods to be replaced by the new template. After three consecutive failures under the chosen interval, the kubelet kills and restarts each affected container. There can be a delay before the restart counter increments.

Step 2 — Inspect Pod events and restart counts:

kubectl get pods -n nimbus-probes-lab -l app=probes-web -w
kubectl describe pod POD_NAME -n nimbus-probes-lab

Replace POD_NAME with a real Pod name from the first command. In the Pod Events section, look for Unhealthy and messages related to failed liveness checks; use the RESTARTS column to confirm container restarts. Timing and event messages vary.

Step 3 — Restore the valid liveness endpoint:

kubectl patch deployment probes-web -n nimbus-probes-lab --type=json -p='[{"op":"replace","path":"/spec/template/spec/containers/0/livenessProbe/httpGet/path","value":"/probes/healthz"}]'
kubectl rollout status deployment/probes-web -n nimbus-probes-lab --timeout=180s

Why it matters: liveness should fail for a state a process restart is likely to fix. Using an overly fragile liveness endpoint can repeatedly kill a working process and create cascading failures.

Exercise 4 — Protect a slow-starting application using a startup probe

Objective: simulate a container that takes 20 seconds to initialize and demonstrate that startup probing lets it finish before liveness/readiness checks begin.

Step 1 — Save as slow-start.yaml:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: slow-start
  namespace: nimbus-probes-lab
spec:
  replicas: 1
  selector:
    matchLabels:
      app: slow-start
  template:
    metadata:
      labels:
        app: slow-start
    spec:
      containers:
      - name: demo
        image: busybox:1.36.1
        command:
        - /bin/sh
        - -c
        - |
          echo "Starting simulated application initialization"
          sleep 20
          touch /tmp/started
          echo "Initialization complete"
          while true; do sleep 3600; done
        startupProbe:
          exec:
            command: ["/bin/sh", "-c", "test -f /tmp/started"]
          periodSeconds: 2
          timeoutSeconds: 1
          failureThreshold: 20
        livenessProbe:
          exec:
            command: ["/bin/sh", "-c", "test -f /tmp/started"]
          periodSeconds: 5
          timeoutSeconds: 1
          failureThreshold: 3
        readinessProbe:
          exec:
            command: ["/bin/sh", "-c", "test -f /tmp/started"]
          periodSeconds: 3
          timeoutSeconds: 1
          failureThreshold: 3
          successThreshold: 1
        resources:
          requests:
            cpu: 10m
            memory: 16Mi
          limits:
            cpu: 100m
            memory: 64Mi

Step 2 — Apply and observe:

kubectl apply -f slow-start.yaml
kubectl get pods -n nimbus-probes-lab -l app=slow-start -w

Before about 20 seconds, the startup command fails because /tmp/started does not yet exist. Once initialization creates the file, startup succeeds and liveness/readiness checks begin. The pod should then become Ready, without a restart.

Step 3 — Verify probe settings and events:

kubectl describe pod -l app=slow-start -n nimbus-probes-lab
kubectl get deployment slow-start -n nimbus-probes-lab

Understand the startup budget: failureThreshold: 20 times periodSeconds: 2 gives approximately 40 seconds of probe-failure budget. It is not an exact wall-clock guarantee because scheduling, image pulls, probe timing and runtime behavior affect the overall elapsed time. The 20-second simulated initialization fits within the configured budget.

Troubleshooting: if it restarts before initialization completes, check the startup threshold, command, image availability and events. Without a startup probe, a strict liveness check may terminate a slow application before it can initialize.

Exercise 5 — Compare an exec probe to an HTTP probe

Objective: understand command-based checks and observe the container restart count increase when a health file disappears.

Step 1 — Save as exec-liveness.yaml:

apiVersion: v1
kind: Pod
metadata:
  name: exec-liveness
  namespace: nimbus-probes-lab
  labels:
    app: exec-liveness
spec:
  restartPolicy: Always
  containers:
  - name: demo
    image: busybox:1.36.1
    command:
    - /bin/sh
    - -c
    - |
      touch /tmp/healthy
      echo "healthy file created"
      sleep 30
      rm -f /tmp/healthy
      echo "healthy file removed; liveness should fail"
      sleep 600
    livenessProbe:
      exec:
        command: ["/bin/sh", "-c", "test -f /tmp/healthy"]
      initialDelaySeconds: 3
      periodSeconds: 5
      timeoutSeconds: 2
      failureThreshold: 2

Step 2 — Apply and inspect:

kubectl apply -f exec-liveness.yaml
kubectl get pod exec-liveness -n nimbus-probes-lab -w

After roughly 30 seconds the application removes the health file. Repeated command failures cause kubelet to restart the container, at which point the command creates the file again. The Pod may repeatedly restart; this is intentional for the lab.

Step 3 — Observe events and restarts:

kubectl describe pod exec-liveness -n nimbus-probes-lab
kubectl get pod exec-liveness -n nimbus-probes-lab

Compare: HTTP probes check an endpoint and are often a good fit for HTTP apps. Exec probes can check local state but spawn a process on each execution, which can be costly at high Pod densities or very short intervals.

6. Complete practical workflow

Requirement

A two-replica web service must not receive traffic before startup has completed, should stop receiving traffic during temporary unavailability, and should restart if the application becomes stuck. This guide's probes-web.yaml implements that workflow using a startup HTTP endpoint, a readiness endpoint, a liveness endpoint, and a ClusterIP Service.

Execution sequence

  1. Verify cluster context and permissions.
  2. Create the dedicated namespace.
  3. Apply probes-web.yaml.
  4. Wait for the Deployment rollout and check that both replicas are ready.
  5. Inspect Pod details and EndpointSlices to verify traffic eligibility.
  6. Open a port-forward and curl the app endpoints.
  7. Perform the readiness-only failure and restore it; observe endpoint readiness without container restart.
  8. Perform the liveness-failure experiment only in the lab; observe restarts, then restore the path.
  9. Complete the cleanup steps.

Commands to verify the end state

kubectl rollout status deployment/probes-web -n nimbus-probes-lab
kubectl get deployment,pods,service -n nimbus-probes-lab
kubectl get endpointslices -n nimbus-probes-lab -l kubernetes.io/service-name=probes-web
kubectl logs deployment/probes-web -n nimbus-probes-lab
kubectl get events -n nimbus-probes-lab --sort-by=.metadata.creationTimestamp

Failure examples

  • Incorrect HTTP path: HTTP 404 makes the probe fail. Confirm the ConfigMap key is mounted at the path called by the probe.
  • App starts slowly: increase startup tolerance based on measured worst-case initialization, rather than weakening the ongoing liveness check blindly.
  • Dependency unavailable: readiness may reflect a required dependency if the app cannot serve useful requests without it. Liveness should generally focus on failure that restarting the app can solve.
  • Timeouts under load: check CPU/memory pressure and endpoint cost before increasing timeouts; a probe endpoint should be lightweight.
Completion criteria: two Ready Pods, Service endpoints marked ready, HTTP response from the service, a demonstrated readiness-only failure without an intentional container restart, and a demonstrated liveness failure that increases the restart count.

8. Best practices

  • Use startup probes for slow initialization. Measure worst-case startup time, then set failureThreshold × periodSeconds large enough to cover it with a sensible margin.
  • Keep liveness narrow. Check whether the process can make progress. Avoid making it fail for every transient dependency problem, or all replicas may restart at once.
  • Make readiness reflect ability to serve. If configuration has not loaded, caches are warming, or a required dependency is unavailable, the app may need to remain out of traffic.
  • Use inexpensive endpoints. Health endpoints should return quickly and avoid expensive database queries, broad fan-out or large payloads.
  • Choose realistic timing. Defaults are a starting point, not a universal best configuration. Tune period, timeout, and thresholds using application startup and response measurements.
  • Model dependencies deliberately. If database failure makes the app unserviceable, it may affect readiness; consider whether it should affect liveness only if restarting can actually fix the condition.
  • Check all replicas during deployment. Probes can gate readiness, but confirm the Deployment's available replicas, rollout status, endpoint membership, and application metrics.
  • Use resource requests and limits thoughtfully. CPU throttling or memory pressure can cause timeouts. Limits that are too small can create false health failures.
  • Use version-controlled manifests and clear labels. Probe settings are part of app deployment configuration. Review them like code.
  • Use container images with appropriate tooling. An exec probe that calls curl fails if curl isn't installed. The image must contain every command the probe uses.
  • Do not rely on a single probe for observability. Collect logs, metrics, traces and external synthetic checks as well.
  • Minimize exec frequency for large clusters. Exec probes start processes. Native HTTP/TCP mechanisms can be more efficient where they appropriately represent app health.
  • Test failure paths in non-production. Intentionally break probe paths only in an isolated namespace and restore them afterward.
  • Understand shutdown grace periods. Probe-triggered restarts need time to stop gracefully. A custom probe-level termination grace period is supported for startup/liveness, not readiness; use only when needed.
Production rule of thumb: separate “process can make progress” from “this instance should receive traffic.” A container may be live but not ready. That separation is often the most important probe-design decision.

9. Interview preparation

Search questions by keyword. Expand each question to view an answer or troubleshooting approach.

Level 1 — Basic questions

1. What is a Kubernetes probe?
A diagnostic run by the kubelet against a container. It can execute a command or make a network request and influences restart or readiness behavior.
2. What are the three probe types?
Startup checks whether initialization completed; liveness checks whether a container should be restarted; readiness checks whether it should receive traffic.
3. What happens when a liveness probe fails repeatedly?
After the configured failure threshold, the kubelet terminates and restarts the affected container. The Pod's restart policy governs subsequent behavior.
4. What happens when a readiness probe fails?
The container keeps running, but the Pod becomes not Ready and is excluded from normal Service traffic endpoints while it remains unready.
5. Why is startupProbe useful?
It lets slow-starting applications initialize without being killed by liveness checks that are intended to detect failures after startup. Liveness and readiness checks do not begin until startup succeeds.
6. Which probe mechanisms are supported?
HTTP GET, TCP socket, exec command, and gRPC health check. gRPC support became stable in Kubernetes v1.27.
7. What does periodSeconds mean?
It is the configured interval, in seconds, between probe checks. Its default is 10 seconds; minimum is 1 second.
8. What does timeoutSeconds mean?
It is how long Kubernetes waits for the probe to complete before considering that attempt failed. The default is 1 second.
9. What is failureThreshold?
The number of consecutive failures before a probe is considered failed. The default is 3; consequences depend on the probe type.
10. What HTTP status codes count as success?
HTTP response codes from 200 through 399 count as successful for an HTTP probe. Other status codes fail the probe.
11. How do you view probe failures?
Use kubectl describe pod POD_NAME -n NAMESPACE and inspect the Events section for Unhealthy and probe-failure messages. Also check current and previous container logs.
12. Does a Pod need a Service to use probes?
No. Probes are configured on a container in a Pod and work without a Service. Readiness affects use as a backend when Services select that Pod.

Level 2 — Intermediate questions

13. Why should readiness and liveness often use separate endpoints?
An application can be running and capable of recovery, yet temporarily unable to serve requests. Separate endpoints let readiness remove it from traffic while liveness avoids unnecessary restarts.
14. Why not check the database from liveness?
If a shared database outage makes every Pod's liveness fail, Kubernetes may restart all replicas simultaneously, increasing recovery load and worsening the incident. Model dependency failure as readiness when appropriate unless restarting the app is a justified recovery action.
15. How do you calculate startup tolerance?
A practical approximation is failureThreshold × periodSeconds. For example, 30 failures at 10 seconds is about 300 seconds of probe budget. Scheduling, image pull, and probe execution affect total elapsed startup time.
16. Does readinessProbe run only during startup?
No. Readiness probes run throughout the container's lifecycle, so a Pod can become unready later if it temporarily cannot accept traffic.
17. Does liveness wait for readiness to pass?
No. Liveness and readiness are independent. A startup probe, if defined, gates both until startup succeeds; otherwise use appropriate startup behavior and delays.
18. What is the difference between HTTP and TCP probes?
HTTP checks an application endpoint and its status code; TCP checks only whether a connection can be opened to a port. TCP can miss application-level failure.
19. When is an exec probe appropriate?
When a local check is needed and a valid command exists in the image. Keep it lightweight; every check launches a process and may add overhead at scale.
20. What must be true for a gRPC probe?
The application must implement the gRPC Health Checking Protocol and the numeric probe port must be configured. A SERVING response is success; gRPC probes do not support named ports.
21. Can HTTP probes validate a server TLS certificate?
No. With scheme: HTTPS, the kubelet sends HTTPS but skips certificate verification. Use an appropriate external security check if certificate validity must be independently verified.
22. What is successThreshold?
The consecutive successes required to recover a previously failing probe. It defaults to 1. Startup and liveness probes require it to be 1; readiness can use a larger value.
23. What is probe-level terminationGracePeriodSeconds?
It overrides the Pod-level termination grace period for startup or liveness probe failure when configured. It cannot be set on readiness probes and is stable starting in Kubernetes v1.28.
24. How do probes interact with Deployments?
Readiness affects Pod availability and rollout progress, while liveness/startup failures can trigger container restarts. A Deployment may stall if replacement Pods never become Ready.

Level 3 — Scenario-based questions

25. A Pod is Running but does not receive Service traffic. How do you investigate?
Approach: run kubectl get pods --show-labels, kubectl describe pod, and inspect EndpointSlices for the Service. If the Pod is not Ready, inspect probe events, path/port and application startup/dependencies. If Ready but missing from endpoints, check Service selectors, namespace and endpoint controller updates. Verify with a request after correction.
26. Your Deployment keeps restarting after adding liveness. What do you do?
Describe a new Pod, inspect Unhealthy/Killing events and previous logs. Test the health endpoint inside the container. Check the path, port, status, timeout, failure threshold, app startup and resource pressure. If liveness is detecting a temporary dependency outage rather than a stuck process, redesign the health endpoint. Restore a known-good probe configuration and verify restart counts stabilize.
27. A Java application needs 90 seconds to start but restarts after 30 seconds.
Add a startup probe with a measured failure budget greater than worst-case initialization, for example a 5-second period and 30 failures (roughly 150 seconds). Use an endpoint or command that accurately signals startup completion. Confirm events show startup succeeds and liveness/readiness begin afterward; don't simply disable health checks.
28. All Pods become unready during a database incident, but do not restart. Is that correct?
It may be correct if the application cannot serve valid requests without the database and readiness represents that dependency. Check database reachability, readiness endpoint behavior, EndpointSlices, and app metrics. Keep liveness independent if restarting the app will not fix the shared database outage.
29. A health endpoint returns 302 and the probe succeeds, but the endpoint is redirecting to a login page.
HTTP probe status codes 200–399 count as success, including redirects. Configure a dedicated health endpoint that returns a clear, minimal 200 only when the intended check passes; don't rely on redirect behavior. Verify with curl and Pod events.
30. A TCP liveness probe passes while users receive HTTP 500 errors.
TCP only proves that the port accepts connections. Use application logs and metrics to find handler/dependency errors, then consider HTTP or gRPC health checks that reflect a meaningful state. Verify the new endpoint behavior from inside the Pod and validate failure semantics in a lab.
31. Probe failures started after CPU limits were reduced.
Check kubectl top pod if metrics-server is available, Pod requests/limits, CPU throttling signals from monitoring, and event timing. Compare endpoint latency to timeoutSeconds. Right-size resources and optimize the health endpoint; adjust the timeout only when measured evidence supports it.
32. An exec probe fails with “curl: not found.”
The container image does not contain curl. Prefer native HTTP probes if the app exposes HTTP, or use a small command that is guaranteed to exist in the image. Avoid installing tools ad hoc into immutable production containers. Verify the actual container image and command path.
33. A liveness probe checks an external payment API and restarts every replica during an outage. What is wrong?
The liveness check is coupled to a shared external dependency that a container restart cannot recover. Remove that check from liveness; consider readiness if payment dependency is essential to serving valid requests, apply bounded timeouts/circuit breakers, and monitor the dependency separately.
34. Readiness fails for one Pod but its restart count is unchanged. Is Kubernetes broken?
No. That is normal. Readiness failure marks the Pod unready and removes it from normal Service endpoints while leaving the container running. Inspect the endpoint path, events and application state, and verify the Ready condition changes back after the endpoint recovers.
35. A Pod has no previous logs. How else can you debug?
Previous logs are available only after a prior container instance and if retained. Use kubectl describe pod, Events, current logs, Deployment status, probe configuration from kubectl get pod -o yaml, application metrics and controlled tests against the endpoint.
36. Liveness is failing intermittently but manually curling the endpoint succeeds.
Check probe timeout, timing, node-to-Pod connectivity, endpoint binding, response spikes, resource pressure and the exact status code during failures. Manual curl from your workstation may follow a different network path than the kubelet. Inspect events and app metrics and design the endpoint for low latency.

10. Practice assignments

Attempt each task before revealing the solution hints. Keep the exercises inside nimbus-probes-lab.

Beginner assignments

  1. HTTP health checks: create an NGINX Pod with a liveness HTTP GET path. Expected state: Pod stays running and ready. Verify using kubectl describe pod and a local port-forward. Hint: use a path actually served by NGINX.
  2. Separate readiness: configure a separate readiness endpoint. Expected: readiness controls Pod Ready status. Verify Pod conditions and matching EndpointSlices. Hint: a failed readiness probe should not restart the container.
  3. Startup gating: use a slow startup command and startup probe. Expected: initialization finishes before liveness/readiness begin. Verify events and restart count. Hint: size the failure budget to measured startup duration.
  4. TCP health: configure a TCP probe for an app listening on a known port. Expected: check succeeds while the socket listens. Verify port binding and events. Hint: TCP does not test application response logic.
  5. Exec health: configure an exec probe that exits 0 only when a known file exists. Expected: successful check while file exists. Verify event behavior after controlled file removal. Hint: ensure the command is installed.

Modification and troubleshooting assignments

  1. Change the readiness path to a non-existent path. Show that the Pod becomes unready without a liveness-triggered restart, then restore the route.
  2. Change the liveness path to a missing resource. Collect evidence of container restart and restore the correct path.
  3. Set timeoutSeconds too low for a deliberately slow lab endpoint; explain the event, then choose a value using measured response times.
  4. Remove a command required by an exec probe by switching to an image without that command. Diagnose the failure and design a supported fix.
  5. Run the slow-start app without startupProbe and describe the effect of a strict liveness check. Then add startupProbe and compare restart counts.

Scenario challenges

  1. Shared database outage: design distinct liveness and readiness behavior so Pods stop taking invalid traffic but are not needlessly restarted. Include the assumptions and verification strategy.
  2. False health failures under load: use Pod events, app metrics and resource data to decide whether to tune probe timeout, reduce endpoint cost or adjust resources.
  3. Slow startup in production: propose a startup budget based on measured warm-up times, with reasons for failure threshold and interval. Include a test plan for slow and failed initialization.

11. Quick revision and cheat sheet

Essential differences

  • Startup: “Has it finished initialization?” Gates liveness/readiness until success. Repeated failure restarts the container.
  • Liveness: “Should this container be restarted?” Repeated failure restarts the container.
  • Readiness: “Should this Pod receive traffic right now?” Failure marks it unready; the container continues running.
  • HTTP: success status is 200–399; TCP: connection succeeds; exec: command exits 0; gRPC: Health Checking Protocol responds SERVING.

  failureThreshold: 3

    path: /readyz
    port: http
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 3

These values are examples, not universal production defaults. Confirm that the app actually serves these paths and tune timing with measurements.
