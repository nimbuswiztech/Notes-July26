01 · Introduction

Why do namespaces and quotas matter?

A Kubernetes cluster can host many applications, teams, environments and workloads. Namespaces provide a logical scope for namespaced resources. ResourceQuota provides a per-namespace budget for selected resource totals and object counts. Together, they help teams share a cluster more predictably. citeturn748731search1turn748731search0

Analogy: office floors and department budgets

A namespace is like a department's workspace: employees can have resources with the same local name in different departments. A ResourceQuota is like a department budget: it limits aggregate spending, but it does not assign a particular desk or guarantee that the building has free capacity.

Real DevOps situations

  • Separate development, test and production resources by namespace.
  • Prevent one team from creating thousands of Pods or Services.
  • Limit aggregate CPU and memory requests/limits in a shared cluster.
  • Cap PersistentVolumeClaims or requested storage in a team namespace.
  • Use namespaces as one component of multi-team organization, paired with access controls.
Don't confuse isolation with security: a namespace does not automatically prevent API access by other users or network traffic from other namespaces. Use RBAC for API permissions, NetworkPolicy for supported network isolation, and appropriate Pod Security/admission controls. citeturn748731search1
02 · Namespaces

Namespace fundamentals

A namespace provides a scope for namespaced resources. Resource names must be unique within a namespace but may be reused in another namespace. Namespaces cannot be nested. A resource belongs to one namespace or, for cluster-scoped kinds, to no namespace. citeturn748731search1

Common namespace purposes

NamespacePurposeStudent note
defaultDefault namespace for namespaced resources when none is specified.Useful for quick experiments; avoid relying on it as a production organization strategy.
kube-systemHolds control-plane and system-related workloads/objects.Do not use it for student applications or delete it.
kube-publicConventionally holds information intended to be readable by all clients.Do not assume this is a place for private workloads.
kube-node-leaseHolds node Lease objects used for node heartbeats.System-managed; leave untouched.

These four namespaces are created by common Kubernetes installation methods, though the exact cluster setup can vary. Kubernetes advises avoiding namespace names with the reserved kube- prefix. citeturn748731search1

Create a namespace imperatively

kubectl create namespace nimbus-team-dev
kubectl get namespaces
kubectl describe namespace nimbus-team-dev

Create with declarative YAML

apiVersion: v1
kind: Namespace
metadata:
  name: nimbus-team-test
  labels:
    environment: test
    owner: platform-training
kubectl apply -f namespace-test.yaml
kubectl get namespace nimbus-team-test --show-labels

Set the current kubectl namespace

kubectl config set-context --current --namespace=nimbus-team-dev
kubectl config view --minify | grep namespace:
Context caution: this changes the default namespace for future kubectl commands in the current context. For training and production safety, explicitly include -n NAMESPACE in commands that alter resources, or switch the context back when finished.

Service DNS and namespace scope

A Service called catalog in namespace dev can normally be reached inside the cluster by its short name from that namespace. From another namespace, use a namespace-qualified name such as catalog.dev or the fully qualified form catalog.dev.svc.cluster.local (the cluster domain can be configured). citeturn748731search1

03 · ResourceQuota fundamentals

What is ResourceQuota?

A ResourceQuota object limits aggregate consumption or object counts inside one namespace. Examples include total CPU and memory requests/limits, the number of non-terminal Pods, numbers of ConfigMaps/Services/Secrets/PVCs, and requested storage. Quotas are expressed in absolute units and are independent of overall cluster capacity. citeturn748731search0

Important behavior to remember

  • Quota is enforced within a namespace when a ResourceQuota exists there and quota admission is enabled (it is enabled by default in many distributions).
  • Quota can limit aggregate compute quantities as well as API object counts.
  • If a quota defines CPU or memory requests/limits, new Pods may need explicit corresponding requests/limits for admission.
  • Quota does not assign resources to nodes, reserve capacity, or spread Pods across nodes.
  • Changing a quota does not retroactively remove already-created resources merely because usage is over the new limit; new admissions/updates can be affected.
  • Multiple quotas in a namespace may apply; a request must fit all applicable quotas and other admission policies.
Quota is not a node-capacity guarantee: a namespace may have quota remaining but still fail to schedule Pods if the cluster has no node capacity. Conversely, node capacity may exist while namespace quota blocks Pod creation. Those are different failure layers. citeturn748731search0

ResourceQuota manifest anatomy

apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-budget
  namespace: nimbus-compute-quota-lab
spec:
  hard:
    pods: "10"
    requests.cpu: "500m"
    requests.memory: "512Mi"
    limits.cpu: "1"
    limits.memory: "1Gi"

apiVersion: v1 is the core API group. kind: ResourceQuota selects the resource type. metadata.namespace defines the scope. spec.hard contains the maximum values; Kubernetes reports current usage in status.used.

07 · Hands-on labs

Progressive exercises

There are three lab namespaces: nimbus-team-dev, nimbus-team-test, nimbus-object-quota-lab, and nimbus-compute-quota-lab. In each command, use the exact namespace specified. Examples and outputs are illustrative; quotas and scheduling are cluster-state dependent.

Exercise 1 — Create two namespaces and reuse a resource name

Objective Demonstrate name scoping and inspect namespace labels.

Step 1: Save as 01-namespaces.yaml.

apiVersion: v1
kind: Namespace
metadata:
  name: nimbus-team-dev
  labels:
    environment: dev
    owner: training
---
apiVersion: v1
kind: Namespace
metadata:
  name: nimbus-team-test
  labels:
    environment: test
    owner: training

Step 2: Apply and inspect.

kubectl apply -f 01-namespaces.yaml
kubectl get namespaces --show-labels
kubectl describe namespace nimbus-team-dev
kubectl describe namespace nimbus-team-test

Step 3: Create ConfigMaps with the same name in both namespaces.

kubectl create configmap app-settings --from-literal=mode=dev -n nimbus-team-dev
kubectl create configmap app-settings --from-literal=mode=test -n nimbus-team-test
kubectl get configmap app-settings -n nimbus-team-dev -o yaml
kubectl get configmap app-settings -n nimbus-team-test -o yaml

Expected result: each namespace contains its own app-settings ConfigMap with different data. Repeating that creation within one namespace would return AlreadyExists until the object is changed or removed.

Interview takeaway: namespace names are unique scopes; they are not nested, and namespaces do not themselves provide a complete security boundary.

Exercise 2 — Apply a Pod-count and object-count quota

Objective Limit non-terminal Pods and ConfigMaps in one namespace.

Step 1: Save as 02-object-quota.yaml.

apiVersion: v1
kind: Namespace
metadata:
  name: nimbus-object-quota-lab
---
apiVersion: v1
kind: ResourceQuota
metadata:
  name: object-budget
  namespace: nimbus-object-quota-lab
spec:
  hard:
    pods: "2"
    configmaps: "3"
    services: "2"

Step 2: Apply and inspect the initial budget.

kubectl apply -f 02-object-quota.yaml
kubectl describe resourcequota object-budget -n nimbus-object-quota-lab
kubectl get resourcequota object-budget -n nimbus-object-quota-lab -o yaml

Step 3: Try to create four ConfigMaps.

kubectl create configmap cm-one --from-literal=key=one -n nimbus-object-quota-lab
kubectl create configmap cm-two --from-literal=key=two -n nimbus-object-quota-lab
kubectl create configmap cm-three --from-literal=key=three -n nimbus-object-quota-lab
kubectl create configmap cm-four --from-literal=key=four -n nimbus-object-quota-lab

Expected result: first three ConfigMaps should be admitted if the namespace starts empty; the fourth request should be rejected because configmaps: "3" is exhausted. Confirm with kubectl get configmaps -n nimbus-object-quota-lab and kubectl describe quota -n nimbus-object-quota-lab.

Troubleshooting: if the third is rejected, inspect any pre-existing ConfigMaps and the current used value. The quota applies to the namespace, not just objects created by your terminal session.

Exercise 3 — Demonstrate a Pod count quota with a Deployment

Objective Observe how quota can prevent a controller from reaching the desired replica count.

Step 1: Save as 03-pod-count-demo.yaml.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-pod-quota-demo
  namespace: nimbus-object-quota-lab
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-pod-quota-demo
  template:
    metadata:
      labels:
        app: web-pod-quota-demo
    spec:
      containers:
      - name: web
        image: nginx:stable-alpine
        ports:
        - name: http
          containerPort: 80

Step 2: Apply and inspect.

kubectl apply -f 03-pod-count-demo.yaml
kubectl get deployment web-pod-quota-demo -n nimbus-object-quota-lab
kubectl get pods -n nimbus-object-quota-lab -o wide
kubectl describe deployment web-pod-quota-demo -n nimbus-object-quota-lab
kubectl get events -n nimbus-object-quota-lab --sort-by=.metadata.creationTimestamp

Expected result: Deployment desired replicas remain 3, but the namespace quota permits only two non-terminal Pods while the quota is otherwise empty of Pods. The ReplicaSet will retry creation and events/messages commonly mention exceeded quota. ConfigMaps from Exercise 2 don't consume the Pod quota.

Important: Kubernetes doesn't automatically scale the quota just because a Deployment requests more replicas. If the quota is exhausted by other Pods, fewer than two may be admitted.

Interview takeaway: a successful kubectl apply of a Deployment does not prove all desired Pods can be created.

Exercise 4 — CPU and memory quotas

Objective Limit aggregate requests/limits and observe missing-capacity versus quota exhaustion.

Step 1: Save as 04-compute-quota.yaml.

apiVersion: v1
kind: Namespace
metadata:
  name: nimbus-compute-quota-lab
---
apiVersion: v1
kind: ResourceQuota
metadata:
  name: compute-budget
  namespace: nimbus-compute-quota-lab
spec:
  hard:
    pods: "10"
    requests.cpu: "500m"
    requests.memory: "512Mi"
    limits.cpu: "1"
    limits.memory: "1Gi"

Step 2: Apply and inspect.

kubectl apply -f 04-compute-quota.yaml
kubectl describe resourcequota compute-budget -n nimbus-compute-quota-lab

Step 3: Save as 04-compute-deployment.yaml.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: compute-quota-demo
  namespace: nimbus-compute-quota-lab
spec:
  replicas: 3
  selector:
    matchLabels:
      app: compute-quota-demo
  template:
    metadata:
      labels:
        app: compute-quota-demo
    spec:
      containers:
      - name: web
        image: nginx:stable-alpine
        ports:
        - name: http
          containerPort: 80
        resources:
          requests:
            cpu: "250m"
            memory: "128Mi"
          limits:
            cpu: "500m"
            memory: "256Mi"

Step 4: Apply and inspect the exact quota reason.

kubectl apply -f 04-compute-deployment.yaml
kubectl get pods -n nimbus-compute-quota-lab -o wide
kubectl describe quota compute-budget -n nimbus-compute-quota-lab
kubectl get events -n nimbus-compute-quota-lab --sort-by=.metadata.creationTimestamp

Expected result: each Pod requests 250m CPU and is limited to 500m CPU. The quota permits aggregate CPU requests of 500m and aggregate limits of 1 CPU, so two such Pods can fit those two CPU quota dimensions; a third may be rejected for exceeding quota, assuming the namespace started empty. Memory usage is within its configured limits for two Pods.

Requests and limits are separate counters. If a quota requires requests.cpu or limits.memory, newly admitted Pods need the corresponding values (or an applicable policy such as LimitRange must provide defaults). A LimitRange can set defaults/constraints; ResourceQuota measures aggregate consumption.

Verify: kubectl describe quota compute-budget -n nimbus-compute-quota-lab should show hard and used. The precise event message and number of running replicas depend on any pre-existing resources and cluster state.

Exercise 5 — Compare quota with LimitRange

Objective Understand a per-container default/bounds policy versus a namespace aggregate budget.

ResourcePurposeScope of measurement
ResourceQuotaCaps total namespace consumption/counts.Aggregate across applicable objects.
LimitRangeCan set defaults and constrain min/max requests/limits for Pods/containers or PVCs.Per individual object/container/claim, per configured rule.

Example LimitRange (optional; apply only in the compute lab after reviewing its effects):

apiVersion: v1
kind: LimitRange
metadata:
  name: container-defaults
  namespace: nimbus-compute-quota-lab
spec:
  limits:
  - type: Container
    defaultRequest:
      cpu: "100m"
      memory: "64Mi"
    default:
      cpu: "300m"
      memory: "128Mi"

Save as 05-limitrange.yaml, then run:

kubectl apply -f 05-limitrange.yaml
kubectl describe limitrange container-defaults -n nimbus-compute-quota-lab

Do not assume a LimitRange automatically increases ResourceQuota. Defaults can help a Pod satisfy a quota's required request/limit fields, but the aggregate budget still applies.

08 · End-to-end example

Design a quota-governed team namespace

Business requirement

A platform team provides a namespace for a training team. The team may create no more than two concurrent Pods, three ConfigMaps, and a bounded amount of CPU/memory. The platform team wants a clear way to view usage and troubleshoot denied requests.

Execution checklist

  1. Confirm the current Kubernetes context.
  2. Create only the dedicated lab namespace.
  3. Apply ResourceQuota before creating workloads to make the budget effective from the start.
  4. Submit a workload with explicit requests/limits when the quota includes those dimensions.
  5. Inspect the desired replica count, actual Pods, quota hard/used fields and recent Events.
  6. When admission fails, compare requested amount, current usage and limit; when a Pod is Pending, inspect scheduler events too.
  7. Adjust quota only with the namespace owner's approval and a reasoned budget decision.

What the platform team should monitor

  • Quota utilization by resource key (used versus hard).
  • Repeated quota-denial messages from ReplicaSets or users.
  • Namespaces whose quota is consistently near the limit.
  • Object-count growth, such as Jobs/Pods/Secrets/ConfigMaps, not just CPU and memory.
  • Cluster capacity independently of namespace quota allocation.

10 · Governance

Best practices and common mistakes

Use meaningful namespace names

Choose stable, DNS-compatible names such as payments-dev or platform-training. Avoid the reserved kube- prefix and avoid relying on default for production workloads.

Pair namespaces with RBAC

A namespace is not an access-control policy. Restrict who can create workloads, read Secrets, change quotas and delete namespaces.

Set quotas based on a budget

Define object counts and compute limits from actual workload needs. Too-low limits can cause failed rollouts; too-high limits may not prevent noisy-neighbor behavior.

Use requests and limits intentionally

Requests influence scheduling and quota accounting. Limits affect runtime ceilings. Make sure quota keys align with the fields the workload declares.

Consider LimitRange too

Use LimitRange for per-container defaults/minimums/maximums. It complements, but does not replace, ResourceQuota's aggregate budget.

Monitor quota usage

Observe used versus hard and watch denied admissions and incomplete deployments. Quota is most useful when usage is visible before teams hit the limit.

Production readiness checklist

  • Use documented owner/environment labels and an agreed naming convention.
  • Apply least-privilege RBAC and protect namespace deletion/quota changes.
  • Define quotas for likely risk dimensions: Pods, requests/limits, object counts and storage where relevant.
  • Use LimitRange to set sensible per-container defaults and bounds where needed.
  • Monitor quota utilization and plan a process for legitimate quota increases.
  • Remember that ResourceQuota is per namespace and does not divide nodes or isolate network traffic.
  • Validate a quota change in a test namespace before applying it across teams.
11 · Interview preparation

36 interview questions and answers

Try answering before expanding. Search by keyword to revise a specific concept.

Level 1 — Basic

1. What is a Kubernetes Namespace?
A namespace provides a scope for namespaced resources. Names must be unique within one namespace but can be reused in another. It supports organization and governance, but is not a complete security boundary by itself.
2. What are the four common initial namespaces?
default, kube-system, kube-public and kube-node-lease. Exact installation details can vary; do not use or delete system namespaces as application labs.
3. Can namespaces be nested?
No. A namespace is a flat scope and a namespaced resource belongs to one namespace.
4. Name two cluster-scoped resources.
Nodes and PersistentVolumes are common examples. They are not contained within an application namespace.
5. What is a ResourceQuota?
A namespaced object that constrains aggregate resource consumption or object counts within that namespace.
6. What is the purpose of quota hard and used fields?
hard indicates the configured ceiling; used reports current quota usage. Inspect both to understand whether a request fits.
7. Does quota reserve CPU on nodes?
No. It limits aggregate namespace usage. The scheduler still needs suitable node capacity for Pod requests.
8. What is the difference between requests.cpu and limits.cpu quota?
They aggregate different fields from Pods. Requests drive scheduler resource-fit calculations; limits describe runtime ceilings. Both can be quota-controlled separately.
9. What does 500m CPU mean?
Half of one CPU core. For quota arithmetic, two Pods each requesting 250m use 500m of aggregate CPU request quota.
10. How do you list namespaces?
Run kubectl get namespaces or the short alias kubectl get ns.
11. How do you inspect ResourceQuota usage?
Use kubectl describe resourcequota -n NAMESPACE or kubectl get resourcequota -o yaml -n NAMESPACE, then compare status.used with the quota hard values.
12. What does LimitRange do?
It can set per-container or per-Pod defaults and constrain individual resource requests/limits or PVC sizes. ResourceQuota instead limits aggregate usage across applicable objects.

Level 2 — Intermediate

13. If two namespaces each have a Service named api, is that allowed?
Yes. Names must be unique within their namespace, not across namespaces. DNS qualification lets callers distinguish the services, such as api.dev and api.test.
14. Does creating a namespace block other namespaces from reaching its Pods?
No. A namespace is not network isolation by itself. Use NetworkPolicy with a compatible network plugin and appropriate access controls.
15. Are Nodes part of a namespace?
No. Nodes are cluster-scoped. Use kubectl api-resources --namespaced=false to inspect cluster-scoped kinds.
16. Can ResourceQuota limit the number of ConfigMaps?
Yes. A quota can include configmaps. When the object-count budget is exhausted, new ConfigMaps in that namespace may be denied.
17. What happens if a Deployment asks for four replicas but pod quota allows two?
The Deployment can exist with desired replicas four while the ReplicaSet can create only the permitted Pods. It retries missing Pods and reports quota-related Events or messages.
18. If ResourceQuota defines requests.cpu, what should a new Pod specify?
It should declare CPU requests so quota admission can account for them, unless an applicable defaulting policy fills the required field. Verify the actual error and namespace policies.
19. Can ResourceQuota cap PVC usage?
Yes. Common quota keys include persistentvolumeclaims and requests.storage; StorageClass-specific forms are also supported. Actual provisioning still depends on storage infrastructure.
20. Does increasing node count automatically increase a namespace quota?
No. Quotas are absolute values configured in ResourceQuota objects. Node scale and namespace quota are separate control mechanisms.
21. Does changing quota remove existing resources above the new limit?
No, a quota change does not retroactively remove already-created resources just because usage exceeds the new limit. New admissions or updates can be affected.
22. Can several ResourceQuota objects exist in one namespace?
Yes. Multiple quotas can apply. A request must satisfy the applicable quotas and other admission policies.
23. What is the quota vs. scheduler distinction?
Quota is an admission/budget check for namespace consumption; scheduler placement determines which node can run an admitted Pod. Quota remaining does not guarantee scheduling success.
24. How can the current kubectl namespace affect commands?
If no -n is supplied, kubectl may use the namespace configured in the current context, often default. Validate it using kubectl config view --minify and use explicit namespaces for safer scripts.

Level 3 — Real-world scenarios

25. A developer receives “exceeded quota” when creating a Pod. How do you diagnose?
Approach: identify the exact namespace and resource key in the error. Run kubectl describe resourcequota -n NAMESPACE and compare hard vs. used. Inspect the Pod's requests/limits. Fix: reduce the requested resources, clean up legitimate stale objects, or request an approved budget adjustment. Verify: inspect quota usage and retry; do not increase quota without an owner decision.
26. A Deployment has desired replicas 5 but only 2 Pods. What do you inspect?
Check kubectl get deployment,replicaset,pods -n NAMESPACE and describe the ReplicaSet. If events say quota exceeded, inspect pod-count and compute quotas. If Pods exist but are Pending, inspect scheduler Events and capacity; if unhealthy, inspect image errors, logs and probes. Desired replicas alone do not identify the failure layer.
27. Quota usage is below hard, but Pod creation is rejected.
Read the exact API error. A ResourceQuota may require a request/limit field when that resource is quota-controlled; other admission validations, LimitRange constraints, policy, or RBAC may also reject the object. Inspect the quota, the full rejected manifest, namespace LimitRanges and server response before changing anything.
28. A Pod is Pending, but the namespace has quota remaining.
Quota admission may have succeeded, while scheduling failed. Run kubectl describe pod POD -n NAMESPACE and review Events for insufficient CPU/memory, taints/tolerations, node affinity, unready nodes or PVC topology. Quota and physical capacity are different layers.
29. A fourth ConfigMap is denied in a namespace with configmaps: 3.
Check whether three ConfigMaps already exist and inspect status.used.configmaps. Delete only obsolete objects approved for removal or request a revised quota. Verify by listing ConfigMaps and describing the quota.
30. A new namespace accidentally has no CPU/memory requests in its workloads.
Check whether its ResourceQuota requires requests.cpu, requests.memory, or limits. Add explicit workload resources or use a reviewed LimitRange policy for defaults. Confirm that adding defaults will still fit within aggregate quota and actual cluster capacity.
31. kubectl created a resource in the wrong namespace.
Check kubectl config view --minify and the resource's metadata.namespace. Use explicit -n in scripts and set context namespace only deliberately. Move/recreate resources with dependency awareness rather than assuming a resource can simply be reassigned to another namespace.
32. A team's quota is nearly exhausted every morning.
Review quota usage trends, workload replica patterns, CronJobs/Jobs, scaling events and object-count growth. Determine whether limits are wrong or workloads leak/retain objects. Coordinate quota changes with the owner and preserve alerts for future exhaustion.
33. A namespace is stuck in Terminating.
Inspect kubectl get namespace NAME -o yaml, deletion conditions and remaining namespaced resources. Unavailable aggregated APIs or finalizers may block deletion. Diagnose the responsible resource/controller before touching finalizers; removing them blindly can orphan external resources.
34. A team requests a larger quota because the cluster has more nodes.
Explain that quota is not automatically proportional to node capacity. Review the team's workload needs, current consumption, cluster capacity, other tenant budgets and operational objectives before changing the absolute quota values.
35. A service is reachable across namespaces; is the namespace broken?
No. Namespace scoping is not a firewall. Service DNS can address services across namespaces, subject to network routing and policy. If isolation is required, implement and test NetworkPolicy and relevant authorization/security controls.
36. How would you roll out namespaces and quotas in production?
Define naming/ownership, RBAC, network policy and Pod Security separately; estimate usage from workloads; pilot ResourceQuota and LimitRange in a test namespace; monitor used/hard values and denial events; document the quota-increase process; and verify that autoscaling and cluster capacity can support the permitted workload. Keep rollback and cleanup scoped.
12 · Independent practice

13 assignments with solution hints

Try each assignment first. The hints provide the main investigative path rather than replacing the exercise.

Beginner exercises

  1. Namespace creation: create a namespace from YAML, add owner/environment labels, and verify with kubectl get ns --show-labels. Expected state: namespace Active and labels visible. Hint: metadata.labels.
  2. Same resource name: create ConfigMaps called app-settings in two namespaces with different data. Verify both. Hint: specify -n explicitly.
  3. Current namespace: set context default namespace to a lab namespace, verify it, then switch it back or use explicit -n. Expected: a no-namespace command targets the selected scope.
  4. Object count quota: cap ConfigMaps at three and try to create four. Verify the fourth is denied. Hint: inspect status.used.configmaps.
  5. Pod quota: create a Deployment with more replicas than allowed non-terminal Pods. Explain desired versus available replicas. Hint: inspect ReplicaSet Events.

Modification and troubleshooting exercises

  1. Change the pod-count quota from 2 to 4. Explain what changes immediately and what does not. Hint: a higher quota does not create Pods automatically; controllers may retry missing replicas.
  2. Remove CPU requests from a test Pod in a namespace with requests.cpu quota. Diagnose the resulting admission message. Hint: check full ResourceQuota and any LimitRange defaults.
  3. Make a Deployment's requests exceed the aggregate quota. Diagnose and lower the requested amount. Hint: calculate per-Pod requests times replicas.
  4. Create a fourth ConfigMap after the quota is exhausted, then delete one approved lab ConfigMap and retry. Hint: inspect quota usage before each attempt.
  5. Put a resource into the wrong namespace by changing the context. Find it and explain how explicit -n prevents ambiguity. Hint: list resources across namespaces.

Real-world scenario challenges

  1. Multi-tenant cluster: propose namespaces, RBAC, NetworkPolicy, ResourceQuota and LimitRange for two teams. Explain which problem each control solves.
  2. Quota exhaustion alert: design a runbook for a team frequently reaching CPU/memory quota. Include usage trends, requests/limits and an approval path for changing budgets.
  3. EKS operations: debug a namespace where Pods are rejected by quota after an application rollout. Distinguish quota denial from node capacity and cloud autoscaling.
