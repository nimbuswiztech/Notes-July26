Learning objectives and roadmap

By the end, students should be able to create a dedicated ServiceAccount, define namespace-scoped permissions, bind permissions to the correct identity, assign that identity to a Pod, and prove what is allowed or denied.

Prerequisites

  • Basic Pods, namespaces, YAML and kubectl
  • Access to a disposable Kubernetes cluster
  • Permission to create test namespaces and RBAC objects

Success criteria

  • App identity is not the human operator's identity
  • Only intended API verbs/resources are allowed
  • kubectl auth can-i confirms the policy
  • Unauthorized operations are denied

1. Why ServiceAccounts and RBAC?

A ServiceAccount is a Kubernetes-managed identity commonly used by workloads and automation. Role-Based Access Control (RBAC) defines which API actions an identity can perform. They solve different parts of the problem: identity answers “who is making this request?”; RBAC answers “what is this identity allowed to do?”

Real-world analogy

A company employee has an ID badge (identity). The building access list says which doors that badge opens (authorization). A badge does not automatically grant access to every room.

DevOps example

A deployment helper needs to list Pods in the training-rbac namespace. It should not need permission to read Secrets, delete workloads, or change cluster-wide settings.

Important: RBAC rules are additive. Kubernetes RBAC does not provide “deny this action” rules. Avoid broad grants and design the smallest set of permissions that satisfies the workload.

2. Core concepts and components

ObjectScopePurposeKey point
ServiceAccountNamespaceWorkload identityPods can select it with spec.serviceAccountName.
RoleNamespaceDefines permissions for namespaced resources in that namespaceContains rules, not subjects.
RoleBindingNamespaceGrants a Role or a ClusterRole to subjects in one namespaceBinding to a ClusterRole does not make the binding cluster-wide.
ClusterRoleClusterDefines reusable rules, including cluster-scoped resourcesCan also be bound within one namespace using a RoleBinding.
ClusterRoleBindingClusterGrants a ClusterRole across the clusterUse carefully; broad scope increases impact.

How to read a rule

rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
  • apiGroups: API group; the core group is written as an empty string.
  • resources: resource types such as pods, configmaps or deployments.
  • verbs: actions such as get, list, watch, create, update, patch, delete.

ServiceAccount token notes

Modern Kubernetes uses short-lived, rotating projected tokens for Pods by default. Avoid relying on manually created, long-lived ServiceAccount token Secrets unless a specific legacy requirement justifies the risk. If a workload does not call the Kubernetes API, consider setting automountServiceAccountToken: false.

3. API request and authorization workflow

  1. A Pod is configured with a ServiceAccount.
  2. Kubernetes provides projected credentials unless token automounting is disabled.
  3. The application sends an authenticated request to the Kubernetes API server.
  4. The API server identifies the caller, then checks applicable authorization rules.
  5. The request is allowed only if policy permits the requested action; otherwise it is denied.
A successful kubectl auth can-i check evaluates authorization for the selected identity and action. It does not test application connectivity, admission policy, or whether the target object exists.

5. Step-by-step hands-on lab

Goal: a dedicated ServiceAccount can list and get Pods only in the training-rbac namespace. It must not be able to list Secrets or delete Pods.

Lab topology

Exercise 1 — Create a dedicated namespace and identity

1
Create the namespace
kubectl create namespace training-rbac
kubectl create serviceaccount pod-reader -n training-rbac
kubectl get serviceaccount -n training-rbac

Expected: the pod-reader ServiceAccount appears in training-rbac. The namespace also has its automatically created default ServiceAccount.

Exercise 2 — Define least-privilege permissions

Create a file named pod-reader-rbac.yaml with the following complete manifest.

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-readonly
  namespace: training-rbac
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: pod-reader-binding
  namespace: training-rbac
subjects:
- kind: ServiceAccount
  name: pod-reader
  namespace: training-rbac
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: pod-readonly
Manifest review: The Role permits read-only Pod operations. The RoleBinding subject must exactly match the ServiceAccount name and namespace. The roleRef points to the Role by name and kind.
kubectl apply -f pod-reader-rbac.yaml
kubectl get role,rolebinding -n training-rbac
kubectl describe role pod-readonly -n training-rbac
kubectl describe rolebinding pod-reader-binding -n training-rbac

Exercise 3 — Verify authorization before running a Pod

kubectl auth can-i list pods -n training-rbac --as=system:serviceaccount:training-rbac:pod-reader
kubectl auth can-i get pods -n training-rbac --as=system:serviceaccount:training-rbac:pod-reader
kubectl auth can-i delete pods -n training-rbac --as=system:serviceaccount:training-rbac:pod-reader
kubectl auth can-i list secrets -n training-rbac --as=system:serviceaccount:training-rbac:pod-reader
kubectl auth can-i list pods -n default --as=system:serviceaccount:training-rbac:pod-reader
Expected authorization results: list Pods = yes; get Pods = yes; delete Pods = no; list Secrets = no; list Pods in default = no (assuming no other applicable grants). The operator running kubectl auth can-i --as needs permission to impersonate the ServiceAccount.

Exercise 4 — Create a test Pod that uses the identity

apiVersion: v1
kind: Pod
metadata:
  name: identity-check
  namespace: training-rbac
spec:
  serviceAccountName: pod-reader
  restartPolicy: Never
  containers:
  - name: shell
    image: bitnami/kubectl:latest
    command: ["sh", "-c", "kubectl get pods -n training-rbac; echo '--- checking forbidden action ---'; kubectl get secrets -n training-rbac"]

Save as identity-check.yaml, then run:

kubectl apply -f identity-check.yaml
kubectl get pod identity-check -n training-rbac
kubectl logs identity-check -n training-rbac

The Pod image must be pullable in your environment. The first command should list Pods; the Secret request should be forbidden. Image availability and network policy can affect whether this optional in-Pod demonstration starts.

Do not treat the demo image as a production recommendation. Pin an approved image version or digest in real projects, and use an approved minimal image. The core RBAC learning objectives can be completed with kubectl auth can-i alone.

Exercise 5 — Inspect the identity and permission objects

kubectl get pod identity-check -n training-rbac -o jsonpath='{.spec.serviceAccountName}{"\n"}'
kubectl get serviceaccount pod-reader -n training-rbac -o yaml
kubectl get role pod-readonly -n training-rbac -o yaml
kubectl get rolebinding pod-reader-binding -n training-rbac -o yaml

6. End-to-end demonstration summary

Requirement

A reporting workload needs to inspect Pods in its own namespace for simple diagnostics. It does not need to read Secrets, modify workloads, or access other namespaces.

Target design

  • Dedicated ServiceAccount: pod-reader
  • Namespace Role: pod-readonly
  • RoleBinding: pod-reader-binding
  • Pod declares serviceAccountName: pod-reader

7. Troubleshooting decision trees

Problem A: expected access is denied

kubectl auth can-i list pods -n training-rbac --as=system:serviceaccount:training-rbac:pod-reader
kubectl get role pod-readonly -n training-rbac -o yaml
kubectl get rolebinding pod-reader-binding -n training-rbac -o yaml
kubectl describe rolebinding pod-reader-binding -n training-rbac

Problem B: Role appears correct, but access is too broad

kubectl get rolebindings -A
kubectl get clusterrolebindings
kubectl get roles -n training-rbac
kubectl get clusterroles

Common symptoms

ForbiddenIdentity, namespace, verbs, API group, bindingFix the exact missing grant; do not grant admin as a shortcut.

8. Best practices and comparisons

Do

  • Create workload-specific ServiceAccounts.
  • Grant only required verbs and resources.
  • Prefer namespace-scoped RoleBindings when sufficient.
  • Verify both allowed and denied actions.
  • Disable token automount for workloads that do not need API access.
  • Review RBAC changes and audit broad bindings.

Avoid

  • Binding workloads to cluster-admin for convenience.
  • Giving every workload permissions through the default ServiceAccount.
  • Granting access to Secrets unless necessary.
  • Using static long-lived tokens as the default approach.
  • Assuming a Role grants permissions without a binding.
  • Assuming a RoleBinding is cluster-wide.
ApproachRisk / scopeRecommendation
Dedicated SA + Role + RoleBindingSmall, namespace-scoped grantPreferred starting point
Default SA with permissionsEvery Pod using default identity can inherit those grantsAvoid when dedicated identity is practical
ClusterRole + RoleBindingReusable rule set, grant confined to one namespaceUseful for standardized namespace roles
ClusterRole + ClusterRoleBindingCluster-wide grant; potentially high impactUse only when cluster scope is required
cluster-admin for app workloadFull control of clusterDo not use for ordinary workloads

9. Interview preparation

Try to answer before opening each response. These are study prompts, not a substitute for explaining the reasoning behind a design.

Level 1 — Basic questions

1. What is a Kubernetes ServiceAccount?

A Kubernetes-managed identity commonly assigned to Pods or automation so requests can be made as that identity.

2. What is RBAC?

Role-Based Access Control authorizes API actions using rules and bindings.

3. What is the difference between authentication and authorization?

Authentication identifies the caller; authorization decides whether that identity may perform a requested action.

4. What is a Role?

A namespaced object containing rules for resources and verbs within its namespace.

5. What is a RoleBinding?

A namespaced grant connecting a Role or ClusterRole to users, groups, or ServiceAccounts in that namespace.

6. What is a ClusterRole?

A cluster-scoped rule object that can describe permissions on cluster-scoped resources or namespaced resources.

7. What is a ClusterRoleBinding?

A cluster-scoped binding that grants a ClusterRole across the cluster.

8. How do you assign a ServiceAccount to a Pod?

Set spec.serviceAccountName in the Pod specification.

9. What does kubectl auth can-i do?

Checks whether the current or specified identity is authorized for a particular action and resource.

10. Does creating a Role automatically grant permissions?

No. A binding must grant the Role to a subject.

Level 2 — Intermediate questions

11. Can a RoleBinding reference a ClusterRole?

Yes. The resulting grant is limited to the RoleBinding's namespace.

12. Why should apps not share the default ServiceAccount?

A dedicated identity makes permissions easier to scope, audit, and revoke. Grants to the default identity can affect every Pod using it.

13. Why is access to Secrets sensitive?

Secret data may contain credentials or tokens. Read access can enable impersonation or access to external systems.

14. What does an empty string in apiGroups mean?

It identifies the core API group, which includes resources such as Pods and ConfigMaps.

15. RBAC says “no” but the Role looks correct. What do you check?

Confirm the caller identity, namespace, exact verb/resource/API group, binding subject, and roleRef. Then check whether the intended binding is actually applied.

16. Why can an action be allowed even when the Role does not include it?

RBAC grants are additive; another RoleBinding or ClusterRoleBinding may grant the action.

17. How do modern Pods receive ServiceAccount credentials?

Typically through a projected, short-lived token that rotates, unless automounting is disabled or the Pod is configured differently.

18. When is ClusterRoleBinding appropriate?

When a subject genuinely requires cluster-wide permissions or access to cluster-scoped resources, with the narrowest possible rules.

19. How would you prove least privilege?

Test required operations as allowed, test sensitive/unneeded operations as denied, and review all applicable bindings for extra grants.

20. What is the risk of binding an app to cluster-admin?

Compromise of that app can become compromise of the cluster; avoid this for normal application workloads.

Level 3 — Real-world scenarios

21. A reporting Pod must list Pods but receives Forbidden. How do you investigate?

Check spec.serviceAccountName; run kubectl auth can-i list pods -n NAMESPACE --as=system:serviceaccount:NAMESPACE:SA; inspect Role rules and RoleBinding subjects/roleRef; retest after a minimal correction.

22. A workload can read Secrets unexpectedly. What do you do?

Do not assume the local Role is the only source of access. Inspect RoleBindings and ClusterRoleBindings, trace every roleRef, assess impact, then remove or narrow excess grants and retest.

23. A Pod must read ConfigMaps in another namespace. What is the design?

Create a Role in the target namespace that grants only the required ConfigMap verbs, then create a RoleBinding in that target namespace whose subject is the ServiceAccount in the source namespace. Validate the cross-namespace subject reference.

24. The Pod uses the default identity despite a dedicated account existing. Why?

Creating a ServiceAccount does not assign it automatically. Set spec.serviceAccountName in the Pod or workload template, then recreate or roll out the workload as appropriate.

25. A team asks for cluster-admin to “fix permissions quickly.” What do you recommend?

Identify the failing API action and resource, reproduce with kubectl auth can-i, and add only the missing rule at the narrowest scope. Explain the blast radius of cluster-admin.

26. Access works in one namespace but not another. What may explain it?

RoleBindings are namespace-scoped. Check whether the target namespace has a binding, whether a ClusterRole is being bound with a RoleBinding, and whether the resource is cluster-scoped.

27. A Pod does not need the Kubernetes API. What security option should you consider?

Set automountServiceAccountToken: false at the Pod or ServiceAccount level where appropriate, and verify the application does not depend on the token.

28. Your can-i check says yes, but the request still fails. Why?

Authorization is only one layer. Check the exact runtime identity and request, API connectivity, admission controls, resource existence, schema/validation errors, and application behavior.

29. A RoleBinding references a Role that was renamed. What happens?

The binding's roleRef must point to an existing role object of the specified kind and name. Inspect the binding and role, then update the configuration safely; roleRef is immutable on a RoleBinding, so recreate the binding if its reference must change.

30. How would you review RBAC in a cluster?

Inventory Roles, ClusterRoles, RoleBindings and ClusterRoleBindings; identify broad grants, wildcard rules, access to Secrets, and default ServiceAccount grants; validate intended access with owners and reduce permissions incrementally.

10. Practice assignments and visual challenges

Beginner exercises

  1. Create a namespace called rbac-practice and a ServiceAccount named config-reader. Verify both exist.
  2. Create a Role that can get and list ConfigMaps in the namespace. Hint: core API group is "".
  3. Bind the Role to config-reader. Verify with kubectl auth can-i list configmaps -n rbac-practice --as=system:serviceaccount:rbac-practice:config-reader.
  4. Confirm the identity cannot delete ConfigMaps or list Secrets.
  5. Assign the ServiceAccount to a test Pod and inspect spec.serviceAccountName.

Modification and troubleshooting exercises

  1. Remove list from the Role and observe how authorization changes.
  2. Intentionally change the RoleBinding subject namespace. Diagnose the denial and restore the correct namespace.
  3. Add watch to the allowed verbs and verify it with can-i.
  4. Find why an identity has unexpected access after an additional broad binding is created in a disposable cluster; remove the extra binding after reviewing it.
  5. Set automountServiceAccountToken: false on a test Pod and inspect the effect on projected credentials.

Real-world challenges

  1. A monitoring agent needs read-only access to Pods and Deployments in one namespace. Propose the minimum API groups, resources, verbs, and binding scope.
  2. A CI job needs to create Jobs but must not read Secrets. Design and verify a scoped policy; consider related permissions the job truly needs rather than adding broad access.
  3. A workload in namespace dev must list Jobs in namespace maintenance. Explain where the RoleBinding belongs and how its subject is referenced.
Show sample solution for beginner exercise 2
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: config-reader
  namespace: rbac-practice
rules:
- apiGroups: [""]
  resources: ["configmaps"]
  verbs: ["get", "list"]

Bind it with a RoleBinding in rbac-practice whose subject is ServiceAccount config-reader in that namespace. Verify the intended “yes” and “no” cases.

Show sample reasoning for the cross-namespace challenge

Create the Role in maintenance, because that is where the Jobs are being accessed. Create the RoleBinding in maintenance; set the subject to the ServiceAccount in dev. The binding namespace determines where the grant applies.

12. Cleanup and resource lifecycle

kubectl delete pod identity-check -n training-rbac --ignore-not-found
kubectl delete namespace training-rbac

Deleting the namespace removes the ServiceAccount, Role, RoleBinding, and other namespaced lab objects created inside it. If you created resources outside that namespace, remove them separately after confirming they belong to this lab.

Shared cluster warning: Do not delete namespaces, bindings, or roles you did not create. Never remove system RBAC objects as part of this exercise.
