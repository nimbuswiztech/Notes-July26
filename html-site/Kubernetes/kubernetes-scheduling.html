01 · Scheduling fundamentals

What does the Kubernetes scheduler do?

When a Pod is created without an explicit node assignment, the scheduler evaluates nodes and chooses one that satisfies the Pod's requirements and has suitable available resources. Scheduling constraints can express hardware requirements, node pools, locality to another workload, or separation between replicas. Use them intentionally; Kubernetes already considers resources and other scheduling rules. The supplied Nimbuswiztech wiki describes examples such as using SSD-equipped nodes or co-locating services that communicate frequently.

Analogy: choosing a workspace

Node selector: only desks with a named feature are allowed. Node affinity: those desks are mandatory or merely preferred. Pod affinity: sit near a teammate in a zone or rack. Pod anti-affinity: avoid sharing the same failure domain with another replica.

Real DevOps situations

  • Schedule CPU-intensive jobs to a dedicated node pool.
  • Keep a latency-sensitive API near its cache.
  • Spread replicas across nodes to reduce the impact of one node failing.
  • Prefer a CPU architecture when the application image needs it.
  • Constrain a workload to a governed node pool alongside appropriate security controls.
Important: Labels are metadata, not hardware enforcement by themselves. A label such as workload=secure matters only if the organization governs who can set it and aligns the scheduling policy with taints, access and security design.

03 · Technique 1

Node selector: exact node-label matching

spec.nodeSelector is the simplest node selection constraint. Every key/value pair must be present on a candidate node. It is a hard requirement: if no feasible node carries all requested labels, the Pod remains unscheduled.

Complete manifest

apiVersion: v1
kind: Pod
metadata:
  name: node-selector-demo
  namespace: nimbus-scheduling-lab
  labels:
    app: node-selector-demo
spec:
  nodeSelector:
    training.nimbuswiztech.io/scheduling-demo: enabled
  containers:
  - name: web
    image: nginx:stable-alpine
    ports:
    - name: http
      containerPort: 80

Add a lab-specific label

Only run node label changes if you have permission and the cluster administrator agrees. Use a unique key to avoid overwriting standard Kubernetes/cloud labels.

kubectl get nodes --show-labels
NODE=$(kubectl get nodes -o jsonpath='{.items[0].metadata.name}')
kubectl label node "$NODE" training.nimbuswiztech.io/scheduling-demo=enabled --overwrite
kubectl get nodes -L training.nimbuswiztech.io/scheduling-demo
Shared cluster warning: This changes node metadata at cluster scope. On a shared cluster, ask the instructor/admin before applying. Remove the training label during cleanup.

Verification: apply the YAML, then use kubectl get pod node-selector-demo -n nimbus-scheduling-lab -o wide. The NODE column should show a node carrying the lab label, assuming that node also satisfies resource, taint and readiness requirements.

04 · Technique 2

Node affinity: hard rules and weighted preferences

Node affinity expands nodeSelector with operators and preference scoring. Required rules filter feasible nodes; preferred rules influence ranking. The preferred weight is from 1 to 100.

Complete Pod example

apiVersion: v1
kind: Pod
metadata:
  name: node-affinity-demo
  namespace: nimbus-scheduling-lab
  labels:
    app: node-affinity-demo
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: training.nimbuswiztech.io/scheduling-demo
            operator: In
            values: ["enabled"]
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 80
        preference:
          matchExpressions:
          - key: training.nimbuswiztech.io/preferred-node
            operator: In
            values: ["yes"]
  containers:
  - name: web
    image: nginx:stable-alpine

Operators and logical rules

OperatorMeaningExample
InValue matches one listed value.class is general or compute.
NotInValue does not match listed values.class not gpu.
ExistsLabel key exists.ssd capability key exists.
DoesNotExistLabel key is absent.maintenance marker absent.
Gt/LtNumeric comparison where a single integer-like value is appropriate.Compare a numeric label value.
Boolean logic: expressions in one nodeSelectorTerm are ANDed. Multiple terms are ORed. When nodeSelector and node affinity are both specified, both requirements must be met.

IgnoredDuringExecution: node affinity rules guide scheduling. Changing a node label later does not automatically evict a running Pod solely because the existing placement no longer matches the rule.

05 · Technique 3

Pod affinity: place related workloads near each other

Pod affinity uses labels on existing Pods—not only labels on nodes—to influence placement. The labelSelector identifies matching Pods; topologyKey names a node label that defines the scope, such as one node or one availability zone.

Example manifest fragment

affinity:
  podAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchLabels:
          app: cache
      topologyKey: kubernetes.io/hostname

In plain English: “Schedule only onto a node whose hostname topology domain contains at least one matching Pod labelled app=cache.” This does not create connectivity or guarantee that the cache application itself is healthy.

Important fields

  • labelSelector — matchLabels and/or matchExpressions identify the other Pods.
  • namespaces — omitted/empty by default means the Pod's own namespace when no namespaceSelector broadens the scope.
  • namespaceSelector — can broaden the namespaces searched for matching Pods; make this explicit when needed.
  • topologyKey — a node-label key defining a domain such as hostname or zone.
  • required... / preferred... — hard eligibility or a best-effort score.
Operational note: Required Pod affinity may leave a Pod Pending if matching Pods don't exist in the eligible topology, selector, or namespace scope. Pod affinity/anti-affinity adds scheduler work in large clusters; use it only when locality requirements justify it.
06 · Technique 4

Pod anti-affinity: avoid placing matching Pods together

Pod anti-affinity repels a Pod from topology domains containing matching Pods. It can reduce the risk that multiple replicas of one service are concentrated on one node. Prefer a soft rule when separation is desirable but not mandatory; use a required rule only when strict separation is worth the risk of unschedulable replicas.

Preferred anti-affinity

affinity:
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 100
      podAffinityTerm:
        labelSelector:
          matchLabels:
            app: web
        topologyKey: kubernetes.io/hostname

Weight values are from 1 to 100. A preferred rule favors nodes whose hostname domain does not contain a matching Pod, but it can be outweighed by other scheduler scoring and constraints.

Required anti-affinity

affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchLabels:
          app: web
      topologyKey: kubernetes.io/hostname

This forbids a node from hosting another matching app=web Pod in the same hostname domain. If a Deployment requests three replicas but only two eligible nodes exist, a replica may remain Pending. Verify resource fit, taints and topology labels before concluding node count is the only cause.

07 · Scheduler mechanics

From Pending Pod to node binding

Why a Pod may remain Pending

  • No node carries the requested label.
  • Pod affinity requires a matching Pod in an eligible topology domain, but none exists.
  • Required anti-affinity excludes all available domains.
  • CPU/memory requests do not fit on matching nodes.
  • Nodes have untolerated taints, are not Ready, or are cordoned.
  • Topology labels are missing or inconsistent.
Debugging rule: Start with kubectl describe pod POD_NAME -n NAMESPACE and the recent Events. Verify rules and labels before weakening a hard constraint.
08 · Amazon EKS

Scheduling considerations in EKS

The scheduling fields are Kubernetes Pod fields and apply on EKS as on other clusters. EKS adds node-group, Fargate-profile, autoscaling, AMI, and infrastructure considerations. A correct affinity rule can still leave a Pod Pending if the eligible pool has no capacity or new nodes do not carry the expected labels.

Inspect actual EKS node labels

kubectl get nodes -o wide
kubectl get nodes --show-labels
kubectl get nodes -L eks.amazonaws.com/nodegroup,topology.kubernetes.io/zone,kubernetes.io/arch
kubectl describe node NODE_NAME

Commonly observed labels include eks.amazonaws.com/nodegroup, topology.kubernetes.io/zone, and kubernetes.io/arch. Inspect your actual nodes and provider configuration rather than assuming all node types expose identical custom labels.

  • Managed/self-managed node groups: verify node labels, taints and capacity.
  • Autoscaling: scaling templates must support the Pod's required labels, resources and tolerations.
  • Availability Zones: ensure eligible capacity exists in the selected zones for zone-level requirements.
  • Fargate: placement follows Fargate profile/platform rules; don't assume EC2 node-label exercises apply identically.
  • Costs: GPU or accelerated pools may incur extra cloud cost. This guide does not create cloud resources.

10 · Hands-on practice

Progressive scheduling labs

Exercise 1 — Schedule a Pod using nodeSelector

Objective Place a Pod on a node carrying an exact lab label.

Step 1: Label an eligible lab node. Run only if you are authorized to modify node labels. Inspect kubectl get nodes -o wide first. If the first node is a tainted control-plane node or otherwise unsuitable, set NODE to the name of an eligible worker node rather than using the first-item shortcut.

NODE=$(kubectl get nodes -o jsonpath='{.items[0].metadata.name}')
kubectl label node "$NODE" training.nimbuswiztech.io/scheduling-demo=enabled --overwrite
kubectl get nodes -L training.nimbuswiztech.io/scheduling-demo

Step 2: Save as 01-node-selector.yaml.

apiVersion: v1

metadata:
  name: node-selector-demo
  namespace: nimbus-scheduling-lab
  labels:
    app: node-selector-demo
spec:
  nodeSelector:
    training.nimbuswiztech.io/scheduling-demo: enabled
  containers:
  - name: web
    image: nginx:stable-alpine

Step 3: Apply and verify.

kubectl apply -f 01-node-selector.yaml

Expected result: after the image is pulled and the Pod is ready, its NODE column should show a node carrying the lab label. A matching label alone does not guarantee scheduling if resources, taints, or node readiness prevent placement.

Exercise 3 — Use Pod affinity to place a client near a cache

Objective Deploy a labelled prerequisite Pod and require a client Pod to share its node topology domain.

Exercise 4 — Prefer spreading replicas with Pod anti-affinity

Objective Prefer to distribute replicas across nodes while still allowing a single-node lab to schedule them.

Step 1: Save as 04-web-spread.yaml.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-spread
  namespace: nimbus-scheduling-lab
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-spread
  template:
    metadata:
      labels:
        app: web-spread
    spec:
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 100
            podAffinityTerm:
              labelSelector:
                matchLabels:
                  app: web-spread
              topologyKey: kubernetes.io/hostname
      containers:
      - name: web
        image: nginx:stable-alpine
        ports:
        - name: http
          containerPort: 80

Step 2: Apply and inspect distribution.

kubectl apply -f 04-web-spread.yaml
kubectl rollout status deployment/web-spread -n nimbus-scheduling-lab --timeout=180s
kubectl get pods -n nimbus-scheduling-lab -l app=web-spread -o wide

Expected result: on multiple feasible nodes the scheduler should favor different hostname domains. On a single node, all three may run together because the anti-affinity rule is preferred.

Strict variant: replace the preferred rule with the following on a cluster with enough eligible nodes:

podAntiAffinity:
  requiredDuringSchedulingIgnoredDuringExecution:
  - labelSelector:
      matchLabels:
        app: web-spread
    topologyKey: kubernetes.io/hostname

On a one-node cluster, replicas beyond the first should remain Pending under this strict rule. This is expected behavior, not automatically a broken Deployment.

Interview takeaway: hard anti-affinity trades scheduling availability for strict separation.

11 · Real-world scenario

End-to-end design: cache-local web workload in EKS

Requirement

Web Pods should run only in a general node pool, prefer a specific eligible node tier, co-locate with cache Pods by hostname topology, and try to spread replicas across nodes. The design must also account for resources, taints and real topology labels.

Implementation checklist

  1. Inspect actual EKS node labels, zones, architecture, taints and current capacity.
  2. Decide which properties are mandatory and which are preferences.
  3. Confirm matching cache Pods exist with the intended labels, namespace and topology.
  4. Check that at least one node satisfies every hard rule and has CPU/memory capacity.
  5. Apply the workload change through reviewed configuration and watch rollout status.
  6. Verify actual placement using kubectl get pods -o wide.
  7. For every Pending replica, inspect its Events rather than inferring a cause from the status alone.

Alternatives worth evaluating

  • Use a normal Service for stable discovery if strict co-location is unnecessary.
  • Use topology spread constraints when the goal is balanced distribution across a changing replica count.
  • Use taints/tolerations plus affinity when a node pool should repel unrelated workloads and attract the intended one.
  • Check node autoscaling and node-group templates if no eligible capacity exists; affinity itself does not provision a node.

13 · Production considerations

Best practices and common mistakes

Prefer capability labels

Use labels for a node pool or capability rather than pinning a workload to one ephemeral instance or hostname.

Separate hard from soft

Use required rules only for non-negotiable needs. Soft preferences allow the scheduler to make progress when ideal placement isn't available.

Govern node labels

Placement labels can affect security and workload isolation. Restrict who can edit them and pair the design with appropriate taints, RBAC and admission controls.

Keep topology labels consistent

Inter-Pod rules depend on labels such as hostname and zone. Missing or incorrect labels can produce unintended placement or block Pods.

Use spread constraints for balancing

When the requirement is even distribution as replica counts change, compare topology spread constraints with anti-affinity.

Account for capacity

Affinity does not supersede CPU/memory requests, taints, readiness, architecture compatibility or persistent-volume topology.

Production review checklist

  • Document why each selector or affinity rule exists.
  • Confirm labels are stable, consistent and protected from unauthorized changes.
  • Use required anti-affinity only when strict separation outweighs the risk of a Pending replica.
  • Review topology spread if even distribution is the real goal.
  • Validate autoscaler templates against node labels, resources and taints.
  • Test rollout and scale up/down, not only initial creation.
  • For EKS, check the actual labels on nodes from each node group and understand Fargate placement rules.
14 · Interview preparation

36 questions and answers

Try answering before expanding each question. Search by keyword.

Level 1 — Basic questions

1. What does the Kubernetes scheduler do?
It selects a feasible node for a Pod that has not been assigned to a node, considering resource fit, scheduling constraints and scoring rules. The scheduler does not create node capacity.
2. What is nodeSelector?
A hard constraint consisting of node-label key/value pairs. Candidate nodes must have every requested pair. Use it for simple exact requirements.
3. What is node affinity?
A more expressive node-label matching feature that supports required rules and preferred weighted rules. It belongs under spec.affinity.nodeAffinity.
4. What is the difference between required and preferred affinity?
Required rules filter nodes that don't match. Preferred rules contribute to node ranking but do not guarantee placement.
5. What is Pod affinity?
A rule that attracts a Pod to topology domains containing Pods selected by a label selector.
6. What is Pod anti-affinity?
A rule that avoids topology domains containing Pods selected by a label selector. It is often used to reduce replica concentration.
7. What does topologyKey specify?
A node-label key defining the topology domain for Pod affinity/anti-affinity. For example, kubernetes.io/hostname treats each node as a separate domain.
8. What does topology.kubernetes.io/zone mean?
It is a conventional node label whose value identifies an availability zone. As topologyKey, it defines a zone-wide domain, assuming labels are present and consistent.
9. What is the purpose of node labels?
They associate metadata with nodes. Node selectors and affinity can use them to target capabilities, architecture, node pools, zones or other governed properties.
10. What does IgnoredDuringExecution mean?
The rules guide scheduling. Changing labels later does not automatically evict an already-running Pod solely because the original rule no longer matches.
11. Does a toleration force a Pod onto a tainted node?
No. A toleration permits scheduling onto that node if other constraints pass. Use node affinity or nodeSelector if placement onto a particular pool is required.
12. Why might a Pod be Pending?
No node may satisfy all hard rules; nodes may lack CPU/memory, have untolerated taints, be unavailable/cordoned, or fail another scheduling check. Read the Pod Events for the actual reason.

Level 2 — Intermediate questions

13. If nodeSelector and node affinity are both defined, what happens?
Both requirements must be satisfied. A node that matches one but not the other is not eligible.
14. How do nodeSelectorTerms combine?
Multiple terms are ORed: a node can satisfy any one term. Expressions within the same term are ANDed.
15. What does node affinity weight do?
For a matched preferred rule, the weight contributes to scoring. Weight is between 1 and 100; it influences ranking, not eligibility.
16. Explain In, NotIn, Exists and DoesNotExist.
In/NotIn compare a label value with a list; Exists/DoesNotExist test key presence. Node affinity also supports Gt/Lt for numeric-like values.
17. Why does Pod affinity need both a selector and topologyKey?
The selector identifies matching Pods; topologyKey defines the node-label domain in which those Pods affect eligibility or preference.
18. Which namespace does Pod affinity search by default?
If namespaces and namespaceSelector are omitted, matching Pods are searched in the incoming Pod's own namespace. Cross-namespace matching should be explicitly designed.
19. Does affinity guarantee that two services communicate successfully?
No. Affinity influences placement. It does not create Service connectivity, fix application configuration, ensure credentials, or make a dependency healthy.
20. Why can required anti-affinity leave replicas Pending?
Every eligible topology domain may already contain a matching Pod, or there may be fewer eligible domains than replicas. Other filters such as resources and taints also matter.
21. What is the difference between Pod anti-affinity and topology spread?
Anti-affinity repels selected Pods from topology domains. Topology spread constraints aim to keep counts balanced according to maxSkew and the selected unsatisfiable behavior.
22. Why is nodeName usually not the first recommendation?
Setting nodeName bypasses normal scheduler selection and can make a workload tightly coupled to one node. Use selectors/affinity when you want the scheduler to choose from eligible nodes.
23. Can a soft preference be overridden?
Yes. Preferred rules influence scoring but are not hard guarantees. Other scores, required constraints and capacity can result in a different feasible node.
24. Why can Pod affinity/anti-affinity cost more scheduler work?
The scheduler evaluates Pod selectors and relationships across topology domains. Use inter-Pod rules when they deliver a meaningful locality/separation benefit, and consider topology spread for balancing goals in large clusters.

Level 3 — Real-world scenario questions

25. A Pod is Pending with nodeSelector. How do you diagnose it?
Approach: run kubectl describe pod POD -n nimbus-scheduling-lab and read Events. Compare exact keys/values with kubectl get nodes --show-labels. If a node matches, check resource requests, taints/tolerations and node readiness/cordoning. Fix: correct the mistaken label/rule, add suitable capacity, or supply the required toleration if appropriate. Verify: recheck Events and kubectl get pod POD -o wide. Alternative causes include image pull failure after binding, not scheduling failure.
26. Node affinity requires SSD nodes, but no node is labelled SSD.
Approach: inspect kubectl get nodes --show-labels and the node pool provisioning source. Confirm whether SSD is truly a requirement or just a preference. Fix: provision or correctly label suitable nodes according to the organization's node-label policy; only change a hard rule if the application can safely run without SSD. Verify: check that the Pod is scheduled on a node satisfying the rule and validate storage behavior.
27. A preferred node affinity rule appears to be ignored.
Approach: examine the preferred label, current feasible nodes and actual node assignment. Use kubectl get nodes -L LABEL_KEY with the real label key. Reason: soft rules affect scores; they cannot guarantee a node and may be outweighed by other priorities. Fix: correct labels if wrong; use required affinity only if the property is mandatory and unschedulability is acceptable. Verify over multiple feasible nodes—not just one.
28. Web Pods with required cache affinity are Pending.
Approach: verify cache Pod labels using kubectl get pods --show-labels -o wide -n nimbus-scheduling-lab; inspect labelSelector, namespace scope and topologyKey in the web Pod. Confirm the cache Pod is assigned to a node in the expected topology domain. Fix: correct the selector/scope/topology, deploy the prerequisite Pod first, or soften the locality requirement when appropriate. Verify: compare NODE columns and re-read scheduler Events. Resources or taints may still block placement.
29. Three replicas use required hostname anti-affinity, but only two eligible nodes exist.
Approach: inspect Events and count nodes satisfying all hard constraints, not just raw cluster node count. Reason: a required hostname rule prevents more than one matching replica per node. Fix: add eligible capacity or switch to preferred anti-affinity if strict separation is not mandatory. Verify: all replicas should be Ready when constraints and capacity allow; otherwise a remaining Pending replica is expected.
30. Node labels change after a workload is running. Will the Pod move?
Answer: not automatically due solely to the ignored-during-execution rule. Inspect actual placement with kubectl get pods -o wide. If placement must change, plan a controlled rollout or rescheduling after verifying new nodes satisfy all constraints. Don't assume a label update migrates an existing Pod.
31. A Pod has nodeSelector and node affinity, but a candidate matches only one.
Approach: inspect the full Pod spec and candidate labels. Reason: both requirements are applied when both are present. Fix: align the rules with the intended policy, but retain both if they represent distinct requirements. Verify: compare labels and ensure scheduler Events no longer report a selector/affinity mismatch.
32. An EKS Pod remains Pending after a node group scales up.
Approach: check Pod Events, kubectl get nodes --show-labels, node taints, allocatable resources and node readiness. Compare new nodes against the required node-group label, architecture and zone. Inspect autoscaler/controller events where available. Fix: adjust node-group configuration/labels or Pod policy based on the true requirement; add capacity that can satisfy hard rules. Verify: new nodes become Ready and match the constraints. Scaling alone doesn't guarantee eligibility.
33. Anti-affinity uses zone topology, but some nodes lack zone labels.
Approach: inspect kubectl get nodes -L topology.kubernetes.io/zone and actual cloud/provider labels. Pod anti-affinity requires consistent topology labels to behave predictably. Fix: correct node provisioning/provider labels or use a topology key that is reliably present. Verify: every eligible node has a valid topology value and the resulting placement matches expectations.
34. A team wants replicas evenly spread across zones. Should it use anti-affinity?
Approach: clarify whether the requirement is “never share a domain” or “keep replica counts balanced.” For balance, evaluate topologySpreadConstraints using topology.kubernetes.io/zone, a justified maxSkew, and DoNotSchedule versus ScheduleAnyway. Fix: ensure zones are labelled and have sufficient capacity. Verify counts per zone after rollout. Anti-affinity and topology spread are related but not equivalent.
35. A team wants all workloads kept off a dedicated tainted pool. Are taints enough?
Approach: check node taints and each Pod's tolerations. A matching toleration permits scheduling there, but does not attract a workload. If a workload must target that pool, add appropriate node affinity/selector. Fix: review taint effect, toleration matching and node labels together. Verify: inspect scheduled nodes and ensure unrelated workloads do not have broad unnecessary tolerations.
36. How would you roll out a new affinity policy safely?
Approach: inventory current labels, resources and capacity; classify each rule as mandatory or preferred; test with a small workload; validate node autoscaling compatibility; then update through reviewed configuration and watch rollout status/Events. Fix: retain a rollback plan and avoid strict rules until enough eligible capacity exists. Verify: confirm actual Pod placement, readiness and behavior during scaling/rolling update—not just successful manifest application.
