Kubernetes Services

A practical beginner guide to stable networking for Pods: ClusterIP, NodePort, LoadBalancer, ExternalName, selectors, ports, EndpointSlices, troubleshooting and interview preparation.

1. Introduction

A Kubernetes Service is an API object that provides a stable way to reach a logical group of backend endpoints, commonly Pods. Pods are replaceable and their IP addresses can change. A Service gives clients a stable name and, for most Service types, a stable virtual IP while the selected endpoints change behind it.

Why it exists

Applications need to communicate without hard-coding individual Pod IPs. A Service separates clients from the changing set of replicas.

Analogy

A Service is like a company help-desk number. Employees (Pods) may change shifts, but callers keep using the same number and the desk routes calls to an available employee.

DevOps example

A frontend calls catalog-api. Kubernetes selects healthy matching backend Pods through a Service; scaling or replacing Pods does not require changing the frontend's destination.

Learning objectives

  • Explain why Services are needed when Pod IPs are ephemeral.
  • Understand selectors, labels, Service ports, target ports and EndpointSlices.
  • Compare ClusterIP, NodePort, LoadBalancer, ExternalName and headless Services.
  • Apply manifests and validate traffic using kubectl.
  • Diagnose empty endpoints, selector mismatches, port mistakes and external exposure problems.
Important: A Service is not the application process and does not create Pods. Workload controllers such as Deployments create and maintain Pods. A Service selects endpoints and provides a stable networking abstraction.

2. Core concepts and terminology

Service types

TypeReachabilityTypical useKey caution
ClusterIPInside the cluster; default typeInternal APIs, databases, service-to-service callsNot directly reachable from outside the cluster by default.
NodePortExposes a port on node IP addresses, subject to cluster networking and firewall rulesLearning labs or environments with an external load balancer of their ownDefault NodePort range is commonly 30000–32767; access depends on node network reachability.
LoadBalancerRequests an external load balancer through a supported cloud/provider integration or installed implementationExpose an application outside the clusterMay create billable infrastructure; local clusters may not provision one automatically.
ExternalNameDNS alias to an external hostnameGive a Kubernetes DNS name for an external serviceReturns a DNS CNAME; it does not proxy traffic or select Pods.
Headless (clusterIP: None)DNS publishes endpoint records rather than a Service virtual IPStateful discovery where clients need individual endpointsNo virtual-IP load balancing by the Service proxy.

Important Service fields

  • metadata.name: stable DNS name within a namespace.
  • spec.type: exposure behavior.
  • spec.selector: label map used to identify matching Pods for a selector-based Service. Keys and values must match Pod labels exactly.
  • spec.ports[].port: port exposed by the Service.
  • spec.ports[].targetPort: destination port on the backend Pod; can be a number or a named container port.
  • spec.ports[].protocol: usually TCP for HTTP applications.
  • spec.ports[].nodePort: allocated or specified node port for NodePort Services.
  • spec.clusterIP: virtual IP assigned to most Services; setting it to None creates a headless Service.
  • spec.externalName: target DNS hostname for ExternalName Services.

Port vocabulary

FieldExampleMeaning
Container portcontainerPort: 8080Documents the port the container is expected to listen on; it does not itself publish the port.
Service portport: 80Port clients use when connecting to the Service.
Target porttargetPort: 8080Port on the selected backend endpoint.
Node portnodePort: 30080Port exposed on nodes for NodePort Services, if allocated.

Example: a client calls catalog-api:80; the Service forwards to a ready endpoint's port 8080. The Service port and target port do not need to be identical.

Labels, selectors and endpoints

Labels are key/value metadata on Pods. A Service selector matches labels to find backends. EndpointSlices represent sets of network endpoints for a Service and include readiness-related endpoint information. If a selector matches no Pods, the Service can exist normally but have no usable endpoints.

DNS and namespaces

Within the same namespace, clients can typically call http://catalog-api. Across namespaces, use a qualified name such as catalog-api.team-a; the full DNS name commonly follows catalog-api.team-a.svc.cluster.local, though the cluster domain can differ.

Services without selectors

A Service may omit a selector when an administrator intentionally manages EndpointSlices or connects to non-Pod endpoints. Kubernetes does not automatically create selector-derived endpoints for that Service. This is an advanced pattern; beginner labs should use selectors.

3. Architecture and traffic flow

  1. A client resolves a Service name through cluster DNS.
  2. For ClusterIP/NodePort/LoadBalancer Services, traffic is sent to the Service virtual IP or applicable external entry point and port.
  3. Kubernetes networking components (commonly kube-proxy or a replacement implementation) direct traffic toward an eligible endpoint.
  4. The Service selector matches Pod labels; EndpointSlices represent endpoint addresses and readiness information.
  5. As Pods scale, become unready, or are replaced, endpoint information is updated without changing the client's Service name.
Kubernetes Service APIs define the desired abstraction. The exact packet-routing implementation depends on the cluster's networking implementation; do not assume every cluster uses kube-proxy in the same mode.

4. Environment preparation

Use Minikube, kind, or an authorized existing cluster. This guide does not require EKS. Public images are used in labs; a cluster needs registry access. Cloud LoadBalancer examples may provision billable cloud infrastructure, so the default lab uses ClusterIP and port-forwarding instead.

kubectl version --client
kubectl cluster-info
kubectl get nodes
kubectl get namespaces
kubectl config current-context
  • kubectl version --client: checks the local client.
  • kubectl cluster-info: checks API connectivity.
  • kubectl get nodes: verifies registered nodes and Ready state.
  • kubectl get namespaces: lists namespaces.
  • kubectl config current-context: shows the target cluster/context.

Optional local cluster start (requires Minikube installed):

minikube start
kubectl get nodes
mkdir -p kubernetes-services-lab
cd kubernetes-services-lab
kubectl create namespace nimbus-services-lab
If the namespace already exists, inspect it and verify it is dedicated to your lab. On shared clusters, avoid deleting or changing resources outside your own namespace. If access is Forbidden, request the correct least-privilege RBAC permissions.

5. Step-by-step hands-on practice

Exercise 1 — Create a Deployment as a Service backend

Objective: Create three repeatable Pods with a matching label. A Service routes to workload endpoints; it does not create the Pods.

Save as web-deployment.yaml:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: nimbus-services-lab
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: nginx
        image: nginx:1.27
        ports:
        - name: http
          containerPort: 80
        resources:
          requests:
            cpu: 50m
            memory: 64Mi
          limits:
            cpu: 250m
            memory: 128Mi
kubectl apply -f web-deployment.yaml
kubectl rollout status deployment/web -n nimbus-services-lab
kubectl get pods -n nimbus-services-lab -l app=web -o wide

Explanation: The Deployment's selector and Pod template labels must match. Three replicas help demonstrate multiple endpoints. Resource values are small lab examples, not universal production sizing.

Expected result: Three Pods normally reach Running/Ready if scheduling and image pulls succeed.

Troubleshooting: If not ready, describe the Pods and inspect Events. Check node capacity and image access.

Exercise 2 — Expose the Pods with ClusterIP

Objective: Create a stable internal name.

Save as web-clusterip.yaml:

apiVersion: v1
kind: Service
metadata:
  name: web
  namespace: nimbus-services-lab
spec:
  type: ClusterIP
  selector:
    app: web
  ports:
  - name: http
    protocol: TCP
    port: 80
    targetPort: http
kubectl apply -f web-clusterip.yaml
kubectl get service web -n nimbus-services-lab
kubectl get endpointslices -n nimbus-services-lab -l kubernetes.io/service-name=web
kubectl describe service web -n nimbus-services-lab

Explanation: Service port 80 is mapped to the named container port http (80). The selector matches the Deployment's Pod labels. The Service receives a cluster-internal virtual IP.

Expected result: ClusterIP is assigned and EndpointSlices list the matching ready Pod addresses. EndpointSlice output can vary by Kubernetes version.

Troubleshooting: If no endpoints appear, compare spec.selector with actual Pod labels and check Pod readiness.

Exercise 3 — Test Service traffic safely using port-forward

Objective: Access a ClusterIP Service from the local machine without exposing it publicly.

kubectl port-forward service/web 8080:80 -n nimbus-services-lab

Keep that terminal running. In a second terminal:

curl -I http://127.0.0.1:8080

Expected result: A typical NGINX response is an HTTP success response. Use Ctrl+C in the first terminal to stop port-forwarding.

Explanation: Port-forwarding creates a temporary local tunnel through the Kubernetes API. It is useful for testing, but is not the same as publicly exposing the Service.

Exercise 4 — Demonstrate a selector mismatch

Objective: Understand why a Service can exist with zero endpoints.

kubectl get pods -n nimbus-services-lab --show-labels
kubectl patch service web -n nimbus-services-lab --type merge -p '{"spec":{"selector":{"app":"wrong-label"}}}'
kubectl get endpointslices -n nimbus-services-lab -l kubernetes.io/service-name=web

Expected result: The Service remains, but it no longer matches the app=web Pods, so usable endpoints disappear.

Restore the selector:

kubectl patch service web -n nimbus-services-lab --type merge -p '{"spec":{"selector":{"app":"web"}}}'
kubectl get endpointslices -n nimbus-services-lab -l kubernetes.io/service-name=web

Safety: Perform this only on the Service created in this lab. On a shared namespace, do not patch an unknown Service.

Exercise 5 — Use NodePort in a lab

Objective: Understand the NodePort exposure mechanism without assuming the node is internet-accessible.

Save as web-nodeport.yaml:

apiVersion: v1
kind: Service
metadata:
  name: web-nodeport
  namespace: nimbus-services-lab
spec:
  type: NodePort
  selector:
    app: web
  ports:
  - name: http
    port: 80
    targetPort: http
    nodePort: 30080
kubectl apply -f web-nodeport.yaml
kubectl get service web-nodeport -n nimbus-services-lab
kubectl describe service web-nodeport -n nimbus-services-lab
kubectl get nodes -o wide

Expected result: Service displays port mapping such as 80:30080/TCP. Access via NodeIP:30080 depends on node routing, firewall rules and local-cluster networking.

Minikube tip: minikube service web-nodeport -n nimbus-services-lab --url may provide a reachable URL depending on driver/platform.

Troubleshooting: Check endpoints first, then node address reachability and firewall/security-group rules. Do not open a node port to the internet without a security review.

Exercise 6 — Understand LoadBalancer and ExternalName

Objective: Recognize how the types differ; do not create a public cloud load balancer in a cost-sensitive lab without approval.

Illustrative LoadBalancer manifest (apply only in an authorized environment where external load balancer provisioning is expected):

apiVersion: v1
kind: Service
metadata:
  name: web-public
  namespace: nimbus-services-lab
spec:
  type: LoadBalancer
  selector:
    app: web
  ports:
  - name: http
    port: 80
    targetPort: http
# Only if you intentionally choose to provision this:
kubectl apply -f web-loadbalancer.yaml
kubectl get service web-public -n nimbus-services-lab -w

In a supported cloud environment, a controller may provision an external load balancer asynchronously. In local clusters, EXTERNAL-IP may remain pending unless an appropriate implementation is installed.

ExternalName example, which creates only a DNS alias and does not forward traffic:

apiVersion: v1
kind: Service
metadata:
  name: external-docs
  namespace: nimbus-services-lab
spec:
  type: ExternalName
  externalName: kubernetes.io
kubectl apply -f external-name.yaml
kubectl get service external-docs -n nimbus-services-lab -o yaml

DNS resolution can be tested from a Pod with DNS tools available. HTTP/TLS may be affected by hostname and certificate expectations when using ExternalName.

Exercise 7 — Create a headless Service

Objective: See a Service that publishes endpoint DNS without a virtual IP.

Save as web-headless.yaml:

apiVersion: v1
kind: Service
metadata:
  name: web-headless
  namespace: nimbus-services-lab
spec:
  clusterIP: None
  selector:
    app: web
  ports:
  - name: http
    port: 80
    targetPort: http
kubectl apply -f web-headless.yaml
kubectl get service web-headless -n nimbus-services-lab
kubectl get endpointslices -n nimbus-services-lab -l kubernetes.io/service-name=web-headless

Expected result: The Service's ClusterIP field displays None. Endpoint addresses are still represented through EndpointSlices and DNS behavior, but no Service virtual-IP load balancing is provided.

6. End-to-end example: internal catalog web application

Requirement: Run three NGINX replicas and give internal clients a stable DNS name. Validate that traffic continues through the Service abstraction when a Pod is replaced.

Complete manifest — save as catalog-app.yaml

apiVersion: v1
kind: Namespace
metadata:
  name: nimbus-services-lab
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: catalog
  namespace: nimbus-services-lab
spec:
  replicas: 3
  selector:
    matchLabels:
      app: catalog
  template:
    metadata:
      labels:
        app: catalog
    spec:
      containers:
      - name: nginx
        image: nginx:1.27
        ports:
        - name: http
          containerPort: 80
        readinessProbe:
          httpGet:
            path: /
            port: http
          initialDelaySeconds: 2
          periodSeconds: 5
        resources:
          requests:
            cpu: 50m
            memory: 64Mi
          limits:
            cpu: 250m
            memory: 128Mi
---
apiVersion: v1
kind: Service
metadata:
  name: catalog
  namespace: nimbus-services-lab
spec:
  type: ClusterIP
  selector:
    app: catalog
  ports:
  - name: http
    port: 80
    targetPort: http

Execution:

kubectl apply -f catalog-app.yaml
kubectl rollout status deployment/catalog -n nimbus-services-lab
kubectl get deployment,replicaset,pods,service -n nimbus-services-lab
kubectl get endpointslices -n nimbus-services-lab -l kubernetes.io/service-name=catalog

Test from the local machine:

kubectl port-forward service/catalog 8080:80 -n nimbus-services-lab

In another terminal, run:

curl -I http://127.0.0.1:8080

Observe replacement:

kubectl get pods -n nimbus-services-lab -l app=catalog
# Replace POD_NAME with one actual catalog Pod name:
kubectl delete pod POD_NAME -n nimbus-services-lab
kubectl get pods -n nimbus-services-lab -l app=catalog -w

What is happening? Deployment maintains three replicas; Service selects Pods labelled app=catalog; port 80 forwards to named port http; readiness affects endpoint eligibility; deleting one Pod causes its ReplicaSet to create a replacement. Clients continue to use the stable Service name.

Common failure paths

  • No endpoints: selector and Pod labels differ, or Pods are not ready.
  • Connection refused: app not listening on the target port, or incorrect targetPort.
  • Port-forward fails: verify Service exists, local port is free, and selected Pods are available.
  • LoadBalancer pending: verify provider integration and permissions; do not assume local clusters can provision external infrastructure.

8. Best practices

  • Use ClusterIP for internal traffic. Do not expose a service externally unless the requirement calls for it.
  • Make selectors specific. Reuse a consistent label convention such as app.kubernetes.io/name to avoid accidentally selecting unrelated Pods.
  • Understand the port chain. Document the relationship between client port, Service port, targetPort and the actual listener.
  • Use readiness checks for traffic eligibility. A process existing does not mean it is ready to serve requests.
  • Prefer DNS names over Pod IPs. Pod addresses change when Pods are replaced. Use Service DNS for stable discovery.
  • Be deliberate with NodePort and LoadBalancer. Check security groups, firewall rules, source ranges and cost before external exposure.
  • Keep namespaces and naming consistent. Namespace-qualified Service names reduce ambiguity across teams.
  • Do not use ExternalName as a reverse proxy. It returns a DNS alias; HTTP Host and TLS certificate behavior may still need attention.
  • Use headless Services for a clear discovery need. They do not provide a Service virtual IP or Service-proxy load balancing.
  • Inspect EndpointSlices when debugging. They show which endpoint addresses Kubernetes has recorded for the Service.
  • Do not hard-code ClusterIP addresses into application config. Prefer DNS names unless there is a compelling, managed reason otherwise.
  • Plan production exposure. Consider Ingress or Gateway API for HTTP routing, TLS and host/path rules where appropriate; these are separate resources and may require a controller.

9. Interview preparation

Search and expand the questions. Answers focus on reasoning and verification, not memorization.

Level 1 — Basic questions

1. What is a Kubernetes Service?
An API object that provides a stable networking abstraction for a logical set of endpoints, commonly Pods, so clients do not need to track changing Pod IPs.
2. Why are Services needed?
Pods are ephemeral and may be recreated with new IP addresses. A Service gives clients a stable name and stable virtual IP for supported types while backends change.
3. What are the four standard Service types?
ClusterIP, NodePort, LoadBalancer and ExternalName. Headless is a ClusterIP Service configured with clusterIP: None.
4. What is ClusterIP?
The default type, exposing a Service on an internal virtual IP for cluster-internal access.
5. What is NodePort?
It exposes a Service on a port on each node, in addition to ClusterIP behavior. Actual reachability depends on routing and firewall rules.
6. What does LoadBalancer do?
It requests an external load balancer from a supported provider or installed implementation. Kubernetes alone does not guarantee a load-balancing infrastructure is present.
7. What does ExternalName do?
It maps a Service DNS name to an external DNS hostname using a CNAME. It does not proxy traffic or select Pod endpoints.
8. What is a Service selector?
A set of label key/value requirements used to find matching Pods. If it matches no Pods, selector-derived endpoints are absent.
9. What is targetPort?
The port on the backend endpoint to which Service traffic is directed. It can be a number or a named container port.
10. What is the difference between port and targetPort?
Clients connect to Service port; traffic is forwarded to the endpoint's targetPort. They can be different.
11. What is an EndpointSlice?
An API object that stores a subset of a Service's network endpoints and associated information, including endpoint readiness metadata.
12. What is a headless Service?
A Service with clusterIP: None. It has no virtual IP; DNS can publish endpoint addresses for direct discovery.

Level 2 — Intermediate questions

13. How does a Service discover backend Pods?
For a selector-based Service, the control plane matches the selector against Pod labels and updates EndpointSlices as matching endpoints change. Readiness affects whether endpoints are considered ready for normal traffic.
14. Why can a Service exist but have no endpoints?
The selector may not match Pod labels, no matching Pods may exist, Pods may not be ready, or the Service may be selectorless without manually managed endpoint data. Compare Service selector, Pod labels and EndpointSlices.
15. Does containerPort publish a port by itself?
No. It documents a port in the Pod specification. Service, port-forwarding, host networking or other networking configuration determines how clients reach the application.
16. How does cross-namespace DNS work?
Use a namespace-qualified name such as web.team-a, or a full service DNS name. The cluster domain may differ from cluster.local.
17. Does NodePort guarantee internet access?
No. A node's IP must be reachable and network policies/firewalls/security groups must allow the traffic. Local cluster drivers may require a helper or tunnel.
18. Why might LoadBalancer remain pending?
The cluster may lack a compatible provider controller, permissions, subnet configuration or a load balancer implementation. Inspect Service events and provider logs rather than assuming the manifest is wrong.
19. What happens if targetPort is incorrect?
Traffic reaches the wrong port on the endpoint and may fail. Verify the actual application listener, named ports and Service port mapping.
20. Can a Service target endpoints outside the cluster?
Yes, for specialized selectorless Service patterns with manually managed EndpointSlices, subject to API and networking constraints. ExternalName is another approach for DNS aliasing but does not proxy traffic.
21. How does readiness affect Service traffic?
For typical selector-based Services, unready endpoints are not normally used for regular traffic. Investigate Pod readiness and EndpointSlice conditions when a running Pod is not receiving requests.
22. Does a Service load-balance equally across all Pods?
A Service provides endpoint distribution through the cluster networking implementation, but it does not promise mathematically equal request counts. Connections, session behavior, topology and implementation affect distribution.
23. What is the difference between Service and Ingress?
A Service gives stable access to a set of endpoints. Ingress defines HTTP/HTTPS routing rules and requires an Ingress controller; it commonly routes external traffic to Services.
24. When would you choose headless instead of ClusterIP?
When clients need endpoint-level discovery, commonly for stateful systems or custom peer discovery, rather than a single virtual IP. Use ordinary ClusterIP when stable service-level access is sufficient.

Level 3 — Real-time scenario-based questions

25. The Service exists but requests time out. How do you investigate?
Approach: Run kubectl describe svc SERVICE -n NS, inspect selector and ports, then kubectl get endpointslices -n NS -l kubernetes.io/service-name=SERVICE. If endpoints are absent, check labels and readiness. If endpoints exist, test the backend port and inspect NetworkPolicies, application listener, routing and client DNS. Verify with a request from an in-cluster client or port-forward. Timeouts can have multiple causes.
26. A Service has zero endpoints after a deployment update.
Compare kubectl get svc SERVICE -o yaml selector with kubectl get pods --show-labels. Confirm the Deployment template labels and readiness. A changed label or selector mismatch is common; if Pods match but are unready, inspect probe events. Fix only the actual mismatch, then verify EndpointSlices repopulate.
27. The Service sends traffic to the wrong application.
Inspect selector and all matching Pod labels: kubectl get pods -n NS --show-labels. Check EndpointSlice target addresses. Broad selectors may match another workload. Apply unique labels/selectors and verify only intended Pods appear as endpoints.
28. Service port is 80 but app listens on 8080. Is this valid?
Yes. Set Service port: 80 and targetPort: 8080 (or a named port whose container listener is 8080). Verify the application actually listens on 8080 and test the Service after applying the corrected manifest.
29. NodePort works inside a node but not from a laptop.
Verify kubectl get svc shows the allocated nodePort, inspect node IPs, and test node reachability. Check routing, firewall/security groups and local cluster driver behavior. Do not assume NodePort is automatically public; use Minikube's service helper where applicable.
30. LoadBalancer EXTERNAL-IP stays pending in a local lab.
This can be expected if the local cluster has no load balancer implementation. Check kubectl describe svc and events. Use ClusterIP plus port-forward for the basic lab, or install/configure an appropriate load-balancer implementation only when authorized.
31. One of three Pods is unhealthy and users report intermittent failures.
Inspect Pods, readiness, logs and EndpointSlice endpoints. Determine whether the unhealthy Pod is still marked ready, has a probe misconfiguration, or returns application errors. Fix the root cause and confirm the endpoint is removed while unready and returns after recovery.
32. A frontend in another namespace cannot resolve backend Service name.
A short name resolves relative to the caller's namespace. Try backend.namespace-name or the full service DNS name. If qualified DNS still fails, verify Service existence and cluster DNS health from a test Pod.
33. ExternalName resolves but HTTPS fails certificate validation.
ExternalName creates a DNS alias, not a proxy that rewrites HTTP Host or TLS SNI. The target may expect a different hostname/certificate. Use an appropriate hostname or a proxy/gateway architecture that explicitly handles TLS and host routing.
34. After scaling the Deployment, traffic does not reach new Pods.
Check new Pod readiness and labels, then inspect EndpointSlices. New Pods may be unready, use different labels, or fail startup. Confirm the Service selector matches the template labels and probe succeeds before expecting them to receive normal traffic.

10. Practice assignments

Beginner exercises

  2. Change Service port to 8081 while retaining targetPort 80. Verify with port-forward mapping 9090:8081. Hint: clients use Service port.
  3. Create a NodePort Service with an automatically allocated nodePort. Verify its port mapping. Hint: omit nodePort and inspect the allocated value.
  4. Create an ExternalName Service pointing to kubernetes.io. Inspect the Service object and explain that it is DNS aliasing only.
  5. Create a headless Service and compare its clusterIP field with an ordinary ClusterIP Service.

Modification and troubleshooting exercises

  1. Intentionally change a selector in your own lab Service; document how EndpointSlices change, then restore it.
  2. Use a wrong targetPort and observe the connection failure; restore the correct target port.
  3. Scale the Deployment from three replicas to five and verify endpoint changes.
  4. Delete one Deployment-managed Pod and observe the replacement; confirm the Service name remains unchanged.
  5. Investigate a NodePort that cannot be reached from outside the local cluster. Separate Service endpoint problems from node-network reachability.

Scenario challenges

  1. Users report intermittent 503s after a rollout. Determine whether Pods are unready, app instances fail, or selectors are too broad.
  2. A frontend cannot call a backend in another namespace. Implement and validate namespace-qualified DNS.
  3. The platform team requests public access for a demo. Compare NodePort, LoadBalancer and an HTTP routing option; recommend a safe design and identify any cost or firewall impact.

11. Quick revision and cheat sheet

Must remember

  • ClusterIP is the default Service type and is internal to the cluster.
  • NodePort exposes a node port; firewall/routing still determines reachability.
  • LoadBalancer needs a supported provider/controller and may incur cost.
  • ExternalName returns a DNS CNAME; it does not proxy traffic.
  • Headless Service uses clusterIP: None and does not provide a virtual IP.
  • Selectors match Pod labels. Service creation alone does not create backend Pods.
  • Service port is the client-facing port; targetPort is the endpoint port.
  • EndpointSlices show endpoint addresses and readiness metadata.

12. Final lab cleanup

First inspect the namespace to make sure it contains only resources you created:

kubectl get all,configmap,secret -n nimbus-services-lab

Delete the named lab resources:

kubectl delete deployment web catalog -n nimbus-services-lab --ignore-not-found
kubectl delete service web web-nodeport web-public web-headless catalog external-docs -n nimbus-services-lab --ignore-not-found

After confirming the namespace is dedicated to this training lab and contains no shared resources, remove it:

kubectl delete namespace nimbus-services-lab
Shared-cluster warning: Namespace deletion removes all namespaced resources in it, including resources you did not create. Never delete shared namespaces, nodes, cluster roles or cluster-wide components for this lab. A LoadBalancer Service may create cloud infrastructure; verify the associated resource was removed and review provider billing if you created one.
