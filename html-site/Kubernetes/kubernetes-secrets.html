01 · Why Secrets exist

Introduction and real-world purpose

A Kubernetes Secret is an API object intended to hold a small amount of sensitive data such as passwords, tokens, or keys. It separates credentials from Pod specifications and container images, allowing applications to receive only the values they need. Secrets are a delivery mechanism—not a complete secret-management or encryption system by themselves. citeturn948129view0turn319051search4

Analogy: a locked credential envelope

An application image is like a reusable appliance. The Secret is a credential envelope handed only to an authorized operator or workload. The envelope is not truly safe just because it is labelled “secret”: who can open it, where it is stored, and whether copies exist still matter.

Real-world DevOps examples

  • Application database username/password.
  • Private container registry credentials used when pulling images.
  • TLS certificate and private key for a TLS endpoint.
  • SSH credentials for a narrowly scoped integration.

Creating Secret objects: three common options

Imperative command

# Only fake training values; never put real credentials
# into command lines or shell history.
kubectl create secret generic demo-creds \
  --from-literal=username=training-user \
  --from-literal=password=TRAINING_ONLY_NOT_A_REAL_PASSWORD \
  -n nimbus-secrets-lab

Convenient for demonstrations. Real literal values can remain in shell history, terminal logging, and process inspection. Prefer a protected credential workflow for real values.

Declarative YAML with stringData

apiVersion: v1
kind: Secret
metadata:
  name: demo-creds
  namespace: nimbus-secrets-lab
type: Opaque
stringData:
  username: training-user
  password: TRAINING_ONLY_NOT_A_REAL_PASSWORD

Easy to understand, but real plaintext in a manifest can leak through Git, reviews, backups, or generated artifacts. Do not commit real values.

Creating type-specific Secrets

Generic

kubectl create secret generic db-demo \
  --from-literal=username=training-user \
  -n nimbus-secrets-lab

Training use only. The password and real credentials are deliberately omitted.

TLS

kubectl create secret tls demo-tls \
  --cert=./tls.crt \
  --key=./tls.key \
  -n nimbus-secrets-lab

Requires a matching PEM certificate and private key. Exercise 4 creates temporary local test files.

Registry credentials

kubectl create secret docker-registry regcred \
  --docker-server=REGISTRY_HOST \
  --docker-username=REGISTRY_USER \
  --docker-password=REGISTRY_PASSWORD \
  -n nimbus-secrets-lab

Syntax illustration only. Do not paste a real password on the command line: shell history or process inspection can expose it. Use an approved credential provider/workflow.

04 · How Pods consume secrets

Environment variables, files, and image pull credentials

Environment variable reference

env:
- name: DB_USERNAME
  valueFrom:
    secretKeyRef:
      name: db-credentials
      key: username
- name: DB_PASSWORD
  valueFrom:
    secretKeyRef:
      name: db-credentials
      key: password

Use secretKeyRef when the application expects a specific environment variable. Use envFrom.secretRef only when importing all valid keys is intentional. Existing process environment values do not change when the Secret is updated; recreate the Pod or roll out its owning workload.

File volume reference

volumes:
- name: credentials
  secret:
    secretName: db-credentials
    defaultMode: 0440
containers:
- name: app
  image: example.invalid/app:1.0
  volumeMounts:
  - name: credentials
    mountPath: /run/credentials
    readOnly: true

The volume projects keys as files. A normal Secret volume is updated eventually when the Secret changes, though the application may still need to reread the file. A Secret used through subPath does not receive automated updates. citeturn644162view4

Private registry Secret reference

spec:
  imagePullSecrets:
  - name: regcred
  containers:
  - name: app
    image: private-registry.example/team/app:1.0

The referenced registry Secret needs to exist in the same namespace and contain the expected Docker config Secret format. This excerpt is a Pod-spec fragment, not a complete deployable manifest. Real registry values are intentionally omitted.

05 · Security model

What protects a Kubernetes Secret?

Essential security facts

  • Base64 is not encryption. A user who can read a Secret can decode its value.
  • Encryption at rest is separate. Kubernetes supports encryption of API resource data at rest, but cluster operators must configure and manage it. Confirm provider and cluster configuration rather than assuming it is enabled.
  • RBAC must be narrow. Permission to get reveals a Secret; list and watch can also expose Secret content. citeturn319051search7
  • Pod creation is security-sensitive. A user who can create Pods in a namespace may be able to mount Secrets available there. Namespace boundaries are useful but not an absolute trust boundary.
  • Don't leak through tooling. Avoid displaying Secret YAML, decoded values, credentials in command arguments, terminal transcripts, CI logs, issue trackers, or Git history.
  • Backups and nodes matter. Protect etcd backups, control plane data, node access and storage. Consider the impact of a compromised privileged workload.
  • Rotate after exposure. Deleting a Secret object is not enough if copies or credentials remain valid elsewhere. Revoke/rotate the actual credential and assess exposure.

Access-at-rest checklist

ControlQuestion to askEvidence / action

07 · Hands-on training

Progressive practical labs

Use only fake credentials supplied in this document. All resources go in nimbus-secrets-lab. Exact Pod names, timing, and status output vary by cluster.

Exercise 1 — Create a generic Secret and inject values into a Pod

Objective Create an Opaque Secret and prove that the Pod has the referenced environment values without printing those values to logs.

Step 1: Save as 01-generic-env.yaml. Values are fake training placeholders only.

apiVersion: v1
kind: Secret
metadata:
  name: demo-db-credentials
  namespace: nimbus-secrets-lab
type: Opaque
stringData:
  username: training-user
  password: TRAINING_ONLY_NOT_A_REAL_PASSWORD
---
apiVersion: v1
kind: Pod
metadata:
  name: secret-env-demo
  namespace: nimbus-secrets-lab
spec:
  restartPolicy: Always
  containers:
  - name: check-env
    image: busybox:1.36
    command: ["/bin/sh", "-c"]
    args:
    - 'if [ -n "$DB_USERNAME" ] && [ -n "$DB_PASSWORD" ]; then echo "credential variables loaded"; else echo "credential variables missing"; fi; sleep 3600'
    env:
    - name: DB_USERNAME
      valueFrom:
        secretKeyRef:
          name: demo-db-credentials
          key: username
    - name: DB_PASSWORD
      valueFrom:
        secretKeyRef:
          name: demo-db-credentials
          key: password

Step 2: Apply and verify.

kubectl apply -f 01-generic-env.yaml
kubectl get secret demo-db-credentials -n nimbus-secrets-lab
kubectl describe secret demo-db-credentials -n nimbus-secrets-lab
kubectl wait --for=condition=Ready pod/secret-env-demo -n nimbus-secrets-lab --timeout=120s
kubectl logs secret-env-demo -n nimbus-secrets-lab

Expected result (illustrative): the Secret is listed as Opaque with two data items; the Pod logs credential variables loaded. The values themselves should not be printed.

Step 3: Inspect access and restart semantics.

kubectl auth can-i get secrets -n nimbus-secrets-lab
kubectl describe pod secret-env-demo -n nimbus-secrets-lab

Explanation: secretKeyRef maps one Secret key to a named environment variable. If the object or required key is missing, container startup can fail. Environment values already given to a running process do not change when the Secret is updated; restart/recreate the Pod to consume new values.

Troubleshooting: Read Pod Events using kubectl describe pod for missing Secret/key errors. Verify both Secret and Pod are in the same namespace.

Interview takeaway: kubectl get secret and kubectl describe secret normally avoid displaying the contents, but kubectl get secret -o yaml can expose Base64 values.

Exercise 2 — Mount Secret data as read-only files

Objective Make a Secret available as files and verify their paths and values using fake credentials.

Step 1: Save as 02-secret-volume.yaml.

apiVersion: v1
kind: Secret
metadata:
  name: demo-file-credentials
  namespace: nimbus-secrets-lab
type: Opaque
stringData:
  username: file-demo-user
  password: TRAINING_ONLY_FAKE_FILE_PASSWORD
---
apiVersion: v1
kind: Pod
metadata:
  name: secret-volume-demo
  namespace: nimbus-secrets-lab
spec:
  containers:
  - name: shell
    image: busybox:1.36
    command: ["/bin/sh", "-c"]
    args: ["sleep 3600"]
    volumeMounts:
    - name: credentials
      mountPath: /run/demo-credentials
      readOnly: true
  volumes:
  - name: credentials
    secret:
      secretName: demo-file-credentials
      defaultMode: 0440

Step 2: Apply and inspect without printing file contents.

kubectl apply -f 02-secret-volume.yaml
kubectl wait --for=condition=Ready pod/secret-volume-demo -n nimbus-secrets-lab --timeout=120s
kubectl exec secret-volume-demo -n nimbus-secrets-lab -- ls -la /run/demo-credentials
kubectl exec secret-volume-demo -n nimbus-secrets-lab -- sh -c 'test -s /run/demo-credentials/username && test -s /run/demo-credentials/password && echo "credential files present"'

Expected result: files named username and password exist. The check prints only a status message, not the sensitive content.

Why file mounts? Some programs expect a credential file instead of environment variables. Secret volumes are read-only. A normal Secret volume can eventually reflect updated values, but application reload behavior must be considered.

Exercise 3 — Demonstrate update behavior: environment, normal volume, subPath

Objective Observe the three different update behaviors using the same fake Secret values.

Step 1: Save as 03-update-behavior.yaml.

apiVersion: v1
kind: Secret
metadata:
  name: rotating-demo-secret
  namespace: nimbus-secrets-lab
type: Opaque
stringData:
  password: TRAINING_ONLY_PASSWORD_V1
---
apiVersion: v1
kind: Pod
metadata:
  name: secret-update-demo
  namespace: nimbus-secrets-lab
spec:
  containers:
  - name: shell
    image: busybox:1.36
    command: ["/bin/sh", "-c"]
    args: ["sleep 3600"]
    env:
    - name: DEMO_PASSWORD
      valueFrom:
        secretKeyRef:
          name: rotating-demo-secret
          key: password
    volumeMounts:
    - name: credentials
      mountPath: /run/all-secret-files
      readOnly: true
    - name: credentials
      mountPath: /run/subpath-password
      subPath: password
      readOnly: true
  volumes:
  - name: credentials
    secret:
      secretName: rotating-demo-secret

Step 2: Apply and check the initial version.

kubectl apply -f 03-update-behavior.yaml
kubectl wait --for=condition=Ready pod/secret-update-demo -n nimbus-secrets-lab --timeout=120s
kubectl exec secret-update-demo -n nimbus-secrets-lab -- sh -c 'test "$DEMO_PASSWORD" = "TRAINING_ONLY_PASSWORD_V1" && echo "env v1"'
kubectl exec secret-update-demo -n nimbus-secrets-lab -- sh -c 'grep -q TRAINING_ONLY_PASSWORD_V1 /run/all-secret-files/password && echo "normal volume v1"'
kubectl exec secret-update-demo -n nimbus-secrets-lab -- sh -c 'grep -q TRAINING_ONLY_PASSWORD_V1 /run/subpath-password && echo "subPath v1"'

Step 3: Save as 03-secret-v2.yaml and apply the changed Secret.

apiVersion: v1
kind: Secret
metadata:
  name: rotating-demo-secret
  namespace: nimbus-secrets-lab
type: Opaque
stringData:
  password: TRAINING_ONLY_PASSWORD_V2
kubectl apply -f 03-secret-v2.yaml
kubectl get secret rotating-demo-secret -n nimbus-secrets-lab
kubectl exec secret-update-demo -n nimbus-secrets-lab -- sh -c 'test "$DEMO_PASSWORD" = "TRAINING_ONLY_PASSWORD_V1" && echo "env remains v1"'
kubectl exec secret-update-demo -n nimbus-secrets-lab -- sh -c 'grep -q TRAINING_ONLY_PASSWORD_V1 /run/subpath-password && echo "subPath remains v1"'

For the normal volume, poll until the new value is projected (it is eventually consistent, so do not expect an immediate change):

kubectl exec secret-update-demo -n nimbus-secrets-lab -- sh -c 'i=0; while [ "$i" -lt 30 ]; do if grep -q TRAINING_ONLY_PASSWORD_V2 /run/all-secret-files/password; then echo "normal volume updated"; exit 0; fi; i=$((i+1)); sleep 2; done; echo "not yet observed; inspect kubelet/events and retry later"; exit 1'

Expected outcome: the environment variable still says V1, the subPath file stays V1, and the normal volume eventually shows V2. This is expected Kubernetes behavior.

Step 4: Recreate the Pod to update environment and subPath mounts.

kubectl delete pod secret-update-demo -n nimbus-secrets-lab
kubectl apply -f 03-update-behavior.yaml
kubectl wait --for=condition=Ready pod/secret-update-demo -n nimbus-secrets-lab --timeout=120s
kubectl exec secret-update-demo -n nimbus-secrets-lab -- sh -c 'test "$DEMO_PASSWORD" = "TRAINING_ONLY_PASSWORD_V2" && grep -q TRAINING_ONLY_PASSWORD_V2 /run/subpath-password && echo "new Pod sees v2"'
Lab note: Reapplying 03-update-behavior.yaml still references the same Secret name; the Pod is deleted and recreated so it reads the currently stored V2 value. The demonstration is designed around obviously fake strings only.

Exercise 4 — Create a TLS Secret using a temporary self-signed certificate

Objective Understand the kubernetes.io/tls type and its required keys without using a real certificate or private key.

Step 1: In a local terminal, create a short-lived test certificate. This requires OpenSSL on your workstation; it does not require a cloud service.

mkdir -p secrets-tls-lab
cd secrets-tls-lab
openssl req -x509 -nodes -days 1 -newkey rsa:2048 \
  -keyout tls.key -out tls.crt \
  -subj "/CN=secrets-lab.invalid"

This creates a local private key and self-signed certificate for practice. They are not trusted for production use. Keep them private and delete them after the lab.

Step 2: Create and inspect the Kubernetes Secret.

kubectl create secret tls demo-tls \
  --cert=./tls.crt \
  --key=./tls.key \
  -n nimbus-secrets-lab

kubectl get secret demo-tls -n nimbus-secrets-lab
kubectl describe secret demo-tls -n nimbus-secrets-lab
kubectl get secret demo-tls -n nimbus-secrets-lab -o jsonpath='{.type}{"\n"}'

Expected result: Secret type kubernetes.io/tls and two data keys. describe lists key sizes, not the private key content.

Important: the API server verifies the required TLS key names are present; the TLS type does not mean the certificate is trusted, current, or correctly matched to the service. Validate certificate properties separately in a real deployment.

10 · Secure operations

Best practices

Use least privilege

Grant Secret read permissions only to users and workloads that need them. list and watch can expose secret contents just like direct reads.

Encrypt at rest

Confirm API data encryption is configured for the cluster. Keep encryption keys protected and plan key rotation. Don't assume the Secret kind encrypts data automatically.

Never commit real values

Use an approved secret manager, protected pipeline integration, or an encrypted/sealed workflow. Base64-encoded YAML is still sensitive.

Minimize consumers

Mount credentials only into the required container and only into the workloads that need them. Avoid granting unnecessary Pod creation rights in sensitive namespaces.

Rotate intentionally

Update the credential at the source, update Secret delivery, reload/restart consumers, verify success, then revoke the old credential.

Protect outputs and backups

Don't print secret values, include them in debug dumps, or leave them in artifacts. Protect etcd backups, nodes, logs and audit access.

Production checklist

  • Secret is in the correct namespace and only consumed where required.
  • Real credential source is not in Git, image layers, shell history, output, or CI artifacts.
  • RBAC for get, list, watch, and workload creation is reviewed.
  • Encryption-at-rest and backup protection are confirmed for the cluster.
  • Credential rotation is documented and old credentials can be revoked.
  • Environment/volume/subPath refresh behavior is tested.
  • ServiceAccount API credentials use short-lived projected tokens where applicable rather than manually managed long-lived token Secrets.
11 · Interview preparation

Interview questions and answers

Try answering before expanding an item. Search filters questions by keyword.

Level 1 — Basic questions

1. What is a Kubernetes Secret?
A namespace-scoped API object intended for small amounts of sensitive information such as credentials, tokens, or keys. Pods can consume Secret values as environment variables or files, and kubelet can use registry pull credentials.
2. Is Base64 encryption?
No. Base64 is a reversible encoding. Anyone who can read the value can decode it without a key. Encryption at rest is a separate control.
3. What is the default Secret type?
Opaque, which stores arbitrary user-defined data.
4. What is the difference between data and stringData?
data accepts Base64-encoded values; stringData accepts plain strings for writes and is merged into data. It is not returned as plaintext on reads and has limitations with server-side apply.
5. What is the size limit for a Secret?
Individual Secrets are limited to 1 MiB. Large bundles or files need a more suitable mechanism.
6. Can Pods reference Secrets in another namespace?
No. Put the Secret in the same namespace as the Pod that references it.
7. How do you inject one Secret key into an environment variable?
Use env[].valueFrom.secretKeyRef, specifying the Secret name and key. Keep the actual value out of manifests and logs.
8. How do you mount a Secret as files?
Define a Secret volume in spec.volumes and mount that volume in the required container through volumeMounts. Each key is projected as a file by default.
9. What is an imagePullSecret?
A Pod-level reference to registry credentials—usually a Secret of type kubernetes.io/dockerconfigjson—used by kubelet when pulling a private image.
10. What keys are expected in a TLS Secret?
The built-in kubernetes.io/tls type expects tls.crt and tls.key. The API server checks key presence, but that does not establish that the certificate is trusted or matches the key.
11. How can you inspect a Secret without showing its values?
Use kubectl get secret NAME -n NAMESPACE or kubectl describe secret NAME -n NAMESPACE. Avoid printing data via full YAML/JSON outputs.
12. Do Secret environment variables update automatically?
No. Existing container process environments do not change when a Secret changes. Restart/recreate the Pod or roll out the owning workload.

Level 2 — Intermediate questions

13. Do Secret volume files update when the Secret changes?
A normal Secret volume is updated eventually using an eventually consistent approach. The application may need to reread/reload the file before it uses the new value. A subPath mount does not receive automated updates.
14. What is different about a Secret subPath mount?
It mounts one file or subdirectory at a specific path without mounting the full volume over the target directory. It does not receive automatic Secret updates, so Pod recreation is required to pick up changed data.
15. Does Kubernetes enable encryption at rest just because the object is a Secret?
No. Kubernetes supports API data encryption at rest, but the cluster configuration/provider must enable and manage it. Verify the cluster's actual encryption configuration and key management.
16. Why are get, list, and watch permissions sensitive?
They can reveal Secret data. A list response includes the Secret values, and watch can stream object changes. Grant the least privilege required.
17. Why can permission to create Pods imply access to Secrets?
A user who can create a Pod in a namespace may be able to define a Pod that mounts an available Secret. Namespace isolation is useful but should not be treated as a strong boundary between mutually untrusted users without additional controls.
18. What are common built-in Secret types?
Opaque, kubernetes.io/dockerconfigjson, kubernetes.io/dockercfg, kubernetes.io/basic-auth, kubernetes.io/ssh-auth, kubernetes.io/tls, kubernetes.io/service-account-token, and bootstrap.kubernetes.io/token.
19. What is the recommended replacement for legacy ServiceAccount token Secrets?
Use short-lived, automatically rotating tokens via the TokenRequest API or projected ServiceAccount token volume. Manually managed long-lived token Secrets are generally not recommended.
20. What does immutable: true do?
It prevents the Secret's data from being changed in place. Use a new versioned Secret object and update the workload reference when values must change.
21. Why can stringData be awkward with server-side apply?
The API converts/merges stringData into data and doesn't return stringData as the persistent read representation; the official docs caution that stringData does not work well with server-side apply. For SSA-managed workflows, use the appropriate declared data representation or an approved secret-management tool.
22. What is the right way to update a Secret-based environment variable?
Update the Secret through the approved source and recreate/restart the Pod or roll out its Deployment. Verify the new process has loaded the intended value without printing it.
23. Does kubectl describe secret show the password?
By default, describe lists data key names and byte sizes rather than their contents. A full get -o yaml or JSON output can expose Base64 values.
24. How do you create a TLS Secret?
Provide an existing matching PEM certificate and private key with kubectl create secret tls NAME --cert=PATH --key=PATH -n NAMESPACE. The certificate/private key must be managed securely and the certificate's validity/trust must be checked separately.

Level 3 — Real-world scenarios

25. Secret object is updated but an app still uses an old environment variable. Diagnose it.
Reasoning: Confirm the correct Secret and Pod reference without displaying its values. Environment variables are snapshots when the process starts. Check the workload's Secret name/key, trigger a rollout restart, wait for readiness, and verify behavior with a safe authenticated health check. Other causes include wrong namespace, another overriding variable, or the app reading a different name.
26. A Pod is in CreateContainerConfigError after a Secret was deployed.
Run kubectl describe pod POD_NAME -n NAMESPACE and read Events. Check the Secret exists in the same namespace and that the requested key is present. Correct the reference or key; use optional: true only if missing values are genuinely safe. Verify the Pod becomes Ready.
27. ImagePullBackOff appears after adding imagePullSecrets.
Inspect Pod Events for authorization, registry, DNS/network, or image name errors. Ensure the Secret is in the Pod's namespace, is the correct dockerconfigjson format, and the registry host matches the image registry. Rotate credentials if a real value was exposed. Retry after targeted correction.
28. The normal Secret volume contains new content, but the service still authenticates with old credentials.
The app may cache values after the file was first read. Verify file metadata/content using fake data or a safe comparison, then check the application's reload mechanism and logs. Reload or restart as designed. Also confirm which file path the application actually opens.
29. A Secret mounted via subPath stays stale after update.
This is expected behavior. Confirm the Pod's volumeMounts includes subPath. Recreate the Pod or roll out the owning Deployment and verify the new Pod's behavior. A normal Secret volume is an alternative if eventual file updates are needed.
30. A security scan finds a password in a Git commit.
Treat it as exposed even if the commit is reverted. Revoke/rotate the credential first, assess which systems and artifacts may contain copies, remove/redact where possible, review audit/logs, and change CI/documentation practices so actual credentials are not committed again.
31. A team says Base64 values are safe to store publicly because they are encoded.
Explain that Base64 is reversible without a key. Restrict access, avoid public Git, use an approved secret manager, configure encryption at rest, and rotate any value already exposed. Encoding is representation, not confidentiality.
32. How would you handle a 1.5 MiB Secret?
A single Secret is limited to 1 MiB. Reassess why the data is so large. Split logically only if appropriate and within quotas, or use an object store, encrypted volume, or external secret/configuration system designed for larger assets.
33. A Pod creator in a namespace can read a Secret even without direct Secret read permission. Why?
Pod creation may allow the caller to define a workload that mounts namespace Secrets. Restrict workload creation and the privilege of workloads in sensitive namespaces; use namespace separation, Pod Security controls, admission policy, and least privilege.
34. The TLS Secret exists, but clients reject the certificate.
Secret type and required key presence do not prove the cert is trusted, current, matches its private key, or has the right SANs. Validate certificate chain, expiry, hostname/SAN, key match, and the consumer's TLS configuration. Avoid dumping the private key for debugging.
35. A Secret update should be rolled out across many replicas. How do you make the change safer?
Use a controlled change process: rotate/create new credential at the authoritative system, update the Secret reference/data, trigger a Pod-template change or rollout, observe readiness and authenticated checks, then revoke old credentials after consumers have moved. Consider versioned Secret names or checksum annotations. Define rollback and blast-radius handling.
36. Which is safer: env variables or Secret files?
There isn't a universal winner. Environment variables can be exposed via process inspection, debugging or logs and do not update in place. Files can suit applications with file-based credential support, but node/workload access and mount behavior still matter. Choose the application-compatible pattern, limit access, avoid logging values, and plan rotation.
12 · Practice on your own

Assignments and scenario challenges

Attempt each problem first. Expand the solution hint only after trying your own implementation. Keep all objects in the dedicated lab namespace.

Beginner assignments

  1. Create a generic Secret with two fake keys. Requirements: specify namespace and type, then verify it exists without showing values. Expected state: Secret type Opaque, two data items. Verify using kubectl get secret and kubectl describe secret. Hint: use stringData with demo-only values.
  2. Inject one Secret key into a Pod environment variable. Expected state: Pod reaches Ready and a safe script can check the variable is non-empty. Verify with Pod logs that show status only. Hint: use secretKeyRef.
  3. Mount a Secret as files. Expected state: keys appear under a read-only mount path. Verify with ls and a test command that checks file presence. Hint: define both the volume and the matching volumeMount.
  4. Create a TLS Secret using a test certificate. Expected state: type is kubernetes.io/tls with both expected keys. Verify with kubectl describe secret. Hint: OpenSSL can create a one-day self-signed lab certificate.
  5. Write a private registry Pod-spec fragment. Expected state: imagePullSecrets references a registry Secret in the same namespace. Verify the names and expected dockerconfigjson type. Hint: don't hardcode a real registry password in a manifest.

Modification / troubleshooting assignments

  1. Update the fake password in a Secret consumed as an environment variable. Prove the existing process is unchanged; roll out the Pod and verify the new value using a safe check.
  2. Update a Secret mounted as a regular volume. Poll for eventual projection, then explain whether the app needs to reload.
  3. Update a Secret mounted using subPath. Demonstrate that the file is stale until Pod recreation.
  4. Introduce a Secret-name typo in a disposable Pod. Diagnose it through Events and repair it.
  5. Change the requested key to a missing key. Explain the difference between a required and optional reference and fix the reference.

Scenario challenges

  1. Credential accidentally logged: write the incident response, rotation steps, and verification approach without printing the exposed value.
  2. Multiple teams, shared cluster: design namespace/RBAC boundaries so unrelated app teams cannot read each other's Secrets or mount them through arbitrary Pods.
  3. Production certificate rotation: propose how to change a TLS Secret, roll dependent workloads or reload the consumer, validate the certificate, and revoke the old key safely.

Remember: kubectl get secret NAME -o yaml can expose Base64-encoded values. Use it only when you are authorized and deliberately need to see the object representation. Never confuse encoded values with protected values.

Five things to recall before an interview

  1. Secret is for sensitive values, but it is not a full secret-management system.
  2. Base64 is reversible encoding, not encryption.
  3. RBAC, at-rest encryption, backups, logs and node/workload access all matter.
  4. Environment variables do not refresh in a running process; a normal volume updates eventually; subPath does not update automatically.
  5. Rotate/revoke real credentials after exposure, even if the visible YAML or log line is removed.
14 · Lab cleanup

Remove only your training resources

Stop any local port-forward sessions or terminals used for the lab. Inspect the dedicated namespace before deletion:

kubectl get all,secret -n nimbus-secrets-lab

If the namespace was created exclusively for this training guide and contains no shared resources, delete it:

kubectl delete namespace nimbus-secrets-lab

If the namespace is shared, delete only the resources created for the guide after checking the list. Do not delete a namespace that contains another student's work.

kubectl delete pod secret-env-demo secret-volume-demo secret-update-demo -n nimbus-secrets-lab --ignore-not-found
kubectl delete secret demo-db-credentials demo-file-credentials rotating-demo-secret demo-tls -n nimbus-secrets-lab --ignore-not-found

Delete the local self-signed certificate and private key created by Exercise 4 when you no longer need them:

# Run from the secrets-tls-lab directory only after confirming these are the lab files
rm -f tls.crt tls.key
cd ..
rmdir secrets-tls-lab
Cleanup warning: Deleting a Secret object does not revoke a password, token, key, certificate, or copies of it that exist elsewhere. For real credentials, perform rotation/revocation at the credential's source. Never delete shared cluster resources or credentials that belong to another workload.
