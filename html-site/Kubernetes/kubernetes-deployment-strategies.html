Kubernetes Deployment Strategies

Learn how teams release application changes safely using Recreate, Rolling Update, Blue/Green, and Canary deployment patterns. Includes visual workflows, copyable manifests, rollback labs, troubleshooting, and interview preparation.

1. Introduction

A deployment strategy describes how a new application release replaces or runs alongside the current version and how users are moved to the new release. Kubernetes Deployments natively support RollingUpdate and Recreate. Blue/Green and Canary are release patterns typically assembled from multiple Deployments, Services, and—when precise traffic control is required—an Ingress controller, Gateway implementation, or service mesh.

Why strategies matter

A release can introduce defects, incompatibility, poor performance, or startup delays. A deliberate strategy limits user impact and gives the team a defined validation and rollback path.

Analogy

Replacing every cashier at once is Recreate. Replacing cashiers one at a time is Rolling Update. Opening a fully prepared second checkout hall and switching all customers is Blue/Green. Letting a small group try the new hall before expanding it is Canary.

DevOps example

A team releases a new web application version. It updates a Deployment, checks readiness and error rates, then either proceeds, pauses, routes traffic back to the old version, or promotes the new version.

Learning objectives

  • Distinguish Kubernetes' native Deployment strategies from higher-level release patterns.
  • Explain downtime, rollout speed, rollback options, cost, risk, and traffic control.
  • Implement and inspect RollingUpdate and Recreate Deployments.
  • Build Blue/Green and basic Canary demonstrations with labels and Services.
  • Use readiness probes, rollout status, history, pause/resume, and rollback commands.
  • Diagnose stuck rollouts, empty endpoints, bad releases, and incompatible application/database changes.
Key technical distinction: A standard Kubernetes Deployment does not have a native strategy: BlueGreen or strategy: Canary setting. Native Deployment strategy values are RollingUpdate and Recreate. Blue/Green and Canary use resource and traffic-routing patterns around Deployments.

2. Core concepts and strategy comparison

Strategy comparison at a glance

StrategyHow it worksDowntime / user impactStrengthTrade-off
RecreateTerminate old Pods before creating the new revision's Pods for an update.Expected during the handover; the length depends on shutdown and startup.Simple; avoids running old and new application Pods simultaneously during an update.Not appropriate when uninterrupted service is required.
Rolling UpdateGradually scales the new ReplicaSet up and the old ReplicaSet down.Can maintain availability when enough replicas remain ready, but zero downtime is not guaranteed by the strategy alone.Native Deployment default; controlled incremental replacement.Old and new versions can coexist; needs backward/forward compatibility and capacity.
Blue/GreenRun old and new versions separately; switch a Service selector or routing rule after validating the new version.Fast traffic switch is possible, but active connections, propagation, startup, and dependencies can still affect users.Clear cutover and quick route-back path.Requires extra capacity and a plan for state/data compatibility.
CanaryExpose the new version to a limited subset of users/traffic, observe metrics, then increase exposure.Limits blast radius if routing and monitoring are designed correctly.Evidence from a small release before broad promotion.Requires meaningful telemetry and traffic control; rollout is more operationally involved.

Native Deployment strategy fields

spec.strategy.type accepts RollingUpdate or Recreate. Rolling Update is the default.

  • maxSurge: maximum number or percentage of extra Pods that may be created above the desired replica count during a Rolling Update.
  • maxUnavailable: maximum number or percentage of desired Pods that may be unavailable during the update.
  • minReadySeconds: how long a Pod must remain Ready without container crashes before it counts as available.
  • progressDeadlineSeconds: how long Kubernetes waits without observed rollout progress before reporting a stalled Deployment condition. The default is 600 seconds; the controller reports the condition but does not automatically roll back the release.
  • revisionHistoryLimit: number of old ReplicaSets retained for rollback history; deleting history can remove rollback options.
  • readinessProbe: provides a health signal used to decide whether a Pod should receive traffic and count as ready.
Percent calculation: Kubernetes rounds percentage values down for maxUnavailable and up for maxSurge. For a small replica count, percentages may calculate to zero or one Pod; inspect the actual values when planning a release.

How to choose

RequirementStarting pointQuestions before deciding
Development/test system can tolerate a pauseRecreateWill dependent clients tolerate downtime? Does the workload have a single writer or lock requirement?
General stateless web/API applicationRolling UpdateDo readiness checks work? Can old and new versions coexist? Is there spare capacity?
Need to test new release privately and switch all users afterwardBlue/GreenCan two environments fit in the budget? Are database changes compatible during a rollback?
Need limited exposure with controlled ramp-upCanary with a traffic controllerCan you route a defined percentage/user group? Are metrics and abort thresholds available?

Common misunderstandings

  • “Rolling Update guarantees zero downtime.” No. Readiness, available capacity, app compatibility, startup time, and external dependencies still matter.
  • “Blue/Green resets the database.” No. Kubernetes switches routing; it does not clone, reset, or automatically reverse database state.
  • “One canary replica means 10% of traffic.” Not reliably. Replica ratios are not precise traffic weights for a normal Service.
  • “Rolling back a Deployment reverses every change.” Rollback restores the Pod template revision. It does not automatically undo external schema migrations or arbitrary changes to shared ConfigMap/Secret data.
  • “Recreate resets application state.” It replaces Pods during an update. Data in external databases or persistent volumes is not automatically reset.

3. Architecture and traffic workflows

The diagrams below are original conceptual SVG illustrations, not screenshots from a live cluster.

Step-by-step: Rolling Update

  1. A changed Pod template causes the Deployment to create a new ReplicaSet.
  2. The new ReplicaSet scales up within maxSurge; old Pods scale down within maxUnavailable.
  3. Readiness checks help Kubernetes determine when new Pods are available.
  4. The rollout completes when the new desired replicas are updated and available; inspect using kubectl rollout status.

Step-by-step: Blue/Green

  1. Deploy Blue and Green as separate Deployments with non-overlapping selectors.
  2. Test Green via a preview Service or isolated route.
  3. Change the live Service selector or routing rule to point at Green.
  4. Observe health and metrics; if needed, point the live Service back to Blue. Retain Blue until rollback is no longer required.

Step-by-step: Canary

  1. Keep a stable Deployment serving most of the application.
  2. Run a small canary revision and expose it only to the intended cohort.
  3. Compare error rate, latency, logs and business metrics against stable.
  4. Increase exposure in stages or abort by removing canary traffic.
Traffic-splitting warning: In the lab later in this guide, the standard Service selects Pods from both stable and canary Deployments to demonstrate a mixed endpoint pool. This is not a deterministic 90/10 or 99/1 canary. For precise weights, use a supported Ingress/Gateway controller or service mesh that documents weighted routing.

4. Environment preparation

Use an authorized cluster with kubectl, such as Minikube, kind, or an existing training cluster. The examples use NGINX and ConfigMaps to make release differences visible as simple web page text. No cloud load balancer is required. Public image pulls and enough CPU/memory are needed.

Verify the cluster

kubectl version --client
kubectl cluster-info
kubectl get nodes
kubectl get namespaces
kubectl config current-context
  • kubectl version --client checks the local client binary.
  • kubectl cluster-info checks API connectivity.
  • kubectl get nodes lists the nodes; make sure suitable nodes are Ready.
  • kubectl get namespaces lists resource namespaces.
  • kubectl config current-context confirms which cluster the commands will affect.

Optional local-cluster setup if Minikube is already installed:

minikube start
kubectl get nodes
kubectl config current-context

Create the lab working folder and namespace

mkdir -p kubernetes-deployment-strategies
cd kubernetes-deployment-strategies
kubectl create namespace nimbus-deploy-strategies
Safe lab boundary: All manifests use nimbus-deploy-strategies. If the namespace already exists, inspect it and verify it is your training namespace. Namespace deletion removes every namespaced object inside; do not use the cleanup procedure on a shared namespace containing other users' resources.

How examples make release versions visible

Each Deployment mounts a version-specific ConfigMap key at NGINX's /usr/share/nginx/html/index.html. Page text such as “VERSION 1” or “GREEN RELEASE” makes it easy to verify which revision answered. The example switches the referenced ConfigMap name so the Pod template changes and the intended rollout strategy occurs.

5. Step-by-step hands-on labs

Run each lab in sequence. The exercises use independent workload names so you can compare strategies without accidentally overlapping Deployment selectors. Stop each kubectl port-forward with Ctrl+C before reusing a local port.

Exercise 1 — Build a versioned app and perform a Rolling Update

Objective: See a safe incremental release using Kubernetes' native Deployment strategy.

Step 1 — Save as rolling-v1.yaml:

apiVersion: v1
kind: ConfigMap
metadata:
  name: rolling-page-v1
  namespace: nimbus-deploy-strategies
data:
  index.html: |
    <!doctype html>
    <html><body><h1>Nimbuswiztech - ROLLING VERSION 1</h1></body></html>
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: rolling-web
  namespace: nimbus-deploy-strategies
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  minReadySeconds: 3
  progressDeadlineSeconds: 120
  selector:
    matchLabels:
      app: rolling-web
  template:
    metadata:
      labels:
        app: rolling-web
    spec:
      containers:
      - name: nginx
        image: nginx:1.27
        ports:
        - name: http
          containerPort: 80
        readinessProbe:
          httpGet:
            path: /
            port: http
          periodSeconds: 3
          failureThreshold: 3
        resources:
          requests:
            cpu: 50m
            memory: 64Mi
          limits:
            cpu: 250m
            memory: 128Mi
        volumeMounts:
        - name: page
          mountPath: /usr/share/nginx/html/index.html
          subPath: index.html
      volumes:
      - name: page
        configMap:
          name: rolling-page-v1
---
apiVersion: v1
kind: Service
metadata:
  name: rolling-web
  namespace: nimbus-deploy-strategies
spec:
  type: ClusterIP
  selector:
    app: rolling-web
  ports:
  - name: http
    port: 80
    targetPort: http

Step 2 — Apply and verify:

kubectl apply -f rolling-v1.yaml
kubectl rollout status deployment/rolling-web -n nimbus-deploy-strategies --timeout=180s
kubectl get deployment,replicaset,pods,service -n nimbus-deploy-strategies
kubectl port-forward service/rolling-web 18080:80 -n nimbus-deploy-strategies

Keep port-forward running. In a second terminal, run curl -s http://127.0.0.1:18080. The response should include ROLLING VERSION 1.

kubectl apply -f rolling-v2.yaml

Explain the fields: maxSurge: 1 allows one extra Pod above three desired; maxUnavailable: 0 asks Kubernetes not to intentionally reduce the available count during the update; minReadySeconds requires a brief stability interval; the readiness probe checks HTTP on the named port.

Expected result: A new ReplicaSet appears, new Pods become ready, and old Pods are scaled down. Exact event timing varies with image availability and cluster resources.

Troubleshooting: If rollout stalls, inspect the Deployment and newest Pods. Insufficient capacity can block surge Pods; readiness failure blocks progress; image pull problems prevent new Pods starting.

Interview connection: A changed spec.template triggers a new rollout. Updating a ConfigMap object alone would not change the Pod template; this lab changes the ConfigMap reference so it triggers a new revision.

In another terminal, run curl -s http://127.0.0.1:18082. Confirm “SHOP GREEN - CANDIDATE RELEASE” before cutover. Stop the preview port-forward with Ctrl+C when done.

Step 3 — Inspect the live Blue page:

kubectl port-forward service/shop-live 18083:80 -n nimbus-deploy-strategies

In another terminal: curl -s http://127.0.0.1:18083. It should show “SHOP BLUE - CURRENT RELEASE”. Leave the port-forward running.

Step 4 — Cut over by changing the live Service selector:

kubectl patch service shop-live -n nimbus-deploy-strategies --type=merge -p '{"spec":{"selector":{"app":"shop","track":"green"}}}'
kubectl get endpointslices -n nimbus-deploy-strategies -l kubernetes.io/service-name=shop-live
curl -s http://127.0.0.1:18083

The response should switch to the Green page after endpoint updates. Active connections and propagation can mean a real service does not switch every in-flight request instantaneously.

Step 5 — Roll back traffic to Blue:

kubectl patch service shop-live -n nimbus-deploy-strategies --type=merge -p '{"spec":{"selector":{"app":"shop","track":"blue"}}}'
curl -s http://127.0.0.1:18083

Key learning: Blue and Green Deployments use different selectors, so their ReplicaSets do not compete over the same Pods. A single Service selector controls which release receives new traffic. The preview Service lets you validate Green before switching users.

Both versions use the same example NGINX image but different page configuration to make the routing easy to see. Real releases typically differ in application image/artifacts and configuration. Blue/Green requires enough capacity to run both versions, and rollback does not automatically reverse data migrations.

Exercise 4 — Canary pattern with two Deployments and one Service pool

6. End-to-end release workflow

Business requirement

Release a changed web page while minimizing risk. The team should create a candidate version, validate it before switching, have a clear abort path, and retain a previous known-good release until confidence is high.

Suggested decision workflow

  1. Pre-release: confirm image/artifact version, backward-compatible configuration and schema plan, required capacity, health checks, and rollback owner.
  2. Choose pattern: Rolling Update for routine stateless updates; Blue/Green for full cutover with a preview environment; Canary when traffic can be split and metrics can be evaluated; Recreate only where downtime is acceptable or the app requires it.
  3. Deploy: use version-controlled manifests and a dedicated namespace or controlled production namespace.
  4. Validate: confirm rollout completion, desired/available replicas, readiness, logs, and synthetic/business checks.
  5. Observe: watch error rate, latency, saturation, logs and user-impact metrics over a defined window.
  6. Promote or abort: increase exposure or switch routing after success; otherwise pause, rollback or switch back to the last known-good version.
  7. Close release: record version, change, observed signals, decision and follow-up. Keep the rollback target until the rollback window expires.

Core deployment inspection commands

kubectl get deployment,replicaset,pods -n nimbus-deploy-strategies
kubectl rollout status deployment/rolling-web -n nimbus-deploy-strategies
kubectl rollout history deployment/rolling-web -n nimbus-deploy-strategies
kubectl describe deployment rolling-web -n nimbus-deploy-strategies
kubectl get events -n nimbus-deploy-strategies --sort-by=.metadata.creationTimestamp
Definition of release success: “kubectl apply” completing is not enough. Confirm desired replicas are available, new Pods pass readiness, the intended version serves requests, and application-level signals remain within agreed limits.

8. Best practices

  • Set meaningful readiness probes. A Pod should not enter the serving pool before it can handle requests. Test the probe path and port against the real app.
  • Plan sufficient capacity. Rolling Update with maxSurge and Blue/Green both need room for overlapping Pods/environments. Verify quotas and node capacity before release.
  • Keep versions backward-compatible during overlap. Rolling and Canary can run old and new code simultaneously. Coordinate API contracts, cache formats and database migrations.
  • Use immutable release artifacts. Pin a specific application version or image digest, record it, and avoid changing an image behind a reused tag.
  • Keep selectors unique and deliberate. Blue/Green Deployments should have distinct selectors, such as app: shop, track: blue and app: shop, track: green, while the live Service changes its selector.
  • Choose rollback rules before launch. Define which metrics cause an abort, who can authorize traffic switch-back, and how to verify recovery.
  • Monitor more than Pod status. Track errors, request latency, saturation and business behavior. Ready Pods can still produce incorrect results or downstream failures.
  • Do not mistake rollout completion for full application health. A Deployment rollout checks Pod availability; synthetic requests and service-level indicators are still needed.
  • Keep history intentionally. Old ReplicaSets enable rollback, but unlimited history consumes resources. Set a suitable revisionHistoryLimit for the environment.
  • Protect external release controls. Restrict who can patch live Service selectors or alter release manifests using RBAC and change review.
  • Plan stateful change separately. Persistent data and database schema changes are not automatically rolled back by Deployment revision history. Use migration plans, backups and compatibility windows.
  • Do not promise exact canary weights from replica counts. Use a routing layer that explicitly supports weights or request matching, and validate the realized traffic distribution.
  • Prefer declarative source control. Keep manifests in Git, review differences, and ensure the intended manifest and running objects do not drift unnoticed.
  • Use Recreate only intentionally. It can be valid for jobs or workloads that cannot overlap, but document downtime and recovery expectations.

9. Interview preparation

Use search to filter questions, and expand an item to reveal its answer.

Level 1 — Basic questions

1. What is a deployment strategy?
It describes how a new application version replaces or runs alongside an existing version, and how traffic and availability are managed during release.
2. Which strategy types are native to a Kubernetes Deployment?
Recreate and RollingUpdate. RollingUpdate is the default. Blue/Green and Canary are patterns implemented using workloads and traffic-routing mechanisms.
3. What is Recreate?
For a Deployment template update, existing Pods are terminated before Pods for the new revision are created. This commonly introduces downtime.
4. What is Rolling Update?
The Deployment gradually scales up a new ReplicaSet and scales down the old ReplicaSet, with progress controlled by availability and surge settings.
5. What is maxSurge?
It caps how many extra Pods above desired replicas may be created during a rolling update. It can be an integer or percentage.
6. What is maxUnavailable?
It caps how many desired Pods may be unavailable during a rolling update. Kubernetes rounds percentage values down for this field.
7. What is Blue/Green deployment?
Two versions run alongside one another. The new version is validated before the live routing target is changed, commonly by updating a Service selector or gateway route.
8. What is Canary deployment?
A new release is exposed to a limited subset of traffic/users first. The team evaluates health and metrics before increasing exposure or aborting.
9. What is a ReplicaSet's role in a Deployment?
The Deployment creates and manages ReplicaSets. Each ReplicaSet maintains the desired number of Pods for a specific Pod template revision.
10. How do you verify rollout completion?
Use kubectl rollout status deployment/NAME -n NAMESPACE, then inspect Deployment, ReplicaSets, Pods and application behavior.
11. How do you undo a Deployment rollout?
Use kubectl rollout history to inspect revisions and kubectl rollout undo deployment/NAME to restore a previous Pod template revision.
12. What does readiness have to do with a rollout?
Readiness helps Kubernetes determine whether a Pod can serve traffic and whether a new replica is available. A bad probe can stall rollout or allow unhealthy traffic if readiness is missing/misconfigured.

Level 2 — Intermediate questions

13. Why does Rolling Update usually need old/new compatibility?
During the overlap period, both revisions may serve traffic or access the same data. APIs, database schema, messages and shared cache formats must tolerate the old and new versions until the transition completes.
14. Does maxUnavailable: 0 guarantee zero downtime?
No. It prevents the controller from intentionally making the specified number of desired replicas unavailable due to the update, but capacity, probe correctness, app behavior, dependencies, node failures and routing can still cause user impact.
15. Does Kubernetes automatically roll back a failed Deployment?
No. It reports stalled progress through Deployment status and continues retrying. An operator or higher-level deployment system must decide whether to roll back.
16. How do you implement Blue/Green using a Service?
Deploy Blue and Green using separate non-overlapping selectors; make the live Service select Blue initially; test Green through a preview route; then update the Service selector to Green. Keep Blue available during the rollback window.
17. What is a limitation of implementing Canary with a regular Service?
A selector can include both stable and canary Pods but does not provide configurable weighted percentages. Replica ratios only approximate a pool mix and do not guarantee request-level traffic weights.
18. Why use different labels in Blue/Green Deployments?
Selectors must be unambiguous. Overlapping Deployment selectors can cause controllers to compete for Pods. Track labels separate each Deployment, while the Service selects the active track.
19. What does progressDeadlineSeconds do?
It defines how long a Deployment may go without observed progress before the controller reports a stalled condition. Default is 600 seconds. It does not trigger automatic rollback.
20. Does rollout undo restore a database migration?
No. It restores the Deployment's Pod template revision. Database migrations, external state, and separately managed ConfigMaps or Secrets require their own change/rollback process.
21. How do you pause and resume a rollout?
Use kubectl rollout pause deployment/NAME, inspect or stage changes as appropriate, then kubectl rollout resume deployment/NAME. Paused rollouts require care: verify the final intended template before resuming.
22. Why are versioned ConfigMaps used in the lab?
A ConfigMap name change in the Pod template triggers a Deployment rollout and preserves the old configuration object for a rollback. Editing data in-place does not inherently create a new Deployment revision.
23. What extra cost does Blue/Green introduce?
It often requires capacity for both environments until confidence is sufficient to retire the old version. External databases, caches and shared dependencies also need compatibility planning.
24. What metrics matter for Canary?
At minimum compare error rate, latency percentiles, saturation, logs and relevant business outcomes between stable and canary. Define thresholds and observation windows before release, and ensure traffic cohorting is actually controlled.

Level 3 — Real-world scenario questions

25. A rolling release is stuck after one new replica starts. How do you troubleshoot?
Approach: Run kubectl rollout status, kubectl describe deployment, kubectl get rs,pods and describe the failing new Pod. Check events for image pulls, scheduling, quota and probe failure. Inspect logs and readiness. Fix the evidenced cause; if the release is unsafe, run kubectl rollout undo deployment/rolling-web -n nimbus-deploy-strategies and verify availability.
26. The new version passes readiness but users report 500 errors.
Readiness proves only the configured readiness check succeeds, not every business path. Inspect application logs, metrics, dependencies, request payloads and changed API behavior. Consider pausing further promotion or rolling back while investigating. Validate with a representative synthetic or integration test.
27. The Recreate strategy caused an outage longer than expected.
Inspect deletion and startup events, image pull time, scheduling capacity and app initialization. Recreate deliberately removes old replicas before new revision Pods are created. If downtime is unacceptable, use Rolling Update or Blue/Green after confirming old/new compatibility and capacity.
28. Blue/Green switch was applied but users still see Blue.
Check the live Service selector and EndpointSlices, then confirm Green Pods are Ready and carry exactly the selected labels. Start a new request to rule out connection reuse/cache. Verify with kubectl get svc shop-live -o yaml and the service-name-labeled EndpointSlices.
29. Blue/Green rollback points back to Blue, but the app still fails.
The old code can still depend on incompatible database state or shared configuration changed during release. Confirm the Service endpoints now target Blue, then assess database/schema compatibility, migrations, shared caches and external dependencies. A routing rollback is not a full infrastructure/data rollback.
30. A team wants exactly 5% of traffic on a canary with only native Deployment/Service objects.
A normal Service cannot express a reliable weighted 5% split. Use a supported routing controller or service mesh with weighted backend support, validate the configured rule and observed distribution, and monitor the canary. Replicas alone are not precise request weighting.
31. New Pods cannot be scheduled because maxSurge needs extra capacity.
Inspect scheduling events and available node capacity. Options include adding capacity, adjusting rollout surge/unavailable parameters to match risk tolerance, or selecting Blue/Green/Recreate based on requirement. Do not reduce safety settings blindly; explain availability impact.
32. After rollback, the Pod still reads the new setting from a ConfigMap.
Check whether the revision references a versioned ConfigMap or the same ConfigMap name whose data was edited in-place. Rollback restores the Pod template, not the ConfigMap's previous content. Restore data explicitly or use versioned configuration objects and verify the mounted file.
33. Canary metrics look normal but the canary was not receiving the intended users.
Validate traffic-routing rules and inspect actual request labels/headers or access logs. A healthy Pod and endpoints do not prove the intended cohort reached it. Confirm weights/user routing in the Ingress, Gateway or mesh implementation and run controlled test requests.
34. A new release breaks older clients during a Rolling Update.
Both versions can be active during rolling replacement, and clients may continue using an older contract. Restore compatibility using a staged expand-and-contract API/schema migration, or roll back the Pod template if safe. Verify versions, client behavior and downstream schemas.
35. Deployment says ProgressDeadlineExceeded. Has Kubernetes stopped trying?
No. The controller reports that rollout progress did not meet the deadline; it continues reconciling the Deployment. Inspect its conditions and Pods. An operator or higher-level system should determine whether to fix, wait, or roll back.
36. Why might a rollout have enough Ready Pods but still cause downtime?
App-level failures, broken dependencies, connection draining, incorrect Service selectors, traffic-layer issues, or incompatible schema can occur despite Pod readiness. Verify client requests and service-level indicators, not just replica counts.

11. Quick revision and command sheet

Key concepts

  • Recreate: terminate old revision Pods before creating new revision Pods; downtime is expected.
  • RollingUpdate: progressively replaces Pods. Tune maxSurge and maxUnavailable.
  • Blue/Green: deploy new version separately and switch a Service selector or route when validated.
  • Canary: expose a controlled subset of traffic, watch metrics, then promote or abort. Precise weighting needs a traffic controller.
  • Readiness: health signal for traffic eligibility; a readiness failure can block rollout progress.
  • Rollback: reverts the Deployment Pod template revision, not external data or every separately managed resource.
  • Progress deadline: reports stalled rollout; does not automatically roll back.
