DaemonSet & StatefulSet

Understand node-local agents, stable Pod identity, headless DNS, per-replica storage, rollout behavior, and practical debugging in Kubernetes and Amazon EKS.

Beginner → IntermediateEstimated hands-on: 2.5–3.5 hoursOffline-friendly SVG diagramsNimbuswiztech

1. Learning objectives and roadmap

This guide teaches two different Kubernetes workload patterns: DaemonSet for node-local services and StatefulSet for replicas that need stable identity, ordered operations, and often persistent storage. It is designed for beginner-to-intermediate DevOps learners and includes copy-ready examples with deliberate safety boundaries.

Pattern A

DaemonSet

One managed Pod on every eligible node. Common for log collection, node metrics, storage agents, and network components.

Pattern B

StatefulSet

Named replicas such as nimbus-store-0, each with a stable ordinal and optional persistent claim.

Practice

Learn by observing

Use kubectl get, describe, events, rollout status, DNS, and PVC state to verify behavior instead of assuming success.

By the end of this guide, students should be able to

  • Explain node coverage and reconcile a DaemonSet.
  • Identify node selectors, affinity, taints, resource and security constraints.
  • Perform and verify a DaemonSet rollout.
  • Distinguish per-node agents from fixed-replica apps.
  • Explain ordinal Pod names, stable DNS and headless Services.
  • Connect volumeClaimTemplates to per-Pod PVCs.
  • Diagnose Pending Pods/PVCs and ordered rollout blocks.
  • Remove lab workloads without accidentally losing needed data.

Prerequisites

Basic Kubernetes familiarity, working kubectl, access to a disposable cluster, ability to create workloads in a namespace, and (for the StatefulSet storage lab) a working StorageClass/provisioner or a matching pre-created PersistentVolume. Before starting, confirm nimbus-ds-sts-lab is not already used by unrelated workloads; if it exists, choose a new namespace and update all manifests and commands. EKS access is optional; do not create an AWS cluster solely for this lesson.

Lesson roadmap

  1. Understand how workload controllers differ.
  2. Inspect DaemonSet placement and updates.
  3. Inspect StatefulSet identity, DNS, ordering, and storage.
  4. Run two labs and one combined architecture walkthrough.
  5. Use the diagnostic paths, interviews, and assignments to revise.

2. Foundations: controllers, desired state, and Pods

Kubernetes controllers compare a declared desired state with observed cluster state and take actions to reduce the difference. A workload manifest describes the Pod template and controller settings; it is not a guarantee that every Pod has already become Ready.

Remember the distinction: the API server stores and validates resources; controllers create or remove Pods; scheduling, kubelet, image pulls, storage, networking, and application health determine whether those Pods become usable.

Four useful observation layers

LayerCommandWhat it answers
Controllerkubectl get ds,sts -n NSWas the workload created? What are its replica/coverage counts?
Pod placementkubectl get pods -o wide -n NSWhich node hosts each Pod, and what is its status?
Events / reasonskubectl describe pod POD -n NSScheduling, image, mount, probe and admission errors.
Storagekubectl get pvc,pv,scAre claims bound? What provisioner and reclaim policy are involved?

Declarative versus imperative changes

For teaching and repeatability, store manifests in files and use kubectl apply -f. Use kubectl set image, kubectl scale, and kubectl delete pod as focused investigative commands, then bring the file back into alignment to avoid configuration drift.

3. DaemonSet: run a Pod on each eligible node

A DaemonSet ensures that a copy of a Pod runs on every node that matches its eligibility rules. If an eligible node is added, a Pod is normally added; when a node is removed, its managed Pod is garbage-collected. It is not a fixed replica count.

Why use it?

Logging agent

Collect local container/node logs from each node where logs exist.

Node telemetry

Export host and runtime metrics from selected nodes.

Infrastructure helper

Support networking, storage, GPU/device or other node-local integrations.

Important fields

FieldPurposeCommon mistake
spec.selectorIdentifies the Pods owned by this DaemonSet.Selector does not match template labels.
spec.templatePod specification, including image, resources, security, volumes, and probes.Assuming controller health guarantees container health.
nodeSelector / affinityLimits eligible nodes.Expecting coverage on nodes that do not match.
tolerationsAllows placement despite matching taints.Adding broad tolerations without understanding impact.
updateStrategyControls how template changes replace Pods.Updating an image and not watching rollout status.
resources and security contextBound resource usage and reduce privileges.Running a node agent privileged by default.

How reconciliation works

DaemonSet updates

Useful commands:

kubectl get daemonsets -A
kubectl get ds nimbus-node-agent -n nimbus-ds-sts-lab -o wide
kubectl describe ds nimbus-node-agent -n nimbus-ds-sts-lab
kubectl get pods -n nimbus-ds-sts-lab -l app=nimbus-node-agent -o wide
kubectl rollout status ds/nimbus-node-agent -n nimbus-ds-sts-lab
kubectl rollout history ds/nimbus-node-agent -n nimbus-ds-sts-lab
Security warning: many real node agents mount host paths or use elevated permissions. Do not copy hostPath mounts, privileged mode, host networking, or broad tolerations into a student lab unless the need and risk are specifically understood.

DaemonSet versus a hand-created Pod

A bare Pod pinned to a node is not automatically recreated after deletion. A DaemonSet is a managed controller and is appropriate when the node-local agent should be maintained automatically.

4. StatefulSet: stable identity, ordered lifecycle, and storage

A StatefulSet manages a set of Pods that share a template but are not meant to be completely interchangeable. It provides stable ordinals and stable network identifiers, and can provide stable storage through per-replica PVCs. It does not itself implement database replication, consensus, backups, or application-level failover.

Three promises to understand

Stable identity

Pod names include ordinals, for example nimbus-store-1, including after a replacement.

Stable network

A governing headless Service supports predictable Pod DNS names.

Stable storage

Each ordinal receives its own claim; the storage backend must provision or supply the volume.

Headless Service and DNS

A headless Service uses clusterIP: None. Set the StatefulSet’s spec.serviceName to the Service’s name and match the Service selector with Pod labels. A common DNS pattern is:

<pod-name>.<headless-service>.<namespace>.svc.<cluster-domain>

# Example with the default cluster domain:
nimbus-store-0.nimbus-store-headless.nimbus-ds-sts-lab.svc.cluster.local

Per-Pod persistent claims

Data protection: deleting or scaling down a StatefulSet does not automatically delete the PVCs created from its volume claim templates. A PV’s reclaim policy and cloud storage configuration determine what happens after a claim is removed. Treat PVC deletion as a data lifecycle decision, not routine cleanup.

Default ordering

When is StatefulSet a fit?

It is a useful building block for data stores, clustered systems, queues, or applications whose replicas need stable addresses or separate disk state. A Deployment is usually simpler for stateless web/API replicas that can be replaced interchangeably. StatefulSet is not automatically the correct choice for every database: storage, quorum, backup, and recovery requirements still drive design.

StatefulSet manifest fields to review

FieldWhat it means
serviceNameName of the governing headless Service.
replicasDesired number of ordinal Pods.
selectorMust match the Pod template labels.
podManagementPolicyOrderedReady by default; Parallel relaxes ordered create/delete semantics.
volumeClaimTemplatesPer-Pod PVC specification, including capacity and access mode.
updateStrategyControls update behavior; StatefulSet rolling updates can be blocked by an unhealthy Pod.

Before using a shared cluster: confirm your current context and namespace permissions. Never paste production credentials or run broad deletion commands without verifying the exact context and resource scope.

Storage readiness: must check before Lab 2

The StatefulSet uses a 1 GiB claim per replica and intentionally relies on the cluster’s default StorageClass when one is configured. On Amazon EKS, validate that an intended StorageClass and CSI provisioner (for example, EBS CSI if using EBS block storage) are installed and healthy. In local clusters, use the cluster’s supported storage provisioner. If no appropriate dynamic provisioner exists, an administrator must provide a matching PV or storage setup before the claim can bind.

Ready checkpoint: kubectl cluster-info works; you have permission to create namespaced workloads; and a suitable StorageClass/provisioner is available before applying the PVC-backed StatefulSet.

7. Hands-on Lab 1 — DaemonSet node agent

Lab scope A minimal, non-privileged BusyBox process prints the hostname once and then sleeps. It is an illustrative node-local agent pattern, not a real log collector. It intentionally avoids hostPath mounts.

Exercise A — Create an isolated namespace

kubectl apply -f namespace.yaml
kubectl get namespace nimbus-ds-sts-lab
namespace.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: nimbus-ds-sts-lab
  labels:
    app.kubernetes.io/part-of: nimbus-training

Exercise B — Apply the DaemonSet manifest

daemonset.yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: nimbus-node-agent
  namespace: nimbus-ds-sts-lab
  labels:
    app: nimbus-node-agent
spec:
  selector:
    matchLabels:
      app: nimbus-node-agent
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1
  template:
    metadata:
      labels:
        app: nimbus-node-agent
    spec:
      terminationGracePeriodSeconds: 10
      containers:
        - name: agent
          image: busybox:1.36.1
          command:
            - sh
            - -c
            - while true; do echo "node-agent alive on $(hostname)"; sleep 3600; done
          resources:
            requests:
              cpu: 10m
              memory: 16Mi
            limits:
              cpu: 100m
              memory: 64Mi
          securityContext:
            runAsNonRoot: true
            runAsUser: 10001
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: ["ALL"]
            seccompProfile:
              type: RuntimeDefault

Important manifest details: selector exactly matches the Pod-template label; the default selector gives the demo no extra node filter; resource requests/limits are small; and the container runs non-root without extra capabilities. On a real cluster, a node can still lack capacity or fail image retrieval.

kubectl apply -f daemonset.yaml
kubectl get ds nimbus-node-agent -n nimbus-ds-sts-lab
kubectl get pods -n nimbus-ds-sts-lab -l app=nimbus-node-agent -o wide
kubectl describe ds nimbus-node-agent -n nimbus-ds-sts-lab
kubectl logs -n nimbus-ds-sts-lab -l app=nimbus-node-agent --tail=10

What should you expect?

The DaemonSet status should report desired/current/ready counts. With no additional node filter, each eligible node normally has a Pod. Do not infer failure just because desired count is lower than all nodes: control-plane taints, labels, architecture, scheduling limits, cluster policy, and other constraints may intentionally exclude nodes.

Representative log line: node-agent alive; pod hostname nimbus-node-agent-xxxxx (exact Pod/hostname output is cluster-specific). This is illustrative; it is not a claim that the commands have been executed against your cluster.

Exercise C — Update the template and observe rollout

# Change the image to a second valid BusyBox tag for the lab
kubectl set image ds/nimbus-node-agent agent=busybox:1.36 -n nimbus-ds-sts-lab
kubectl rollout status ds/nimbus-node-agent -n nimbus-ds-sts-lab
kubectl get pods -n nimbus-ds-sts-lab -l app=nimbus-node-agent -o wide
kubectl rollout history ds/nimbus-node-agent -n nimbus-ds-sts-lab

Use only a tag you have verified is available from your permitted registry. The command changes the live Pod template. If you maintain YAML as source of truth, update daemonset.yaml to match or the next apply can revert the image.

Exercise D — Optional node-coverage investigation

kubectl get nodes --show-labels
kubectl describe node NODE_NAME
kubectl describe ds nimbus-node-agent -n nimbus-ds-sts-lab
kubectl get events -n nimbus-ds-sts-lab --sort-by=.lastTimestamp

Replace NODE_NAME with an actual node. Do not add/delete production labels or taints just to make the lab count line up.

Success criteria

  • The DaemonSet exists in nimbus-ds-sts-lab.
  • Its selector and template labels match.
  • Pods appear on eligible nodes and are Ready.
  • The image update finishes or the failure is understood from events/logs.

8. Hands-on Lab 2 — StatefulSet with stable DNS and per-Pod storage

Storage required This lab creates three NGINX Pods and a 1 GiB PVC for each Pod. The PVC is mounted at NGINX’s document root so you can write a test file, delete a Pod, and confirm that the replacement uses the same claim. This does not configure NGINX application replication; the files in each replica are intentionally separate.

Preflight: run kubectl get sc. If there is no default/appropriate StorageClass, do not apply the StatefulSet until storage is configured. A Pending PVC is a storage setup/availability issue, not a reason to remove the PVC blindly.

Exercise A — Create the headless Service

service-headless.yaml
apiVersion: v1
kind: Service
metadata:
  name: nimbus-store-headless
  namespace: nimbus-ds-sts-lab
  labels:
    app: nimbus-store
spec:
  clusterIP: None
  publishNotReadyAddresses: false
  selector:
    app: nimbus-store
  ports:
    - name: http
      port: 80
      targetPort: http

clusterIP: None marks this as a headless Service. serviceName on the StatefulSet will reference this exact name, and the selector must match the Pod template labels.

Exercise B — Create the StatefulSet

statefulset.yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: nimbus-store
  namespace: nimbus-ds-sts-lab
  labels:
    app: nimbus-store
spec:
  serviceName: nimbus-store-headless
  replicas: 3
  podManagementPolicy: OrderedReady
  selector:
    matchLabels:
      app: nimbus-store
  template:
    metadata:
      labels:
        app: nimbus-store
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: web
          image: nginx:1.27-alpine
          ports:
            - name: http
              containerPort: 80
          resources:
            requests:
              cpu: 50m
              memory: 64Mi
            limits:
              cpu: 250m
              memory: 128Mi
          readinessProbe:
            httpGet:
              path: /
              port: http
            initialDelaySeconds: 3
            periodSeconds: 5
          volumeMounts:
            - name: web-data
              mountPath: /usr/share/nginx/html
  volumeClaimTemplates:
    - metadata:
        name: web-data
        labels:
          app: nimbus-store
      spec:
        accessModes:
          - ReadWriteOnce
        resources:
          requests:
            storage: 1Gi

The image, resource settings, readiness probe, and volume mount are part of the Pod template. The web-data template creates claims named web-data-nimbus-store-0, web-data-nimbus-store-1, and web-data-nimbus-store-2. Storage class is omitted so a configured default can be used. For broader production storage security, evaluate ReadWriteOncePod where supported by your CSI driver, application compatibility, and operational needs.

Exercise C — Apply in order and inspect

kubectl apply -f service-headless.yaml
kubectl get svc nimbus-store-headless -n nimbus-ds-sts-lab
kubectl apply -f statefulset.yaml
kubectl rollout status statefulset/nimbus-store -n nimbus-ds-sts-lab
kubectl get pods -n nimbus-ds-sts-lab -l app=nimbus-store -o wide
kubectl get pvc -n nimbus-ds-sts-lab
kubectl get statefulset nimbus-store -n nimbus-ds-sts-lab

With default OrderedReady, the controller normally creates nimbus-store-0 first and waits for it to be Ready before creating ordinal 1, then ordinal 2. If the first Pod is blocked by a Pending PVC, image pull, or readiness issue, later Pods may not appear yet.

Exercise D — Verify the stable DNS pattern

kubectl get endpointslices -n nimbus-ds-sts-lab -l kubernetes.io/service-name=nimbus-store-headless
kubectl get pods -n nimbus-ds-sts-lab -l app=nimbus-store --show-labels

# Pattern for the first Pod when the cluster domain is cluster.local:
# nimbus-store-0.nimbus-store-headless.nimbus-ds-sts-lab.svc.cluster.local

For a DNS lookup test, run a temporary diagnostic Pod with a DNS tool approved for your cluster, or use a container image already available in the environment. Exact FQDN and DNS caching behavior can differ if the cluster DNS domain is not cluster.local.

Exercise E — Write a file, delete a Pod, verify data

kubectl exec -n nimbus-ds-sts-lab nimbus-store-0 -- sh -c 'echo "persisted-from-nimbus-store-0" > /usr/share/nginx/html/index.html'
kubectl exec -n nimbus-ds-sts-lab nimbus-store-0 -- cat /usr/share/nginx/html/index.html

# Delete only this lab Pod. The StatefulSet controller should recreate ordinal 0.
kubectl delete pod nimbus-store-0 -n nimbus-ds-sts-lab
kubectl wait --for=condition=Ready pod/nimbus-store-0 --timeout=180s -n nimbus-ds-sts-lab
kubectl exec -n nimbus-ds-sts-lab nimbus-store-0 -- cat /usr/share/nginx/html/index.html
Expected result if the claim remains healthy and remounts correctly: nimbus-store-0 is recreated and the content persisted-from-nimbus-store-0 remains. If it does not, investigate whether the correct claim was mounted, whether storage attached, whether the file was written to the mounted path, and whether the storage/filesystem remains healthy.

Success criteria

  • Three named Pods become Ready.
  • Three PVCs become Bound.
  • The headless Service selects the Pod labels.
  • Deleting ordinal 0 results in a replacement named ordinal 0.
  • The test file remains on the same claim across Pod replacement.

9. End-to-end architecture: node telemetry plus a stateful service

Imagine an internal application running three stateful web replicas, while a node-local agent gathers basic node-level logs from eligible workers. The two controllers solve different problems and can coexist in a namespace; in a real system, the agent would usually need carefully scoped log access and a log destination.

Execution plan

1

Check environment

Verify cluster context, RBAC, node readiness, and storage provisioner before touching resources.

2

Apply the namespace and DaemonSet

Observe node placement and reconcile any failures through events instead of assuming every node is eligible.

3

Apply the headless Service, then StatefulSet

Observe ordinal create ordering and inspect PVC binding. Wait for all Pods to become Ready before declaring success.

4

Validate lifecycle behavior

Update the DaemonSet template, replace one StatefulSet Pod, verify name and claim continuity, and inspect the final object state.

Final verification checklist

kubectl get ds,sts,svc -n nimbus-ds-sts-lab
kubectl get pods -n nimbus-ds-sts-lab -o wide
kubectl get pvc -n nimbus-ds-sts-lab
kubectl get events -n nimbus-ds-sts-lab --sort-by=.lastTimestamp
kubectl rollout status ds/nimbus-node-agent -n nimbus-ds-sts-lab
kubectl rollout status statefulset/nimbus-store -n nimbus-ds-sts-lab

Representative final state (not actual cluster output): the DaemonSet’s Ready count equals its eligible-node target; the StatefulSet has three Ready replicas; the headless Service selects the StatefulSet Pods; and all three claims are Bound. Actual counts and names of underlying PVs depend on the cluster and provisioner.

10. Troubleshooting with diagnostic decision paths

Start with observed state and events. A symptom narrows the search; it does not prove the root cause.

A. DaemonSet missing or not Ready on a node

Useful commands

kubectl get nodes --show-labels
kubectl get ds NAME -n NS -o yaml
kubectl get pods -n NS -l APP_LABEL -o wide
kubectl describe pod POD -n NS
kubectl describe node NODE
kubectl get events -n NS --sort-by=.lastTimestamp

Common clues

  • Desired count is lower: selector/affinity/eligibility may be intended.
  • Pod Pending: insufficient resources, taints, quota, or scheduling constraints.
  • ImagePullBackOff: bad tag, auth, DNS, or registry access.
  • CrashLoopBackOff / NotReady: logs, command, probes, permissions, or dependencies.
  • Rolling update stuck: unhealthy replacement or capacity constraint.

B. StatefulSet Pod stuck Pending

kubectl get pods,pvc -n NS -o wide
kubectl describe pod POD -n NS
kubectl describe pvc CLAIM -n NS
kubectl get storageclass
kubectl get pv
kubectl get events -n NS --sort-by=.lastTimestamp
SignalInvestigateNext action
PVC PendingStorageClass, provisioner/CSI, PV matching, quota/capacity, topologyFix the relevant storage configuration; do not blindly delete the claim.
Pod Pending, PVC BoundNode capacity, affinity, taints, topology, quotasRead scheduler events and fix the actual placement constraint.
ContainerCreating / mount errorAttach/mount events, node plugin, volume topology, filesystem errorsRepair storage or node/CSI issue; preserve data.
ImagePullBackOffImage tag, registry authentication, network/DNSUse a valid accessible image and verify credentials if needed.
CrashLoopBackOff / NotReadyApplication logs, probes, permissions, data format, resource limitsFix the application or probe and re-check lower ordinal health.

C. Higher StatefulSet ordinal never appears or rollout stalls

D. DNS is not resolving

  1. Check Service name and namespace: kubectl get svc nimbus-store-headless -n NS.
  2. Check selector/labels: compare Service selector with Pod labels.
  3. Check endpoints: inspect EndpointSlices and Ready status.
  4. Verify exact Pod FQDN, namespace, and configured cluster domain.
  5. If records were looked up before the Pod existed, account for DNS negative caching; test again after readiness and cache expiry.
  6. Inspect CoreDNS logs and NetworkPolicy only after object names, labels, and endpoints are correct.

E. Data appears missing after Pod replacement

Do not immediately delete or recreate the PVC/PV. First check the claim expected for the ordinal, the Pod’s volumeMounts, the actual path used by the test, mount events, underlying volume state, filesystem permissions, and backups. A container writable layer is not the same thing as the PVC mount.

11. Best practices and common anti-patterns

Do

DaemonSet

  • Declare narrow node selection and tolerations.
  • Set requests/limits and health checks appropriate to the agent.
  • Use non-root, drop unnecessary capabilities, and minimize hostPath access.
  • Monitor desired/current/ready counts and rollout progress.
  • Test template updates on a safe node pool first.
Do

StatefulSet

  • Match Service selectors, Pod labels, and serviceName.
  • Check storage provisioning, capacity, topology, and reclaim policy.
  • Define backups, restore tests, failure behavior, and application replication separately.
  • Use readiness probes that reflect real service readiness.
  • Delete PVCs only after an explicit data lifecycle review.
Anti-patternRiskBetter practice
Use a DaemonSet to force a fixed number of PodsCoverage changes as eligible nodes change.Use Deployment when you need a fixed replica count.
Assume DaemonSet means one Pod on every machineEligibility and scheduling constraints are ignored.Define eligible nodes and interpret desired/current/ready status.
Use StatefulSet and assume it creates DB consensusIdentity is confused with application availability.Use an operator/database design for replication, quorum, failover, backup.
Delete claims as routine cleanupPersistent data can be irreversibly lost or disks can be provisioned/deleted unexpectedly.Review PVC/PV/StorageClass reclaim policy and data retention first.
Give a node agent privileged host access by defaultCompromised agent may affect the host/cluster.Apply least privilege and mount only necessary host paths.
Use latest image tags in productionUnplanned drift and rollback ambiguity.Pin and validate image versions/digests and test upgrades.

These lab resources are examples, not a universal production baseline. Tune security context, storage class, capacity, topology spreading, probes, image pinning, and disruption strategy to the application and cluster.

12. Interview preparation — 36 expandable questions

Try answering aloud before expanding each answer. Use the search box to filter by a word such as “PVC”, “DaemonSet”, “rollout”, or “DNS”.

Level 1 — Basic concepts (12)

What problem does a DaemonSet solve?
It maintains a Pod on every eligible node, making it suitable for node-local services such as logging agents, monitoring agents, storage helpers, or network components.
Does a DaemonSet always run on every node in the cluster?
No. It targets eligible nodes. Node selectors, node affinity, taints/tolerations, resources, platform constraints, and admission policy can affect placement.
Which API version should a DaemonSet use?
Use apps/v1 with kind: DaemonSet.
What must match between a controller selector and its Pod template?
The keys and values in spec.selector.matchLabels must match labels in spec.template.metadata.labels. Mismatches are rejected at creation.
What are common DaemonSet use cases?
Node-level log collection, monitoring/telemetry agents, storage daemons, network plugins, and device plugins—when an agent needs to operate on each relevant node.
What is the default DaemonSet update strategy?
RollingUpdate. It replaces old Pods automatically in a controlled way. OnDelete waits until old Pods are manually deleted.
How do you inspect DaemonSet coverage?
Use kubectl get ds -A, then kubectl describe ds NAME -n NAMESPACE. Compare desired, current, ready, available, and misscheduled counts.
Is a DaemonSet cluster-scoped?
No. The DaemonSet object is namespaced, but its Pods can run on nodes throughout the cluster. Govern who can create or update one carefully because its Pod template may request broad node access.
How is a DaemonSet different from a Deployment?
A Deployment manages a desired replica count of interchangeable Pods. A DaemonSet is node-coverage oriented: one Pod per eligible node.
Do DaemonSet Pods tolerate all taints automatically?
No. Kubernetes adds certain built-in tolerations, but custom taints may still exclude Pods unless matching tolerations are configured.
What happens when an eligible node is added?
The DaemonSet controller normally creates a Pod targeted to that eligible node. Existing node selection and scheduling constraints still apply.
Should every DaemonSet mount host directories or run privileged?
No. Use the minimum host access, Linux capabilities, and privilege required. A node agent with broad host access has an expanded blast radius.

Level 2 — Intermediate concepts (12)

What distinguishes a StatefulSet Pod from a Deployment Pod?
A StatefulSet Pod has a stable ordinal identity and can be paired with stable storage and network identity. Deployment replicas are ordinarily interchangeable.
What is a StatefulSet ordinal?
An index in the Pod identity, by default starting at zero: for three replicas, nimbus-store-0, nimbus-store-1, and nimbus-store-2.
Why does a StatefulSet commonly use a headless Service?
The Service, typically with clusterIP: None, provides a governing DNS domain for stable Pod network identities. The Service must be created by the operator.
What does volumeClaimTemplates do?
It creates one PersistentVolumeClaim for each StatefulSet Pod for each template entry, allowing each ordinal to receive its own claim.
Does a StatefulSet guarantee application-level replication or consensus?
No. It supplies identity and lifecycle primitives. The application must implement or be configured for its own replication, quorum, leader election, consistency, and recovery behavior.
What is the default Pod management policy?
OrderedReady. Creation is ordered from lower to higher ordinal, waiting for predecessors to be Ready; scale-down proceeds from higher to lower ordinal.
What does Parallel Pod management change?
It relaxes ordered create/delete behavior by allowing Pods to be created or terminated in parallel. Identity guarantees remain, but the application must tolerate more concurrent lifecycle actions.
Are PVCs deleted when a StatefulSet is deleted?
The StatefulSet controller does not delete the PVCs created from volumeClaimTemplates simply because the StatefulSet is deleted or scaled down. Inspect and delete claims deliberately when data removal is intended.
What happens when a StatefulSet Pod is recreated?
The controller recreates the same ordinal identity. If its associated PVC remains available and can attach/mount, the new Pod can reconnect to the same data volume.
Is a StatefulSet automatically highly available?
Not by itself. Availability also depends on application replication, topology, storage characteristics, pod disruption, probes, scheduling, backups, and network/service design.
What is the difference between ReadWriteOnce and ReadWriteOncePod?
ReadWriteOnce usually means a volume can be mounted read-write by one node at a time; multiple Pods on that node may still use it. ReadWriteOncePod restricts a volume to a single Pod and requires compatible CSI support.
Can I use a Deployment for a database?
Sometimes a single-instance or application-managed architecture may use other patterns, but a StatefulSet is often useful when replicas need stable identity/storage. The controller alone does not make the database safe.

Level 3 — Real-world scenarios (12)

Why might the StatefulSet controller wait before creating ordinal 2?
With default OrderedReady behavior, lower ordinals must be Running and Ready (and satisfy minReadySeconds if set) before a later ordinal is created.
How can you inspect the claim mounted by a StatefulSet Pod?
Use kubectl get pvc -n NAMESPACE, inspect a claim with kubectl describe pvc CLAIM -n NAMESPACE, and check Pod events/mount status with kubectl describe pod POD -n NAMESPACE.
What is a headless Service?
A Service configured with clusterIP: None. It does not allocate a virtual ClusterIP and is commonly used for direct discovery of selected Pods through DNS.
Why might a per-Pod DNS name not resolve immediately?
DNS negative caching and endpoint readiness can delay discovery. Check Pod readiness, Service selectors/endpoints, CoreDNS, and allow for cache TTL before concluding identity is wrong.
How can a stuck StatefulSet rollout be diagnosed?
Inspect rollout status, then the lowest unhealthy ordinal, Pod events/logs/probes, PVC binding/mount status, and image pulls. OrderedReady can block later replicas behind one bad Pod.
Scenario: A cluster has five worker nodes but a DaemonSet shows four desired Pods. What do you check?
First determine whether all five nodes are eligible. Check node labels and conditions, DaemonSet nodeSelector/affinity, taints/tolerations, and platform/admission policies; then inspect DS status and events. Desired count is not always equal to raw node count.
Scenario: A DaemonSet Pod is missing from a newly joined node. How do you debug it?
Run kubectl get nodes --show-labels, kubectl describe node NODE, kubectl describe ds NAME -n NS, and inspect Pod/events. Check selectors, custom taints, resource fit, image pulls, and quotas/admission.
Scenario: A DaemonSet rollout is stuck after an image update. What next?
Use kubectl rollout status ds/NAME -n NS, kubectl get pods -o wide, describe failed Pods, and inspect logs/events for ImagePullBackOff, crashes, readiness failure, or resource shortage. Correct the template and verify the rollout; rollback if the previous revision is known-good.
Scenario: A student wants exactly three telemetry Pods even when the cluster scales to ten nodes. Is DaemonSet suitable?
Usually not. A Deployment with replicas: 3 better matches a fixed replica count. A DaemonSet is for per-eligible-node coverage.
Scenario: StatefulSet Pods remain Pending and their PVCs remain Pending. What do you inspect?
Check kubectl get storageclass, kubectl describe pvc CLAIM, and events. Validate dynamic provisioner/CSI driver, StorageClass, requested capacity, topology/capacity, quotas, access modes, and any pre-provisioned PV matching rules.
Scenario: nimbus-store-1 was deleted but returns without its data. What could be wrong?
Verify it reattached the expected PVC (claim naming and volumeMount), inspect PVC/PV status, volume topology/attachment and filesystem permissions, and make sure the test wrote into the mounted path rather than the container filesystem. Restore data from backup if the volume/data is actually gone.
Scenario: nimbus-store-2 never appears because nimbus-store-1 is not Ready. Why?
Default StatefulSet policy is OrderedReady, so a lower ordinal not Ready can block creation of a higher ordinal. Diagnose the lower Pod first: image, probes, logs, PVC, scheduling, and application startup.

14. Quick revision cheat sheet

DaemonSet

  • API: apps/v1
  • Purpose: node-local Pod coverage
  • Check: kubectl get ds -A
  • Placement: node selector/affinity, taints, capacity and policy
  • Rollout: kubectl rollout status ds/NAME -n NS
  • Remember: desired count reflects eligible nodes, not a manually set replica count.

StatefulSet

  • API: apps/v1
  • Purpose: stable ordinal identity and ordered management
  • Check: kubectl get sts,pods,pvc -n NS
  • Network: governing headless Service
  • Storage: one claim per ordinal from volumeClaimTemplates
  • Remember: deletion of a StatefulSet is not a signal to delete the data claims.

15. Cleanup and resource lifecycle

Cleanup is split into workload deletion and storage deletion. This makes the data-loss boundary explicit.

Step 1 — Inspect the resources you are about to remove

kubectl config current-context
kubectl get ds,sts,svc,pods,pvc,pv -n nimbus-ds-sts-lab
kubectl get pvc -n nimbus-ds-sts-lab -o wide
kubectl get pv

Step 2 — Remove workload controllers and Service

kubectl delete daemonset nimbus-node-agent -n nimbus-ds-sts-lab
kubectl scale statefulset nimbus-store --replicas=0 -n nimbus-ds-sts-lab
kubectl delete statefulset nimbus-store -n nimbus-ds-sts-lab
kubectl delete service nimbus-store-headless -n nimbus-ds-sts-lab
kubectl get pods,pvc -n nimbus-ds-sts-lab

Scaling the StatefulSet to zero can help terminate replicas in order before deleting the controller, but it is not a substitute for an application-specific shutdown or backup procedure for real data stores.

Step 3 — Decide whether lab data can be deleted

Destructive step — only when you have confirmed that the lab data is disposable:
# Review the exact claims first. This pattern deletes only claims carrying the lab label.
kubectl get pvc -n nimbus-ds-sts-lab -l app=nimbus-store

# Only if the claims are lab-only and no data must be retained:
kubectl delete pvc -n nimbus-ds-sts-lab -l app=nimbus-store
kubectl get pvc -n nimbus-ds-sts-lab
kubectl get pv

Deleting a PVC can trigger storage backend cleanup depending on the PV reclaim policy and StorageClass. For EKS/EBS or other cloud-backed volumes, check the resulting PV and cloud storage state according to your organization’s policy. Do not run a broad PVC deletion in a shared or production namespace.

Step 4 — Remove the namespace when empty and lab-only

kubectl get ds,sts,svc,pods,pvc -n nimbus-ds-sts-lab
# Only after confirming the namespace contains no resources/data to retain:
kubectl delete namespace nimbus-ds-sts-lab
kubectl get namespace nimbus-ds-sts-lab

The final query should report that the namespace no longer exists after deletion completes. Do not delete cluster nodes, cluster-wide add-ons, StorageClasses, CSI drivers, or unrelated PersistentVolumes as part of this lesson.
