01 · Why this exists

Introduction and real-world purpose

A ConfigMap is a Kubernetes API object for storing non-confidential configuration as key-value pairs. It lets teams change settings—such as log level, feature toggles, application properties, or web content—without baking those values into a container image. A Pod can consume a ConfigMap as environment variables, command-line arguments, or files in a volume. citeturn605144search1turn508162search3

Analogy: recipe card versus kitchen appliance

The container image is the appliance; a ConfigMap is the recipe card or settings sheet. The same appliance image can be used in test, staging, and production with different non-secret settings. The application must still read or reload the supplied configuration correctly.

When it is useful: application properties, server configuration files, feature flags, log verbosity, simple web-page files, or command arguments.

Advantages and limitations

AdvantagesLimitations
Decouples settings from image; supports declarative YAML; reusable between Pods; good for simple text files and key-value settings.Not secret storage; a ConfigMap is limited to 1 MiB; consumers differ in how they see updates; applications may need their own reload or restart workflow.
Versioned ConfigMap names can make rollouts explicit and rollback easier.ConfigMaps are namespace-scoped; Pod and ConfigMap must be in the same namespace. A normal ConfigMap mount does not automatically make the app reread a file.
02 · Fundamentals

ConfigMap object and its fields

What does a ConfigMap contain?

A ConfigMap does not have a normal workload-style spec. Its data field stores UTF-8 strings, including multi-line configuration text. binaryData supports binary values represented as base64-encoded data. The total object data is limited to 1 MiB. Keys can contain letters, digits, -, _, and ., and a key may not appear in both data and binaryData. citeturn605144search1

Annotated example: a multi-line configuration file

apiVersion: v1
kind: ConfigMap
metadata:
  name: app-settings
  namespace: nimbus-config-lab
data:
  LOG_LEVEL: "info"
  FEATURE_BANNER: "true"
  application.properties: |
    server.port=8080
    logging.level.root=INFO
    feature.banner=true
FieldMeaningCommon mistake
apiVersion: v1Core Kubernetes API version for ConfigMap.Using a made-up API group/version.

metadata.nameName referenced by Pods.Pod references a different or misspelled name.
metadata.namespaceNamespace containing the ConfigMap.Assuming Pods can reference ConfigMaps across namespaces.

Two simple creation paths

Imperative creation is useful for a quick experiment; declarative manifests are easier to review, version-control, and reuse.

# Imperative: key=value
kubectl create configmap app-flags \
  --from-literal=LOG_LEVEL=debug \
  --from-literal=FEATURE_BANNER=true \
  -n nimbus-config-lab

# Inspect the object
kubectl get configmap app-flags -n nimbus-config-lab -o yaml
Data size and confidentiality: Do not put passwords or API tokens in ConfigMaps. Avoid using ConfigMaps for large artifacts; the documented size limit is 1 MiB. Use a suitable Secret management process or external configuration store where appropriate. citeturn605144search1
03 · Consumption patterns

Ways a Pod can consume a ConfigMap

The consumption method determines when the value is read and how updates become visible. Choose it based on how the application expects to receive configuration.

MethodGood fitUpdate behaviorGotcha
env / envFromApplications expecting settings as process environment values.Running container's environment does not change when ConfigMap changes; recreate/restart Pods.Key names imported through envFrom must be valid environment variable names; invalid ones may be skipped and recorded in events.
Volume mounted as a directoryApplications read configuration files from a directory.Projected file content updates eventually after kubelet/cache propagation delay.Application must reread the file or reload config; mounting on an existing directory hides image files at that mount path.

04 · The key topic

How ConfigMap subPath works

volumeMounts.subPath mounts a specific file or subdirectory from a volume at a specific location inside the container. For ConfigMaps, a common use is to replace one application configuration file while leaving other files under the container image's directory visible. The critical limitation: a ConfigMap mounted using subPath does not receive updates when the ConfigMap changes. citeturn605144search0turn508162search2

Manifest fields that form the relationship

volumes:
- name: page
  configMap:
    name: web-page
    items:
    - key: index.html
      path: index.html

containers:
- name: nginx
  volumeMounts:
  - name: page
    mountPath: /usr/share/nginx/html/index.html
    subPath: index.html
    readOnly: true

When should I use subPath?

Use it when

  • You need to mount one file into an existing application directory.
  • You want to keep image-provided sibling files visible.
  • The operational plan includes an explicit Pod restart/rollout when configuration changes.

Avoid it when

  • You expect file contents to refresh automatically after a ConfigMap edit.
  • You want the entire configuration directory projected and can tolerate the directory mount behavior.
  • The app requires reload-on-change but you have no reload or restart mechanism.
Most important interview fact: Updating a ConfigMap does not refresh a file that was mounted through subPath. To consume the new content, recreate the Pod (for example, with kubectl rollout restart deployment/NAME) or use a different design. citeturn605144search0turn508162search2
05 · Under the hood

Architecture and lifecycle

Update lifecycle: full volume versus subPath

Step-by-step workflow

  1. Create or update the ConfigMap.
  2. Reference it from a Pod template in the same namespace.
  3. Kubernetes schedules/runs the Pod and the kubelet resolves the referenced configuration.
  4. For environment variables, the process receives values as the container is launched.
  5. For a ConfigMap volume, files are projected into a read-only mount.
  6. If ConfigMap data changes, check how it is consumed. For subPath, roll out/recreate the Pod; for environment variables, restart the Pod; for full-volume mounts, wait for projection and verify the application reload behavior.

07 · Practical implementation

Step-by-step hands-on practice

Run the labs in order. All Kubernetes resources use nimbus-config-lab. The commands assume a Unix-like shell such as macOS Terminal, Linux, or WSL. Representative output is illustrative; Pod names, timing, and status can vary.

Exercise 1 — ConfigMap as environment variables

Objective Inject scalar settings into a container process and show that the process gets them at startup.

Step 1: Save as 01-env.yaml.

apiVersion: v1
kind: ConfigMap
metadata:
  name: env-demo
  namespace: nimbus-config-lab
data:
  LOG_LEVEL: "debug"
  FEATURE_BANNER: "true"
  APP_REGION: "training"
---
apiVersion: v1
kind: Pod
metadata:
  name: config-env-demo
  namespace: nimbus-config-lab
spec:
  restartPolicy: Always
  containers:
  - name: shell
    image: busybox:1.36
    command: ["/bin/sh", "-c"]
    args:
    - echo "LOG_LEVEL=$LOG_LEVEL FEATURE_BANNER=$FEATURE_BANNER APP_REGION=$APP_REGION";
      sleep 3600
    envFrom:
    - configMapRef:
        name: env-demo
    env:
    - name: APP_REGION
      valueFrom:
        configMapKeyRef:
          name: env-demo
          key: APP_REGION

Step 2: Apply and inspect.

kubectl apply -f 01-env.yaml
kubectl get configmap env-demo -n nimbus-config-lab
kubectl get pod config-env-demo -n nimbus-config-lab
kubectl logs config-env-demo -n nimbus-config-lab

Expected result (illustrative): the log line includes LOG_LEVEL=debug FEATURE_BANNER=true APP_REGION=training.

Explanation: envFrom imports valid ConfigMap keys as environment variables. The explicit env mapping illustrates configMapKeyRef for a single value. In this example, APP_REGION is explicitly set to the same ConfigMap value as the bulk import; avoid duplicate patterns in real manifests unless there is a clear reason.

Verify a running process:

kubectl exec config-env-demo -n nimbus-config-lab -- sh -c 'printf "%s\n" "$LOG_LEVEL" "$FEATURE_BANNER" "$APP_REGION"'

Interview takeaway: Updating ConfigMap data does not mutate environment variables in an already running process. Restart/recreate the Pod or roll out its owning workload to consume a changed environment value.

Exercise 2 — Mount a ConfigMap as a directory

Objective Map ConfigMap keys to files, then inspect their content inside the container.

Step 1: Save as 02-volume.yaml.

apiVersion: v1
kind: ConfigMap
metadata:
  name: directory-config
  namespace: nimbus-config-lab
data:
  application.properties: |
    app.name=NimbusDemo
    log.level=INFO
    feature.banner=true
  feature-flags.txt: |
    search.enabled=true
    reports.enabled=false
---
apiVersion: v1
kind: Pod
metadata:
  name: config-volume-demo
  namespace: nimbus-config-lab
spec:
  containers:
  - name: shell
    image: busybox:1.36
    command: ["/bin/sh", "-c"]

      mountPath: /etc/app-config

Step 2: Apply and inspect.

kubectl apply -f 02-volume.yaml
kubectl wait --for=condition=Ready pod/config-volume-demo -n nimbus-config-lab --timeout=120s
kubectl exec config-volume-demo -n nimbus-config-lab -- ls -la /etc/app-config

Expected result (illustrative): the directory contains files named application.properties and feature-flags.txt; cat shows the text in the corresponding ConfigMap keys.

Important: Mounting the entire ConfigMap directory at an existing directory path hides that directory's prior image contents at the mount point. This exercise uses an otherwise dedicated path, /etc/app-config.

kind: Pod

  name: config-items-demo
  namespace: nimbus-config-lab

  containers:

    image: busybox:1.36
    command: ["/bin/sh", "-c"]
    args: ["sleep 3600"]

kubectl apply -f 04-items.yaml

Exercise 5 — Compare whole-volume updates with subPath behavior

Objective Prove the difference with a simple file-read test. This exercise focuses on the expected mechanics; kubelet propagation has a delay.

Use the resources from Exercises 2 and 3. First change the directory-mounted ConfigMap:

kubectl patch configmap directory-config -n nimbus-config-lab --type=merge -p '{"data":{"application.properties":"app.name=NimbusDemoUpdated\nlog.level=DEBUG\nfeature.banner=false\n"}}'

Poll the mounted file while waiting for propagation:

kubectl exec config-volume-demo -n nimbus-config-lab -- cat /etc/app-config/application.properties

The normal volume should eventually project the changed content. The application may need to reopen/reload the file before behavior changes. In contrast, after patching web-page, an existing subpath-web Pod will not get the new file content until it is recreated.

Do not expect an immediate update at the exact moment a ConfigMap patch completes. Kubernetes documents a propagation delay for normal volume projection, which depends on kubelet sync and cache behavior. citeturn605144search0turn508162search8
08 · Complete workflow

End-to-end practical demonstration

Requirement

A small web application must use an HTML welcome page supplied by a ConfigMap. The image's other default web-root files should remain available, so the page is mounted at one path using subPath. A release operator must be able to change the page and understand why a Pod rollout is required.

Execution order

  1. Create 03-subpath.yaml from Exercise 3 in a dedicated namespace.
  2. Apply it and wait for rollout completion.
  3. Inspect the ConfigMap, Deployment, Pod and Service.
  4. Port-forward the Service and confirm the returned HTML version.
  5. Update the ConfigMap using the v2 file.
  6. Confirm the existing response has not changed, because the file uses subPath.
  7. Restart the Deployment and confirm the new response.
  8. Review Events and logs if the response is not as expected.

10 · Reliable configuration

Best practices and visual comparisons

Before and after: mounting the right path

Practical recommendations

  • Version config when releases matter. Names such as app-config-v17 make changes explicit and help a rollout use known configuration. Pair with a manifest update, checksum annotation, or deployment automation so the Pod template changes when appropriate.
  • Document update behavior. Use a clear comment in YAML explaining that a subPath mount requires Pod recreation to pick up changes.
  • Prefer a dedicated directory for full-volume mounts. Mounting a volume over an image directory can hide files shipped with the image.
  • Use immutable ConfigMaps for stable release artifacts when suitable. immutable: true prevents data changes in place. For a new configuration version, create another ConfigMap and update the Pod template reference.
  • Keep values non-secret. A ConfigMap is not the right place for passwords or access tokens; restrict access through RBAC regardless.
  • Observe actual consumer behavior. Confirm the file or environment value in the running Pod, and confirm the application has loaded it. API object state alone is insufficient.
  • Plan reload/restart explicitly. Environment values require process recreation. subPath mounts require Pod recreation. Full-directory projected files update eventually, but the app may need to reread the file.
  • Keep the ConfigMap small and clear. Keep total data within 1 MiB and use files or external storage better suited for large content.
  • Use namespaces deliberately. ConfigMaps are namespace-scoped and Pods refer to ConfigMaps in the same namespace.
  • Keep source of truth in version control. Prefer reviewed manifest changes with kubectl apply -f over undocumented manual edits in production.

Imperativekubectl create configmap feature-flags --from-literal=FEATURE_X=trueQuick demos, one-time exploration, simple troubleshooting.Harder to review/reproduce unless command history is captured.

11 · Interview preparation

Interview questions and answers

Level 1 — Basic questions

1. What is a ConfigMap?
A ConfigMap is a Kubernetes API object that stores non-confidential configuration as key-value pairs. Pods can consume it as environment variables, command arguments, or files through a volume.
2. Why should configuration be separated from an image?
The same image can be promoted across development, staging and production while each environment supplies its own configuration. This avoids building a different image for every non-secret setting.
3. Which API version and kind are used for a ConfigMap?
The manifest begins with apiVersion: v1 and kind: ConfigMap, because ConfigMap is a core API resource.
4. What is stored in data?
String values, including single-line values and multi-line text stored using YAML block scalars such as |. Use binaryData for binary values represented as base64-encoded content.
5. What is the maximum ConfigMap size?
The ConfigMap data size is limited to 1 MiB. Use a more suitable mechanism for large artifacts or datasets.
6. Can a Pod reference a ConfigMap in another namespace?
No. A Pod's ConfigMap reference is resolved in the same namespace as the Pod. Create or copy the relevant ConfigMap in the Pod's namespace if needed.
7. How can a ConfigMap be consumed as environment variables?
Use env with valueFrom.configMapKeyRef for a specific key, or envFrom.configMapRef to import valid key names from the ConfigMap.
8. How can a ConfigMap be mounted as files?
Add a ConfigMap volume under spec.volumes and reference the volume under the container's volumeMounts. The keys are projected as files; items can select keys and set relative file paths.
9. What does subPath do?
It mounts a specific file or subdirectory from a volume at a specified container path rather than mounting the entire volume at that path.
10. Do ConfigMap subPath mounts receive updates?
No. A container using a ConfigMap as a subPath volume mount does not receive ConfigMap updates. Recreate the Pod to mount the new value.
11. Is a ConfigMap a secure place for passwords?
No. ConfigMaps are intended for non-confidential data. Use Secrets or an external secret manager with suitable access controls for sensitive values.
12. How do you inspect a ConfigMap?
Use kubectl get configmap NAME -n NAMESPACE -o yaml to inspect its keys and values, then verify how the target Pod consumes them.

Level 2 — Intermediate questions

13. What is the difference between env and envFrom?
env can map a named variable from one key using configMapKeyRef. envFrom imports all valid key names as environment variables. Explicit env gives more control over names and individual keys.
14. Why does changing a ConfigMap not change environment variables in a running container?
The container process receives its environment when it starts. Kubernetes does not rewrite the environment of the existing process. Restart/recreate the Pod or roll out its owning workload to load the new value.
15. What is the difference between whole-volume mount and subPath mount?
A whole-volume mount projects all keys (or selected items) into a directory and can update eventually. A subPath mount targets one path, preserving sibling image files, but it does not receive ConfigMap updates.
16. Why can a whole-volume mount hide image files?
The mount overlays the target directory in the container's filesystem view. Existing files under that directory from the image are hidden by the mounted volume. Use a dedicated configuration directory or mount only a needed file via subPath.
17. What does items do in a ConfigMap volume?
It selects which ConfigMap keys are projected and specifies their relative paths inside the volume. If only one key is listed, other keys are not projected in that volume.
18. If a regular ConfigMap volume eventually updates, does the application immediately use the new settings?
Not necessarily. Kubernetes refreshes the projected files after propagation delay, but the application might have read the file only once at startup. Confirm the file content and use an application reload mechanism or Pod restart as needed.
19. Why might an envFrom key not appear in the process environment?
The key might be invalid as an environment variable name, the Pod may reference a different ConfigMap or namespace, or the container may be running with older environment values. Check ConfigMap data, Pod YAML, events, and the actual process environment.
20. What does immutable: true mean on a ConfigMap?
It prevents the ConfigMap data from being changed in place. To publish different data, create a new ConfigMap object and update the Pod template to reference it. Use this for controlled release practices where appropriate.
21. Does updating the ConfigMap automatically restart a Deployment?
No. A Deployment rollout is normally triggered by a change to its Pod template. A ConfigMap's data changing by itself does not change the Deployment's Pod template. Update a versioned ConfigMap reference or use a deliberate rollout/reloader mechanism.
22. Why should subPath mounts be documented in deployment manifests?
Their update behavior differs from a normal volume. The team must know that a Pod rollout/recreation is required after configuration changes, otherwise stale configuration can be misdiagnosed as an application defect.
23. Can a ConfigMap be used by a static Pod?
The kubelet does not support ConfigMap references in static Pod specifications. Use supported configuration mechanisms for static Pods rather than assuming API object references work.
24. What should be checked before using a ConfigMap for an application file?
Check the key and target path, namespace, size, file permissions/readonly behavior, whether to mount a directory or subPath, whether update propagation is needed, and how the application reloads configuration.

Level 3 — Real-world scenarios

25. ConfigMap shows the new value, but the website serves old HTML. What do you do?
Reasoning: First separate API state from the file currently served. Run kubectl get cm web-page -n nimbus-config-lab -o yaml, inspect the Pod's volumeMounts and subPath, then run kubectl exec POD_NAME -n nimbus-config-lab -- cat /usr/share/nginx/html/index.html. If it is a subPath mount, trigger kubectl rollout restart deployment/subpath-web -n nimbus-config-lab, wait for rollout and retest with curl. Other possibilities include testing the wrong Service/port-forward or an image/container that doesn't serve the mounted path.
26. A Pod is stuck in CreateContainerConfigError after a ConfigMap deployment.
Approach: Use kubectl describe pod POD_NAME -n nimbus-config-lab and read the Events. Confirm ConfigMap name and namespace with kubectl get cm -n nimbus-config-lab; check the referenced key and items. Fix the actual missing object/key or invalid mount. Mark references optional only if missing configuration is explicitly safe for that application.
27. After mounting a ConfigMap, NGINX returns 404 for a file that was present in its image.
Likely cause: A whole ConfigMap volume mounted over /usr/share/nginx/html hides image-provided sibling files. Check Pod volume mounts and list the directory inside the container. If only one file must be overridden, mount it to the file path with subPath; plan to restart Pods for ConfigMap changes.
28. A normal volume mount has the new file, but the app still uses old log settings.
The projected file may have updated, while the app cached the old configuration in memory. Read the file inside the container first. If it is current, check the app's documented reload signal/API and logs; otherwise wait for projection or inspect the ConfigMap reference. Restart only if the application lacks a safe reload path.
29. Updating an environment-based feature flag didn't change application behavior.
Environment variables in an existing process do not update. Verify the ConfigMap, inspect the Pod's env reference, then restart/recreate the Pod or perform a Deployment rollout. Also verify the application reads the expected variable name and that a feature flag isn't overridden elsewhere.
30. The YAML applies, but a file is not found at the expected path.
Trace the chain: ConfigMap data key → volume configMap.name → optional items.key/path → volume name in volumeMounts → mountPath and subPath. Inspect the actual container path with find and ls -la. Consider whether a whole-volume mount hid other files or the selected key was not projected.
31. Two Pods need different settings but reference the same ConfigMap name.
If they are in the same namespace and reference the same object, they receive the same object data through their consumption mechanism. Use distinct ConfigMaps or an explicit templating/release strategy for different settings, while keeping secrets separate and avoiding duplicate uncontrolled objects.
32. A ConfigMap exceeds the allowed size.
Kubernetes documents a 1 MiB limit for ConfigMap data. Identify whether the object contains a large artifact or excessive settings. Keep ConfigMaps for small configuration and use a suitable file/object store, volume, or application data service for larger content.
33. A teammate proposes putting a database password in a ConfigMap because the YAML is easier to read.
Reject the approach: ConfigMaps are for non-confidential data. Use a Secret or approved external secret manager and least-privilege access. Remember that a Secret also requires correct access controls and cluster security configuration; choosing the resource alone is not the whole security design.
34. A rollout restart did not update the expected file.
Inspect the new Pod and compare its mount to the ConfigMap data. Check whether the Deployment references the correct ConfigMap name and whether items.key, items.path, and subPath agree. Verify that the new Pod actually replaced the old one and that curl hits the correct endpoint. A file might also be coming from an image path or another volume mount.
35. How would you reduce configuration drift between clusters?
Keep manifests or templates in version control, review changes, use declarative apply/GitOps, separate environment values intentionally, and use versioned/immutable ConfigMaps for controlled releases when appropriate. Verify which configuration version each workload references.
36. An app needs to watch config changes without restarting.
Prefer a normal ConfigMap volume (not subPath) if the app can reopen/reload projected files. Document that projection is eventually consistent. If it must subscribe to updates across Kubernetes objects, an application/controller can use the Kubernetes API with appropriate RBAC and watch/retry logic. Never assume file projection automatically reloads the app's in-memory settings.

Assignments and visual challenges

Try each challenge first. Expand the solution hints only after you have a working hypothesis. All commands should remain scoped to nimbus-config-lab.

Beginner assignments

  1. Create a feature-flags ConfigMap. Requirements: three keys including a string-valued boolean. Expected state: object exists and keys appear in YAML. Verify with kubectl get cm NAME -n nimbus-config-lab -o yaml. Hint: use quoted strings for settings.
  2. Inject one key as an environment variable. Expected state: the process sees it. Verify using kubectl exec and printenv. Hint: use valueFrom.configMapKeyRef.
  3. Mount a multi-key ConfigMap as a directory. Expected state: each key appears as a file. Verify with ls and cat inside the Pod. Hint: volume name must match between volumes and volumeMounts.
  4. Project one selected key to a custom relative path. Expected state: only the specified key is projected. Verify with find /mount/path -type f. Hint: use items.
  5. Mount one ConfigMap file with subPath. Expected state: the chosen file is available, while sibling image files remain accessible. Verify by listing the target directory. Hint: use a file path for mountPath and a matching subPath.

Modification and troubleshooting assignments

  1. Update a value consumed through environment variables. Demonstrate that the running process is unchanged and that Pod recreation loads the new value.
  2. Update a ConfigMap mounted as a normal directory. Poll the file until the new value appears and explain the propagation delay.
  3. Update a ConfigMap mounted through subPath. Demonstrate stale content before restart and updated content after a Deployment rollout restart.
  4. Intentionally misspell a ConfigMap name in a lab Pod. Capture the event message and repair the reference.
  5. Mount a ConfigMap over an existing image directory in a disposable Pod. Prove that sibling files are hidden, then change the design to use a dedicated directory or subPath.

Real-world scenario challenges

  1. Release-safe configuration update: Design a rollout process for a configuration file mounted with subPath. Specify validation, restart, rollback, and verification.
  2. Shared config versus environment-specific config: Two application environments need different feature settings. Show how you would organize ConfigMaps and keep images identical.
  3. Large or sensitive config: An application team stores an API token and a 2 MiB certificate bundle in one ConfigMap. Redesign the approach, explaining which values belong in a Secret manager and how to handle large files.

QuestionAnswer to remember
ConfigMap or Secret?ConfigMap for non-confidential configuration; Secret or external secret manager for sensitive data.
Env or volume?Environment for process values; volume for file-based configuration.

14 · Safe finish

Cleanup and resource lifecycle

Ordered cleanup

Stop any running kubectl port-forward commands with Ctrl+C. Then inspect the namespace:

kubectl get all,configmap -n nimbus-config-lab

If this is a dedicated namespace containing only the resources from this guide, you can remove it in one operation:

kubectl delete namespace nimbus-config-lab

If this is a shared namespace, do not delete the namespace. Delete only the named objects that you created and verify the list first. Example targeted cleanup:

kubectl delete pod config-env-demo config-volume-demo config-items-demo -n nimbus-config-lab --ignore-not-found
kubectl delete deployment subpath-web -n nimbus-config-lab --ignore-not-found
kubectl delete service subpath-web -n nimbus-config-lab --ignore-not-found
kubectl delete configmap env-demo directory-config web-page selected-config -n nimbus-config-lab --ignore-not-found
Shared-cluster warning: Namespace deletion removes every namespaced object within it—not just this guide's resources. Do not delete shared namespaces, cluster-wide resources, or other students' work. Inspect before cleanup and get authorization when in doubt.
