Kubernetes
HPA & VPA

Understand how Kubernetes scales the number of Pods, right-sizes container resources, and uses metrics to respond to changing workload demand.

Horizontal Pod AutoscalerVertical Pod AutoscalerMetrics ServerHands-on labs
01 • Outcome

Scale the workload

Configure an HPA that changes replicas from measured CPU utilization, then verify the scaling loop.

02 • Outcome

Right-size Pods

Install or verify VPA components where permitted, observe recommendations in safe Off mode, and understand update policies.

03 • Outcome

Operate safely

Distinguish metrics failures from capacity issues, tune safeguards, and plan cleanup without touching shared resources.

Learning objectives

  • Explain HPA, VPA, Metrics Server, requests and replicas.
  • Read autoscaling/v2 HPA manifests.
  • Interpret replica recommendations and HPA conditions.
  • Read VPA recommendations and update modes.
  • Diagnose missing metrics, unavailable capacity and target mismatches.

Prerequisites

  • Basic Pods, Deployments, Services and resource requests.
  • kubectl configured to a disposable learning cluster.
  • Metrics Server installed for resource metrics.
  • Cluster-admin or suitable permissions only if installing VPA cluster-wide.
  • Internet access for image pulls and cloning the VPA repository, if used.

Estimated practice duration: 2–3 hours, depending on cluster setup and whether VPA installation is permitted.

Source and scopeThe Nimbuswiztech wiki describes HPA as scaling Pod count against CPU or custom metrics and VPA as automatically setting requests from usage. The topic-specific repository directory could not be inspected through the browser during preparation; repository-specific filenames or manifests are therefore not claimed. 01

Core concepts: autoscaling in plain English

First decide which thing should change: replica count, Pod resource size, or node count.

HPA

Horizontal Pod Autoscaler changes the desired replica count of a scalable workload according to observed metrics. More Pods can share incoming load; fewer Pods can reduce idle capacity.

Typical use: stateless API, web front end, workers with independent replicas.

VPA

Vertical Pod Autoscaler estimates appropriate CPU and memory resource requests for containers based on observed usage and history, then recommends or applies them according to policy.

Typical use: right-sizing workloads with uncertain or changing resource demand.

Cluster / node autoscaler

Changes the number of worker nodes when supported and configured. It is separate from both HPA and VPA and is needed when Pod scaling cannot fit existing capacity.

Typical use: scale node groups as scheduling demand changes.

QuestionHPAVPANode autoscaler
What changes?Number of replicasPer-container resource requests (and policy-dependent limits)Number of worker nodes
Typical inputCPU / memory / custom / external metricsCurrent and historical resource usage, events and policyUnschedulable Pods / cluster-specific capacity signals
Typical riskFlapping, too many or too few replicasPod disruption or over/under-sizingCost, provisioning delays, quota or cloud limits
Installed by default?HPA controller is part of Kubernetes control plane; resource metrics still need a sourceNo, VPA must be installed separatelyDepends on platform and configuration

Key terms to remember

Request

The resource amount Kubernetes uses for scheduling. CPU utilization-based HPA compares measured CPU usage with CPU requests.

Limit

A configured resource ceiling for a container, enforced differently for CPU and memory. It is not the same as a scheduler reservation.

Metric

A signal used to make an autoscaling decision. Resource, custom and external metrics use different API sources and setup requirements.

02

Horizontal Pod Autoscaler (HPA)

Scale the number of replicas in response to workload demand.

HPA is a Kubernetes API resource and controller loop. It periodically compares observed metrics with configured targets and updates the scale of a workload such as a Deployment. It cannot scale an object that does not expose a scalable replica count, such as a DaemonSet.

How HPA behaves

  1. The Metrics API supplies measurements for the selected Pods or another configured metric source.
  2. The HPA controller calculates whether the workload is above or below the target.
  3. The recommendation is bounded by minReplicas and maxReplicas and affected by tolerance, readiness, missing metrics and scaling behavior.
  4. The HPA writes desired replica count through the target's scale subresource.
  5. The workload controller creates or removes Pods; the scheduler places newly created Pods if capacity and constraints permit.
Illustrative calculationIf there are 3 current replicas, average CPU utilization is 90%, and the target is 60%, a simplified recommendation is ceil(3 × 90 / 60) = 5. The controller applies implementation safeguards and min/max bounds, so this arithmetic is an intuition—not a promise of the exact next state.

HPA metrics and API

Metric target typeWhat it meansCommon prerequisite
Resource / UtilizationPercentage of the resource request, e.g. CPU at 60%Metrics API plus requests configured on relevant containers
Resource / AverageValueAverage raw metric value per PodMetrics API for the selected resource
Pods / Object / ExternalCustom per-Pod, object-level, or external signals such as requests/sec or queue depthCustom or external metrics API plus a compatible adapter/provider

03

Vertical Pod Autoscaler (VPA)

Use observed behavior to make Pod resource sizing more appropriate.

VPA is a separately installed Kubernetes add-on defined through the autoscaling.k8s.io/v1 VerticalPodAutoscaler custom resource. The VPA policy identifies a target workload and controls what resources may be changed and how recommendations are applied.

Recommender

Analyzes historical and current resource consumption; writes recommendation values to VPA status.

Updater

Decides whether Pods should be updated. Depending on mode/version, it can evict Pods for recreation or use supported in-place resizing behavior.

Admission controller

Applies selected resource values to Pods as they are admitted, including replacement Pods after an eviction-based update.

Recommendation fields

  • target: the recommender's best estimate for requested resources.
  • lowerBound and upperBound: bounds indicating the range in which resources may be appropriate under the model.
  • uncappedTarget: recommendation before resource-policy bounds are applied, where provided.

VPA update modes

ModeBehaviorUse / caution
OffProduces recommendations but does not automatically update Pods.Best starting mode for learning and observation.
InitialApplies recommendations when Pods are created; does not actively update already-running Pods.Pods created later may have different request values than current Pods.
RecreateMay evict Pods and rely on the workload controller and admission controller to recreate them with updated values.Can disrupt service; consider replicas, readiness, PDBs and workload behavior.
InPlaceOrRecreate / InPlaceIn-place resizing options supported under specific version and feature conditions; behavior differs by VPA release.Do not enable without checking the exact VPA/Kubernetes support matrix and operational limits.
Version-sensitive behaviorVPA update modes and in-place resize support have evolved. This guide uses Off in the first lab and does not assume in-place actuation. Follow the official VPA installation/feature documentation for your cluster release before enabling active updates.

Resource policy example

A containerPolicies entry can constrain the range and choose which resources VPA controls. Bound the recommendation to values your nodes and application can support, and review results before applying them automatically.

resourcePolicy:
  containerPolicies:
  - containerName: web
    controlledResources: ["cpu", "memory"]
    minAllowed:
      cpu: 50m
      memory: 32Mi
    maxAllowed:
      cpu: 500m
      memory: 256Mi
04

Choosing HPA, VPA, or both

Assign each autoscaler a clear responsibility.

Practical design guidance

  • HPA for demand: use when additional replicas can increase throughput. Make sure app instances can share load and state is managed appropriately.
  • VPA for right-sizing: use to study and improve resource requests, especially where workloads have uncertain memory/CPU needs.
  • HPA + VPA: can coexist, but avoid competing on the same dimension without a deliberate design. CPU utilization is usage divided by CPU request; changing CPU requests can alter the HPA signal even if absolute CPU usage does not change.
  • Node autoscaling: is a different layer. If HPA adds Pods but nodes lack capacity, a separate node autoscaler may be needed and must be configured for the platform.
Design patternBenefitWatch-out
HPA on CPU, VPA in Off modeMeasure VPA recommendations without changing HPA denominatorRecommendations need time and representative traffic.
HPA on CPU, VPA controlling memory onlySeparate replica scaling on CPU from memory right-sizingValidate the VPA policy and actual supported fields; memory pressure and eviction still matter.
HPA on custom metric, VPA on CPU/memoryCan reduce direct coupling between CPU requests and HPA utilizationCustom metrics pipeline needs an adapter and good metric semantics.
VPA Recreate on critical stateful workloadAutomatically applies new resource requestsPlan disruption tolerance, PDBs, graceful shutdown and rollback first.

Prerequisites and environment preparation

Check cluster and metrics before deploying an autoscaler.

kubectl version --client
kubectl config current-context
kubectl cluster-info
kubectl get nodes
kubectl get namespaces
kubectl get apiservices | grep metrics
kubectl top nodes
kubectl top pods -A

What to expect

  • kubectl top should return current metrics. If not, check whether Metrics Server is installed and healthy in the selected cluster.
  • On many clusters, Metrics Server is not installed by default. Do not install a cluster-wide add-on into a shared/prod environment without approval.
  • HPA may use custom or external metrics, but this requires the appropriate APIs and providers; Metrics Server alone does not provide arbitrary business metrics.
  • VPA requires its CRD and controller components. Check whether it already exists before installing another version.
# Check HPA and VPA API resources
kubectl api-resources | grep -i horizontalpodautoscaler
kubectl api-resources | grep -i verticalpodautoscaler

# Check common metrics and autoscaling components
kubectl get apiservice v1beta1.metrics.k8s.io
kubectl get pods -n kube-system
Cluster-wide add-on cautionVPA installation modifies cluster-scoped API definitions/RBAC and creates components in kube-system. Installing or removing it affects other namespaces and teams. For a class, use a disposable cluster or ask the cluster administrator.

Lab 1 — Deploy HPA and observe scale-out

A gradual lab using CPU utilization and a sample HTTP application.

Lab objectiveDeploy a one-replica workload with CPU requests, expose it with a ClusterIP Service, configure HPA to target 50% average CPU utilization, generate CPU load, and inspect scaling decisions.

Step 1 — Create the app and Service

Save this manifest as hpa-demo.yaml. It uses the sample web image from the official Kubernetes HPA walkthrough. Verify image access in your environment.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: hpa-demo
  labels:
    app: hpa-demo
spec:
  replicas: 1
  selector:
    matchLabels:
      app: hpa-demo
  template:
    metadata:
      labels:
        app: hpa-demo
    spec:
      containers:
      - name: web
        image: registry.k8s.io/hpa-example
        ports:
        - containerPort: 80
        resources:
          requests:
            cpu: 100m
            memory: 64Mi
          limits:
            cpu: 500m
            memory: 128Mi
---
apiVersion: v1
kind: Service
metadata:
  name: hpa-demo
spec:
  selector:
    app: hpa-demo
  ports:
  - port: 80
    targetPort: 80
  type: ClusterIP
kubectl apply -f hpa-demo.yaml
kubectl rollout status deployment/hpa-demo
kubectl get deploy,pods,svc -l app=hpa-demo
kubectl top pods

What matters: the resources.requests.cpu: 100m value provides the denominator for CPU utilization. The Service selector and Deployment Pod labels both use app: hpa-demo.

Step 2 — Apply HPA policy

Save as hpa-demo-hpa.yaml.

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: hpa-demo
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: hpa-demo
  minReplicas: 1
  maxReplicas: 5
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 120
kubectl apply -f hpa-demo-hpa.yaml
kubectl get hpa hpa-demo
kubectl describe hpa hpa-demo
kubectl get hpa hpa-demo -w
Illustrative output (values depend on metrics and cluster timing): NAME REFERENCE TARGETS MINPODS MAXPODS REPLICAS hpa-demo Deployment/hpa-demo 12%/50% 1 5 1

Step 3 — Generate load in a second terminal

Start a temporary busybox container that repeatedly calls the Service. Adjust duration and stop it once sufficient metrics appear.

kubectl run -it --rm load-generator \
  --image=busybox:1.36 \
  --restart=Never -- /bin/sh -c \
  "while true; do wget -q -O- http://hpa-demo; done"
Do not expect an instant resultMetrics collection and HPA reconciliation take time. The simple demo image is CPU-oriented in the official walkthrough; if your cluster/image does not create enough load, verify the load generator is reaching the target and use the official tutorial's load pattern.

Step 4 — Observe and verify

kubectl get hpa hpa-demo -w
kubectl get deployment hpa-demo -w
kubectl get pods -l app=hpa-demo -o wide
kubectl describe hpa hpa-demo
kubectl top pods -l app=hpa-demo
Traffic / CPU increases→Metrics update→HPA recommends replicas→Deployment creates Pods

Verify the HPA target and current metric appear; then verify replicas and Pods increase if CPU exceeds the target and capacity permits. When load ends, scale-down may wait for the configured stabilization window.

Step 5 — Modify policy

# Change the target to 70% and observe new behavior
kubectl patch hpa hpa-demo --type merge \
  -p '{"spec":{"metrics":[{"type":"Resource","resource":{"name":"cpu","target":{"type":"Utilization","averageUtilization":70}}}]}}'

# Inspect the effective configuration
kubectl get hpa hpa-demo -o yaml

Interview takeaway: HPA does not route traffic by itself; the Service distributes traffic to matching ready Pods while HPA changes desired replica count.

Lab 2 — Install VPA (if needed) and inspect recommendations

First observe; do not automatically evict training Pods.

Installation is cluster-wideSkip the installation steps if VPA already exists or you do not administer a disposable cluster. Use the official installation process matching your Kubernetes version. Installing from the current upstream branch is not a substitute for version compatibility review.

Step 1 — Install VPA in a disposable cluster

The upstream VPA repository documents an install script. The command sequence below follows that documented workflow; inspect the repository instructions and pin a compatible release/version for a production setup.

git clone https://github.com/kubernetes/autoscaler.git
cd autoscaler/vertical-pod-autoscaler

# Read the current installation notes before running this script.
# It installs cluster-wide VPA components and may update kube-system.
./hack/vpa-up.sh

# Verify VPA components and CRD
kubectl get pods -n kube-system
kubectl get crd verticalpodautoscalers.autoscaling.k8s.io

If VPA is already installed, just run the verification commands. Metrics Server is also required for VPA resource metrics; do not assume installing VPA provides a ready metrics pipeline.

Step 2 — Apply VPA in recommendation-only mode

This policy targets the Deployment created in Lab 1. It is intentionally set to Off: it produces a recommendation but leaves the running workload alone.

apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: hpa-demo-vpa
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: hpa-demo
  updatePolicy:
    updateMode: Off
  resourcePolicy:
    containerPolicies:
    - containerName: web
      controlledResources: ["cpu", "memory"]
      minAllowed:
        cpu: 50m
        memory: 32Mi
      maxAllowed:
        cpu: 500m
        memory: 256Mi
kubectl apply -f hpa-demo-vpa.yaml
kubectl get vpa
kubectl describe vpa hpa-demo-vpa
kubectl get vpa hpa-demo-vpa -o yaml

Step 3 — Interpret the status

Look for the recommendation fields in status.recommendation.containerRecommendations, including target, lowerBound and upperBound. These values may be absent initially while the recommender accumulates usage and metrics.

kubectl get vpa hpa-demo-vpa -o jsonpath='{.status.recommendation.containerRecommendations[*].target}'
echo
kubectl get deploy hpa-demo -o jsonpath='{.spec.template.spec.containers[0].resources}'
echo

Compare the recommendation with the Deployment's declared requests. In Off mode, the Deployment template should remain unchanged by VPA.

Step 4 — Discuss active modes, do not enable blindly

To study an active policy, create a separate staging example and review the official VPA docs for your exact release. A policy using Recreate can trigger evictions and replacement Pods. Check replica count, readiness probes, PodDisruptionBudget, termination grace periods, stateful behavior and scheduling headroom before using it.

# Inspect the fields without enabling actuation:
kubectl get vpa hpa-demo-vpa -o yaml
kubectl get pdb -A
kubectl describe deployment hpa-demo

Interview takeaway: The VPA object stores policy; the recommender computes advice, while updater/admission-controller components participate in applying changes.

08

End-to-end scenario: web workload under variable demand

Connect the architecture, manifests, metrics and operational controls.

Requirement

A team runs a stateless web API. During peak load, CPU consumption increases and latency approaches the service objective. The team wants replicas to scale automatically and wants better resource requests, without enabling VPA-driven replacement unexpectedly.

Implementation plan

  1. Confirm resource requests and readiness behavior on the web Deployment.
  2. Confirm resource metrics are visible with kubectl top.
  3. Apply HPA with measured min/max bounds and a tested CPU target.
  4. Run a controlled load test while watching HPA, Deployment, Pods and metrics.
  5. Apply VPA in Off mode to study recommendations over representative load.
  6. Compare target recommendations with current requests and node capacity; review limits and cost.
  7. Only after a staging evaluation, decide whether a VPA actuation mode or a different HPA metric should be used.
  8. Document alerts, rollback, scale boundaries and cleanup.

Check facts in order; do not assume an error has a single root cause.

10

Best practices and common anti-patterns

Autoscaling needs guardrails, feedback and realistic tests.

Prefer

  • Use autoscaling/v2 for new HPA configurations.
  • Set CPU/memory requests based on evidence, not guesses.
  • Start VPA with recommendations only in new environments.
  • Set HPA min/max and test scale behavior under expected traffic.
  • Use readiness probes so traffic is sent only to ready Pods.
  • Watch metrics, events, latency, errors and resource pressure together.
  • Test node capacity, quotas and downstream database/service limits.
  • Pin and validate addon versions for production.

Avoid

  • Enabling VPA Recreate on a critical service without a disruption plan.
  • Assuming HPA automatically creates new worker nodes.
  • Using CPU-utilization HPA when CPU requests are missing.
  • Allowing HPA and VPA to fight over the same dimension without validation.
  • Choosing maxReplicas only from a guess or a copied tutorial.
  • Assuming kubectl top is a long-term monitoring platform.
  • Installing/removing VPA cluster-wide in a shared cluster without approval.
  • Using sample values as production recommendations.

Before / after: safer autoscaling

Risky setupSafer setup
CPU HPA target, but no CPU requestsExplicit and reviewed requests on relevant containers, plus a working metrics pipeline.
VPA active from day oneStart in Off, observe recommendations through representative workloads, and review outliers.
maxReplicas set very highSet max from load-test results, node capacity, cost ceiling and downstream service limits.
Only watching replica countCorrelate replicas with HPA conditions, CPU/memory, pending Pods, latency, throughput and error rates.

Interview preparation

36 expandable questions — basic, intermediate and workplace scenarios.

Try to answer each question aloud before opening the suggested response. Scenario answers should show a diagnostic sequence, not just a single command.

Basic — 12 questions

01What does HPA scale?
Suggested answer

It changes the desired replica count of a scalable workload such as a Deployment or StatefulSet using observed metrics.

02What does VPA change?
Suggested answer

It recommends or applies container resource requests (and, according to policy and configuration, limits) based on observed usage.

03Is HPA installed as an add-on?
Suggested answer

HPA controller functionality is built into Kubernetes control-plane components; a metrics source such as Metrics Server is needed for CPU/memory resource metrics.

04Is VPA built in by default?
Suggested answer

No. VPA is a separately installed add-on with a CRD and controller components.

05What is Metrics Server?
Suggested answer

A cluster add-on that collects resource metrics and exposes them through metrics.k8s.io; it is commonly used by HPA and VPA.

06Why does HPA need CPU requests?
Suggested answer

CPU utilization targets are calculated as usage divided by requested CPU. Missing requests for relevant containers can make utilization undefined.

07What is minReplicas?
Suggested answer

The lower bound on replicas that the HPA may request.

08What is maxReplicas?
Suggested answer

The upper bound on replicas that the HPA may request.

09What does updateMode Off mean in VPA?
Suggested answer

VPA computes and records recommendations in status but does not automatically apply them to Pods.

10What is VPA recommender?
Suggested answer

The component that analyzes current and historical usage and writes resource recommendations to VPA status.

11What does kubectl top show?
Suggested answer

A current snapshot of CPU and memory usage when the resource metrics pipeline is working; it is not long-term monitoring.

12Does HPA add nodes?
Suggested answer

No. HPA adds workload replicas. Additional nodes require spare capacity or a separately configured cluster/node autoscaler.

Intermediate — 12 questions

01Explain the HPA replica formula.
Suggested answer

A simplified formula is ceil(current replicas × current metric / target metric), bounded by min/max and subject to tolerance, readiness, missing metrics, and behavior policies.

02How do averageUtilization and averageValue differ?
Suggested answer

averageUtilization targets a percentage of resource requests. averageValue targets an average raw metric value per Pod.

03Which API version should new HPA manifests use?
Suggested answer

Use autoscaling/v2 for current stable HPA features such as multiple metrics and behavior configuration.

04Can HPA use queue depth?
Suggested answer

Yes, through a correctly configured custom or external metrics API and an appropriate metric adapter/source.

05What does HPA behavior do?
Suggested answer

It tunes scale-up and scale-down policies and stabilization windows to manage how quickly replica counts change.

06Why might an HPA show unknown CPU?
Suggested answer

Metrics Server/API may be unavailable, Pods may not have CPU requests, metrics may be temporarily missing, or the target/selectors may not line up.

07What are VPA update modes commonly used for?
Suggested answer

Off for recommendations only; Initial to set values at Pod creation; Recreate to apply recommendations through Pod replacement. Other in-place modes depend on the VPA/Kubernetes release and feature support.

08Why can VPA recreate Pods?
Suggested answer

In Recreate mode, the updater may evict Pods whose requests differ enough from recommendations; their workload controller then replaces them.

09Can VPA be used with HPA?
Suggested answer

Yes, but design metric ownership carefully. VPA changing CPU requests can change the denominator of CPU utilization that HPA measures; test the combination or use different metrics/resources.

10What is a container resource request?
Suggested answer

A scheduler-facing reservation used for placement and, for CPU/memory utilization-based HPA, as a utilization denominator. It is not a hard runtime cap.

11What is the VPA admission controller for?
Suggested answer

It injects selected resource settings into newly created or recreated Pods according to VPA recommendations and policy.

12Does autoscaling guarantee capacity?
Suggested answer

No. A desired replica count can be reached only if cluster capacity, quotas, topology, affinity, image pulls, and other scheduling constraints permit it.

Scenario-based — 12 questions

01HPA exists but CPU is shown as unknown. What do you check?
Suggested answer

Run kubectl top nodes and kubectl top pods; check Metrics Server Pods and APIService; describe the HPA; verify every relevant container has CPU requests; inspect events and labels/selectors. Fix the underlying metrics or spec issue, then watch HPA status.

02Traffic rises, HPA increases replicas, but Pods stay Pending. Why?
Suggested answer

Likely no schedulable capacity, resource requests too large, namespace quotas, affinity/taints/topology restrictions, or image pull delays. Inspect kubectl describe pod, events, node allocatable resources, quotas and node autoscaler status; scaling Pods alone does not create nodes.

03HPA repeatedly jumps up and down. How would you stabilize it?
Suggested answer

Review noisy metrics, target suitability, readiness behavior, min/max bounds, and HPA behavior/stabilization windows. Apply a tested scale-down stabilization window and conservative policies; compare before and after using metrics.

04A CPU-based HPA scales differently after VPA changes requests. Explain.
Suggested answer

CPU utilization is usage divided by CPU request. If VPA increases the request, the same absolute CPU usage is a lower percentage, which can reduce HPA scale pressure. Test combinations and consider VPA memory-only or HPA on a different metric.

05VPA CRD is not recognized. What next?
Suggested answer

Check kubectl get crd verticalpodautoscalers.autoscaling.k8s.io, VPA installation steps, and controller pods. Do not apply a VPA object until its CRD exists and the API discovery has refreshed.

06VPA object exists but recommendation fields are empty.
Suggested answer

Check the VPA targetRef exactly matches a workload; inspect VPA status and events, metrics-server availability, recommender logs, and whether target Pods have recent usage/history. Give metrics time to accumulate.

07The team wants VPA automation with no downtime. What is your plan?
Suggested answer

Start with updateMode Off and observe recommendations. Evaluate supported in-place update capabilities for the exact Kubernetes/VPA versions, validate Pod disruption budgets, readiness, replicas and rollout behavior in staging. Do not assume Recreate is disruption-free.

08Autoscaling is configured but load test does not scale replicas.
Suggested answer

Confirm the test actually increases the measured metric, Pods are ready, metrics are available, requests and HPA metric targets are valid, and min/max permit movement. Observe kubectl get hpa -w and events.

09The HPA scales but application latency remains high.
Suggested answer

Scaling may be too late or based on a weak metric; the app may be database/network-bound, concurrency-limited, or startup-heavy. Check saturation, requests per second, latency, downstream limits, readiness and resource constraints; consider custom/external metrics and pre-scaling.

10VPA recommends more memory than a node can fit.
Suggested answer

Recommendations are not capacity guarantees. Inspect node allocatable and scheduling events, set sensible minAllowed/maxAllowed policy bounds, reduce overcommit or increase cluster capacity. Avoid blindly applying upper recommendations.

11A Deployment was manually scaled but HPA resets replicas.
Suggested answer

Once HPA manages scale, manual replicas may be overwritten by the controller loop. Change HPA min/max or target metrics rather than treating Deployment.spec.replicas as a durable manual control.

12How would you roll out autoscaling in production?
Suggested answer

Establish baselines, ensure metrics and alerts, use safe min/max and behavior bounds, load-test in staging, start VPA in Off mode, assess capacity and disruption budgets, deploy gradually, monitor changes and retain rollback/disable steps.

Quick revision and cheat sheet

Commands you will use regularly in HPA/VPA labs.

CommandPurpose
kubectl get hpaList HorizontalPodAutoscalers and current metric/replica information.
kubectl describe hpa NAMEInspect target, conditions, events and metric calculation issues.
kubectl top podsView current Pod resource usage when resource metrics are available.
kubectl get vpaList VPA policies after the CRD is installed.
kubectl describe vpa NAMEInspect the VPA target, recommendations and status.
kubectl get vpa NAME -o yamlRead detailed VPA spec and status recommendation fields.
kubectl get events --sort-by=.lastTimestampReview recent cluster and workload events.
kubectl get apiservice v1beta1.metrics.k8s.ioCheck the resource metrics APIService registration/availability.

Must remember

HPA = quantity

Horizontal = number of Pods. It does not add nodes.

VPA = sizing

Vertical = resource requests for containers. Install VPA separately.

Metrics first

Unknown metrics or missing requests prevent resource-based recommendations from behaving as expected.
