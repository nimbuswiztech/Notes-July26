01 · The big picture

What are container patterns?

Container patterns are reusable ways to compose containers so that related processes collaborate without turning every function into one large application image. Kubernetes Pods provide a shared network namespace and can provide shared volumes, making some close cooperation possible. The patterns here are often called structural patterns because they describe how containers are organized and interact inside or around a Pod. citeturn879401search3turn185217search7

Real-world analogy: a small operations team

An Init container is the setup technician who prepares a workstation before an operator begins. A Sidecar is a teammate who works beside the operator throughout the shift. An Adapter translates the operator's specialized report into a standard format. An Ambassador is the communications desk that handles access to outside systems.

Why teams use them

  • Keep the primary app focused on its main responsibility.
  • Reuse a helper container with a separate image or release cycle.
  • Keep tools such as download utilities or template engines out of the application image.
  • Standardize metrics/logs or abstract a remote dependency.
Pattern, not resource: Init, Sidecar, Adapter and Ambassador are not built-in resource kinds named kind: Sidecar or kind: Ambassador. They are designs implemented with Pod containers, volumes, network sharing and/or Services.
02 · Choose deliberately

Compare all four patterns

SidecarAdd supporting behavior without changing main app code.Runs alongside the app for its lifetime.Shared volume, localhost network, or both.Collect logs; synchronize files; provide proxy support.

AmbassadorAbstract access to external services behind a local proxy.Usually alongside the app.Shared Pod network; app calls local proxy.Proxy requests to backend/cache with routing or connection policy.

When to use each—and when not to

Init

Use: bounded setup, generated files, migrations that are safe to retry, or startup dependency checks.

Avoid: using an init container as an infinite background worker; it must finish.

Sidecar

Use: support tasks tightly coupled to the Pod (log forwarding, proxy, sync).

Avoid: helper services that need independent scaling or independent availability when a separate Deployment/Service fits better.

Adapter

Use: translate a legacy app's metrics or output to a standard interface.

Avoid: duplicating a simple function the app already implements consistently.

Ambassador

Use: make a local proxy handle routing, TLS, retries or connection policy to remote dependencies.

Avoid: adding proxy complexity when normal Kubernetes Service DNS is sufficient.

03 · Pattern 1

Init container pattern

An init container performs preparation that must finish before the regular application containers start. Multiple regular init containers run sequentially; each must succeed before the next starts. If an init container fails, kubelet retries it according to Pod restart behavior. Regular init containers do not support liveness, readiness or startup probes because their job is to finish, not stay running. citeturn187219search0

Typical use cases and trade-offs

  • Generate a configuration file into a shared emptyDir.
  • Wait for an API or dependency to become reachable, with retries and an appropriate timeout.
  • Fetch immutable startup assets into a volume.
  • Prepare permissions or directory structure, within appropriate security boundaries.
Production caution: Init containers can be retried. Any operation they perform should be safe to rerun, bounded where possible, and observable. Do not use an init container to perform an unguarded destructive database migration on every Pod creation.
04 · Pattern 2

Sidecar container pattern

A sidecar is a supporting container that runs alongside the primary application container in the same Pod. The sidecar can add log collection, file synchronization, monitoring, security, or proxy behavior without requiring the main application image to implement that helper function. Containers in a Pod share a network namespace and can communicate via localhost; they can also share explicitly defined volumes. citeturn187219search2turn879401search3

Regular sidecar vs native Kubernetes sidecar

The sidecar pattern is a design idea. Kubernetes also supports a built-in native sidecar lifecycle: a restartable sidecar is declared under initContainers with restartPolicy: Always. This feature became stable in Kubernetes v1.33; it has been available in earlier versions with the relevant feature support. Native sidecars have ordered startup and shutdown semantics useful for lifecycle-sensitive helpers. citeturn187219search2turn187219search3

05 · Pattern 3

Adapter pattern

The Adapter pattern makes an application's output or interface conform to a common format that external systems can consume. It is commonly implemented as a specialized sidecar: the main application keeps its legacy behavior, while the adapter translates that behavior into a standard interface—such as normalized log lines or a metrics format. citeturn185217search0turn185217search5

Where adapters help

  • Normalize legacy application metrics for a shared monitoring convention.
  • Translate custom log lines into a standard structured format.
  • Expose a compatibility interface without modifying an old or vendor-owned image.
Design note: An Adapter is not automatically an HTTP proxy or a Kubernetes resource. It needs a clearly defined input contract, output contract, error handling, and resource limits. Do not claim that sample text is scrapeable by Prometheus unless an HTTP metrics endpoint is actually implemented.
06 · Pattern 4

Ambassador pattern

An Ambassador is a proxy-oriented sidecar that hides complexity when an application accesses a service outside its Pod. The app talks to a predictable local endpoint; the Ambassador handles the upstream connection, routing, TLS, retries or other policy that the proxy is configured to provide. citeturn185217search1turn187219search9

Common responsibilities

  • Proxy to a changing upstream endpoint through a stable local interface.
  • Apply configured TLS, client certificate, authentication, or header policies.
  • Centralize connection pooling, timeouts, routing, or retries when the chosen proxy supports them.
  • Provide consistent local behavior without adding a new networking library to the main app.
Boundary: A Kubernetes Service can already provide stable discovery for many in-cluster services. Do not add an Ambassador just to duplicate basic Service DNS; use one when it provides a needed application-level proxy capability.

09 · Hands-on lab series

Progressive implementation labs

All manifests below use the namespace nimbus-container-patterns. Create the files with the exact names shown. Images busybox:1.36 and nginx:stable-alpine must be pullable from your environment.

Exercise 1 — Init container prepares a file

Objective Generate a file in an emptyDir volume before NGINX starts, then serve it.

Step 1: Save as 01-init-pattern.yaml.

apiVersion: v1
kind: Pod
metadata:
  name: init-pattern-demo
  namespace: nimbus-container-patterns
  labels:
    app: init-pattern-demo
spec:
  initContainers:
  - name: prepare-page
    image: busybox:1.36
    command: ["/bin/sh", "-c"]
    args:
    - mkdir -p /work && printf '%s\n' 'Generated by init container' > /work/index.html
    volumeMounts:
    - name: shared-page
      mountPath: /work
  containers:
  - name: web
    image: nginx:stable-alpine
    ports:
    - name: http
      containerPort: 80
    volumeMounts:
    - name: shared-page
      mountPath: /usr/share/nginx/html
  volumes:
  - name: shared-page
    emptyDir: {}

Step 2: Apply and wait.

kubectl apply -f 01-init-pattern.yaml
kubectl wait --for=condition=Ready pod/init-pattern-demo -n nimbus-container-patterns --timeout=120s
kubectl get pod init-pattern-demo -n nimbus-container-patterns
kubectl logs init-pattern-demo -n nimbus-container-patterns -c prepare-page

Step 3: Verify the file and HTTP response.

kubectl exec init-pattern-demo -n nimbus-container-patterns -c web -- cat /usr/share/nginx/html/index.html
kubectl port-forward pod/init-pattern-demo 18080:80 -n nimbus-container-patterns

Leave port-forward running in that terminal and run in another:

curl -s http://127.0.0.1:18080

Expected output (illustrative): Generated by init container.

Why it works: initContainers must complete successfully before the regular NGINX container starts. The init and app containers mount the same emptyDir, so the page written by the init container is visible to NGINX.

What to notice: The volume is mounted over NGINX's document root, so image-provided files in that directory are hidden. This is intentional for the simple demo; a production design should choose the mount path carefully.

Interview takeaway: Init containers run to completion in order. They are for initialization, not for an infinite service loop.

Exercise 2 — Sidecar tails a shared application log

Objective Keep the app process simple and let a sidecar read its log file from a shared volume.

Step 1: Save as 02-sidecar-logs.yaml.

apiVersion: v1
kind: Pod
metadata:
  name: sidecar-log-demo
  namespace: nimbus-container-patterns
  labels:
    app: sidecar-log-demo
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["/bin/sh", "-c"]
    args:
    - touch /var/log/app/app.log; i=0; while true; do i=$((i+1)); printf 'event=%s level=INFO\n' "$i" >> /var/log/app/app.log; sleep 5; done
    volumeMounts:
    - name: app-logs
      mountPath: /var/log/app
  - name: log-sidecar
    image: busybox:1.36
    command: ["/bin/sh", "-c"]
    args:
    - until [ -f /var/log/app/app.log ]; do sleep 1; done; tail -n +1 -f /var/log/app/app.log
    volumeMounts:
    - name: app-logs
      mountPath: /var/log/app
      readOnly: true
  volumes:
  - name: app-logs
    emptyDir: {}

Step 2: Apply and verify.

kubectl apply -f 02-sidecar-logs.yaml
kubectl wait --for=condition=Ready pod/sidecar-log-demo -n nimbus-container-patterns --timeout=120s
kubectl logs sidecar-log-demo -c app -n nimbus-container-patterns --tail=5
kubectl logs sidecar-log-demo -c log-sidecar -n nimbus-container-patterns --tail=10

Expected behavior: the app writes incrementing event lines; the sidecar can read those same lines and emits them to its own stdout. The Kubernetes logging agent can collect the sidecar's stdout independently of the app's.

Important: both containers share Pod network and any explicitly shared volumes; they do not automatically share their root filesystems. The Pod as a whole remains unready if a required regular container is not running/ready.

Troubleshooting: use kubectl logs sidecar-log-demo -c log-sidecar to inspect the helper and kubectl exec ... -c app -- ls -l /var/log/app to verify the file path. If both containers do not mount the same volume name at the expected path, sharing will fail.

Exercise 3 — Adapter normalizes a legacy metrics file

Objective Show how a sidecar translates app-specific output into a normalized output format without changing the app container.

Step 1: Save as 03-adapter-pattern.yaml.

apiVersion: v1
kind: Pod
metadata:
  name: adapter-pattern-demo
  namespace: nimbus-container-patterns
  labels:
    app: adapter-pattern-demo
spec:
  containers:
  - name: legacy-app
    image: busybox:1.36
    command: ["/bin/sh", "-c"]
    args:
    - i=0; while true; do i=$((i+1)); printf 'legacy_requests:%s\n' "$i" > /shared/legacy.metrics; sleep 5; done
    volumeMounts:
    - name: exchange
      mountPath: /shared
  - name: adapter
    image: busybox:1.36
    command: ["/bin/sh", "-c"]
    args:
    - while true; do if [ -f /shared/legacy.metrics ]; then value="$(sed 's/^legacy_requests://' /shared/legacy.metrics)"; case "$value" in ''|*[!0-9]*) echo "adapter: invalid input" ;; *) printf 'app_requests_total %s\n' "$value" ;; esac; fi; sleep 5; done
    volumeMounts:
    - name: exchange
      mountPath: /shared
      readOnly: true
  volumes:
  - name: exchange
    emptyDir: {}

Step 2: Apply and inspect each container.

kubectl apply -f 03-adapter-pattern.yaml
kubectl wait --for=condition=Ready pod/adapter-pattern-demo -n nimbus-container-patterns --timeout=120s
kubectl logs adapter-pattern-demo -c legacy-app -n nimbus-container-patterns --tail=5
kubectl logs adapter-pattern-demo -c adapter -n nimbus-container-patterns --tail=10

Expected output (illustrative): adapter log lines like app_requests_total 7. Numbers vary because the loop increments continuously.

What this teaches: the adapter reads the legacy app's custom legacy_requests:NUMBER file format and translates it to a normalized metric name/value. This demonstrates the interface idea; it is not a complete Prometheus exporter because it does not expose an HTTP scrape endpoint.

Troubleshooting: if output says “invalid input,” inspect the shared file and the exact legacy format. If there are no lines, inspect the app and adapter containers separately and confirm the shared volume is mounted in both.

Exercise 4 — Ambassador proxies requests to a backend Service

Objective Make the application call a local proxy at 127.0.0.1:8080; let the Ambassador forward to a Kubernetes Service.

Step 1: Save as 04-ambassador-backend.yaml.

apiVersion: v1
kind: ConfigMap
metadata:
  name: backend-page
  namespace: nimbus-container-patterns
data:
  index.html: |
    Nimbuswiztech Ambassador demo: response from backend Service.
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: pattern-backend
  namespace: nimbus-container-patterns
spec:
  replicas: 1
  selector:
    matchLabels:
      app: pattern-backend
  template:
    metadata:
      labels:
        app: pattern-backend
    spec:
      containers:
      - name: web
        image: nginx:stable-alpine
        ports:
        - name: http
          containerPort: 80
        volumeMounts:
        - name: page
          mountPath: /usr/share/nginx/html/index.html
          subPath: index.html
          readOnly: true
      volumes:
      - name: page
        configMap:
          name: backend-page
          items:
          - key: index.html
            path: index.html
---
apiVersion: v1
kind: Service
metadata:
  name: pattern-backend
  namespace: nimbus-container-patterns
spec:
  selector:
    app: pattern-backend
  ports:
  - name: http
    port: 80
    targetPort: http

Step 2: Apply backend and wait.

kubectl apply -f 04-ambassador-backend.yaml
kubectl rollout status deployment/pattern-backend -n nimbus-container-patterns --timeout=180s
kubectl get service pattern-backend -n nimbus-container-patterns

Step 3: Save as 04-ambassador-pod.yaml.

apiVersion: v1
kind: ConfigMap
metadata:
  name: ambassador-nginx-config
  namespace: nimbus-container-patterns
data:
  default.conf: |
    server {
      listen 8080;
      location / {
        proxy_pass http://pattern-backend:80;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
      }
    }
---
apiVersion: v1
kind: Pod
metadata:
  name: ambassador-demo
  namespace: nimbus-container-patterns
  labels:
    app: ambassador-demo
spec:
  containers:
  - name: app-client
    image: busybox:1.36
    command: ["/bin/sh", "-c"]
    args:
    - while true; do echo "request via localhost Ambassador"; wget -qO- http://127.0.0.1:8080/ || echo "upstream request failed"; sleep 10; done
  - name: ambassador-proxy
    image: nginx:stable-alpine
    ports:
    - name: proxy
      containerPort: 8080
    volumeMounts:
    - name: proxy-config
      mountPath: /etc/nginx/conf.d/default.conf
      subPath: default.conf
      readOnly: true
  volumes:
  - name: proxy-config
    configMap:
      name: ambassador-nginx-config
      items:
      - key: default.conf
        path: default.conf

Step 4: Apply and verify request flow.

kubectl apply -f 04-ambassador-pod.yaml
kubectl wait --for=condition=Ready pod/ambassador-demo -n nimbus-container-patterns --timeout=120s
kubectl logs ambassador-demo -c app-client -n nimbus-container-patterns --tail=12
kubectl logs ambassador-demo -c ambassador-proxy -n nimbus-container-patterns --tail=12

Expected behavior: app-client log lines show request via localhost Ambassador followed by the backend's text. NGINX access logs in the Ambassador container should show requests. Exact order of the two containers' startup logs varies; the backend is deployed first to reduce initial DNS/startup confusion.

Troubleshooting: check the backend Service and endpoints, NGINX config mount, proxy logs, and app-client logs. Containers in the same Pod share the network namespace, so 127.0.0.1:8080 reaches the proxy inside that Pod.

10 · Put it together

End-to-end pattern selection and design

Scenario

A web application needs a generated file at startup, writes legacy log events, and calls an internal backend. An observability platform requires normalized metrics, and the application should not need its own proxy library.

Deployment and verification sequence

  1. Check current context and the dedicated lab namespace.
  2. Apply the init example; prove the file exists and is served.
  3. Apply the sidecar example; inspect logs using the container name.
  4. Apply the adapter example; compare source format to normalized output.
  5. Apply the Ambassador backend Deployment and Service first and wait until they are ready.
  6. Apply the Ambassador Pod; check client output and proxy access logs.
  7. Run the troubleshooting flows if behavior differs from the expected state.
  8. Clean up only these training resources.

Checklist for a design review

  • Does the helper need to run before the app, alongside it, or only on outbound calls?
  • Is the shared volume required, and what happens if it fills up?
  • Can helper failure block application readiness? Is that intentional?
  • Do all containers have resource requests/limits and sensible security contexts?
  • Could a normal Service, application feature, or external component solve this more simply?

12 · Design quality

Best practices and common mistakes

PracticeWhyExample
Keep containers single-purpose.Separate images, ownership and responsibilities are easier to reason about.Application writes logs; sidecar handles log collection.
Declare resource requests/limits.All containers share the Pod's scheduling and resource budget.Set suitable CPU/memory on both application and helper after measuring.
Use shared volumes intentionally.File sharing must be explicitly defined; writable shared paths can create concurrency and tampering risks.Mount app log volume read-write in app and read-only in log sidecar.
Make init operations safe to retry.Init containers may be restarted and startup may repeat.Use idempotent file generation; avoid one-time unguarded destructive operations.
Handle upstream unavailability.Proxy or helper may start before remote endpoints are ready, and DNS/network may be temporarily unavailable.Use meaningful retries/timeouts and observable failure messages.
Avoid unnecessary proxies.Each helper adds memory, config, logs and failure modes.Use Service DNS unless a proxy provides specific needed behavior.
Protect local ports and shared paths.Containers share port space and can affect each other's local endpoints/files.Assign distinct listeners; mount only required volumes and use readOnly where possible.
Version helper images.A helper can be a production dependency.Use approved immutable/tagged images and scan them like application images.
Expose health signals thoughtfully.Pod readiness and helper readiness can influence whether the Pod is useful.Add probes to long-running helper containers; do not add regular probes to normal init containers.

Native sidecar: optional current-Kubernetes feature

For cluster versions that support native sidecars, an init-container entry with restartPolicy: Always can be a restartable sidecar. Native sidecars became stable in Kubernetes v1.33; the feature was introduced in earlier versions and behavior depends on cluster support. Check the versioned official documentation before using it. 13 · Interview preparation

36 interview questions and answers

Try answering first, then expand. Search by pattern name, lifecycle, volume, or proxy concept.

Level 1 — Basic questions

1. What is a container pattern?
A reusable design for organizing containers so that a workload can perform a focused function while collaborating with other containers through Pod lifecycle, network, or volume primitives.
2. Are Init, Sidecar, Adapter and Ambassador Kubernetes resource kinds?
No. They are design patterns. Kubernetes implements them using ordinary Pod fields such as initContainers, containers, volumes and Services.
3. What is an Init container?
A container in spec.initContainers that runs before normal application containers and must complete successfully before those app containers can start.
4. What is a Sidecar?
A supporting container that runs alongside the main application to add functionality without changing its core code or image.
5. What is an Adapter?
A specialized sidecar pattern that normalizes the application's interface or output into a consistent format expected by another system, such as a common metrics/logging consumer.
6. What is an Ambassador?
A proxy-oriented sidecar that gives the application a stable local interface for accessing external services and can apply configured routing or connection behavior.
7. What is emptyDir?
A Pod volume whose data starts empty and persists for the lifetime of the Pod. Containers can share it when it is mounted in each container.
8. How can containers communicate in the same Pod?
They share the Pod's network namespace and IP, so they can connect using localhost and the relevant port. They do not automatically share a filesystem.
9. When should an Init container be used?
When setup, a bounded precondition check, or file generation must complete before app startup. An init container should not be used as a background daemon.
10. What can a Sidecar do?
It may collect logs, synchronize data, provide a proxy, or deliver support services. The helper's lifecycle and failure behavior are coupled to the Pod.
11. What is the main difference between Adapter and Ambassador?
Adapter normalizes how the app is presented to a consumer; Ambassador abstracts how the app communicates with an external service.
12. How do you see logs from one container in a multi-container Pod?
Use kubectl logs POD_NAME -c CONTAINER_NAME -n NAMESPACE. Name the container so you do not inspect the wrong process.

Level 2 — Intermediate questions

13. Do multiple regular Init containers run concurrently?
No. Kubernetes runs regular init containers sequentially in the order specified, and each must succeed before the next starts.
14. Can an Init container and app container share generated files?
Yes. Define a volume such as emptyDir and mount it in both containers. The Init container writes data before exiting; the app can read the same data after it starts.
15. Does array order guarantee regular sidecar startup order?
No. Regular containers in spec.containers can start concurrently. If you need native sidecar startup/shutdown semantics, evaluate the native sidecar feature supported by the cluster version.
16. What is a native sidecar container?
A restartable sidecar declared under initContainers with restartPolicy: Always in supported Kubernetes versions. It can start ahead of normal app containers and participates in native sidecar lifecycle ordering.
17. How do all containers in a Pod share networking?
They share one Pod network namespace/IP and port space, so they may use localhost to connect. Their listening ports must not conflict.
18. Do containers in one Pod share their root filesystems?
No. Each container has its own image/container filesystem. To exchange files, define a volume and mount it in the necessary containers.
19. Why use an Adapter rather than change the legacy app?
A separate adapter can normalize formats without modifying or rebuilding a vendor-owned or legacy image. The trade-off is another component and an explicit input/output contract.
20. Why use an Ambassador rather than call the upstream directly?
A proxy can centralize supported connection policy, routing, retries, TLS, or discovery so the application uses a stable local interface. If Service DNS is enough, the extra proxy may not be justified.
21. How does an init failure affect a Pod?
Normal app containers do not start until init containers succeed. Inspect the specific init container's status, logs and Pod Events.
22. What resource issue can a sidecar introduce?
It adds CPU/memory requests and limits to the Pod's effective resource needs, consumes node capacity, and can add log volume, port conflicts and failure modes.
23. How can a sidecar consume application logs without changing the app image?
Configure the app to write to a file on an explicitly shared volume, mount that same volume into a sidecar, and have the helper tail/forward it. Ensure log rotation and disk usage are managed.
24. Is every Ambassador a service mesh?
No. Ambassador is a pattern that can be implemented with a local proxy. Service meshes may inject or manage proxies at scale, but a pattern and a full mesh platform are not the same thing.

Level 3 — Real-world scenarios

25. Pod is stuck in Init:CrashLoopBackOff. What is your process?
Get the Pod and Events; use kubectl logs POD -c INIT_NAME, including --previous when a previous attempt is relevant. Identify whether the init command, permissions, image, dependency or volume path failed. Fix the evidenced cause and verify init completes before the app starts.
26. Application starts before a helper is ready and fails intermittently.
If the helper is defined as a regular container, array order does not guarantee startup sequence. Use app-side retry/readiness logic or consider supported native sidecar semantics if it is truly a sidecar. A dependency check in a regular init container is appropriate only if the condition should block startup and the check is bounded/retry-safe.
27. Sidecar logs are empty, but the app is writing a log file.
Inspect each container separately. Confirm both mount the same named volume, the paths match, the sidecar process is running and has read access, and the file format matches the reader. Use kubectl exec POD -c app -- ls -l /var/log/app and kubectl logs POD -c log-sidecar.
28. Adapter logs report invalid input.
The source format may differ from what the adapter parser expects, the file could be empty/partially written, or the value may not be numeric. Inspect only the demo/source payload needed, validate the contract, and change parsing/atomic writing with appropriate error handling. Verify normalized output after the correction.
29. Ambassador returns 502 or logs upstream resolution errors.
Check proxy config, startup logs, Service name/namespace, Service port and EndpointSlices. Confirm backend Pods are Ready. Ensure the proxy was not started before the upstream DNS name existed or use proxy features/configuration that support dynamic resolution if upstream endpoints change.
30. Two containers fail because both bind port 8080.
Containers in a Pod share one network namespace and port space. Choose distinct listening ports or move one listener to a separate Pod/service where appropriate. Container port declarations alone do not isolate the port namespace.
31. An Init container waits forever for a database.
Inspect the init logs and validate DNS, Service endpoints, port, credentials and network policy. Use a reasonable retry/backoff and useful log message; design startup timeout behavior deliberately. Do not rely on a vague infinite loop that hides a permanent misconfiguration.
32. A helper sidecar uses more resources than the main app.
Measure CPU/memory and log volume, set requests/limits for both containers, and decide whether the helper belongs in each app Pod or should be a separate scalable workload. Avoid automatically duplicating an expensive helper for every replica.
33. A sidecar needs to read an app file but the app file is inside the container layer.
The containers do not share the image filesystem. Change the application to write to a shared volume or use a supported endpoint/API; mount the volume in both containers. Do not assume a sidecar can see arbitrary paths inside another container.
34. When would you avoid an Ambassador?
If the application can use normal Service DNS and does not need proxy policy, the ambassador adds avoidable complexity. Weigh the needed routing/TLS/retry behavior against resource cost, config management and additional failure modes.
35. Can an Adapter transform metrics and expose them for scraping?
Yes, if implemented with an actual exporter or HTTP endpoint that presents the agreed metrics protocol. A helper that only prints normalized-looking text to stdout is an educational demonstration, not automatically a scrape endpoint.
36. How would you deploy these patterns safely in production?
Keep the Pod as simple as possible, use reviewed manifests, resource requests/limits and security contexts, health checks for long-running helpers, bounded retries for init tasks, clear logs, versioned helper images, and monitoring for each container. Test termination and failure behavior and document each helper's owner and purpose.
14 · Practice assignments

13 assignments with solution hints

Attempt each exercise first. Use the hints after trying. Keep work inside the dedicated namespace.

Beginner exercises

  1. Init file preparation. Write a Pod where an init container creates two files in an emptyDir and the app reads them. Verify init completion and file contents. Hint: mount the same volume into both containers.
  2. Dependency check. Create an init container that retries a harmless DNS lookup up to a fixed attempt count. Expected: it exits successfully if the lookup works and fails with a useful message after timeout. Hint: use a counter and sleep interval.
  3. Sidecar logger. Extend the log sidecar example with a timestamp. Verify app and sidecar logs independently. Hint: write to a shared file, not the container root alone.
  4. Adapter format. Change the legacy input to legacy_latency_ms:42 and adapt it to app_latency_milliseconds 42. Verify output. Hint: define and validate the input contract.
  5. Ambassador upstream. Change the proxy destination to a second lab Service and confirm the app still calls localhost. Verify proxy and backend logs. Hint: deploy the backend Service before the proxy.

Modification / troubleshooting exercises

  1. Change the init command to write to the wrong path. Diagnose why the app response is incorrect and repair it.
  2. Remove the sidecar's volumeMount. Inspect what changes and explain why it can no longer see the app log.
  3. Give the adapter an unexpected input line. Add explicit validation and a useful error log.
  4. Change the Ambassador proxy upstream port to an invalid value. Diagnose it using app logs, proxy logs and Service configuration, then restore the valid port.
  5. Add requests and limits to every long-running container. Explain how Pod-level scheduling requirements change.

Real-world scenario challenges

  1. Startup chain: design a bounded init dependency check for a service that may start later than the application Pod.
  2. Legacy metrics: introduce an adapter for two services whose metrics use different names/formats. Define one normalized output contract.
  3. External service access: propose an Ambassador proxy design with timeout and TLS policy requirements, identify failure modes, and explain when a Kubernetes Service alone is sufficient.
