Kubernetes Basic Objects

1. Introduction

Kubernetes is a platform for deploying and operating containerized applications. A Kubernetes object is a persistent record of the desired state of part of a cluster. You declare what you want, and Kubernetes controllers continually work to make the observed state match that intent.

Why objects?

They provide a consistent API for describing workloads, networking, configuration, and isolation rather than relying on manual server-by-server operations.

Real-world analogy

A Deployment is like a manager requesting three identical shop employees; Pods are the workers, and a Service is the stable reception desk directing customers to available workers.

DevOps example

Deploy a web app with three replicas, expose it internally with a Service, place it in a dedicated namespace, and keep environment-specific settings in a ConfigMap.

Learning objectives

  • Read Kubernetes YAML manifests and understand apiVersion, kind, metadata, and spec.
  • Explain Pods, Deployments, ReplicaSets, Services, Namespaces, labels/selectors, ConfigMaps, and Secrets.
  • Apply, inspect, update, scale, debug, and safely delete lab resources.
  • Reason through common workload and connectivity failures.

Prerequisites

Basic command-line use, YAML indentation, container image concepts, and a terminal. You do not need a cloud account for the core lab.

Lab safety: Run commands against a cluster you are authorized to use. The lab creates resources only in the nimbus-basic-lab namespace. Do not delete namespaces or resources belonging to other students or teams.

2. Core concepts and terminology

Object manifest anatomy

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: nimbus-basic-lab
  labels:
    app: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: nginx
        image: nginx:1.27
  • apiVersion: API group and version accepted by the cluster.
  • kind: resource type.
  • metadata: identity and descriptive metadata such as name, namespace, labels, and annotations.
  • spec: desired configuration.
  • status: observed state reported by Kubernetes; normally do not write it in a manifest.

Service types

Imperative versus declarative management

Imperative commands directly request an action, such as kubectl create deployment web --image=nginx. Declarative management describes the desired state in YAML and applies it with kubectl apply -f file.yaml. Declarative manifests are easier to review, version-control, repeat, and share with a team.

Common misunderstanding: containerPort: 80 documents a port in the Pod specification; it does not by itself publish the app externally. A Service or another networking mechanism is typically needed.

3. Architecture and workflow

This diagram is a conceptual view, not a screenshot of a live cluster.

  1. kubectl sends a request to the Kubernetes API server.
  2. The API server validates the object and persists desired state.
  3. The Deployment controller creates or updates a ReplicaSet.
  4. The ReplicaSet controller creates Pods to meet the requested replica count.
  5. The scheduler assigns unscheduled Pods to suitable nodes; node agents and the container runtime start containers.
  6. A Service selector identifies matching Pods and provides stable access despite Pod replacement.

A Service does not normally create Pods. A Deployment does not directly route client traffic. Each resource has a distinct responsibility.

4. Environment preparation

Use an existing authorized cluster, Minikube, or kind. The main lab uses standard Kubernetes APIs and does not require EKS. A cloud cluster can incur charges for nodes, load balancers, storage, or data transfer; this lab uses a ClusterIP Service to avoid requesting a cloud load balancer.

Verify tools and cluster context

kubectl version --client
kubectl cluster-info
kubectl get nodes
kubectl get namespaces
kubectl config current-context
  • kubectl version --client: confirms the client is installed.
  • kubectl cluster-info: checks access to the API server and cluster endpoints.
  • kubectl get nodes: lists registered nodes; nodes should be Ready for normal workloads.
  • kubectl get namespaces: lists namespace scopes.
  • kubectl config current-context: identifies the selected kubeconfig context. Confirm it before applying resources.

Optional local cluster

If you do not have a cluster, install Minikube or kind using their official instructions, then start a cluster. Example for Minikube (requires Minikube and a supported container runtime or VM driver already installed):

minikube start
kubectl config current-context
kubectl get nodes
Do not paste cloud credentials into manifests or share kubeconfig files. If a command reports Forbidden, you may lack RBAC permissions; contact the cluster administrator instead of trying to bypass access controls.

Create a lab folder

mkdir -p kubernetes-basic-objects
cd kubernetes-basic-objects

5. Step-by-step hands-on practice

All exercises use the namespace nimbus-basic-lab and the app label app: web. Create the namespace once before the exercises.

Exercise 1: Create a namespace

Objective: Keep training resources grouped and easy to clean up.

Concept: Namespaces scope namespaced objects. They do not automatically isolate network traffic or grant access restrictions by themselves.

kubectl create namespace nimbus-basic-lab
kubectl get namespaces
kubectl get pods -n nimbus-basic-lab

Expected result: The namespace appears as Active; initially there may be no Pods.

Troubleshooting: If it already exists, continue after confirming it is your lab namespace. If Forbidden, request namespace creation permission or use a namespace assigned by your trainer.

Interview connection: Are Nodes namespaced? No. Pods, Deployments, and Services are namespaced; Nodes and PersistentVolumes are cluster-scoped.

Exercise 2: Create a standalone Pod

Objective: Understand the smallest deployable unit.

Create pod.yaml:

apiVersion: v1
kind: Pod
metadata:
  name: web-pod
  namespace: nimbus-basic-lab
  labels:
    app: web
spec:
  containers:
  - name: nginx
    image: nginx:1.27
    ports:
    - containerPort: 80

Run and verify:

kubectl apply -f pod.yaml
kubectl get pods -n nimbus-basic-lab -o wide
kubectl describe pod web-pod -n nimbus-basic-lab
kubectl logs web-pod -n nimbus-basic-lab

Explanation: v1 is the core API group version. The Pod has a name, namespace, and app=web label. The container uses an NGINX image. containerPort documents the expected listening port but does not expose it outside the Pod.

Expected result: Pod phase becomes Running if the image can be pulled and the node can schedule it. Output and timing vary by cluster.

Troubleshooting: Use kubectl describe pod to inspect scheduling and image-pull events. Use kubectl logs for container output. A direct Pod is not automatically replaced if you delete the Pod object.

Exercise 3: Replace manual Pod management with a Deployment

Objective: Keep multiple replicas running and enable rolling updates.

Create deployment.yaml:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: nimbus-basic-lab
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-deploy
  template:
    metadata:
      labels:
        app: web-deploy
    spec:
      containers:
      - name: nginx
        image: nginx:1.27
        ports:
        - containerPort: 80
        resources:
          requests:
            cpu: 50m
            memory: 64Mi
          limits:
            cpu: 250m
            memory: 128Mi
kubectl apply -f deployment.yaml
kubectl get deployments,replicasets,pods -n nimbus-basic-lab
kubectl rollout status deployment/web -n nimbus-basic-lab
kubectl describe deployment web -n nimbus-basic-lab

Explanation: The Deployment selector must match labels in the Pod template. replicas: 3 asks for three Pods. Requests influence scheduling; limits constrain container resource use. These example values are for a small lab and should be tuned for real workloads.

Expected result: Deployment shows 3 desired/available replicas when the cluster has enough resources and the image starts successfully.

The standalone Pod uses app: web; the Deployment Pods use app: web-deploy. This deliberate difference prevents the standalone Pod from being counted as a Deployment replica.

Useful actions:

kubectl scale deployment/web --replicas=2 -n nimbus-basic-lab
kubectl scale deployment/web --replicas=3 -n nimbus-basic-lab
kubectl set image deployment/web nginx=nginx:1.27 -n nimbus-basic-lab
kubectl rollout history deployment/web -n nimbus-basic-lab
kubectl rollout undo deployment/web -n nimbus-basic-lab

Interview connection: A Deployment manages ReplicaSets; a ReplicaSet ensures the desired number of matching Pods exist.

Exercise 4: Add a Service for stable access

Objective: Reach a changing set of Deployment Pods through a stable name and virtual IP.

Create service.yaml:

apiVersion: v1
kind: Service
metadata:
  name: web
  namespace: nimbus-basic-lab
spec:
  type: ClusterIP
  selector:
    app: web-deploy
  ports:
  - name: http
    port: 80
    targetPort: 80
    protocol: TCP
kubectl apply -f service.yaml
kubectl get service web -n nimbus-basic-lab
kubectl get endpointslices -n nimbus-basic-lab
kubectl describe service web -n nimbus-basic-lab

Explanation: port is the Service port; targetPort is the port on selected Pods. The selector must match the Deployment Pod labels. EndpointSlices show backend endpoints when available.

Verify from inside the cluster:

kubectl run curl-test --image=curlimages/curl:8.10.1 --restart=Never -n nimbus-basic-lab --command -- sh -c 'sleep 3600'
kubectl wait --for=condition=Ready pod/curl-test -n nimbus-basic-lab --timeout=120s
kubectl exec curl-test -n nimbus-basic-lab -- curl -I --max-time 5 http://web

Expected result: An HTTP response such as HTTP/1.1 200 OK. This requires image registry access and cluster DNS/networking to work.

Troubleshooting: If the Service has no endpoints, compare Service selector labels with Pod labels and check Pod readiness. If curl times out, inspect DNS, network policy, Pod readiness, and application listening port.

Exercise 5: Configure the application using a ConfigMap

Objective: Separate non-sensitive configuration from an image.

Create configmap.yaml:

apiVersion: v1
kind: ConfigMap
metadata:
  name: web-settings
  namespace: nimbus-basic-lab
data:
  APP_ENV: training
  WELCOME_MESSAGE: Hello-from-Nimbuswiztech

Add the following environment variables to the Deployment container under image (or apply the complete Deployment manifest again after editing):

        envFrom:
        - configMapRef:
            name: web-settings
kubectl apply -f configmap.yaml
kubectl apply -f deployment.yaml
kubectl rollout status deployment/web -n nimbus-basic-lab
kubectl exec deployment/web -n nimbus-basic-lab -- printenv APP_ENV

Note: The supplied deployment.yaml in Exercise 3 does not yet contain envFrom. Add the shown snippet beneath the container's image line before reapplying. Existing Pods are recreated by the Deployment when its Pod template changes.

Expected result: training is printed. A ConfigMap environment variable update generally requires Pods to be restarted/recreated before the new environment value is present.

Exercise 6: Understand Secret handling safely

Objective: Learn the API shape for confidential values without committing credentials to source control.

Security: Do not put real passwords, access tokens, or production credentials in a training file or Git repository. Kubernetes Secret data is base64-encoded in manifests, which is not encryption. Restrict RBAC and enable encryption at rest where supported.

Create a disposable lab Secret imperatively so the literal value does not need to be committed to a file:

kubectl create secret generic demo-credentials --from-literal=demo-user=student -n nimbus-basic-lab
kubectl describe secret demo-credentials -n nimbus-basic-lab
kubectl get secret demo-credentials -n nimbus-basic-lab -o yaml

Expected result: The Secret exists and shows key names. YAML output includes encoded data; do not share it if it contains sensitive values. For real workloads, use a suitable secret-management workflow and least-privilege access.

Exercise 7: Inspect labels and selectors

Objective: Prove which Pods are targeted by the Deployment and Service.

kubectl get pods -n nimbus-basic-lab --show-labels
kubectl get pods -n nimbus-basic-lab -l app=web-deploy
kubectl get pods -n nimbus-basic-lab -l app=web
kubectl get service web -n nimbus-basic-lab -o yaml

Expected result: app=web-deploy selects Deployment Pods; app=web selects the standalone Pod. Labels are metadata; selectors are queries or matching rules that use labels.

6. Complete practical example: a small web application

Requirement

Run three NGINX replicas in a dedicated namespace, provide stable in-cluster access, add basic resource requests/limits, and keep a non-secret environment setting outside the image.

Target architecture

Namespace → ConfigMap + Deployment → ReplicaSet → three Pods; Service selects those Pods. The example does not create an external load balancer.

Complete manifest

Save as complete-lab.yaml. Multiple resources are separated by ---.

apiVersion: v1
kind: Namespace
metadata:
  name: nimbus-basic-lab
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: web-settings
  namespace: nimbus-basic-lab
data:
  APP_ENV: training
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: nimbus-basic-lab
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-deploy
  template:
    metadata:
      labels:
        app: web-deploy
    spec:
      containers:
      - name: nginx
        image: nginx:1.27
        ports:
        - name: http
          containerPort: 80
        envFrom:
        - configMapRef:
            name: web-settings
        resources:
          requests:
            cpu: 50m
            memory: 64Mi
          limits:
            cpu: 250m
            memory: 128Mi
---
apiVersion: v1
kind: Service
metadata:
  name: web
  namespace: nimbus-basic-lab
spec:
  type: ClusterIP
  selector:
    app: web-deploy
  ports:
  - name: http
    port: 80
    targetPort: http
    protocol: TCP

Apply in order and verify

kubectl apply -f complete-lab.yaml
kubectl rollout status deployment/web -n nimbus-basic-lab --timeout=180s
kubectl get deployment,replicaset,pods,service -n nimbus-basic-lab
kubectl get pods -n nimbus-basic-lab --show-labels
kubectl get endpointslices -n nimbus-basic-lab
kubectl exec deployment/web -n nimbus-basic-lab -- printenv APP_ENV

To test HTTP from a temporary in-cluster client:

kubectl run curl-test --image=curlimages/curl:8.10.1 --restart=Never -n nimbus-basic-lab --command -- sh -c 'sleep 3600'
kubectl wait --for=condition=Ready pod/curl-test -n nimbus-basic-lab --timeout=120s
kubectl exec curl-test -n nimbus-basic-lab -- curl -I --max-time 5 http://web

What to inspect if it fails

  • Deployment not available: inspect kubectl describe deployment web -n nimbus-basic-lab and the Pods' events.
  • ImagePullBackOff: check image spelling, registry reachability, rate limits, and any required image-pull credentials.
  • No Service endpoints: confirm selector app: web-deploy matches Pod labels exactly and Pods are Ready.
  • APP_ENV missing: verify ConfigMap name/namespace and that the Deployment Pod template includes envFrom.
  • Pending Pods: inspect scheduling events and node capacity; requests may exceed available resources.

Cleanup: kubectl delete namespace nimbus-basic-lab deletes every namespaced resource in that lab namespace, including any extra resources someone placed there. On a shared cluster, inspect the namespace first and coordinate with the trainer. The final cleanup section gives a resource-scoped alternative.

8. Best practices

  • Use Deployments for most stateless services. They manage replica count and rollouts; avoid relying on hand-created Pods for long-running apps.
  • Use descriptive labels consistently. For example, app: web and app.kubernetes.io/name: web. Check that Deployment selectors and Pod template labels agree.
  • Use a dedicated namespace. It improves organization and supports quota/RBAC boundaries, but pair it with policies when security isolation is required.
  • Declare resource requests and limits thoughtfully. Requests influence scheduling; limits can prevent noisy neighbors but overly tight CPU limits can throttle workloads. Measure real usage.
  • Use health probes for real applications. Readiness controls whether a Pod should receive traffic; liveness can restart an unhealthy container; startup probes help slow-starting apps. Do not add probes with guessed paths.
  • Separate configuration from the image. Use ConfigMaps for non-secret settings and a Secret or external secret manager for credentials.
  • Protect Secrets. Limit RBAC, avoid committing secret values to Git, enable encryption at rest where supported, and rotate credentials.
  • Prefer declarative manifests in version control. Review changes before applying and use the right environment/context.
  • Pin images deliberately. For reproducible production releases, prefer controlled version tags or immutable digests and a vulnerability/update process. Avoid relying on floating tags for critical workloads.
  • Monitor rollouts and events. Use rollout status, logs, metrics, and events instead of assuming that a successful apply means the application is healthy.
  • Plan availability beyond replica count. Three replicas on one failure domain may still be vulnerable; consider topology spread, disruption budgets, and capacity for production.
  • Keep lab shortcuts out of production. Demo image tags, low resource values, no probes, and broad access may be acceptable for learning but require review before deployment.

9. Interview preparation

Use the filter to find questions. Answers are expandable so students can quiz themselves first.

Level 1 — Basic questions

1. What is a Kubernetes object?
A persistent API record describing desired or relevant cluster state, such as a Pod, Deployment, or Service. Controllers act to reconcile observed state with desired state.
2. What is a Pod?
The smallest deployable Kubernetes unit. It contains one or more co-scheduled containers that share networking and can share volumes.
3. Why use a Deployment instead of a standalone Pod?
A Deployment manages ReplicaSets, replicas, and rollout history. It helps replace failed Pods and supports controlled application updates.
4. What is a ReplicaSet?
A controller-managed resource that maintains a desired number of Pods matching its selector. Deployments normally manage ReplicaSets for you.
5. What is a Service?
A stable networking abstraction that directs traffic to a set of backend endpoints, commonly selected by Pod labels.
6. What is a Namespace?
A logical scope for namespaced resources and a useful organization boundary. It does not by itself enforce network isolation or all security controls.
7. What are labels?
Key-value metadata used to organize and select objects, for example app=web.
8. What is a selector?
A rule that matches labels. Deployments use selectors to identify their Pods; Services use selectors to find backend Pods in common configurations.
9. What is a ConfigMap?
An API object for non-confidential configuration, consumed as environment variables, command arguments, or mounted files.
10. What is a Secret and is base64 encryption?
A Kubernetes object intended for confidential values such as tokens. Base64 is encoding, not encryption; access control and encryption-at-rest configuration matter.
11. What do apiVersion, kind, metadata, and spec mean?
apiVersion identifies the API version, kind the resource type, metadata identifies/describes it, and spec states desired configuration.
12. What is the difference between ClusterIP and NodePort?
ClusterIP provides a stable internal Service IP. NodePort additionally exposes a port on cluster nodes, subject to network/firewall reachability.

Level 2 — Intermediate questions

13. How does a Deployment create Pods?
The Deployment controller creates or updates a ReplicaSet from the Pod template. The ReplicaSet controller creates Pods to meet the desired count, and the scheduler assigns them to nodes.
14. Why must selector labels match?
Controllers and Services rely on label matching to identify target Pods. A mismatch can mean no managed replicas or no Service endpoints. Compare kubectl get pods --show-labels with the selector.
15. What is the difference between port and targetPort in a Service?
port is the port exposed by the Service; targetPort is the backend Pod port. They can differ if the application listens on a different port.
16. Does containerPort expose a Pod publicly?
No. It describes a container port in the Pod spec. Reachability depends on Pod networking, Service or other exposure configuration, and cluster/network rules.
17. What happens if a Deployment Pod is deleted?
The ReplicaSet controller normally creates a replacement to restore the desired count. A standalone Pod has no ReplicaSet to recreate its Pod object.
18. What happens when you change the Deployment image?
The Pod template changes, so the Deployment creates a new ReplicaSet and rolls out replacement Pods according to its update strategy. Watch with kubectl rollout status.
19. How are ConfigMaps consumed?
As environment variables, command arguments, or mounted volumes. Environment variables in running processes do not update automatically; mounted files may update eventually, depending on the volume and application reload behavior.
20. Are namespaces security boundaries?
They provide resource scoping, but not complete isolation by default. Combine namespaces with RBAC, NetworkPolicies, quotas, and appropriate admission/security controls.
21. How do you check whether a Service has backend Pods?
Inspect Service selector and Pod labels, then check EndpointSlices: kubectl get svc web -n nimbus-basic-lab -o yaml and kubectl get endpointslices -n nimbus-basic-lab.
22. What is the difference between requests and limits?
Requests inform scheduling and resource reservation decisions. Limits cap resource use according to resource-specific enforcement; CPU may be throttled and memory over-limit can cause OOM termination.
23. How do you roll back a Deployment?
Inspect history with kubectl rollout history deployment/web -n nimbus-basic-lab, then use kubectl rollout undo deployment/web -n nimbus-basic-lab if rollback is appropriate.
24. How do imperative and declarative management differ?
Imperative commands specify an action. Declarative files describe the intended configuration and are applied repeatedly, making changes easier to review and version-control.

Level 3 — Real-time scenarios

25. Deployment shows 3 desired replicas but 0 available. What do you do?
Approach: Run kubectl get pods -n nimbus-basic-lab, kubectl describe deployment web -n nimbus-basic-lab, and describe a failing Pod. Check events for scheduling, image pulls, failed probes, and resource constraints. Use kubectl logs POD -n nimbus-basic-lab --previous if it restarts. Fix the evidenced cause, then watch kubectl rollout status deployment/web -n nimbus-basic-lab. Several causes are possible; do not assume the image is the problem without evidence.
26. Service DNS resolves, but requests fail. How do you isolate the cause?
Check kubectl get endpointslices -n nimbus-basic-lab, Service selector and ports, Pod readiness, and whether the app listens on the target port. Test the Pod directly where permitted, then test through the Service. If endpoints exist, inspect network policy, app logs, and port mismatch. DNS success alone does not prove the backend is healthy.
27. A new image rollout is unhealthy. What is a safe response?
Inspect rollout status, new Pod events, logs, readiness and image details. If the new version is impacting service and rollback is approved, run kubectl rollout undo deployment/web -n nimbus-basic-lab, verify availability, and investigate the failed release separately.
28. A Service has no endpoints although Pods are Running.
Running does not necessarily mean Ready. Compare Service selector to labels, verify namespace, and inspect Pod readiness conditions. Commands: kubectl get pods --show-labels -n nimbus-basic-lab, kubectl describe svc web -n nimbus-basic-lab, kubectl get endpointslices -n nimbus-basic-lab.
29. An application cannot read APP_ENV from its ConfigMap.
Check the ConfigMap exists in the same namespace, key spelling, and Pod template's env/envFrom. Confirm with kubectl exec POD -n nimbus-basic-lab -- printenv APP_ENV. Environment variables are set at container start, so update/recreate Pods after changing the ConfigMap.
30. Pods are Pending after adding memory requests.
Inspect Pod events and node allocatable/capacity. Requests can make Pods unschedulable if no node has enough unallocated capacity or placement constraints exclude nodes. Review requests against measured needs; do not simply remove them in production without understanding capacity and safety trade-offs.
31. A Secret was accidentally committed to Git. What next?
Treat the credential as exposed: revoke/rotate it immediately, investigate access, remove it from current files and repository history according to organizational process, and migrate to a safe secret-management method. Deleting the visible line alone does not invalidate the credential or erase history copies.
32. One student accidentally created resources in the default namespace. How do you find them?
List likely resource types in the relevant namespace, for example kubectl get deploy,pods,svc,configmap,secret -n default, and inspect ownership/labels before cleanup. Do not delete resources based on names alone on a shared cluster.
33. A Pod is repeatedly OOMKilled. What evidence guides the fix?
Check kubectl describe pod POD -n nimbus-basic-lab for termination reason, metrics if available, memory limits, workload load, and application logs. Determine whether to optimize memory use, increase a justified limit, or adjust workload sizing. Increasing the limit alone may hide a leak or exceed node capacity.
34. A rollout is stuck after a probe was added.
Inspect Pod events and readiness/liveness probe configuration. Verify the endpoint/path, port, protocol, startup delay, and app startup time. A readiness failure removes a Pod from ready Service endpoints; repeated liveness failures can restart it. Use a probe that reflects actual app health rather than a guessed URL.

10. Practice assignments

Attempt the challenge before opening its solution. All commands assume an authorized lab namespace.

Beginner exercises

  1. Create a namespace named student-practice. Expected state: namespace is Active. Verify with kubectl get ns student-practice. Hint: use kubectl create namespace.
  2. Create a standalone Pod named hello-pod using nginx:1.27. Verify its status and labels. Hint: use a Pod manifest and kubectl get pod --show-labels.
  3. Create a Deployment with two replicas. Verify desired and available counts. Hint: kubectl create deployment or apps/v1 YAML.
  4. Create a ClusterIP Service for the Deployment. Verify that EndpointSlices contain backends. Hint: match the Service selector to Pod labels.
  5. Create a ConfigMap with APP_ENV=practice and consume it as an environment variable. Verify using printenv. Hint: use envFrom.configMapRef.

Modification and troubleshooting exercises

  1. Scale the Deployment from two to four replicas. Verify with kubectl get deployment. Hint: kubectl scale.
  2. Make the Service selector incorrect, observe the missing endpoints, then correct it. Expected: EndpointSlices populate again after the fix.
  3. Update the Deployment image to a valid new version and watch the rollout. Hint: kubectl set image and kubectl rollout status.
  4. Inspect Pod events for a deliberately misspelled image tag, then restore a valid image. Do this only in your isolated practice namespace. Hint: kubectl describe pod.
  5. Change a ConfigMap environment value and demonstrate why existing container environment values may require a Pod restart. Hint: compare ConfigMap content with printenv before and after rollout.

Scenario-based challenges

  1. Traffic failure: Pods are Ready, but the Service has no endpoints. Identify and fix the cause. Expected: Service selects ready Pods. Verify EndpointSlices and an HTTP request.
  2. Capacity issue: Pods stay Pending after increasing CPU/memory requests. Determine whether scheduling capacity or a placement rule is blocking them. Expected: explain the evidence from Pod Events before changing requests.
  3. Bad release: A new image rollout fails. Collect evidence, roll back if appropriate, and verify the prior revision is available. Expected: stable Deployment and a short incident explanation.

11. Quick revision and cheat sheet

Core relationships

  • Deployment → ReplicaSet → Pods.
  • Service selector → matching Pod labels → backend endpoints.
  • ConfigMap → non-secret configuration; Secret → confidential values requiring access controls.
  • Namespace scopes namespaced resources; it does not automatically create network isolation.
  • spec is desired configuration; status is observed state.

12. Final lab cleanup

First inspect the resources to confirm the namespace contains only your training objects.

kubectl get all,configmap,secret -n nimbus-basic-lab

Resource-scoped cleanup: remove only named resources created by this guide. Missing-resource messages are harmless if a resource was not created.

kubectl delete pod web-pod -n nimbus-basic-lab --ignore-not-found
kubectl delete pod curl-test -n nimbus-basic-lab --ignore-not-found
kubectl delete deployment web -n nimbus-basic-lab --ignore-not-found
kubectl delete service web -n nimbus-basic-lab --ignore-not-found
kubectl delete configmap web-settings -n nimbus-basic-lab --ignore-not-found
kubectl delete secret demo-credentials -n nimbus-basic-lab --ignore-not-found

If you applied the complete manifest, deleting the namespace is the simplest option only when the namespace is dedicated to you and contains no shared resources:

kubectl delete namespace nimbus-basic-lab
Shared-cluster warning: Deleting a namespace removes all namespaced resources inside it, including objects you did not create. Never delete a shared namespace, nodes, cluster roles, persistent volumes, or cluster-wide components as part of this beginner lab. Confirm with the trainer before broad cleanup.
